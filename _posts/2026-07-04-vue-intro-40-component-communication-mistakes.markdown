컴포넌트 통신은 Vue 입문자가 가장 많이 막히는 구간입니다. 컴포넌트를 나누는 것까지는 어렵지 않은데, 나눈 뒤 값이 어디로 가야 하는지, 이벤트를 누가 받아야 하는지, 상태를 어디에서 바꿔야 하는지가 헷갈립니다. 이때 자주 나오는 실수는 대부분 비슷합니다.

첫 번째는 props 직접 수정입니다. 자식이 부모에게 받은 값을 바로 바꾸면 상태 흐름이 불명확해집니다. 두 번째는 이벤트 이름 불일치입니다. 자식은 `remove-item`을 emit했는데 부모는 `@remove`를 듣고 있으면 아무 일도 일어나지 않습니다. 세 번째는 상태 중복입니다. 부모도 같은 값을 갖고 자식도 복사해서 갖는데 동기화 기준이 없으면 화면이 어긋납니다.

이 문제를 해결하는 기본 원칙은 단순합니다. 상태 소유자를 정하고, 아래로는 props를 내려주고, 위로는 emit을 올립니다. 그래도 단계가 너무 깊어져서 props를 계속 전달해야 한다면 컴포넌트 구조가 적절한지 먼저 보고, 이후 provide/inject나 전역 상태를 고려합니다.

## 이번 글에서 먼저 잡을 관점

이번 구간부터는 Vue를 단순히 한 파일 안에서 쓰는 단계에서 벗어나, 여러 컴포넌트가 함께 동작하는 구조를 다룹니다. 그래서 문법 하나만 보는 것보다 역할과 책임을 같이 보는 것이 중요합니다. 부모 컴포넌트가 무엇을 알고 있어야 하는지, 자식 컴포넌트는 어디까지 책임져야 하는지, 사용자의 행동을 어느 방향으로 전달해야 하는지 계속 질문하면서 읽어보시면 좋습니다.

컴포넌트 설계는 처음부터 완벽하게 나누는 일이 아닙니다. 작은 화면을 만들고, 반복되는 부분이나 책임이 분명한 부분을 발견하고, 그때 적절히 분리하는 과정에 가깝습니다. 이 글의 예제도 정답이라기보다 기준을 잡기 위한 출발점으로 봐주세요. 직접 이름을 바꿔보고, props를 하나 추가해보고, 이벤트 흐름을 바꿔보면 훨씬 오래 기억에 남습니다.

## 작은 실습으로 확인해보기

아래 예제는 이벤트 이름을 명확히 하고 부모가 상태를 수정하는 안전한 구조입니다.

{% raw %}
```vue
<!-- ChildCounter.vue -->
<script setup>
defineProps({
  count: {
    type: Number,
    required: true
  }
})

const emit = defineEmits(['increase-requested'])
</script>

<template>
  <button @click="emit('increase-requested')">
    현재 값: {{ count }}
  </button>
</template>

<!-- ParentCounter.vue -->
<script setup>
import { ref } from 'vue'
import ChildCounter from './ChildCounter.vue'

const count = ref(0)
</script>

<template>
  <ChildCounter
    :count="count"
    @increase-requested="count += 1"
  />
</template>
```
{% endraw %}

## 코드가 움직이는 순서

자식은 `count`를 읽기만 합니다. 버튼 클릭이 발생하면 `increase-requested` 이벤트를 올립니다. 이벤트 이름에 requested를 붙이면 자식이 직접 증가시키는 것이 아니라 부모에게 요청한다는 의미가 더 분명해집니다. 부모는 이벤트를 듣고 자신이 소유한 `count`를 변경합니다.

여기서 중요한 것은 코드 줄 수보다 의도입니다. 컴포넌트를 나누면 파일은 늘어나지만, 각 파일이 맡는 역할이 선명해져야 합니다. 부모는 전체 상태와 흐름을 관리하고, 자식은 자신이 맡은 UI 조각을 표현하거나 사용자 행동을 이벤트로 알려주는 식으로 역할을 나누면 디버깅이 훨씬 쉬워집니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 자식에서 props 값을 바꿔도 당장은 동작하는 것처럼 보일 수 있지만, 부모가 다시 렌더링되면 값이 덮이거나 흐름이 꼬일 수 있습니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 이벤트 이름은 부모와 자식 양쪽에서 정확히 맞아야 합니다. 템플릿 표기와 emit 이름을 함께 확인하세요. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 여러 단계로 props를 넘기는 일이 반복되면 컴포넌트 경계나 상태 위치를 다시 검토해야 합니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.

컴포넌트 관련 오류는 한 파일만 봐서는 바로 보이지 않을 때가 많습니다. 부모가 넘기는 prop 이름, 자식이 선언한 prop 이름, 자식이 emit하는 이벤트 이름, 부모가 듣는 이벤트 이름을 한 줄씩 맞춰보는 습관이 필요합니다. 브라우저 콘솔의 Vue warning도 그냥 넘기지 말고, 어떤 컴포넌트에서 발생했는지 확인해보시면 좋습니다.

## 실무에서 생각할 점

props와 emit은 가장 기본적이고 명시적인 통신 방식입니다. 작은 규모에서는 이 방식이 제일 읽기 쉽습니다. 다만 앱이 커지고 여러 먼 컴포넌트가 같은 상태를 공유해야 한다면 다른 도구가 필요할 수 있습니다. 그때도 기본 흐름을 알고 있어야 도구를 남용하지 않습니다.

실무에서는 컴포넌트가 "동작한다"보다 "변경에 견딘다"가 더 중요해집니다. 요구사항은 계속 바뀌고, 디자인도 바뀌고, 같은 컴포넌트를 다른 화면에서 쓰고 싶어질 수 있습니다. 그래서 처음부터 모든 것을 일반화하려고 하기보다, 현재 책임을 명확히 하고 나중에 반복이 보일 때 재사용성을 높이는 방향이 안전합니다.
