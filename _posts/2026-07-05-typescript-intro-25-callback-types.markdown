TypeScript를 처음 배우는 분들은 문법이 많아 보인다는 이유로 겁을 먹기 쉽습니다. 그런데 실제로는 문법을 외우는 것보다, "이 기능이 왜 존재하는지"와 "이 기능이 없으면 어떤 실수가 생기는지"를 먼저 이해하는 쪽이 훨씬 중요합니다. 이번 글에서도 그 관점으로 접근하겠습니다. 코드가 길어 보이더라도 한 줄씩 뜯어보면 충분히 따라갈 수 있으니, 급하게 넘기기보다 작은 예제를 손으로 바꿔보며 읽어보시면 좋습니다.

callback 함수 타입은 프론트엔드와 백엔드 어디서나 자주 등장합니다. 여기서 타입을 잘 잡아두면 버그가 크게 줄어듭니다. TypeScript는 결국 개발자가 미래의 실수를 조금 더 빨리 발견하게 도와주는 도구입니다. 그래서 단순히 문법 정의를 읽는 것만으로는 감이 잘 오지 않고, 직접 예제 코드를 보면서 "어떤 값이 허용되고 어떤 값이 막히는지"를 확인해봐야 이해가 단단해집니다. 이번 글에서는 기본 예제와 함께 잘못 작성한 예제도 같이 보면서, 왜 컴파일러가 특정 코드를 막는지까지 살펴보겠습니다.

## 먼저 이해해야 할 핵심 관점

이번 글의 핵심은 함수 타입 기본기 흐름 안에서 현재 주제가 어떤 역할을 하는지 파악하는 것입니다. 많은 분들이 TypeScript를 배우다가 중간에 막히는 이유는, 각각의 문법을 따로 기억하려고 하기 때문입니다. 하지만 실제로는 타입 선언, 함수 작성, 분기 처리, 에러 확인이 모두 하나의 흐름 안에 연결되어 있습니다. 지금 주제를 이해할 때도 "이 개념이 나중에 어떤 실수를 줄여주지?"라는 질문을 계속 붙여보시면 훨씬 오래 기억에 남습니다.

함수 타입은 특히 협업에서 중요합니다. 입력과 출력이 흐릿하면 호출하는 쪽과 구현하는 쪽이 서로 다른 기대를 가지게 됩니다. 특히 처음에는 "왜 이렇게 엄격하게 검사하지?"라는 느낌이 드실 수 있는데, 그 엄격함이 바로 TypeScript의 장점입니다. 개발 초반에는 불편하게 보일 수 있지만, 코드가 길어지고 파일 수가 늘어나면 이 차이가 정말 크게 느껴집니다. 그래서 지금 단계에서는 편법으로 에러를 없애는 것보다, 에러가 왜 났는지를 한 번 더 읽어보는 습관이 훨씬 중요합니다.

## 기본 예제부터 차근차근 보기

아래 첫 번째 예제는 이번 주제를 가장 단순한 형태로 보여줍니다. 처음 읽으실 때는 모든 줄을 외우려고 하지 마시고, 값과 타입의 관계가 어떻게 드러나는지만 먼저 보시면 됩니다.

```ts
function runTask(callback: (success: boolean) => void) {
  callback(true)
}
```

이 코드는 이번 주제를 가장 작은 단위로 보여줍니다. 여기서 중요한 것은 "타입이 붙은 선언이 코드의 의도를 더 명확하게 만든다"는 점입니다. 입문 단계에서는 결과가 똑같아 보여도 타입을 써두는 이유를 자주 놓치게 되는데, 실제 프로젝트에서는 몇 시간 뒤, 며칠 뒤, 혹은 다른 사람이 코드를 읽을 때 이 차이가 크게 드러납니다. 그래서 작은 예제라도 "왜 이 값은 이 타입이어야 하는지"를 한 번 더 말로 설명해보는 습관이 좋습니다.

## 한 단계 더 나아간 예제

첫 예제가 감각을 잡는 용도였다면, 두 번째 예제는 조금 더 실전적인 상황을 떠올리게 해줍니다. 실제 개발에서는 값 하나만 선언하고 끝나는 경우보다, 함수를 만들거나 여러 속성을 묶거나, 조건에 따라 분기하는 경우가 훨씬 많기 때문입니다.

```ts
runTask((success) => {
  if (success) {
    console.log('작업 성공')
  }
})
```

이 단계에서는 "문법이 맞는가?"만 볼 것이 아니라, "읽는 사람이 의도를 쉽게 이해할 수 있는가?"도 같이 봐야 합니다. TypeScript를 쓰는 목적은 단순히 빨간 줄을 없애는 것이 아니라, 코드를 더 예측 가능하게 만드는 데 있습니다. 그래서 타입이 너무 장황해졌는지, 반대로 너무 느슨해서 거의 도움을 주지 못하는지는 항상 같이 점검해야 합니다.

## 초보자가 자주 만드는 잘못된 예제

이제 일부러 잘못 작성한 코드를 보겠습니다. 이런 코드를 함께 보는 이유는, 에러를 피하는 방법을 외우기 위해서가 아니라 TypeScript가 왜 그 코드를 막는지 이해하기 위해서입니다.

```ts
runTask((message: string) => {
  console.log(message)
})
```

이런 형태의 코드는 처음에는 "조금만 우회하면 되지 않을까?"라는 생각을 들게 만들 수 있습니다. 하지만 바로 그 지점에서 무리하게 타입 단언이나 any를 섞기 시작하면, 그 뒤부터는 타입 시스템의 도움을 계속 잃어버리게 됩니다. 그래서 에러를 만났을 때는 먼저 회피하지 말고, 지금 값의 실제 형태가 무엇인지, 내가 함수에 기대하는 입력과 출력이 무엇인지부터 다시 확인하시는 편이 좋습니다.

## 에러와 유의사항을 자세히 짚어보기

- 첫 번째로 주의할 점은, 이 주제를 눈으로만 읽고 넘어가면 실제 코드에서는 바로 막힐 수 있다는 점입니다. 한 줄이라도 직접 바꿔보면서 어떤 값이 허용되고 어떤 값에서 에러가 나는지 확인해야 감각이 생깁니다.
- 두 번째로, 빨간 줄이 사라졌다고 해서 항상 올바르게 작성된 것은 아닙니다. TypeScript에서는 편법으로 에러를 잠시 숨길 수 있기 때문에, "지금 타입이 실제 데이터를 제대로 설명하고 있는가?"를 한 번 더 확인해야 합니다.
- 세 번째로, 지금 주제는 뒤에서 배우는 더 큰 개념과 연결됩니다. 그래서 당장 완벽하게 외우지 못해도 괜찮지만, 왜 이 개념이 필요한지는 분명히 이해하고 넘어가는 것이 중요합니다.

특히 입문 단계에서 가장 흔한 실수는 "작동하면 됐다"는 기준으로만 코드를 보는 것입니다. JavaScript에서는 우연히 작동하던 코드가, 타입을 붙이는 순간 불편하게 느껴질 수 있습니다. 하지만 그 불편함은 대체로 미래의 버그를 앞당겨 보여주는 신호입니다. 그래서 지금처럼 작은 예제에서부터 타입이 막아주는 지점을 반복해서 보는 것이 정말 중요합니다.

## 실무에서는 어떻게 연결될까요?

실무에서는 지금 배우는 작은 개념이 곧바로 API 응답 타입, 폼 데이터, 상태 관리, 컴포넌트 props, 유틸 함수 설계로 연결됩니다. 즉, 지금 단계에서 기본기를 정확하게 잡아두면 나중에 Vue, React, Node.js 코드로 확장할 때 훨씬 편해집니다. 반대로 입문 구간에서 any나 모호한 타입에 익숙해지면, 프로젝트가 커질수록 타입이 있어도 없는 것 같은 상태가 되기 쉽습니다.

그래서 이번 글을 읽으실 때는 "문법 하나를 배웠다" 정도로 끝내지 마시고, 실제로 이 주제가 어떤 종류의 실수를 줄여주는지 같이 기억해두시면 좋겠습니다. 예를 들어 입력값의 형태가 예상과 다를 때, 함수에 잘못된 타입이 들어올 때, 조건 분기가 빠졌을 때 지금 배운 개념이 어떻게 도움이 되는지 연결해서 보시면 다음 글로 넘어갈 때 훨씬 덜 흔들립니다.

## 오늘 내용 정리

이번 글에서는 callback 함수 타입을 안전하게 작성하기 주제를 중심으로, 왜 이 개념이 필요한지, 어떤 코드에서 도움이 되는지, 그리고 초보자가 어디서 자주 실수하는지를 함께 살펴봤습니다. 지금 단계에서는 완벽하게 외우는 것보다 예제 코드를 직접 바꿔보면서 흐름을 잡는 것이 더 중요합니다. 가능하시면 기본 예제를 그대로 한 번 입력해보시고, 변수 이름이나 값, 함수 입력을 살짝 바꿔보면서 TypeScript가 어떤 반응을 보이는지 확인해보세요. 그 경험이 쌓이면 이후의 타입 문법도 훨씬 덜 어렵게 느껴집니다.
