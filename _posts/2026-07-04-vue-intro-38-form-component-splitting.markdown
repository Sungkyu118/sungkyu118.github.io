# Vue 입문 38: 입력 폼 컴포넌트를 분리하면서 생기는 고민들

> 폼을 분리할 때 입력 컴포넌트와 부모가 어떤 책임을 나눠 가져야 하는지 배웁니다.

폼은 컴포넌트 분리를 시작하면 가장 먼저 어려워지는 영역입니다. 입력값은 자식 컴포넌트 안에서 바뀌지만, 그 값은 부모의 상태나 API 제출과 연결되는 경우가 많습니다. 그래서 입력 폼 컴포넌트를 만들 때는 "누가 값을 소유하는가"와 "누가 검증하고 저장하는가"를 분명히 해야 합니다.

가장 단순한 입력 컴포넌트는 `modelValue`를 props로 받고, 값이 바뀌면 `update:modelValue` 이벤트를 emit합니다. Vue의 component v-model은 이 패턴을 편하게 써주는 문법입니다. 부모는 `<BaseInput v-model="email" />`처럼 쓰고, 자식은 내부 input 변경을 부모에게 알려줍니다.

검증 메시지도 고민 지점입니다. 입력 컴포넌트가 자체 검증까지 모두 맡으면 재사용하기 어려워질 수 있습니다. 반대로 부모가 모든 스타일과 메시지를 처리하면 입력 컴포넌트가 너무 얇아집니다. 입문 단계에서는 입력 컴포넌트는 값 표시와 에러 메시지 표시를 맡고, 어떤 에러인지 판단하는 로직은 부모가 맡는 방식이 이해하기 쉽습니다.

## 이번 글에서 먼저 잡을 관점

이번 구간부터는 Vue를 단순히 한 파일 안에서 쓰는 단계에서 벗어나, 여러 컴포넌트가 함께 동작하는 구조를 다룹니다. 그래서 문법 하나만 보는 것보다 역할과 책임을 같이 보는 것이 중요합니다. 부모 컴포넌트가 무엇을 알고 있어야 하는지, 자식 컴포넌트는 어디까지 책임져야 하는지, 사용자의 행동을 어느 방향으로 전달해야 하는지 계속 질문하면서 읽어보시면 좋습니다.

컴포넌트 설계는 처음부터 완벽하게 나누는 일이 아닙니다. 작은 화면을 만들고, 반복되는 부분이나 책임이 분명한 부분을 발견하고, 그때 적절히 분리하는 과정에 가깝습니다. 이 글의 예제도 정답이라기보다 기준을 잡기 위한 출발점으로 봐주세요. 직접 이름을 바꿔보고, props를 하나 추가해보고, 이벤트 흐름을 바꿔보면 훨씬 오래 기억에 남습니다.

## 작은 실습으로 확인해보기

아래 예제는 `BaseInput.vue`가 v-model과 에러 메시지 표시를 지원하는 구조입니다.

{% raw %}
```vue
<!-- BaseInput.vue -->
<script setup>
defineProps({
  modelValue: {
    type: String,
    default: ''
  },
  label: {
    type: String,
    required: true
  },
  errorMessage: {
    type: String,
    default: ''
  }
})

const emit = defineEmits(['update:modelValue'])
</script>

<template>
  <label class="field">
    <span>{{ label }}</span>
    <input
      :value="modelValue"
      :class="{ error: errorMessage }"
      @input="emit('update:modelValue', $event.target.value)"
    />
    <small v-if="errorMessage">{{ errorMessage }}</small>
  </label>
</template>

<!-- Parent.vue -->
<template>
  <BaseInput
    v-model="email"
    label="이메일"
    :error-message="emailError"
  />
</template>
```
{% endraw %}

## 코드가 움직이는 순서

부모는 `v-model="email"`로 상태를 연결합니다. 자식은 `modelValue`를 input의 value로 표시하고, 사용자가 입력하면 `update:modelValue` 이벤트로 새 값을 올립니다. 에러 메시지는 부모가 계산해서 prop으로 내려줍니다. 이렇게 하면 입력 UI는 재사용하고, 검증 기준은 화면마다 다르게 가져갈 수 있습니다.

여기서 중요한 것은 코드 줄 수보다 의도입니다. 컴포넌트를 나누면 파일은 늘어나지만, 각 파일이 맡는 역할이 선명해져야 합니다. 부모는 전체 상태와 흐름을 관리하고, 자식은 자신이 맡은 UI 조각을 표현하거나 사용자 행동을 이벤트로 알려주는 식으로 역할을 나누면 디버깅이 훨씬 쉬워집니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 자식 입력 컴포넌트가 부모 상태를 직접 바꾸려고 하면 재사용성이 떨어집니다. v-model 이벤트 규칙을 따르는 편이 좋습니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 에러 메시지를 문자열로만 처리하면 여러 에러 상태가 복잡해질 수 있습니다. 큰 폼에서는 에러 객체나 검증 라이브러리를 고려할 수 있습니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: input 이벤트에서 `$event.target.value`를 사용할 때 이벤트 대상이 실제 input인지 확인해야 합니다. 복잡한 컴포넌트에서는 더 명확한 핸들러 함수를 두는 편도 좋습니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.

컴포넌트 관련 오류는 한 파일만 봐서는 바로 보이지 않을 때가 많습니다. 부모가 넘기는 prop 이름, 자식이 선언한 prop 이름, 자식이 emit하는 이벤트 이름, 부모가 듣는 이벤트 이름을 한 줄씩 맞춰보는 습관이 필요합니다. 브라우저 콘솔의 Vue warning도 그냥 넘기지 말고, 어떤 컴포넌트에서 발생했는지 확인해보시면 좋습니다.

## 실무에서 생각할 점

폼 컴포넌트는 빨리 과해지기 쉽습니다. 처음부터 모든 타입의 입력을 하나의 컴포넌트로 처리하려고 하지 말고, 텍스트 입력처럼 가장 단순한 것부터 분리해보는 것이 좋습니다. 이후 checkbox, select, textarea를 별도로 확장하면 구조를 더 안정적으로 가져갈 수 있습니다.

실무에서는 컴포넌트가 "동작한다"보다 "변경에 견딘다"가 더 중요해집니다. 요구사항은 계속 바뀌고, 디자인도 바뀌고, 같은 컴포넌트를 다른 화면에서 쓰고 싶어질 수 있습니다. 그래서 처음부터 모든 것을 일반화하려고 하기보다, 현재 책임을 명확히 하고 나중에 반복이 보일 때 재사용성을 높이는 방향이 안전합니다.
