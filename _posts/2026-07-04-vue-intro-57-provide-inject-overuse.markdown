# Vue 입문 57: provide/inject를 남용하면 유지보수가 어려워지는 이유

> provide/inject가 편한 만큼 데이터 흐름을 숨길 수 있다는 위험과 사용 기준을 배웁니다.

provide/inject는 깊은 컴포넌트에 값을 전달할 때 매우 편합니다. 하지만 편하다는 이유로 모든 상태를 provide하고 아무 곳에서나 inject하기 시작하면 유지보수가 어려워집니다. props를 쓰면 부모 템플릿에 데이터 전달이 보이지만, inject는 컴포넌트 내부를 열어봐야 어떤 값을 쓰는지 알 수 있습니다.

문제가 가장 크게 드러나는 지점은 디버깅입니다. 어떤 버튼 색상이 이상하게 바뀌었는데 그 값이 props로 온 것이 아니라 inject로 들어온 것이라면, 제공자가 어디인지 찾아야 합니다. 테스트에서도 컴포넌트를 단독으로 렌더링하려면 inject 값을 따로 제공해야 할 수 있습니다. 재사용할 때도 해당 컨텍스트가 없으면 컴포넌트가 제대로 동작하지 않을 수 있습니다.

그래서 provide/inject는 "깊어서 props 전달이 불편한 모든 상황"이 아니라 "하나의 컴포넌트 집합 안에서 공유되는 컨텍스트"에 쓰는 편이 좋습니다. 예를 들어 탭 그룹과 탭 패널, 폼과 폼 필드, 테마 컨테이너와 내부 버튼처럼 계층이 의미 있는 경우입니다.

## 이번 글에서 먼저 잡을 관점

이번 구간부터는 Vue를 단순히 한 파일 안에서 쓰는 단계에서 벗어나, 여러 컴포넌트가 함께 동작하는 구조를 다룹니다. 그래서 문법 하나만 보는 것보다 역할과 책임을 같이 보는 것이 중요합니다. 부모 컴포넌트가 무엇을 알고 있어야 하는지, 자식 컴포넌트는 어디까지 책임져야 하는지, 사용자의 행동을 어느 방향으로 전달해야 하는지 계속 질문하면서 읽어보시면 좋습니다.

컴포넌트 설계는 처음부터 완벽하게 나누는 일이 아닙니다. 작은 화면을 만들고, 반복되는 부분이나 책임이 분명한 부분을 발견하고, 그때 적절히 분리하는 과정에 가깝습니다. 이 글의 예제도 정답이라기보다 기준을 잡기 위한 출발점으로 봐주세요. 직접 이름을 바꿔보고, props를 하나 추가해보고, 이벤트 흐름을 바꿔보면 훨씬 오래 기억에 남습니다.

## 작은 실습으로 확인해보기

아래 예제는 provide/inject를 쓰되, 기본값과 명확한 키 이름을 둬서 실패 상황을 줄이는 방식입니다.

```vue
<!-- FormProvider.vue -->
<script setup>
import { provide, reactive } from 'vue'

const formContext = reactive({
  disabled: false,
  errors: {}
})

provide('formContext', formContext)
</script>

<template>
  <form>
    <slot />
  </form>
</template>

<!-- FormField.vue -->
<script setup>
import { inject } from 'vue'

const formContext = inject('formContext', {
  disabled: false,
  errors: {}
})
</script>

<template>
  <input :disabled="formContext.disabled" />
</template>
```

## 코드가 움직이는 순서

`FormProvider`는 폼 하위 컴포넌트들이 공통으로 참고할 컨텍스트를 제공합니다. `FormField`는 inject로 값을 받되, 제공자가 없을 때 사용할 기본값도 둡니다. 이렇게 하면 컴포넌트를 단독으로 테스트하거나 잘못된 위치에서 사용할 때 완전히 깨지는 것을 줄일 수 있습니다.

여기서 중요한 것은 코드 줄 수보다 의도입니다. 컴포넌트를 나누면 파일은 늘어나지만, 각 파일이 맡는 역할이 선명해져야 합니다. 부모는 전체 상태와 흐름을 관리하고, 자식은 자신이 맡은 UI 조각을 표현하거나 사용자 행동을 이벤트로 알려주는 식으로 역할을 나누면 디버깅이 훨씬 쉬워집니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: inject 값이 어디서 오는지 찾기 어렵다면 이미 남용 신호일 수 있습니다. 제공자와 소비자의 관계가 도메인상 자연스러운지 확인하세요. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: provide/inject로 변경 가능한 큰 객체를 공유하면 여러 자식이 동시에 수정할 수 있습니다. 변경 권한을 어디에 둘지 정해야 합니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 테스트에서 inject 값을 준비해야 하는 컴포넌트가 많아지면 독립성이 떨어질 수 있습니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.

컴포넌트 관련 오류는 한 파일만 봐서는 바로 보이지 않을 때가 많습니다. 부모가 넘기는 prop 이름, 자식이 선언한 prop 이름, 자식이 emit하는 이벤트 이름, 부모가 듣는 이벤트 이름을 한 줄씩 맞춰보는 습관이 필요합니다. 브라우저 콘솔의 Vue warning도 그냥 넘기지 말고, 어떤 컴포넌트에서 발생했는지 확인해보시면 좋습니다.

## 실무에서 생각할 점

provide/inject는 props drilling을 줄이지만 명시성을 낮춥니다. 그래서 편의성과 추적 가능성 사이의 균형이 중요합니다. 특정 컴포넌트 패밀리 안에서 공유되는 컨텍스트에는 잘 맞지만, 앱 전체 데이터 흐름을 대체하는 도구로 쓰기에는 조심스럽습니다.

실무에서는 컴포넌트가 "동작한다"보다 "변경에 견딘다"가 더 중요해집니다. 요구사항은 계속 바뀌고, 디자인도 바뀌고, 같은 컴포넌트를 다른 화면에서 쓰고 싶어질 수 있습니다. 그래서 처음부터 모든 것을 일반화하려고 하기보다, 현재 책임을 명확히 하고 나중에 반복이 보일 때 재사용성을 높이는 방향이 안전합니다.
