환경변수는 API 주소처럼 환경마다 달라지는 값을 코드 밖에서 관리하기 위한 방법입니다. 하지만 프론트엔드 환경변수는 브라우저에 포함될 수 있다는 점을 반드시 이해해야 합니다.

개발 API와 운영 API 주소를 VITE_API_BASE_URL로 나누어 사용하는 예제를 작성하겠습니다.

이 글에서는 단순히 “이렇게 쓰면 됩니다”에서 멈추지 않고, 왜 이런 선택을 하는지, 언제 도움이 되는지, 그리고 언제 오히려 문제를 만들 수 있는지를 함께 보겠습니다. 입문 단계에서는 문법을 많이 외우는 것보다 상황을 나누어 생각하는 힘이 훨씬 오래 갑니다. Vue는 문법 자체가 비교적 부드러운 편이지만, 프로젝트가 커지면 결국 상태, 화면, 서버, 빌드, 접근성, 운영이라는 여러 기준이 동시에 움직이기 때문입니다.

## 이번 글에서 먼저 잡을 관점

이번 배포와 운영 구간에서는 로컬에서 잘 돌아가는 Vue 앱을 실제 사용자에게 안전하게 전달하는 과정을 보겠습니다. 빌드, 환경변수, base 경로, 로그, source map, 배포 전 체크리스트는 화려해 보이지 않지만 실무에서 장애를 줄이는 아주 현실적인 장치입니다.

지금 단계에서는 완벽한 구조를 처음부터 외우려고 하지 않으셔도 괜찮습니다. 대신 “이 코드는 어떤 문제를 줄이려고 있는가”, “이 선택 때문에 새로 생기는 비용은 무엇인가”, “문제가 생겼을 때 어디부터 확인해야 하는가”를 말로 설명하는 연습을 해보시면 좋습니다. 이렇게 생각하면 예제 코드를 그대로 복사하는 수준을 넘어서, 내 프로젝트 상황에 맞게 조정할 수 있는 힘이 생깁니다.

본문 중간에 연결해서 보면 좋은 흐름도 하나 짚고 가겠습니다. [Vue 입문 142: API 응답 타입과 런타임 검증을 구분하기](/vue/intro-142-api-response-type-runtime-check) 글을 먼저 다시 보면 지금 글이 갑자기 튀어나온 주제가 아니라는 점이 보입니다. 이전 글에서 다룬 기준이 지금 글에서 더 실무적인 판단으로 확장되기 때문입니다. 반대로 지금 글이 어느 정도 이해된다면, 다음 글로 넘어가면서 같은 기준이 다른 문제에서 어떻게 적용되는지 확인해보시면 좋습니다.

## 작은 실습으로 확인해보기

아래 예제는 실제 프로젝트에서 바로 응용할 수 있는 작은 형태로 구성했습니다. 예제를 볼 때는 코드 줄 수보다 책임의 위치를 먼저 봐주세요. 어떤 값이 입력이고, 어떤 함수가 상태를 바꾸고, 어떤 결과가 화면이나 빌드 결과에 영향을 주는지 따라가면 훨씬 이해가 쉽습니다.

{% raw %}
~~~vue
// .env.development
VITE_API_BASE_URL=http://localhost:8080

// .env.production
VITE_API_BASE_URL=https://api.example.com

// src/services/http.js
const baseUrl = import.meta.env.VITE_API_BASE_URL

export async function request(path, options) {
  const response = await fetch(`${baseUrl}${path}`, options)

  if (!response.ok) {
    throw new Error(`API 요청 실패: ${response.status}`)
  }

  return response.json()
}
~~~
{% endraw %}

## 코드가 움직이는 순서

첫 번째로 확인할 것은 “어떤 시점에 실행되는 코드인가”입니다. Vue 앱에서는 같은 코드처럼 보여도 컴포넌트가 렌더링될 때 실행되는 코드, 사용자가 클릭했을 때 실행되는 코드, 빌드 시점에 결정되는 코드, 운영 브라우저에서 실행되는 코드가 서로 다릅니다. 이 시점을 구분하지 못하면 문제를 고칠 때 엉뚱한 곳을 보게 됩니다.

두 번째로 확인할 것은 “이 코드가 사용자 경험에 어떤 영향을 주는가”입니다. 성능 최적화라면 사용자가 더 빨리 화면을 보는지, 접근성이라면 키보드와 보조 기술 사용자가 막히지 않는지, 타입이라면 잘못된 데이터 모양을 더 빨리 발견하는지, 배포라면 로컬과 운영의 차이를 줄이는지 확인해야 합니다.

세 번째로 확인할 것은 “실패했을 때 어떤 모습인가”입니다. 좋은 코드는 성공할 때만 예쁜 코드가 아니라 실패했을 때도 원인을 찾을 수 있는 코드입니다. 예제 코드를 직접 따라 작성한 뒤에는 일부러 잘못된 값, 느린 네트워크, 빈 데이터, 잘못된 경로를 넣어보세요. 이 연습을 해보면 문서에서 읽은 설명이 훨씬 현실적인 감각으로 바뀝니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: VITE_ 접두사가 없는 값은 클라이언트 코드에서 접근할 수 없다고 착각하기 쉽습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타나는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: API 키나 토큰을 프론트엔드 env에 넣으면 빌드 결과에 노출될 수 있습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타나는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: 환경별 파일을 바꿨는데 dev server를 재시작하지 않아 이전 값이 계속 쓰이는 경우가 있습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타나는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.

문제가 생겼을 때는 한 번에 모든 코드를 의심하지 말고, 입력값, 실행 시점, 상태 변경, 렌더링 결과, 빌드 결과를 차례로 확인해보세요. 특히 이번 구간의 주제들은 “개발 서버에서는 괜찮았는데 운영에서 깨지는 문제”와 자주 연결됩니다. 그래서 로컬 화면만 보는 것보다 빌드 결과, 브라우저 Network 탭, 콘솔 경고, 실제 HTML 구조까지 함께 보는 습관이 중요합니다.

## 실무에서 생각할 점

환경변수는 배포 유연성을 높여주지만 비밀값을 숨기는 도구가 아닙니다. 브라우저에 내려가는 값과 서버에서만 알아야 하는 값을 분리해야 합니다.

실무에서는 정답 패턴을 한 번에 고르는 것보다 현재 팀과 프로젝트의 복잡도에 맞는 선택을 하는 것이 중요합니다. 작은 화면에서는 단순한 코드가 가장 좋은 코드일 수 있고, 여러 화면에서 같은 문제가 반복되기 시작하면 그때 분리하는 편이 더 안전할 수 있습니다. 반대로 인증, 결제, 관리자 권한, 접근성, 배포 자동화처럼 실수의 영향이 큰 영역은 초반부터 기준을 조금 더 엄격하게 잡는 것이 좋습니다.

또 하나 중요한 점은 “최적화”라는 단어를 너무 좁게 보지 않는 것입니다. 빠르게 만드는 것도 최적화지만, 실수를 줄이는 타입 설계, 사용자를 막지 않는 접근성, 배포 후 문제를 찾을 수 있는 로그 기준도 모두 넓은 의미의 최적화입니다. 결국 좋은 Vue 앱은 문법을 많이 쓴 앱이 아니라 사용자가 안정적으로 목적을 달성할 수 있는 앱입니다.

## 디버깅하거나 검증할 때 확인할 순서

1. 지금 문제를 사용자의 행동으로 다시 설명합니다.
2. 개발 서버와 production build 중 어디에서 재현되는지 확인합니다.
3. 브라우저 콘솔과 Network 탭에서 오류, 404, 느린 요청을 확인합니다.
4. 컴포넌트 상태, props, emit, store, router 중 어느 경계에서 값이 달라지는지 확인합니다.
5. 접근성 주제라면 마우스를 쓰지 않고 Tab, Enter, Space, ESC만으로 흐름을 확인합니다.
6. 배포 주제라면 새로고침, 직접 URL 접근, 정적 파일 경로, 환경변수 값을 확인합니다.
7. 수정 후에는 같은 문제가 다시 생기지 않도록 테스트, 체크리스트, 문서 중 하나로 남깁니다.

이 순서를 습관처럼 적용하면 문제가 생겼을 때 훨씬 덜 흔들립니다. 입문 단계에서 가장 큰 차이는 “모든 API를 외웠는가”가 아니라 “어디부터 확인할지 알고 있는가”에서 생깁니다.
