# Vue 입문 47: onUnmounted로 타이머와 이벤트 리스너 정리하기

컴포넌트는 화면에 나타날 때만 중요한 것이 아닙니다. 화면에서 사라질 때도 해야 할 일이 있습니다. 타이머를 만들었거나, window 이벤트 리스너를 등록했거나, 외부 구독을 시작했다면 컴포넌트가 사라질 때 정리해야 합니다. 그렇지 않으면 보이지 않는 컴포넌트의 코드가 계속 실행될 수 있습니다.

`onUnmounted`는 컴포넌트가 언마운트된 뒤 실행되는 hook입니다. 여기에서 `clearInterval`, `removeEventListener` 같은 정리 작업을 수행합니다. 입문자는 작은 예제에서는 문제가 잘 보이지 않기 때문에 정리 코드를 생략하기 쉽지만, 실제 앱에서는 메모리 누수나 중복 실행 문제로 이어질 수 있습니다.

특히 라우터로 페이지를 이동하거나 조건부 렌더링으로 컴포넌트를 자주 열고 닫는 경우, 정리하지 않은 타이머가 여러 개 쌓일 수 있습니다. 버튼을 한 번 눌렀는데 로그가 여러 번 찍힌다면 이런 정리 누락을 의심해볼 수 있습니다.

## 이번 글에서 먼저 잡을 관점

이번 구간부터는 Vue를 단순히 한 파일 안에서 쓰는 단계에서 벗어나, 여러 컴포넌트가 함께 동작하는 구조를 다룹니다. 그래서 문법 하나만 보는 것보다 역할과 책임을 같이 보는 것이 중요합니다. 부모 컴포넌트가 무엇을 알고 있어야 하는지, 자식 컴포넌트는 어디까지 책임져야 하는지, 사용자의 행동을 어느 방향으로 전달해야 하는지 계속 질문하면서 읽어보시면 좋습니다.

컴포넌트 설계는 처음부터 완벽하게 나누는 일이 아닙니다. 작은 화면을 만들고, 반복되는 부분이나 책임이 분명한 부분을 발견하고, 그때 적절히 분리하는 과정에 가깝습니다. 이 글의 예제도 정답이라기보다 기준을 잡기 위한 출발점으로 봐주세요. 직접 이름을 바꿔보고, props를 하나 추가해보고, 이벤트 흐름을 바꿔보면 훨씬 오래 기억에 남습니다.

## 작은 실습으로 확인해보기

아래 예제는 1초마다 시간을 갱신하는 타이머를 만들고, 컴포넌트가 사라질 때 정리합니다.

{% raw %}
```vue
<script setup>
import { onMounted, onUnmounted, ref } from 'vue'

const now = ref(new Date().toLocaleTimeString())
let timerId = null

onMounted(() => {
  timerId = window.setInterval(() => {
    now.value = new Date().toLocaleTimeString()
  }, 1000)
})

onUnmounted(() => {
  if (timerId !== null) {
    window.clearInterval(timerId)
  }
})
</script>

<template>
  <p>현재 시간: {{ now }}</p>
</template>
```
{% endraw %}

## 코드가 움직이는 순서

컴포넌트가 마운트되면 `setInterval`이 시작됩니다. 이 타이머는 컴포넌트 바깥 브라우저 환경에 등록됩니다. 따라서 컴포넌트가 사라져도 자동으로 정리된다고 기대하면 안 됩니다. `onUnmounted`에서 `clearInterval`을 호출해 더 이상 실행되지 않게 해야 합니다.

여기서 중요한 것은 코드 줄 수보다 의도입니다. 컴포넌트를 나누면 파일은 늘어나지만, 각 파일이 맡는 역할이 선명해져야 합니다. 부모는 전체 상태와 흐름을 관리하고, 자식은 자신이 맡은 UI 조각을 표현하거나 사용자 행동을 이벤트로 알려주는 식으로 역할을 나누면 디버깅이 훨씬 쉬워집니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 이벤트 리스너를 등록할 때 익명 함수를 바로 넣으면 제거할 때 같은 참조를 전달하기 어렵습니다. 제거가 필요하면 함수 참조를 변수나 함수 선언으로 관리하세요. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 조건부로 열고 닫는 컴포넌트에서 정리 코드를 빼먹으면 타이머나 구독이 여러 개 쌓일 수 있습니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: onUnmounted는 정리 작업을 위한 곳이지, 새로운 장기 작업을 시작하는 곳이 아닙니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.

컴포넌트 관련 오류는 한 파일만 봐서는 바로 보이지 않을 때가 많습니다. 부모가 넘기는 prop 이름, 자식이 선언한 prop 이름, 자식이 emit하는 이벤트 이름, 부모가 듣는 이벤트 이름을 한 줄씩 맞춰보는 습관이 필요합니다. 브라우저 콘솔의 Vue warning도 그냥 넘기지 말고, 어떤 컴포넌트에서 발생했는지 확인해보시면 좋습니다.

## 실무에서 생각할 점

정리 코드는 당장 화면에 보이는 기능을 만들지는 않지만 앱 안정성에 큰 영향을 줍니다. 작은 프로젝트에서도 타이머와 이벤트 리스너를 만들었다면 정리까지 작성하는 습관을 들이면 실무에서 훨씬 안전합니다.

실무에서는 컴포넌트가 "동작한다"보다 "변경에 견딘다"가 더 중요해집니다. 요구사항은 계속 바뀌고, 디자인도 바뀌고, 같은 컴포넌트를 다른 화면에서 쓰고 싶어질 수 있습니다. 그래서 처음부터 모든 것을 일반화하려고 하기보다, 현재 책임을 명확히 하고 나중에 반복이 보일 때 재사용성을 높이는 방향이 안전합니다.
