Vue 템플릿 문법은 읽기 쉽지만, 작은 실수 하나로 화면이 의도와 다르게 렌더링될 수 있습니다. 특히 입문 단계에서는 에러 메시지가 코드의 어느 부분을 말하는지 바로 감이 오지 않아 오래 헤매게 됩니다. 그래서 자주 발생하는 실수를 미리 알고 있으면 디버깅 시간이 크게 줄어듭니다.

가장 흔한 실수는 변수 이름 오타입니다. 스크립트에서는 `message`라고 선언했는데 템플릿에서는 `messege`라고 쓰는 식입니다. 그 다음은 바인딩 누락입니다. `:href="url"`로 써야 하는데 `href="url"`로 쓰면 변수 값이 아니라 문자열 `url`이 들어갑니다. 목록에서는 `key`를 빠뜨리거나 index를 무조건 key로 써서 나중에 항목 상태가 꼬이기도 합니다.

또 다른 실수는 지시문을 한 요소에 과하게 섞는 것입니다. `v-if`와 `v-for`를 같은 태그에 함께 쓰면 의도와 다르게 해석되거나 읽기 어려워집니다. 조건 필터링은 computed로 빼고, 템플릿은 이미 정리된 목록을 그리는 역할로 두는 편이 안전합니다.

## 이번 글에서 먼저 잡을 관점

이번 주제에서 가장 중요한 것은 문법을 외우는 것보다 흐름을 이해하는 것입니다. Vue 코드는 보통 상태를 준비한다 -> 템플릿에서 상태를 읽는다 -> 사용자 행동으로 상태가 바뀐다 -> Vue가 화면을 다시 맞춘다는 순서로 움직입니다. 이 순서를 머릿속에 두고 읽으면 새로운 문법을 만나도 훨씬 덜 흔들립니다.

또 하나 중요한 점은 Vue가 HTML, CSS, JavaScript를 대체하는 것이 아니라는 사실입니다. Vue는 이 세 가지를 더 구조적으로 연결해주는 도구입니다. 그래서 예제를 따라 칠 때도 "이 문법이 Vue에서만 특별한가?", "아니면 원래 HTML/JavaScript 개념을 Vue 방식으로 연결한 것인가?"를 나누어 생각하면 좋습니다.

처음에는 한 번에 완벽하게 이해하지 못해도 괜찮습니다. 대신 예제 코드를 조금씩 바꿔보면서 어떤 값이 바뀌면 화면의 어느 부분이 바뀌는지 확인해보세요. 손으로 바꿔본 경험이 쌓이면, 단순히 읽기만 했을 때보다 훨씬 빠르게 감이 잡힙니다.

## 작은 실습으로 확인해보기

아래 예제는 자주 만나는 실수를 피한 형태입니다. 필터링은 computed로 처리하고, 목록에는 안정적인 key를 사용합니다.

{% raw %}
```vue
<script setup>
import { computed, ref } from 'vue'

const showOnlyActive = ref(true)
const users = ref([
  { id: 1, name: '지민', active: true },
  { id: 2, name: '하린', active: false },
  { id: 3, name: '도윤', active: true }
])

const visibleUsers = computed(() => {
  if (!showOnlyActive.value) return users.value
  return users.value.filter(user => user.active)
})
</script>

<template>
  <label>
    <input v-model="showOnlyActive" type="checkbox" />
    활성 사용자만 보기
  </label>

  <ul>
    <li v-for="user in visibleUsers" :key="user.id">
      {{ user.name }}
    </li>
  </ul>
</template>
```
{% endraw %}

## 코드가 움직이는 순서

`visibleUsers`는 템플릿에 들어가기 전에 이미 조건에 맞게 정리된 목록입니다. 템플릿은 `v-for`로 그 목록을 출력하기만 합니다. 각 사용자는 `user.id`를 key로 갖기 때문에 삭제나 필터링이 일어나도 Vue가 항목을 안정적으로 추적할 수 있습니다.

여기서 꼭 기억하셔야 할 부분은 Vue가 화면을 갱신해준다고 해서 개발자가 흐름을 몰라도 되는 것은 아니라는 점입니다. 오히려 Vue를 잘 쓰려면 상태가 어디에 있고, 어떤 이벤트나 함수가 그 상태를 바꾸며, 템플릿이 그 상태를 어떻게 읽는지 계속 추적할 수 있어야 합니다. 작은 예제부터 이 흐름을 말로 설명해보면 나중에 코드가 길어져도 훨씬 덜 막힙니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 문자열 속성과 동적 바인딩을 구분해야 합니다. `href="url"`은 문자열이고 `:href="url"`은 변수입니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: 템플릿에서 쓰는 이름과 스크립트에서 선언한 이름이 정확히 일치해야 합니다. 자동 완성이 되더라도 최종 이름을 확인하는 습관이 필요합니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: 화면이 하얗게 보이면 터미널만 보지 말고 브라우저 개발자 도구 Console도 확인해야 합니다. 런타임 오류는 브라우저에 더 자세히 나오는 경우가 많습니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.

에러를 만났을 때는 먼저 터미널 로그와 브라우저 개발자 도구 Console을 함께 봐야 합니다. Vue 프로젝트는 빌드 단계에서 나는 오류와 브라우저 실행 중에 나는 오류가 다를 수 있습니다. 터미널은 정상처럼 보여도 브라우저 콘솔에는 컴포넌트 렌더링 오류가 남아 있을 수 있고, 반대로 브라우저를 열기도 전에 Vite 개발 서버가 실패하는 경우도 있습니다.

## 실무에서 생각할 점

템플릿 문법 실수는 누구나 합니다. 중요한 것은 실수를 없애겠다고 모든 것을 복잡한 구조로 감싸는 것이 아니라, 변수 이름, 바인딩 표시, key, 조건과 반복 분리 같은 기본 체크리스트를 갖는 것입니다. 이 체크리스트만 있어도 입문 단계의 렌더링 문제 대부분을 빠르게 좁힐 수 있습니다.

실무에서는 "동작한다"만으로는 부족한 경우가 많습니다. 다른 사람이 읽었을 때 의도를 이해할 수 있는지, 요구사항이 조금 바뀌어도 고치기 쉬운지, 에러 상황에서도 사용자가 무엇을 해야 하는지 알 수 있는지가 중요합니다. 입문 시리즈에서 계속 예제와 주의사항을 함께 보는 이유도 여기에 있습니다. 문법을 하나 배울 때마다 그 문법이 실패할 수 있는 지점까지 같이 봐야 실제 프로젝트에서 덜 흔들립니다.

다음 글로 넘어가기 전에 예제 코드를 그대로 한 번 작성해보시고, 최소한 한 군데는 직접 바꿔보시는 것을 추천드립니다. 버튼 문구를 바꾸거나, 상태 초기값을 바꾸거나, 조건을 하나 추가하는 정도면 충분합니다. 그렇게 작은 변화를 직접 만들어보면 "아, 이 부분이 화면과 연결되어 있구나"라는 감각이 생깁니다.
