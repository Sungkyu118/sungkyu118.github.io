# Redis 입문 실무형 3: 운영 기본 (모니터링, 메모리, eviction)

Redis는 개발 환경에서는 잘 돌아가는데, 운영에서 "어느 날 갑자기" 문제가 보이는 경우가 많습니다. 대부분은 메모리/eviction/핫키/만료 패턴에서 시작해요.

이 글은 Redis를 운영에서 볼 때 최소한의 감각을 잡는 게 목표입니다.

## 1) 제일 먼저 보는 것: 메모리 사용량

Redis는 메모리 기반이기 때문에, 메모리 사용량을 모르고 운영하면 위험합니다.

실무에서 자주 보는 시나리오:

- 캐시를 늘린다 → 히트율은 좋아짐
- 어느 순간 메모리 꽉 참 → eviction 시작
- 캐시가 랜덤하게 날아감 → 히트율 급락
- DB/외부 API로 부하 전파

## 2) eviction(퇴거) 정책 이해하기

eviction은 "메모리가 부족할 때 무엇을 버릴지"를 결정합니다.

- allkeys-lru: 전체 키 중 LRU 기반
- volatile-ttl: TTL 있는 키 중 TTL 짧은 것부터

핵심은, eviction이 발생한다는 건 이미 위험 구간이라는 뜻입니다.

## 3) 핫키(Hot Key)

모두가 한 키만 때리면, Redis 자체가 병목이 되거나 특정 노드만 뜨거워질 수 있습니다.

완화 아이디어:

- 키를 분산(sharding)하거나, 랜덤 접미사를 붙여 분산하는 전략(상황에 따라)
- 캐시 갱신을 단일화(락)하거나 백그라운드 갱신

## 4) 만료 패턴과 부하

TTL은 좋지만, 만료가 "동시에" 몰리면 부하가 튑니다.

- 지터(jitter)로 만료 분산
- 일정 시점에 일괄 만료되는 키가 없는지 점검

## 5) 최소 모니터링 지표

Redis/인프라 도구에 따라 다르지만, 최소로는 이 정도는 보는 게 좋습니다.

- 메모리 사용량
- 명령 처리량(ops/sec)
- keyspace hit/miss(캐시 히트율)
- 연결 수
- 지연 시간(latency)

## 정리

- Redis 운영의 중심은 "메모리"다
- eviction이 시작되면 캐시 품질이 흔들린다
- 핫키/동시 만료를 초기에 방어하면 장애 가능성이 크게 줄어든다
