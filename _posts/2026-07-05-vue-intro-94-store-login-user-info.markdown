# Vue 입문 94: 로그인 사용자 정보를 Pinia에 저장하는 실습

> 사용자 세션 정보를 여러 화면에서 공유하기 위해 Pinia store에 저장하는 기본 흐름을 배웁니다.

로그인 기능은 전역 상태 관리가 필요한 대표적인 예입니다. 로그인한 사용자 이름은 헤더에 보이고, 마이페이지에서는 상세 정보가 필요하며, 라우터 guard는 로그인 여부를 기준으로 접근을 막아야 합니다. 이런 값을 컴포넌트마다 따로 관리하면 금방 어긋납니다.

Pinia store에 사용자 정보와 토큰을 저장하면 여러 화면이 같은 상태를 바라볼 수 있습니다. 로그인 성공 시 store action이 세션을 저장하고, 로그아웃 시 같은 store가 세션을 비우면 됩니다.

다만 토큰 저장은 보안과 연결됩니다. 이 글에서는 입문 예제로 상태 흐름을 설명하지만, 실제 서비스에서는 저장 위치, 만료 시간, refresh token, XSS 위험을 함께 검토해야 합니다.

## 이번 글에서 먼저 잡을 관점

이번 Pinia 구간에서는 store 문법을 외우는 것보다 상태의 범위와 책임을 먼저 보겠습니다. 전역 상태는 여러 화면을 편하게 연결해주지만, 잘못 쓰면 어디서 값이 바뀌는지 추적하기 어려운 큰 공유 공간이 될 수 있습니다.

예제를 읽으실 때는 이 값이 왜 지역 상태가 아니라 전역 상태인지, getter로 계산할 수 있는 값을 state에 중복 저장하고 있지는 않은지, action 이름이 사용자 행동을 잘 설명하는지 함께 살펴보시면 좋습니다.

지금 단계에서는 완벽한 구조를 외우려고 하기보다, 왜 이 코드가 특정 위치에 있어야 하는지, 그 위치가 바뀌면 어떤 장점과 비용이 생기는지 함께 생각해보시면 좋습니다. Vue 프로젝트는 문법을 많이 아는 것보다 상태, 화면, 서버, 테스트의 책임을 구분하는 힘이 중요해지는 순간이 많습니다.

## 작은 실습으로 확인해보기

아래 예제는 로그인 API 호출 후 사용자 정보와 access token을 auth store에 저장하는 흐름입니다.

{% raw %}
~~~vue
import { defineStore } from 'pinia'

export const useAuthStore = defineStore('auth', {
  state: () => ({
    user: null,
    accessToken: ''
  }),
  getters: {
    isLoggedIn: (state) => Boolean(state.accessToken),
    userName: (state) => state.user?.name ?? '손님'
  },
  actions: {
    async login(credentials) {
      const response = await fetch('/api/login', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(credentials)
      })

      if (!response.ok) {
        throw new Error('로그인에 실패했습니다.')
      }

      const session = await response.json()
      this.user = session.user
      this.accessToken = session.accessToken
    },
    logout() {
      this.user = null
      this.accessToken = ''
    }
  }
})
~~~
{% endraw %}

## 코드가 움직이는 순서

`login` action은 API 요청, 실패 처리, 성공 시 state 저장을 담당합니다. 컴포넌트는 `auth.login()`을 호출하고 성공하면 이동만 처리하면 됩니다. `isLoggedIn` getter는 라우터 guard나 헤더에서 로그인 여부를 판단할 때 사용할 수 있습니다.

예제를 따라 작성할 때는 먼저 상태가 만들어지는 위치를 찾고, 그다음 그 상태를 바꾸는 함수를 찾고, 마지막으로 템플릿이나 테스트에서 어떤 결과를 확인하는지 살펴보세요. Vue 코드는 겉으로는 여러 파일에 나뉘어 보이지만, 실제로는 "상태가 바뀌고, 계산값이 갱신되고, 화면이나 테스트 결과가 달라지는 흐름"을 반복합니다. 이 순서를 말로 설명할 수 있으면 문법을 조금 잊어도 다시 찾아가며 구현할 수 있습니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 토큰이 있다고 항상 유효한 것은 아닙니다. 만료된 토큰 처리와 사용자 정보 재확인이 필요할 수 있습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: 로그아웃 시 user만 지우고 token을 남기면 앱은 여전히 로그인 상태처럼 판단할 수 있습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: 토큰을 localStorage에 저장할 경우 XSS 위험을 반드시 고려해야 합니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.

문제가 생겼을 때는 한 번에 모든 코드를 의심하지 말고, 입력값, 상태 변경 함수, 비동기 요청 결과, 화면 렌더링 또는 테스트 검증 지점을 차례로 확인해보세요. 특히 Pinia, API, 테스트는 코드가 여러 파일에 나뉘기 쉬워서 어디서 값이 바뀌었는지 놓치기 쉽습니다. 브라우저 콘솔, Network 탭, Vue Devtools, 테스트 실패 메시지를 함께 보면 눈으로 보이지 않는 흐름을 훨씬 빠르게 확인할 수 있습니다.

## 실무에서 생각할 점

auth store는 앱 전반의 인증 흐름을 단순하게 만들지만, 보안 정책까지 store 하나로 해결되는 것은 아닙니다. 프론트 상태와 서버 권한 검사를 분리해서 생각해야 합니다.

실무에서는 정답 패턴을 한 번에 고르는 것보다 현재 팀과 프로젝트의 복잡도에 맞는 선택을 하는 것이 중요합니다. 작은 화면에서는 단순한 코드가 가장 좋은 코드일 수 있고, 여러 화면에서 같은 문제가 반복되기 시작하면 그때 분리하는 편이 더 안전할 수 있습니다. 반대로 인증, 결제, 관리자 권한, 테스트 자동화처럼 실수의 영향이 큰 영역은 초반부터 책임 경계를 조금 더 엄격하게 잡는 것이 좋습니다.

## 디버깅하거나 검증할 때 확인할 순서

1. 현재 값이 어디에서 만들어지는지 확인합니다.
2. 그 값을 바꾸는 함수나 action이 어느 파일에 있는지 확인합니다.
3. API 요청이 있다면 loading, success, error 상태가 모두 처리되는지 확인합니다.
4. 사용자 입력이 있다면 입력 전, 입력 중, 제출 후 상태를 나누어 확인합니다.
5. 테스트가 있다면 내부 구현보다 사용자에게 보이는 결과를 검증하는지 확인합니다.

이 순서를 습관처럼 적용하면 문제를 만났을 때 훨씬 덜 흔들립니다. 특히 입문 단계에서는 코드를 많이 아는 것보다, 문제가 생겼을 때 확인할 순서를 알고 있는 것이 더 큰 힘이 됩니다.
