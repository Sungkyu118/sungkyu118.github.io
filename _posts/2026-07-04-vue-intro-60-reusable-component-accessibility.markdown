재사용 컴포넌트를 만들 때 디자인과 props만 생각하면 중요한 부분을 놓칠 수 있습니다. 버튼처럼 보이는 요소가 실제로는 div라면 키보드로 조작하기 어렵고, 모달이 열렸는데 제목과 역할을 알 수 없다면 보조기술 사용자는 현재 상황을 이해하기 어렵습니다. 좋은 컴포넌트는 보기 좋은 것뿐 아니라 사용하기 쉬워야 합니다.

접근성은 거창한 별도 기능이 아니라 HTML을 의미 있게 쓰는 것에서 시작합니다. 클릭 가능한 동작은 가능하면 `button`을 사용하고, 링크 이동은 `a`를 사용합니다. 입력에는 label을 연결하고, 상태 변화는 disabled, aria 속성, 문구로 함께 표현합니다. CSS로만 상태를 표현하면 일부 사용자는 변화를 알기 어렵습니다.

재사용 컴포넌트일수록 접근성 실수의 영향이 커집니다. 버튼 컴포넌트 하나가 잘못 만들어지면 그 버튼을 사용하는 모든 화면이 같은 문제를 갖게 됩니다. 반대로 공통 컴포넌트에서 접근성을 잘 잡으면 여러 화면의 품질을 한꺼번에 높일 수 있습니다.

## 이번 글에서 먼저 잡을 관점

이번 구간부터는 Vue를 단순히 한 파일 안에서 쓰는 단계에서 벗어나, 여러 컴포넌트가 함께 동작하는 구조를 다룹니다. 그래서 문법 하나만 보는 것보다 역할과 책임을 같이 보는 것이 중요합니다. 부모 컴포넌트가 무엇을 알고 있어야 하는지, 자식 컴포넌트는 어디까지 책임져야 하는지, 사용자의 행동을 어느 방향으로 전달해야 하는지 계속 질문하면서 읽어보시면 좋습니다.

컴포넌트 설계는 처음부터 완벽하게 나누는 일이 아닙니다. 작은 화면을 만들고, 반복되는 부분이나 책임이 분명한 부분을 발견하고, 그때 적절히 분리하는 과정에 가깝습니다. 이 글의 예제도 정답이라기보다 기준을 잡기 위한 출발점으로 봐주세요. 직접 이름을 바꿔보고, props를 하나 추가해보고, 이벤트 흐름을 바꿔보면 훨씬 오래 기억에 남습니다.

## 작은 실습으로 확인해보기

아래 예제는 로딩 상태를 가진 버튼 컴포넌트에서 실제 button 요소, disabled, aria-busy를 함께 처리합니다.

```vue
<!-- AccessibleButton.vue -->
<script setup>
defineProps({
  loading: {
    type: Boolean,
    default: false
  },
  disabled: {
    type: Boolean,
    default: false
  },
  type: {
    type: String,
    default: 'button'
  }
})

const emit = defineEmits(['click'])
</script>

<template>
  <button
    :type="type"
    :disabled="disabled || loading"
    :aria-busy="loading"
    @click="emit('click')"
  >
    <span v-if="loading">처리 중입니다</span>
    <slot v-else />
  </button>
</template>
```

## 코드가 움직이는 순서

이 컴포넌트는 div가 아니라 실제 `button`을 사용합니다. `disabled || loading`일 때 클릭을 막고, `aria-busy`로 처리 중 상태를 보조기술에 전달할 수 있게 합니다. 버튼 내용은 slot으로 받아 재사용성을 유지합니다. 폼 안에서 의도치 않은 제출을 막기 위해 기본 type도 `button`으로 둡니다.

여기서 중요한 것은 코드 줄 수보다 의도입니다. 컴포넌트를 나누면 파일은 늘어나지만, 각 파일이 맡는 역할이 선명해져야 합니다. 부모는 전체 상태와 흐름을 관리하고, 자식은 자신이 맡은 UI 조각을 표현하거나 사용자 행동을 이벤트로 알려주는 식으로 역할을 나누면 디버깅이 훨씬 쉬워집니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 버튼처럼 보이는 div는 키보드 조작과 의미 전달에서 문제가 생길 수 있습니다. 가능한 한 의미에 맞는 HTML 요소를 사용하세요. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 로딩 상태를 색상이나 스피너로만 표현하면 일부 사용자가 상태를 알기 어렵습니다. 텍스트와 속성을 함께 고려하세요. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 공통 컴포넌트의 접근성 문제는 여러 화면으로 퍼집니다. 재사용 컴포넌트일수록 처음 설계가 중요합니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.

컴포넌트 관련 오류는 한 파일만 봐서는 바로 보이지 않을 때가 많습니다. 부모가 넘기는 prop 이름, 자식이 선언한 prop 이름, 자식이 emit하는 이벤트 이름, 부모가 듣는 이벤트 이름을 한 줄씩 맞춰보는 습관이 필요합니다. 브라우저 콘솔의 Vue warning도 그냥 넘기지 말고, 어떤 컴포넌트에서 발생했는지 확인해보시면 좋습니다.

## 실무에서 생각할 점

접근성을 고려하면 코드가 조금 길어질 수 있습니다. 하지만 이 비용은 사용자 경험과 유지보수 측면에서 충분히 가치가 있습니다. 특히 재사용 컴포넌트는 한 번 잘 만들어두면 여러 화면에서 같은 기준을 공유할 수 있으므로 장기적으로 훨씬 유리합니다.

실무에서는 컴포넌트가 "동작한다"보다 "변경에 견딘다"가 더 중요해집니다. 요구사항은 계속 바뀌고, 디자인도 바뀌고, 같은 컴포넌트를 다른 화면에서 쓰고 싶어질 수 있습니다. 그래서 처음부터 모든 것을 일반화하려고 하기보다, 현재 책임을 명확히 하고 나중에 반복이 보일 때 재사용성을 높이는 방향이 안전합니다.
