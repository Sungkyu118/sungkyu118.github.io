Vue를 제대로 연습하려면 브라우저 콘솔에 작은 코드만 붙여 넣는 단계에서 한 번쯤 실제 프로젝트 구조로 넘어와야 합니다. 현재 Vue 공식 문서와 생태계에서는 Vite 기반 프로젝트 생성 흐름을 많이 사용합니다. Vite는 개발 서버를 빠르게 띄우고, 저장할 때 변경 사항을 즉시 반영하며, 운영 배포용 정적 파일을 빌드해주는 도구입니다.

입문자가 여기서 자주 헷갈리는 지점은 "Vue와 Vite가 같은 것인가?"입니다. Vue는 화면을 만들기 위한 프레임워크이고, Vite는 개발 서버와 빌드 환경을 제공하는 도구입니다. 쉽게 말해 Vue는 앱의 동작 규칙이고, Vite는 그 앱을 개발하고 포장하는 작업대에 가깝습니다.

Vite 공식 문서 기준으로 최신 Vite는 Node.js 요구 버전이 꽤 높습니다. 그래서 오래전에 설치한 Node.js로 `npm create vite@latest`를 실행하면 템플릿 선택 전부터 버전 오류가 날 수 있습니다. 이때는 Vue 문제가 아니라 Node.js 실행 환경 문제입니다. 설치 글에서는 항상 현재 공식 문서의 요구 버전을 확인하는 습관이 중요합니다.

## 이번 글에서 먼저 잡을 관점

이번 주제에서 가장 중요한 것은 문법을 외우는 것보다 흐름을 이해하는 것입니다. Vue 코드는 보통 상태를 준비한다 -> 템플릿에서 상태를 읽는다 -> 사용자 행동으로 상태가 바뀐다 -> Vue가 화면을 다시 맞춘다는 순서로 움직입니다. 이 순서를 머릿속에 두고 읽으면 새로운 문법을 만나도 훨씬 덜 흔들립니다.

또 하나 중요한 점은 Vue가 HTML, CSS, JavaScript를 대체하는 것이 아니라는 사실입니다. Vue는 이 세 가지를 더 구조적으로 연결해주는 도구입니다. 그래서 예제를 따라 칠 때도 "이 문법이 Vue에서만 특별한가?", "아니면 원래 HTML/JavaScript 개념을 Vue 방식으로 연결한 것인가?"를 나누어 생각하면 좋습니다.

처음에는 한 번에 완벽하게 이해하지 못해도 괜찮습니다. 대신 예제 코드를 조금씩 바꿔보면서 어떤 값이 바뀌면 화면의 어느 부분이 바뀌는지 확인해보세요. 손으로 바꿔본 경험이 쌓이면, 단순히 읽기만 했을 때보다 훨씬 빠르게 감이 잡힙니다.

## 작은 실습으로 확인해보기

아래 명령은 npm 기준으로 Vue 프로젝트를 생성하고 실행하는 가장 기본 흐름입니다. 실제 터미널에서는 한 줄씩 실행해보는 것이 좋습니다.

```bash
npm create vite@latest my-vue-app -- --template vue
cd my-vue-app
npm install
npm run dev

# 운영 배포용 파일을 만들 때
npm run build

# 빌드 결과물을 로컬에서 미리 확인할 때
npm run preview
```

## 코드가 움직이는 순서

`npm create vite@latest`는 프로젝트 뼈대를 만듭니다. `npm install`은 `package.json`에 적힌 의존성을 내려받습니다. `npm run dev`는 개발 서버를 띄우고, 보통 `localhost:5173` 같은 주소를 보여줍니다. `npm run build`는 개발 서버를 띄우는 명령이 아니라, 배포 가능한 정적 파일을 `dist` 폴더에 만드는 명령입니다. `preview`는 그 결과물이 실제로 어떻게 보이는지 로컬에서 확인하는 단계입니다.

여기서 꼭 기억하셔야 할 부분은 Vue가 화면을 갱신해준다고 해서 개발자가 흐름을 몰라도 되는 것은 아니라는 점입니다. 오히려 Vue를 잘 쓰려면 상태가 어디에 있고, 어떤 이벤트나 함수가 그 상태를 바꾸며, 템플릿이 그 상태를 어떻게 읽는지 계속 추적할 수 있어야 합니다. 작은 예제부터 이 흐름을 말로 설명해보면 나중에 코드가 길어져도 훨씬 덜 막힙니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: Node.js 버전이 낮으면 Vite 자체가 실행되지 않을 수 있습니다. 에러 메시지에 `requires Node.js` 같은 문구가 있으면 Vue 코드가 아니라 런타임 버전을 먼저 확인해야 합니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: 프로젝트 폴더를 만든 뒤 `npm install`을 빼먹으면 `node_modules`가 없어서 `npm run dev`가 실패합니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: 개발 서버 주소를 운영 배포 주소처럼 생각하면 안 됩니다. `localhost`는 내 컴퓨터에서만 열리는 임시 개발 주소입니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.

에러를 만났을 때는 먼저 터미널 로그와 브라우저 개발자 도구 Console을 함께 봐야 합니다. Vue 프로젝트는 빌드 단계에서 나는 오류와 브라우저 실행 중에 나는 오류가 다를 수 있습니다. 터미널은 정상처럼 보여도 브라우저 콘솔에는 컴포넌트 렌더링 오류가 남아 있을 수 있고, 반대로 브라우저를 열기도 전에 Vite 개발 서버가 실패하는 경우도 있습니다.

## 실무에서 생각할 점

Vite는 Vue 입문자에게 매우 편한 기본 선택입니다. 설정이 적고 실행이 빠르기 때문입니다. 다만 회사 프로젝트에서 이미 Webpack, Nuxt, 기존 Vue CLI를 쓰고 있다면 무조건 Vite로 바꾸는 것이 답은 아닙니다. 처음 배우는 프로젝트는 Vite로 시작하고, 기존 프로젝트를 만났을 때는 그 프로젝트의 도구를 존중하는 식으로 접근하는 것이 좋습니다.

실무에서는 "동작한다"만으로는 부족한 경우가 많습니다. 다른 사람이 읽었을 때 의도를 이해할 수 있는지, 요구사항이 조금 바뀌어도 고치기 쉬운지, 에러 상황에서도 사용자가 무엇을 해야 하는지 알 수 있는지가 중요합니다. 입문 시리즈에서 계속 예제와 주의사항을 함께 보는 이유도 여기에 있습니다. 문법을 하나 배울 때마다 그 문법이 실패할 수 있는 지점까지 같이 봐야 실제 프로젝트에서 덜 흔들립니다.

## 오늘 내용 정리

이번 글에서는 $(System.Collections.Specialized.OrderedDictionary.Title) 주제를 중심으로 Vue의 기본 흐름을 살펴봤습니다. 핵심은 Vue 문법을 낱개로 외우는 것이 아니라, 상태와 템플릿과 이벤트가 서로 어떻게 연결되는지 보는 것입니다. 같은 예제라도 값을 바꿔보고, 함수 이름을 일부러 틀려보고, 조건을 반대로 바꿔보면 훨씬 깊게 이해할 수 있습니다.

다음 글로 넘어가기 전에 예제 코드를 그대로 한 번 작성해보시고, 최소한 한 군데는 직접 바꿔보시는 것을 추천드립니다. 버튼 문구를 바꾸거나, 상태 초기값을 바꾸거나, 조건을 하나 추가하는 정도면 충분합니다. 그렇게 작은 변화를 직접 만들어보면 "아, 이 부분이 화면과 연결되어 있구나"라는 감각이 생깁니다.
