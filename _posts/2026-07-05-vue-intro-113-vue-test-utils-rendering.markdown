> 컴포넌트가 props와 상태를 받아 화면에 무엇을 렌더링하는지 테스트합니다.

순수 함수 테스트 다음에는 컴포넌트가 실제로 화면에 무엇을 렌더링하는지 확인할 수 있습니다. Vue Test Utils는 Vue 컴포넌트를 테스트 환경에서 mount하고, 텍스트나 요소를 찾고, 이벤트를 발생시키는 도구를 제공합니다.

렌더링 테스트는 "컴포넌트가 사용자에게 무엇을 보여주는가"에 집중하는 것이 좋습니다. 내부 ref 이름이나 함수 구현보다 화면에 보이는 결과를 기준으로 검증하면 리팩토링에 더 강한 테스트가 됩니다.

이번 글에서는 간단한 환영 메시지 컴포넌트를 mount하고 텍스트를 확인해보겠습니다.

## 이번 글에서 먼저 잡을 관점

이번 테스트 구간에서는 테스트 도구 사용법만이 아니라 무엇을 검증해야 오래가는 테스트가 되는지 함께 보겠습니다. 테스트는 완벽함을 보장하는 장치가 아니라, 중요한 동작이 깨졌을 때 빨리 알려주는 안전망입니다.

예제를 읽을 때는 내부 변수명을 확인하는지, 사용자에게 보이는 결과를 확인하는지 구분해보세요. 좋은 테스트는 리팩토링을 방해하기보다 리팩토링을 더 안전하게 만들어야 합니다.

지금 단계에서는 완벽한 구조를 외우려고 하기보다, 왜 이 코드가 특정 위치에 있어야 하는지, 그 위치가 바뀌면 어떤 장점과 비용이 생기는지 함께 생각해보시면 좋습니다. Vue 프로젝트는 문법을 많이 아는 것보다 상태, 화면, 서버, 테스트의 책임을 구분하는 힘이 중요해지는 순간이 많습니다.

## 작은 실습으로 확인해보기

아래 예제는 userName prop에 따라 인사 문구가 렌더링되는지 테스트합니다.

{% raw %}
~~~vue
<!-- WelcomeMessage.vue -->
<script setup>
defineProps({
  userName: {
    type: String,
    required: true
  }
})
</script>

<template>
  <p>{{ userName }}님, 환영합니다.</p>
</template>

// WelcomeMessage.test.js
import { mount } from '@vue/test-utils'
import { describe, expect, it } from 'vitest'
import WelcomeMessage from './WelcomeMessage.vue'

describe('WelcomeMessage', () => {
  it('사용자 이름을 포함한 환영 문구를 보여줍니다', () => {
    const wrapper = mount(WelcomeMessage, {
      props: {
        userName: '수경'
      }
    })

    expect(wrapper.text()).toContain('수경님, 환영합니다.')
  })
})
~~~
{% endraw %}

## 코드가 움직이는 순서

`mount`는 컴포넌트를 테스트 환경에 렌더링합니다. props로 userName을 넘기고, wrapper.text()에 기대 문구가 포함되어 있는지 확인합니다.

예제를 따라 작성할 때는 먼저 상태가 만들어지는 위치를 찾고, 그다음 그 상태를 바꾸는 함수를 찾고, 마지막으로 템플릿이나 테스트에서 어떤 결과를 확인하는지 살펴보세요. Vue 코드는 겉으로는 여러 파일에 나뉘어 보이지만, 실제로는 "상태가 바뀌고, 계산값이 갱신되고, 화면이나 테스트 결과가 달라지는 흐름"을 반복합니다. 이 순서를 말로 설명할 수 있으면 문법을 조금 잊어도 다시 찾아가며 구현할 수 있습니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 내부 구현보다 사용자에게 보이는 결과를 검증하는 편이 유지보수에 좋습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: mount에 필요한 props를 빼먹으면 컴포넌트 경고나 실패가 발생할 수 있습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: 너무 넓은 컴포넌트를 한 번에 테스트하면 실패 원인을 찾기 어렵습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.

문제가 생겼을 때는 한 번에 모든 코드를 의심하지 말고, 입력값, 상태 변경 함수, 비동기 요청 결과, 화면 렌더링 또는 테스트 검증 지점을 차례로 확인해보세요. 특히 Pinia, API, 테스트는 코드가 여러 파일에 나뉘기 쉬워서 어디서 값이 바뀌었는지 놓치기 쉽습니다. 브라우저 콘솔, Network 탭, Vue Devtools, 테스트 실패 메시지를 함께 보면 눈으로 보이지 않는 흐름을 훨씬 빠르게 확인할 수 있습니다.

## 실무에서 생각할 점

컴포넌트 렌더링 테스트는 실제 화면에 가까운 검증을 제공하지만 순수 함수 테스트보다 느릴 수 있습니다. 중요한 표시 조건부터 테스트하면 효율적입니다.

실무에서는 정답 패턴을 한 번에 고르는 것보다 현재 팀과 프로젝트의 복잡도에 맞는 선택을 하는 것이 중요합니다. 작은 화면에서는 단순한 코드가 가장 좋은 코드일 수 있고, 여러 화면에서 같은 문제가 반복되기 시작하면 그때 분리하는 편이 더 안전할 수 있습니다. 반대로 인증, 결제, 관리자 권한, 테스트 자동화처럼 실수의 영향이 큰 영역은 초반부터 책임 경계를 조금 더 엄격하게 잡는 것이 좋습니다.

## 디버깅하거나 검증할 때 확인할 순서

1. 현재 값이 어디에서 만들어지는지 확인합니다.
2. 그 값을 바꾸는 함수나 action이 어느 파일에 있는지 확인합니다.
3. API 요청이 있다면 loading, success, error 상태가 모두 처리되는지 확인합니다.
4. 사용자 입력이 있다면 입력 전, 입력 중, 제출 후 상태를 나누어 확인합니다.
5. 테스트가 있다면 내부 구현보다 사용자에게 보이는 결과를 검증하는지 확인합니다.

이 순서를 습관처럼 적용하면 문제를 만났을 때 훨씬 덜 흔들립니다. 특히 입문 단계에서는 코드를 많이 아는 것보다, 문제가 생겼을 때 확인할 순서를 알고 있는 것이 더 큰 힘이 됩니다.
