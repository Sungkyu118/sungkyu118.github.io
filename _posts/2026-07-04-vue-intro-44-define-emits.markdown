# Vue 입문 44: defineEmits로 이벤트 계약을 명확히 만들기

> 자식 컴포넌트가 부모에게 어떤 이벤트를 올릴 수 있는지 선언하는 방법을 배웁니다.

`defineEmits`는 `<script setup>`에서 자식 컴포넌트가 발생시킬 이벤트를 선언하는 도구입니다. 이벤트를 선언한다는 것은 이 컴포넌트가 외부에 어떤 신호를 보낼 수 있는지 명확히 하는 일입니다. props가 입력 계약이라면 emits는 출력 계약이라고 볼 수 있습니다.

작은 예제에서는 `const emit = defineEmits(['close'])`처럼 이벤트 이름 배열만으로 충분합니다. 조금 더 엄격하게는 이벤트 payload가 올바른지 검증하는 함수 형태를 사용할 수도 있습니다. TypeScript를 쓰면 이벤트 이름과 payload 타입을 더 안전하게 선언할 수 있습니다.

중요한 것은 이벤트 이름이 사용자 행동의 의미를 드러내야 한다는 점입니다. `click`처럼 너무 일반적인 이름보다 `close`, `save`, `remove`, `select-user`처럼 컴포넌트 바깥에서 처리할 의도를 드러내는 이름이 좋습니다.

## 이번 글에서 먼저 잡을 관점

이번 구간부터는 Vue를 단순히 한 파일 안에서 쓰는 단계에서 벗어나, 여러 컴포넌트가 함께 동작하는 구조를 다룹니다. 그래서 문법 하나만 보는 것보다 역할과 책임을 같이 보는 것이 중요합니다. 부모 컴포넌트가 무엇을 알고 있어야 하는지, 자식 컴포넌트는 어디까지 책임져야 하는지, 사용자의 행동을 어느 방향으로 전달해야 하는지 계속 질문하면서 읽어보시면 좋습니다.

컴포넌트 설계는 처음부터 완벽하게 나누는 일이 아닙니다. 작은 화면을 만들고, 반복되는 부분이나 책임이 분명한 부분을 발견하고, 그때 적절히 분리하는 과정에 가깝습니다. 이 글의 예제도 정답이라기보다 기준을 잡기 위한 출발점으로 봐주세요. 직접 이름을 바꿔보고, props를 하나 추가해보고, 이벤트 흐름을 바꿔보면 훨씬 오래 기억에 남습니다.

## 작은 실습으로 확인해보기

아래 예제는 모달 컴포넌트가 닫기와 저장 이벤트를 부모에게 전달하는 구조입니다.

```vue
<script setup>
const emit = defineEmits(['close', 'save'])

function save() {
  emit('save', {
    savedAt: new Date().toISOString()
  })
}
</script>

<template>
  <section class="modal">
    <h2>설정 변경</h2>
    <p>변경 내용을 저장하거나 모달을 닫을 수 있습니다.</p>

    <button @click="save">저장</button>
    <button @click="emit('close')">닫기</button>
  </section>
</template>

<!-- Parent.vue -->
<template>
  <SettingsModal
    @save="handleSave"
    @close="isOpen = false"
  />
</template>
```

## 코드가 움직이는 순서

자식 모달은 저장 버튼을 누르면 `save` 이벤트를 올리고, 닫기 버튼을 누르면 `close` 이벤트를 올립니다. 부모는 이 이벤트를 받아 실제 저장 처리나 모달 닫기 상태 변경을 수행합니다. 자식은 저장 API를 직접 알 필요가 없고, 부모는 자식의 UI 구조를 자세히 몰라도 됩니다.

여기서 중요한 것은 코드 줄 수보다 의도입니다. 컴포넌트를 나누면 파일은 늘어나지만, 각 파일이 맡는 역할이 선명해져야 합니다. 부모는 전체 상태와 흐름을 관리하고, 자식은 자신이 맡은 UI 조각을 표현하거나 사용자 행동을 이벤트로 알려주는 식으로 역할을 나누면 디버깅이 훨씬 쉬워집니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 이벤트 이름은 부모 템플릿과 정확히 맞아야 합니다. 이름이 조금만 달라도 이벤트가 처리되지 않습니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: emit payload에 필요 이상의 객체를 담으면 부모가 자식 내부 구조에 의존하게 됩니다. 부모가 처리하는 데 필요한 정보만 전달하세요. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 자식이 API 호출과 부모 상태 변경을 모두 처리하면 책임이 커질 수 있습니다. 이벤트로 의도를 올리는 구조를 먼저 고려하세요. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.

컴포넌트 관련 오류는 한 파일만 봐서는 바로 보이지 않을 때가 많습니다. 부모가 넘기는 prop 이름, 자식이 선언한 prop 이름, 자식이 emit하는 이벤트 이름, 부모가 듣는 이벤트 이름을 한 줄씩 맞춰보는 습관이 필요합니다. 브라우저 콘솔의 Vue warning도 그냥 넘기지 말고, 어떤 컴포넌트에서 발생했는지 확인해보시면 좋습니다.

## 실무에서 생각할 점

defineEmits는 컴포넌트 통신을 명시적으로 만들어줍니다. 코드가 조금 길어져도 어떤 이벤트가 발생 가능한지 한눈에 보이므로 유지보수에 유리합니다. 특히 공통 컴포넌트에서는 emits 선언을 빼먹지 않는 것이 좋습니다.

실무에서는 컴포넌트가 "동작한다"보다 "변경에 견딘다"가 더 중요해집니다. 요구사항은 계속 바뀌고, 디자인도 바뀌고, 같은 컴포넌트를 다른 화면에서 쓰고 싶어질 수 있습니다. 그래서 처음부터 모든 것을 일반화하려고 하기보다, 현재 책임을 명확히 하고 나중에 반복이 보일 때 재사용성을 높이는 방향이 안전합니다.
