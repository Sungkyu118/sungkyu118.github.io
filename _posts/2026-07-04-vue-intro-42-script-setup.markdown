# Vue 입문 42: script setup은 무엇을 줄여주는 문법일까요?

> <script setup>이 Composition API 코드를 더 짧고 읽기 쉽게 만들어주는 이유를 이해합니다.

`<script setup>`은 Vue 3의 Single File Component에서 Composition API를 더 간단하게 쓰기 위한 문법입니다. 일반 `setup()` 함수를 직접 작성하면 템플릿에서 사용할 값들을 return해야 합니다. 하지만 `<script setup>`에서는 top-level에 선언한 변수, 함수, import한 컴포넌트를 템플릿에서 바로 사용할 수 있습니다.

이 문법은 단순히 줄 수를 줄이는 것 이상입니다. 컴포넌트 로직을 더 자연스러운 JavaScript 스코프 안에서 작성하게 해줍니다. `const count = ref(0)`를 선언하고, `function increase()`를 만든 뒤 템플릿에서 바로 쓰면 됩니다. 그래서 Vue 3 신규 학습에서는 `<script setup>`을 기준으로 시작하는 경우가 많습니다.

하지만 짧아진 만큼 암묵적으로 처리되는 부분도 있습니다. 템플릿에 무엇이 노출되는지, props와 emits는 어떻게 선언하는지, lifecycle hook은 어디서 호출하는지 이해해야 합니다. 문법이 편해졌다고 내부 흐름까지 몰라도 되는 것은 아닙니다.

## 이번 글에서 먼저 잡을 관점

이번 구간부터는 Vue를 단순히 한 파일 안에서 쓰는 단계에서 벗어나, 여러 컴포넌트가 함께 동작하는 구조를 다룹니다. 그래서 문법 하나만 보는 것보다 역할과 책임을 같이 보는 것이 중요합니다. 부모 컴포넌트가 무엇을 알고 있어야 하는지, 자식 컴포넌트는 어디까지 책임져야 하는지, 사용자의 행동을 어느 방향으로 전달해야 하는지 계속 질문하면서 읽어보시면 좋습니다.

컴포넌트 설계는 처음부터 완벽하게 나누는 일이 아닙니다. 작은 화면을 만들고, 반복되는 부분이나 책임이 분명한 부분을 발견하고, 그때 적절히 분리하는 과정에 가깝습니다. 이 글의 예제도 정답이라기보다 기준을 잡기 위한 출발점으로 봐주세요. 직접 이름을 바꿔보고, props를 하나 추가해보고, 이벤트 흐름을 바꿔보면 훨씬 오래 기억에 남습니다.

## 작은 실습으로 확인해보기

아래 예제는 `<script setup>`에서 상태, 함수, 자식 컴포넌트를 템플릿에서 바로 사용하는 구조입니다.

{% raw %}
```vue
<script setup>
import { ref } from 'vue'
import BaseButton from './components/BaseButton.vue'

const count = ref(0)

function increase() {
  count.value += 1
}
</script>

<template>
  <section>
    <p>현재 숫자: {{ count }}</p>
    <BaseButton @click="increase">증가</BaseButton>
  </section>
</template>
```
{% endraw %}

## 코드가 움직이는 순서

`count`와 `increase`는 스크립트의 top-level에 선언되어 있습니다. `<script setup>`에서는 이 값들이 템플릿에서 바로 사용 가능합니다. `BaseButton`도 import만 하면 템플릿에서 컴포넌트로 사용할 수 있습니다. 일반 setup 함수에서 return을 작성하던 부담이 줄어듭니다.

여기서 중요한 것은 코드 줄 수보다 의도입니다. 컴포넌트를 나누면 파일은 늘어나지만, 각 파일이 맡는 역할이 선명해져야 합니다. 부모는 전체 상태와 흐름을 관리하고, 자식은 자신이 맡은 UI 조각을 표현하거나 사용자 행동을 이벤트로 알려주는 식으로 역할을 나누면 디버깅이 훨씬 쉬워집니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: `<script setup>` 안의 코드는 컴포넌트 인스턴스가 생성될 때 실행되는 setup 범위입니다. 전역으로 한 번만 실행된다고 오해하면 안 됩니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 템플릿에서 쓰는 값이 어디서 왔는지 import와 선언 위치를 확인해야 합니다. 자동 노출이 편한 만큼 이름 충돌에 주의하세요. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: props와 emits는 일반 변수처럼 마음대로 만들기보다 `defineProps`, `defineEmits` 매크로를 사용해 선언합니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.

컴포넌트 관련 오류는 한 파일만 봐서는 바로 보이지 않을 때가 많습니다. 부모가 넘기는 prop 이름, 자식이 선언한 prop 이름, 자식이 emit하는 이벤트 이름, 부모가 듣는 이벤트 이름을 한 줄씩 맞춰보는 습관이 필요합니다. 브라우저 콘솔의 Vue warning도 그냥 넘기지 말고, 어떤 컴포넌트에서 발생했는지 확인해보시면 좋습니다.

## 실무에서 생각할 점

`<script setup>`은 Vue 3 컴포넌트를 짧고 명확하게 만들어줍니다. 하지만 팀에 Options API 기반 코드가 많거나, 기존 setup 함수 패턴을 쓰는 프로젝트라면 무조건 바꾸기보다 점진적으로 이해해야 합니다. 문법 선택보다 중요한 것은 컴포넌트 책임과 상태 흐름입니다.

실무에서는 컴포넌트가 "동작한다"보다 "변경에 견딘다"가 더 중요해집니다. 요구사항은 계속 바뀌고, 디자인도 바뀌고, 같은 컴포넌트를 다른 화면에서 쓰고 싶어질 수 있습니다. 그래서 처음부터 모든 것을 일반화하려고 하기보다, 현재 책임을 명확히 하고 나중에 반복이 보일 때 재사용성을 높이는 방향이 안전합니다.
