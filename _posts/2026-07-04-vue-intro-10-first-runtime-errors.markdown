처음 Vue 프로젝트를 만들 때 가장 당황스러운 순간은 예제 그대로 따라 했는데 실행이 안 되는 때입니다. 화면이 하얗게 비거나, 터미널에 빨간 에러가 나오거나, 브라우저 콘솔에 모듈을 찾을 수 없다는 메시지가 나옵니다. 이때 중요한 것은 에러를 한 덩어리로 무서워하지 않고, 어느 단계에서 실패했는지 나누어 보는 것입니다.

Vue 프로젝트 실행은 크게 네 단계로 볼 수 있습니다. 첫째, Node.js와 npm이 명령을 실행할 수 있어야 합니다. 둘째, 프로젝트 의존성이 설치되어야 합니다. 셋째, Vite 개발 서버가 켜져야 합니다. 넷째, 브라우저에서 Vue 앱이 `#app` 위치에 정상 마운트되어야 합니다. 실패 지점이 어디인지 찾으면 해결도 쉬워집니다.

예를 들어 `npm create vite@latest`부터 안 된다면 Node 버전이나 npm 환경 문제일 가능성이 큽니다. `npm run dev`에서 모듈을 찾지 못한다면 `npm install`이 빠졌거나 import 경로가 잘못되었을 수 있습니다. 브라우저가 하얗다면 터미널뿐 아니라 개발자 도구 Console도 함께 봐야 합니다.

## 이번 글에서 먼저 잡을 관점

이번 주제에서 가장 중요한 것은 문법을 외우는 것보다 흐름을 이해하는 것입니다. Vue 코드는 보통 상태를 준비한다 -> 템플릿에서 상태를 읽는다 -> 사용자 행동으로 상태가 바뀐다 -> Vue가 화면을 다시 맞춘다는 순서로 움직입니다. 이 순서를 머릿속에 두고 읽으면 새로운 문법을 만나도 훨씬 덜 흔들립니다.

또 하나 중요한 점은 Vue가 HTML, CSS, JavaScript를 대체하는 것이 아니라는 사실입니다. Vue는 이 세 가지를 더 구조적으로 연결해주는 도구입니다. 그래서 예제를 따라 칠 때도 "이 문법이 Vue에서만 특별한가?", "아니면 원래 HTML/JavaScript 개념을 Vue 방식으로 연결한 것인가?"를 나누어 생각하면 좋습니다.

처음에는 한 번에 완벽하게 이해하지 못해도 괜찮습니다. 대신 예제 코드를 조금씩 바꿔보면서 어떤 값이 바뀌면 화면의 어느 부분이 바뀌는지 확인해보세요. 손으로 바꿔본 경험이 쌓이면, 단순히 읽기만 했을 때보다 훨씬 빠르게 감이 잡힙니다.

## 작은 실습으로 확인해보기

아래 체크 명령을 순서대로 실행하면 프로젝트가 어느 단계에서 막히는지 좁힐 수 있습니다.

```bash
node -v
npm -v

# 프로젝트 폴더 안에서 실행합니다.
npm install
npm run dev

# 배포 빌드도 따로 확인합니다.
npm run build
```

## 코드가 움직이는 순서

`node -v`와 `npm -v`는 도구 자체가 준비되어 있는지 확인합니다. `npm install`은 의존성을 설치합니다. `npm run dev`는 개발 서버를 실행합니다. `npm run build`는 문법과 번들링 문제가 없는지 확인하는 별도 검증입니다. 특히 `dev`는 되지만 `build`가 실패하는 경우가 있으므로 둘을 분리해서 봐야 합니다.

여기서 꼭 기억하셔야 할 부분은 Vue가 화면을 갱신해준다고 해서 개발자가 흐름을 몰라도 되는 것은 아니라는 점입니다. 오히려 Vue를 잘 쓰려면 상태가 어디에 있고, 어떤 이벤트나 함수가 그 상태를 바꾸며, 템플릿이 그 상태를 어떻게 읽는지 계속 추적할 수 있어야 합니다. 작은 예제부터 이 흐름을 말로 설명해보면 나중에 코드가 길어져도 훨씬 덜 막힙니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: `node_modules` 폴더가 없거나 깨졌다면 `npm run dev`가 실패합니다. 이때는 프로젝트 루트에서 `npm install`을 다시 실행해봅니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: import 경로는 대소문자와 상대 경로에 민감합니다. Windows에서는 우연히 되던 경로가 배포 환경에서는 실패할 수 있습니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: `index.html`의 `id="app"`과 `main.js`의 `mount("#app")`가 맞지 않으면 Vue 앱이 붙을 자리를 찾지 못합니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.

에러를 만났을 때는 먼저 터미널 로그와 브라우저 개발자 도구 Console을 함께 봐야 합니다. Vue 프로젝트는 빌드 단계에서 나는 오류와 브라우저 실행 중에 나는 오류가 다를 수 있습니다. 터미널은 정상처럼 보여도 브라우저 콘솔에는 컴포넌트 렌더링 오류가 남아 있을 수 있고, 반대로 브라우저를 열기도 전에 Vite 개발 서버가 실패하는 경우도 있습니다.

## 실무에서 생각할 점

입문 단계에서는 에러 메시지를 전부 이해하지 못해도 괜찮습니다. 대신 에러가 난 위치를 터미널, 브라우저 Console, 파일 경로, 명령 실행 단계로 나누어 보는 습관이 중요합니다. 이 습관은 Vue뿐 아니라 React, Spring Boot, Flutter 같은 다른 기술을 다룰 때도 그대로 도움이 됩니다.

실무에서는 "동작한다"만으로는 부족한 경우가 많습니다. 다른 사람이 읽었을 때 의도를 이해할 수 있는지, 요구사항이 조금 바뀌어도 고치기 쉬운지, 에러 상황에서도 사용자가 무엇을 해야 하는지 알 수 있는지가 중요합니다. 입문 시리즈에서 계속 예제와 주의사항을 함께 보는 이유도 여기에 있습니다. 문법을 하나 배울 때마다 그 문법이 실패할 수 있는 지점까지 같이 봐야 실제 프로젝트에서 덜 흔들립니다.

## 오늘 내용 정리

다음 글로 넘어가기 전에 예제 코드를 그대로 한 번 작성해보시고, 최소한 한 군데는 직접 바꿔보시는 것을 추천드립니다. 버튼 문구를 바꾸거나, 상태 초기값을 바꾸거나, 조건을 하나 추가하는 정도면 충분합니다. 그렇게 작은 변화를 직접 만들어보면 "아, 이 부분이 화면과 연결되어 있구나"라는 감각이 생깁니다.
