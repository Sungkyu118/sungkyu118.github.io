# Redis 운영 심화: 메모리, eviction, 핫키 사고 패턴

> Redis 메모리 부족, eviction 정책, hot key 문제를 운영 장애 관점에서 정리합니다.
>
> 이전 글: [Redis 분산락: SET NX PX로 시작하는 실전 가이드](/redis/distributed-lock)
> 함께 보면 좋은 글:
> - [Redis 입문 실무형 3: 운영 기본, 메모리와 eviction을 먼저 보자](/redis/practical-ops-basics)
> - [Redis for 캐시: 언제 효과가 크고, 어디서 망가지는가](/redis/cache)

Redis 장애는 대개 "갑자기 느려졌다"로 시작합니다. 하지만 실제 원인은 대부분 이미 오래전부터 쌓이고 있었습니다. 메모리가 서서히 차오르거나, 특정 키가 과도하게 몰리거나, TTL이 한 번에 만료되는 구조가 숨어 있었던 경우가 많습니다.

이 글에서는 실무에서 자주 마주치는 Redis 운영 사고 패턴을 메모리, eviction, hot key 중심으로 정리해보겠습니다.

## 사고 패턴 1: 메모리가 차오르는데 아무도 모른다

캐시를 처음 붙이면 체감 성능이 좋아져서 팀 분위기가 좋아집니다. 문제는 그 다음입니다. 키가 늘고, 값 크기가 커지고, TTL이 길어지고, 일부 키는 지워지지 않으면서 메모리가 계속 올라가기 시작합니다.

이 단계에서 흔한 실수는 "Redis 아직 안 죽었으니 괜찮다"라고 생각하는 것입니다. 하지만 운영에서는 `아직 안 죽었다`가 아니라 `언제부터 위험해졌는가`를 봐야 합니다.

특히 아래 상황은 위험 신호입니다.

- 메모리 사용량이 꾸준히 상승한다.
- 캐시 키 수 증가 속도가 빨라진다.
- 큰 JSON blob를 무심코 많이 저장하고 있다.
- TTL 없는 키가 쌓이고 있다.

이런 구조는 시간이 지나면 결국 eviction이나 hit rate 하락으로 이어집니다.

## 사고 패턴 2: eviction이 시작되면서 캐시가 흔들린다

eviction은 메모리가 부족할 때 일부 키를 버리는 정책입니다. 설정해두면 안전해 보이지만, 실제로는 "어떤 키가 버려지고 있는가"를 모르면 매우 위험할 수 있습니다.

대표 정책:

- `allkeys-lru`: 전체 키에서 최근 덜 쓰인 키 제거
- `volatile-lru`: TTL 있는 키에서 최근 덜 쓰인 키 제거
- `volatile-ttl`: TTL이 짧은 키 우선 제거

문제는 서비스 입장에서 중요한 키가 eviction 대상이 되면, 그 순간부터 캐시 적중률이 흔들리고 원본 DB/API가 바로 부하를 맞을 수 있다는 점입니다.

즉, eviction은 "Redis가 알아서 정리해준다"가 아니라, **시스템이 위험 구간에 들어섰다는 경고**에 가깝습니다.

## 사고 패턴 3: 캐시 적중률이 갑자기 무너진다

운영에서 자주 보는 흐름은 이렇습니다.

1. 메모리 부족
2. eviction 시작
3. 자주 쓰이던 키 일부 제거
4. miss 증가
5. DB나 외부 API 부하 급증
6. 전체 응답 시간 악화

이때 Redis만 보면 "평소보다 조금 바쁜가?" 정도로 보일 수도 있습니다. 하지만 원본 시스템까지 같이 보면 훨씬 큰 문제로 번지고 있는 경우가 많습니다.

그래서 Redis 장애는 Redis 단독으로만 보지 말고, DB latency와 외부 API 호출량까지 같이 보는 편이 좋습니다.

## 사고 패턴 4: hot key 때문에 특정 시점만 유독 느리다

hot key는 특정 키 하나 혹은 소수의 키에 트래픽이 과도하게 몰리는 상황입니다.

예:

- 홈 피드 공용 키
- 이벤트 중인 인기 상품 상세
- 로그인 제한이나 인증 코드 요청 카운터

증상:

- 특정 시간대에 latency 급증
- CPU나 네트워크가 특정 노드에만 치우침
- Redis 전체 문제처럼 보이지만 사실 일부 키가 원인

이런 경우 단순히 서버를 키우는 것보다, 왜 그 키가 몰리는지부터 보는 게 중요합니다.

완화 아이디어:

- 만료 시점 분산
- 백그라운드 갱신
- 읽기 전용 복제본 활용 검토
- 상황에 따라 키 샤딩 또는 응답 캐시 계층 분리

## 사고 패턴 5: TTL이 동시에 만료되어 스탬피드가 발생한다

TTL을 주는 것 자체는 좋습니다. 그런데 같은 시점에 생성된 키에 같은 TTL을 주면, 만료도 비슷한 시점에 몰립니다. 그러면 해당 순간에 캐시 miss가 한꺼번에 발생하고, DB나 외부 API가 급격히 바빠집니다.

이 문제는 특히:

- 배치 직후 생성된 캐시
- 같은 코드 경로에서 대량 저장된 키
- hot key 성격이 있는 데이터

에서 더 자주 드러납니다.

기본 대응:

- TTL에 jitter 추가
- 정말 비싼 키는 proactive refresh 고려
- miss가 몰릴 때 원본 시스템을 보호하는 구조 준비

## 운영 체크리스트

Redis 운영에서 아래 항목은 꼭 보는 편이 좋습니다.

- 메모리 사용량 추세
- eviction 발생 여부
- hit/miss 비율
- latency 급증 시간대
- 특정 key pattern의 증가 여부
- TTL 없는 키 비율

이 체크리스트는 [운영 기본](/redis/practical-ops-basics), [키 설계와 TTL](/redis/practical-key-ttl), [Redis for 캐시](/redis/cache)와 같이 연결해서 봐야 더 의미가 살아납니다.

## 자주 하는 오해

### 1) Redis가 메모리 기반이니 무조건 빠르고 안전하다고 생각한다

빠르다는 사실과 안정적으로 운영된다는 사실은 다릅니다. 메모리 기반이기 때문에 오히려 메모리 관리 실패가 바로 서비스 품질 문제로 이어질 수 있습니다.

### 2) eviction 정책만 설정하면 끝이라고 생각한다

정책은 마지막 방어선일 뿐입니다. 어떤 키를 왜 버리는지 모르면, 장애가 날 때 원인 파악이 어렵습니다.

### 3) hot key를 단순 트래픽 증가로만 본다

트래픽이 늘어난 게 아니라, 트래픽이 비정상적으로 특정 키에 집중된 것일 수 있습니다. 이런 경우 키 설계와 캐시 갱신 전략이 핵심 원인입니다.

## 정리

Redis 운영 사고는 대부분 "메모리 증가 -> eviction 시작 -> hit rate 흔들림 -> 원본 시스템 부하 증가" 같은 흐름으로 연결됩니다. 여기에 hot key와 동시 만료가 겹치면 체감 장애가 훨씬 커집니다.

그래서 Redis를 운영할 때는 단순히 빠른 저장소로 보는 대신, **메모리와 키 분포를 관리하는 시스템**으로 보는 감각이 필요합니다. 이 감각이 생기면 Redis는 훨씬 믿을 수 있는 도구가 됩니다.
