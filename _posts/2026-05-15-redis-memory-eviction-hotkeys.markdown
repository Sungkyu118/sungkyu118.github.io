# Redis 운영 심화: 메모리, eviction, 핫키(Hot Key) 사고 패턴

Redis는 개발 환경에서는 조용히 잘 돌아가다가, 운영에서 갑자기 문제가 보이는 경우가 많습니다. 이유는 단순해요. Redis는 **메모리**이고, 메모리가 꽉 차면 "버리기(eviction)"가 시작되기 때문입니다.

이 글은 다음을 다룹니다.

1. 메모리/eviction이 서비스에 어떤 형태로 터지는지
2. 캐시 히트율이 갑자기 떨어지는 사고 패턴
3. 핫키(Hot Key)로 특정 노드가 병목이 되는 케이스
4. 방어 체크리스트

## 1) 흔한 사고 시나리오

### 시나리오 A: 캐시가 잘 되다가 어느 날부터 느려짐

전형적인 흐름:

1. 캐시를 늘림 → 히트율 상승 → 응답 빨라짐
2. 메모리 사용량이 계속 증가
3. 어느 순간 maxmemory에 도달
4. eviction 시작(키가 랜덤/정책에 따라 삭제)
5. 캐시 히트율 급락 → DB/외부 API 부하 급증
6. 전체 시스템이 느려짐/장애

## 2) eviction 정책 감각

eviction은 "메모리가 부족할 때 무엇을 버릴지"를 결정합니다.

정책에 따라 결과가 달라집니다.

- allkeys-lru: 전체 키 중 LRU 기반 제거
- volatile-lru: TTL이 있는 키 중 LRU 제거
- volatile-ttl: TTL 짧은 키부터 제거

핵심:

- eviction이 시작되었다는 건 이미 위험 구간입니다.
- 어떤 키가 버려지는지(중요 데이터가 버려지는지)를 모르면 원인 분석이 어렵습니다.

## 3) 핫키(Hot Key)

핫키는 "트래픽이 한 키로 몰리는" 문제입니다.

예:

- `feed:home` 같은 키가 모든 사용자에게 공통으로 사용됨
- 특정 인기 상품/콘텐츠의 키만 폭발적으로 조회됨

증상:

- Redis CPU/네트워크가 특정 노드에서만 튐
- 레이턴시가 들쭉날쭉해짐

완화 아이디어:

- 만료 시간 지터로 동시 만료 분산
- 캐시 갱신을 단일화(분산락)해서 DB 폭주 방지
- 상황에 따라 키를 샤딩(여러 키로 쪼개고 애플리케이션에서 합치기)

## 4) TTL/만료 패턴도 운영 변수

TTL을 모두 동일하게 주면, 특정 시점에 대량 만료가 몰릴 수 있습니다.

기본 방어:

- TTL에 랜덤 지터 추가
- 핫키는 별도 TTL/갱신 전략 고려

## 5) 최소 체크리스트

- 캐시 키에 TTL을 걸고 있는가?
- TTL에 지터를 넣고 있는가?
- 캐시 히트율(hit/miss)을 보고 있는가?
- maxmemory/eviction 정책을 알고 있는가?
- 핫키가 생겼을 때 방어(락/갱신 단일화/샤딩)를 준비했는가?

## 정리

- Redis 운영은 메모리 게임이다
- eviction이 시작되면 캐시 품질이 흔들리고, 부하가 DB로 전파된다
- 핫키/동시 만료를 초기에 방어하면 장애 확률을 크게 낮출 수 있다
