# TypeScript 입문 107: const enum을 쓸 때 조심해야 할 점

> const enum은 편리해 보여도 빌드 도구와 라이브러리 배포 환경에 따라 조심해야 하는 선택이 될 수 있습니다.

TypeScript 입문 시리즈가 91번 이후로 넘어오면, 이제 단순 타입 문법을 넘어서 "구조를 어떻게 나눌지", "설정을 어떻게 잡을지", "실무 코드에서 어떤 판단을 해야 하는지"가 더 중요해집니다. 그래서 이번 구간은 앞선 1~90번보다 문법 자체보다 설계와 운영 감각에 더 가까운 내용을 자주 다루게 됩니다. 그렇다고 해서 갑자기 어려운 이야기만 하지는 않겠습니다. 이번 글도 입문자분이 실제로 따라가며 이해할 수 있도록 기본 예제, 잘못된 예제, 실무에서의 판단 포인트를 차근차근 연결해서 설명드리겠습니다.

const enum은 편리해 보여도 빌드 도구와 라이브러리 배포 환경에 따라 조심해야 하는 선택이 될 수 있습니다. 지금 단계에서는 "문법이 된다"와 "좋은 선택이다"를 구분하는 감각이 정말 중요합니다. 같은 기능을 TypeScript에서 여러 방식으로 표현할 수 있기 때문에, 왜 지금 이 방식을 선택하는지, 언제는 오히려 다른 선택이 더 나은지를 함께 보셔야 합니다. 그런 시선이 생기면 이후 프레임워크나 실제 서비스 코드를 읽을 때도 훨씬 덜 흔들리게 됩니다.

## 먼저 이해해야 할 핵심 관점

이번 글의 핵심은 리터럴 고정과 상수 표현 흐름 안에서 현재 주제가 어떤 역할을 하는지 이해하는 것입니다. 초보자분들이 이 단계에서 자주 막히는 이유는, 코드 한 줄 자체는 짧아 보여도 그 뒤에 숨어 있는 설계 의도가 갑자기 늘어나기 때문입니다. 예를 들어 class를 쓰는 이유, enum을 피하는 이유, tsconfig 옵션을 켜는 이유는 단순 암기 항목이 아니라 팀 전체 코드 품질과 연결됩니다. 그래서 지금 주제를 볼 때도 "이 문법이 있으면 무엇이 편해질까?"만 보지 마시고, "이 선택이 나중에 어떤 문제를 줄여줄까?"까지 같이 보시면 좋겠습니다.

enum, as const, satisfies 같은 도구는 모두 상수와 리터럴 정보를 더 안전하게 다루려는 방향으로 연결됩니다. 다만 편의성만 보고 고르면 번들 크기나 런타임 구조가 불필요하게 복잡해질 수 있습니다. 이 구간에서는 빨간 줄이 없더라도 구조가 나쁠 수 있고, 반대로 처음에는 불편해 보여도 장기적으로 훨씬 안전한 선택이 있을 수 있습니다. 따라서 지금은 문법을 외우는 것보다, 작은 예제를 통해 선택 기준을 몸에 익히는 것이 더 중요합니다.

## 기본 예제부터 차근차근 보기

아래 첫 번째 예제는 이번 주제의 가장 기본적인 형태를 보여줍니다. 처음 읽으실 때는 한 줄 한 줄을 모두 외우려 하기보다, "어떤 문제를 해결하려고 이런 구조를 만들었는가?"에 먼저 집중해보시면 좋겠습니다.

```ts
const enum HttpStatus {
  OK = 200,
  NotFound = 404
}
```

이 예제는 지금 주제의 출발점입니다. 길어 보이지는 않지만, 실제로는 코드 의도를 더 명확하게 드러내기 위한 중요한 선언이 들어 있습니다. 입문 단계에서는 이런 기본 예제를 대충 넘기기 쉽지만, 실무에서는 이런 작은 차이가 유지보수 난이도를 꽤 크게 바꾸곤 합니다.

## 한 단계 더 나아간 예제

실제 프로젝트에서는 기본 문법이 단독으로 등장하기보다 다른 객체, 함수, 파일 구성과 연결되어 쓰입니다. 그래서 두 번째 예제에서는 지금 개념이 실제 코드 흐름 안에서 어떻게 자연스럽게 연결되는지 보겠습니다.

```ts
const status = HttpStatus.OK
```

이 예제를 보실 때는 문법이 맞는지뿐 아니라, 읽는 사람이 코드를 얼마나 빠르게 이해할 수 있는지도 함께 생각해보시면 좋겠습니다. TypeScript는 단순히 타입 오류를 막는 도구가 아니라, 협업자가 코드를 오해하지 않도록 돕는 설명 도구이기도 하기 때문입니다.

## 초보자가 자주 만드는 잘못된 예제

이번에는 일부러 잘못 작성한 예제를 보겠습니다. 이런 코드를 같이 보는 이유는 단순히 에러를 구경하기 위해서가 아니라, 왜 이런 방식이 위험한지 감각적으로 익히기 위해서입니다. TypeScript는 틀렸다고만 말하는 도구가 아니라, 더 안전한 방향을 알려주는 도구라고 생각하시면 도움이 됩니다.

```ts
console.log(HttpStatus)
```

이런 코드는 처음에는 더 짧아 보이거나, 빨리 작성한 것처럼 느껴질 수 있습니다. 하지만 실제로는 런타임 버그를 만들거나, 읽는 사람이 잘못된 가정을 하게 만들 가능성이 큽니다. 그래서 지금처럼 작은 예제에서부터 "지금 편한 코드"와 "나중에도 안전한 코드"를 구분하는 연습이 꼭 필요합니다.

## 에러와 유의사항을 자세히 짚어보기

- 첫 번째로, 지금 구간은 클래스 설계나 설정 값처럼 코드 바깥의 문맥까지 함께 이해해야 하는 경우가 많습니다. 그래서 예제를 그냥 눈으로만 읽지 말고, 실제로 필드 하나를 바꿔보거나 옵션 값을 조정해보면서 어떤 차이가 나는지 확인해보시는 편이 훨씬 좋습니다.
- 두 번째로, "이것도 되고 저것도 된다"는 상황에서 무엇을 고를지 고민하지 않으면, TypeScript를 쓰고도 구조가 금방 복잡해질 수 있습니다. 특히 class와 object literal, enum과 union type, default export와 named export 같은 선택지는 장단점을 같이 봐야 합니다.
- 세 번째로, 설정이나 고급 문법에서 생기는 에러는 처음에는 억지로 막는 것처럼 느껴질 수 있습니다. 하지만 그런 에러 대부분은 나중에 더 크게 터질 문제를 미리 알려주는 경우가 많습니다. 그래서 당장 불편하더라도 에러 메시지를 읽는 습관을 같이 들이는 것이 중요합니다.

## 실무에서는 어떻게 연결될까요?

실무에서는 지금 구간의 내용이 거의 곧바로 구조 설계와 빌드 설정 문제로 이어집니다. 예를 들어 class를 잘못 남용하면 데이터 구조가 불필요하게 무거워질 수 있고, enum을 습관적으로 쓰면 번들 결과를 예상하기 어려워질 수도 있습니다. 또 import 구조를 무심코 잡으면 순환 참조나 가독성 저하가 생길 수 있고, tsconfig를 대충 두면 프로젝트 전체가 느슨한 타입 검사 위에서 흔들리게 될 수도 있습니다.

그래서 이번 글은 단순 문법 소개로 끝내지 않고, "왜 이 선택이 실제 프로젝트에서 중요해지는지"를 계속 같이 설명드렸습니다. 이 감각이 생기면 TypeScript를 단지 빨간 줄 잡는 도구로 보는 것이 아니라, 구조를 건강하게 유지하기 위한 도구로 보게 됩니다.

## 오늘 내용 정리

이번 글에서는 const enum을 쓸 때 조심해야 할 점 주제를 중심으로, 왜 이 개념이 필요한지, 어떤 코드에서 도움이 되는지, 그리고 입문자분들이 어떤 부분에서 자주 실수하는지를 함께 살펴봤습니다. 지금 단계에서는 정의를 완벽히 외우는 것보다, 예제 코드를 직접 손으로 입력해보면서 어떤 상황에서 TypeScript가 도와주는지 체감하는 쪽이 훨씬 중요합니다. 가능하시면 기본 예제와 잘못된 예제를 꼭 둘 다 입력해보시고, 어떤 선택이 더 읽기 쉬운 코드로 이어지는지도 같이 느껴보시면 좋겠습니다.
