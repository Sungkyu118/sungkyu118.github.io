탭 컴포넌트는 상태 소유권을 이해하기 좋은 예제입니다. 선택된 탭 상태를 탭 컴포넌트 내부에서 가질 수도 있고, 부모가 가질 수도 있습니다. 둘 다 가능하지만 사용 목적이 다릅니다. 탭 선택 상태가 페이지의 다른 영역에도 영향을 준다면 부모가 소유하는 편이 좋습니다. 탭 내부에서만 쓰이는 단순 UI라면 자식이 내부 상태로 가져도 됩니다.

실무에서는 탭 선택 상태를 부모가 제어해야 하는 경우가 많습니다. URL query와 연결하거나, 선택된 탭에 따라 API를 호출하거나, 다른 컴포넌트와 동기화해야 하기 때문입니다. 이때 탭 컴포넌트는 `v-model` 패턴을 사용해 현재 선택 값을 받고 변경 요청을 emit하는 구조가 자연스럽습니다.

상태 소유권을 정하지 않고 구현하면 문제가 생깁니다. 부모도 selectedTab을 갖고 자식도 internalSelected를 갖는데 둘 사이 동기화 기준이 없으면 화면이 어긋납니다. 그래서 먼저 "이 상태를 누가 최종적으로 결정하는가?"를 정해야 합니다.

## 이번 글에서 먼저 잡을 관점

이번 구간부터는 Vue를 단순히 한 파일 안에서 쓰는 단계에서 벗어나, 여러 컴포넌트가 함께 동작하는 구조를 다룹니다. 그래서 문법 하나만 보는 것보다 역할과 책임을 같이 보는 것이 중요합니다. 부모 컴포넌트가 무엇을 알고 있어야 하는지, 자식 컴포넌트는 어디까지 책임져야 하는지, 사용자의 행동을 어느 방향으로 전달해야 하는지 계속 질문하면서 읽어보시면 좋습니다.

컴포넌트 설계는 처음부터 완벽하게 나누는 일이 아닙니다. 작은 화면을 만들고, 반복되는 부분이나 책임이 분명한 부분을 발견하고, 그때 적절히 분리하는 과정에 가깝습니다. 이 글의 예제도 정답이라기보다 기준을 잡기 위한 출발점으로 봐주세요. 직접 이름을 바꿔보고, props를 하나 추가해보고, 이벤트 흐름을 바꿔보면 훨씬 오래 기억에 남습니다.

## 작은 실습으로 확인해보기

아래 예제는 부모가 선택 상태를 소유하고, 탭 컴포넌트가 변경 요청을 올리는 구조입니다.

{% raw %}
```vue
<!-- BaseTabs.vue -->
<script setup>
defineProps({
  modelValue: {
    type: String,
    required: true
  },
  tabs: {
    type: Array,
    required: true
  }
})

const emit = defineEmits(['update:modelValue'])
</script>

<template>
  <div class="tabs">
    <button
      v-for="tab in tabs"
      :key="tab.value"
      :class="{ active: tab.value === modelValue }"
      @click="emit('update:modelValue', tab.value)"
    >
      {{ tab.label }}
    </button>
  </div>
</template>

<!-- Parent.vue -->
<template>
  <BaseTabs v-model="selectedTab" :tabs="tabs" />
  <p>현재 탭: {{ selectedTab }}</p>
</template>
```
{% endraw %}

## 코드가 움직이는 순서

`BaseTabs`는 현재 선택 값인 `modelValue`를 props로 받습니다. 버튼을 클릭하면 새 선택 값을 `update:modelValue` 이벤트로 부모에게 올립니다. 부모는 `v-model`을 통해 `selectedTab`을 소유합니다. 탭 컴포넌트는 선택 UI를 렌더링하지만 최종 상태는 부모가 갖습니다.

여기서 중요한 것은 코드 줄 수보다 의도입니다. 컴포넌트를 나누면 파일은 늘어나지만, 각 파일이 맡는 역할이 선명해져야 합니다. 부모는 전체 상태와 흐름을 관리하고, 자식은 자신이 맡은 UI 조각을 표현하거나 사용자 행동을 이벤트로 알려주는 식으로 역할을 나누면 디버깅이 훨씬 쉬워집니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 부모와 자식이 같은 선택 상태를 각각 따로 가지면 동기화 문제가 생깁니다. 상태 소유자를 먼저 정하세요. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 탭 값은 label보다 value를 별도로 두는 것이 좋습니다. 화면 문구가 바뀌어도 상태 값은 안정적으로 유지할 수 있습니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 탭은 접근성상 버튼 역할과 키보드 이동도 고려해야 합니다. 입문 예제 이후에는 aria 속성과 키보드 조작을 보강하세요. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.

컴포넌트 관련 오류는 한 파일만 봐서는 바로 보이지 않을 때가 많습니다. 부모가 넘기는 prop 이름, 자식이 선언한 prop 이름, 자식이 emit하는 이벤트 이름, 부모가 듣는 이벤트 이름을 한 줄씩 맞춰보는 습관이 필요합니다. 브라우저 콘솔의 Vue warning도 그냥 넘기지 말고, 어떤 컴포넌트에서 발생했는지 확인해보시면 좋습니다.

## 실무에서 생각할 점

부모 제어형 탭은 명시적이고 확장하기 좋습니다. 다만 단순한 내부 UI에는 코드가 조금 길어질 수 있습니다. 페이지 상태와 연결되는 탭은 부모가 소유하고, 정말 독립적인 작은 탭은 내부 상태로 시작하는 식의 기준이 좋습니다.

실무에서는 컴포넌트가 "동작한다"보다 "변경에 견딘다"가 더 중요해집니다. 요구사항은 계속 바뀌고, 디자인도 바뀌고, 같은 컴포넌트를 다른 화면에서 쓰고 싶어질 수 있습니다. 그래서 처음부터 모든 것을 일반화하려고 하기보다, 현재 책임을 명확히 하고 나중에 반복이 보일 때 재사용성을 높이는 방향이 안전합니다.
