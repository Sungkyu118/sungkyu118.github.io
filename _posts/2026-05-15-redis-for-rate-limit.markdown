# Redis for 레이트리밋

레이트리밋은 "요청 폭주로부터 시스템을 지키는 안전장치"입니다. WebFlux는 높은 동시성을 쉽게 만들 수 있는 만큼, 레이트리밋이 없으면 작은 공격/버그가 큰 장애로 번질 수 있어요.

이 글은 다음을 목표로 합니다.

1. 레이트리밋이 필요한 이유(트레이드오프)
2. Redis로 구현 가능한 대표 전략 소개
3. WebFlux에서 실무적으로 적용할 때의 포인트

## 1) 언제/왜 쓰나 (트레이드오프)

### 레이트리밋을 거는 곳

- 로그인/회원가입/비번찾기(브루트포스 방지)
- SMS/이메일 발송 API(비용 방지)
- 특정 고비용 API(검색, 추천, 결제 전 단계)

### 단점/주의점

- 잘못 걸면 정상 사용자가 막힘(false positive)
- 분산 환경에서 "전역 카운트"가 필요(그래서 Redis가 유리)

## 2) Redis 레이트리밋 전략 3가지

### (1) Fixed Window (INCR + EXPIRE)

가장 단순:

- 키: `rl:{userId}:{yyyyMMddHHmm}` 같은 형태
- 값: 카운트
- TTL: 윈도우 길이

단점은 경계에서 뻥 튀는 문제(윈도우 경계에서 2배 허용될 수 있음)입니다.

### (2) Sliding Window / Log

정확도가 높지만 구현/비용이 증가합니다(타임스탬프를 저장).

### (3) Token Bucket / Leaky Bucket

체감이 좋고 실무에서 선호되지만 보통 Lua 스크립트로 원자성을 확보합니다.

## 3) WebFlux 적용 포인트(개념)

대부분은 필터 레벨(예: WebFilter)에서 처리합니다.

- 사용자 식별(로그인/익명 IP)
- 키 구성(엔드포인트 + 사용자)
- 초과 시 429 반환

이때 중요한 건 "원자성"입니다. 레이트리밋 체크/증가가 레이스로 흔들리면 의미가 없어집니다. 그래서 단순 구현도 `INCR`과 `EXPIRE`를 잘 묶거나, Lua로 묶는 쪽을 추천합니다.

## 4) 실전 팁

- 키에 "엔드포인트"를 포함해 범위를 줄이기: `rl:login:{ip}`
- 관리자를 위한 예외(화이트리스트) 정책
- 429 응답에 재시도 힌트(`Retry-After`) 포함 고려

## 정리

- WebFlux는 동시성이 높아 레이트리밋의 가치가 더 커진다
- Redis는 분산 환경에서 전역 레이트리밋을 구현하기 좋다
- 원자성(Lua 또는 명령 조합)과 키 설계가 핵심이다
