# Redis for 레이트 리밋: 요청 폭주와 남용을 막는 기본기

레이트 리밋은 일정 시간 안에 허용할 요청 수를 제한하는 기능입니다. 로그인 시도, 인증번호 발송, 검색 API, 결제 요청처럼 남용되면 위험하거나 비용이 커지는 기능에 자주 붙입니다.

Redis는 레이트 리밋에 잘 맞습니다. 여러 서버가 동시에 떠 있어도 Redis를 공용 카운터로 쓰면 전체 요청 수를 함께 제한할 수 있기 때문입니다.

## 왜 Redis가 필요할까

서버가 한 대라면 애플리케이션 메모리에 카운터를 둘 수도 있습니다. 하지만 서버가 여러 대라면 문제가 생깁니다. A 서버에서 5번, B 서버에서 5번 요청하면 전체로는 10번인데 각 서버는 5번만 본 셈이 됩니다.

Redis를 쓰면 서버 여러 대가 같은 key를 보고 카운트할 수 있습니다.

## Fixed Window 방식

가장 단순한 방식은 fixed window입니다. 예를 들어 "1분에 30번까지만 허용"하는 구조입니다.

```bash
INCR rl:login:ip:1.2.3.4
EXPIRE rl:login:ip:1.2.3.4 60
```

첫 요청에 key를 만들고 TTL을 걸어둔 뒤, 카운트가 limit을 넘으면 거절합니다.

장점은 단순하다는 점입니다. 단점은 window 경계에서 요청이 몰릴 수 있다는 점입니다. 예를 들어 12:00:59에 30번, 12:01:00에 30번이 들어오면 2초 사이에 60번이 허용될 수 있습니다.

## 원자성이 중요하다

레이트 리밋에서 중요한 점은 "카운트 증가"와 "만료 설정"이 안전하게 처리되어야 한다는 것입니다. 여러 요청이 동시에 들어올 때 카운터와 TTL이 꼬이면 의도와 다른 제한이 생길 수 있습니다.

단순 구현에서는 큰 문제가 없어 보여도, 트래픽이 몰리는 API에서는 원자성이 중요해집니다. 그래서 Lua 스크립트를 이용해 `INCR`, `PEXPIRE`, limit 체크를 한 번에 처리하는 방식을 많이 씁니다.

이 내용은 [Redis 레이트 리밋: Lua로 원자성 보장하기](/redis/rate-limit-lua)에서 더 자세히 다룹니다.

## 어떤 기준으로 제한할까

레이트 리밋은 key 설계가 거의 전부입니다.

예:

- IP 기준: `rl:login:ip:1.2.3.4`
- 사용자 기준: `rl:api:user:42`
- 전화번호 기준: `rl:sms:phone:01012345678`
- 엔드포인트 기준: `rl:search:user:42`

IP만 기준으로 잡으면 회사나 학교처럼 같은 NAT를 쓰는 사용자들이 함께 제한될 수 있습니다. 사용자 ID만 기준으로 잡으면 로그인 전 요청에는 적용하기 어렵습니다. 그래서 기능마다 기준을 다르게 잡아야 합니다.

## 응답은 429로 명확하게

제한에 걸렸다면 보통 HTTP `429 Too Many Requests`를 사용합니다. 가능하면 `Retry-After` 헤더도 함께 내려주는 것이 좋습니다.

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
```

클라이언트가 언제 다시 시도하면 되는지 알 수 있어야 불필요한 재요청을 줄일 수 있습니다.

## 실무에서 자주 하는 실수

### 1) limit을 너무 낮게 잡는다

정상 사용자까지 막히면 레이트 리밋은 보안 장치가 아니라 장애가 됩니다. 실제 사용 패턴을 보고 조정해야 합니다.

### 2) 모든 API에 같은 정책을 적용한다

로그인, 검색, 결제, SMS는 위험도와 비용이 다릅니다. 같은 limit을 쓰면 어떤 API는 너무 느슨하고, 어떤 API는 너무 빡빡해질 수 있습니다.

### 3) 차단 로그를 남기지 않는다

차단이 많이 발생해도 기록이 없으면 정상 사용자가 막힌 것인지 공격 트래픽인지 판단하기 어렵습니다.

### 4) Redis 장애 시 정책이 없다

Redis가 잠깐 느려지거나 장애가 났을 때 요청을 모두 허용할지, 모두 차단할지, 일부만 우회할지 정해야 합니다. 보안이 중요한 API와 사용자 경험이 중요한 API는 선택이 다를 수 있습니다.

## 레이트 리밋은 보안과 UX 사이의 타협이다

레이트 리밋은 공격을 막기 위한 장치이기도 하지만, 정상 사용자를 불편하게 만들 수도 있습니다. 그래서 운영 중에 계속 조정해야 합니다.

처음에는 넉넉하게 시작하고, 로그를 보면서 줄이는 방식이 안전한 경우가 많습니다. 특히 인증번호, 로그인, 결제처럼 민감한 영역은 차단 기준과 사용자 안내를 같이 설계해야 합니다.

## 정리

Redis 레이트 리밋은 분산 환경에서 요청 수를 제한하기 좋은 방법입니다. 하지만 key 기준, limit 값, window 크기, 원자성, 429 응답, Redis 장애 정책까지 같이 정해야 운영 가능한 기능이 됩니다.

처음 구현은 fixed window로 시작해도 좋습니다. 다만 트래픽이 많거나 보안 요구가 강하다면 Lua 기반 원자 처리와 더 정교한 정책을 검토하는 편이 좋습니다.
