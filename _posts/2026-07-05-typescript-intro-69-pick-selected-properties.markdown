# TypeScript 입문 69: Pick<T, K>로 필요한 속성만 고르기

> Pick<T, K>는 큰 타입에서 지금 필요한 조각만 가져오고 싶을 때 매우 편리합니다.

TypeScript 입문 시리즈가 이 구간으로 넘어오면, 이제 단순히 변수나 함수에 타입을 붙이는 단계를 넘어 "기존 타입을 다시 조합하고 변형하는 법"을 배우게 됩니다. 그래서 이번 61~90 구간은 처음보다 추상적으로 느껴질 수 있습니다. 다만 여전히 핵심은 같습니다. 문법 이름을 외우는 것이 아니라, 이 도구가 어떤 중복을 줄여주고 어떤 실수를 막아주는지 이해하는 것이 더 중요합니다. 이번 글도 그 흐름에 맞춰 예제와 잘못된 예제를 충분히 비교하며 설명하겠습니다.

Pick<T, K>는 큰 타입에서 지금 필요한 조각만 가져오고 싶을 때 매우 편리합니다. 특히 이 단계에서는 타입을 직접 새로 쓰기보다, 이미 있는 타입에서 필요한 일부를 뽑아오거나, 다른 형태로 변환하는 상황이 자주 나옵니다. 그래서 코드가 짧아 보여도 의미는 더 응축되어 있습니다. 한 줄 한 줄이 어떤 타입 변형을 만들고 있는지 천천히 확인해보시면 좋겠습니다.

## 먼저 이해해야 할 핵심 관점

이번 글의 핵심은 utility type 이해 흐름 안에서 현재 주제가 어떤 역할을 하는지 파악하는 것입니다. 입문자분들이 이 구간에서 특히 어려움을 느끼는 이유는, 타입이 값처럼 눈에 보이지 않기 때문입니다. 하지만 실제로는 값의 구조를 더 안전하게 설명하고 재사용하는 과정이라고 이해하면 훨씬 덜 막힙니다. 지금 주제를 볼 때도 "이 기능이 없으면 어떤 중복이나 실수가 생길까?"를 같이 생각해보시면 좋겠습니다.

utility type은 편리하지만, 원본 타입의 의미를 흐리게 만들 수도 있습니다. 그래서 무엇을 재사용하고 무엇을 새로 선언할지 기준을 함께 가져가야 합니다. 이 구간에서는 빨간 줄이 없다고 해서 항상 좋은 타입 설계라고 볼 수 없습니다. 너무 복잡한 utility 조합이나 제네릭 설계는 타입 시스템은 만족시켜도 사람은 더 읽기 어려워질 수 있기 때문입니다. 그래서 항상 타입 안정성과 가독성을 같이 점검하는 시선이 필요합니다.

## 기본 예제부터 차근차근 보기

아래 첫 번째 예제는 이번 주제를 가장 작은 단위로 보여줍니다. 처음 읽으실 때는 결과 타입이 어떻게 바뀌는지만 먼저 보시고, 그다음 왜 그런 형태가 필요한지 생각해보시면 좋습니다.

```ts
type User = {
  id: number
  name: string
  email: string
  age: number
}
```

이 예제는 지금 주제가 어떤 방향으로 쓰이는지 보여주는 출발점입니다. 겉보기에는 짧은 한 줄일 수 있지만, 그 안에는 타입을 재사용하고 실수를 줄이려는 의도가 들어 있습니다. 입문 단계에서는 이런 짧은 타입 선언을 대충 넘기기 쉬운데, 실제 프로젝트에서는 이런 조각들이 누적되어 전체 안전성을 결정합니다.

## 한 단계 더 나아간 예제

실제 코드에서는 기본 패턴 하나만 단독으로 쓰이기보다, 다른 타입 선언이나 함수와 연결되어 등장하는 경우가 많습니다. 그래서 두 번째 예제에서는 지금 개념이 실제 흐름 속에서 어떻게 작동하는지를 조금 더 구체적으로 보겠습니다.

```ts
type UserListItem = Pick<User, 'id' | 'name'>
```

이 단계에서는 단순히 문법이 맞는지를 넘어, "이 타입 정의가 의도를 잘 드러내는가?"도 같이 봐야 합니다. TypeScript의 큰 장점은 타입을 통해 협업자에게 코드의 맥락을 전달할 수 있다는 점이기 때문입니다. 읽는 사람이 한 번에 이해할 수 있는 구조인지 계속 점검해보시는 것이 좋습니다.

## 초보자가 자주 만드는 잘못된 예제

이제 일부러 잘못 작성한 코드도 보겠습니다. 이런 예제를 같이 보는 이유는, 어떤 패턴이 왜 위험한지 감각적으로 익히기 위해서입니다. 에러를 피하는 요령만 외우는 것보다, 어떤 생각이 잘못된 방향인지 이해하는 편이 훨씬 오래갑니다.

```ts
const item: UserListItem = {
  id: 1,
  name: 'Sungkyu'
}
```

이런 코드는 처음에는 더 짧고 단순해 보일 수 있습니다. 하지만 실제로는 타입 정보가 너무 느슨하거나, 반대로 너무 과하게 복잡해서 유지보수가 어려워질 가능성이 큽니다. 그래서 지금처럼 작은 예제에서부터 "간단해 보이는 코드"와 "건강한 타입 설계"를 구분하는 연습이 중요합니다.

## 에러와 유의사항을 자세히 짚어보기

- 첫 번째로, 지금 구간은 한 줄 타입 선언이 여러 단계를 한 번에 수행하는 경우가 많아서, 눈으로만 읽으면 실제로 무슨 결과 타입이 되는지 놓치기 쉽습니다. 예제를 직접 바꿔보며 확인하는 편이 훨씬 안전합니다.
- 두 번째로, utility type이나 고급 타입은 많이 안다고 좋은 것이 아니라, 필요한 곳에만 정확하게 쓰는 것이 중요합니다. 불필요한 추상화는 오히려 팀 전체의 이해 속도를 늦출 수 있습니다.
- 세 번째로, 문법 이름이 낯설다고 해서 겁먹을 필요는 없습니다. 결국 대부분은 기존 타입을 가져오고, 좁히고, 바꾸고, 조합하는 흐름 안에 있습니다. 그래서 이전 글과 연결해서 보면 훨씬 이해가 쉬워집니다.

## 실무에서는 어떻게 연결될까요?

실무에서는 이 구간의 개념들이 DTO 분리, API 응답 래퍼, 폼 타입, 권한 타입, 이벤트 이름 타입, 헬퍼 함수 재사용 같은 곳에 바로 연결됩니다. 특히 utility type과 타입 연산자를 잘 이해하면, 같은 구조를 여러 군데에서 복붙하지 않고도 타입을 안정적으로 유지할 수 있습니다. 반대로 이 구간을 감으로만 쓰기 시작하면, 타입 정의가 점점 퍼즐처럼 복잡해질 수 있습니다.

그래서 이번 글도 문법 하나를 배웠다고 끝내기보다, "실제 프로젝트에서 이걸 쓰면 어떤 중복이 줄어들까?", "읽는 사람이 이 타입을 보고 의도를 이해할 수 있을까?"를 같이 떠올려보시면 좋겠습니다. 그런 감각이 생기면 이후 더 고급 타입을 만나도 훨씬 덜 흔들립니다.

## 오늘 내용 정리

이번 글에서는 Pick<T, K>로 필요한 속성만 고르기 주제를 중심으로, 왜 이 개념이 필요한지, 어떤 코드에서 도움이 되는지, 그리고 초보자가 어디서 자주 실수하는지를 함께 살펴봤습니다. 지금 단계에서는 정의를 외우는 것보다 예제 코드를 조금씩 바꿔보면서 결과 타입이 어떻게 달라지는지 확인하는 쪽이 더 중요합니다. 가능하시면 기본 예제와 잘못된 예제를 직접 손으로 입력해보시고, TypeScript가 어떤 부분을 허용하고 어떤 부분을 막는지 비교해보시면 좋겠습니다.
