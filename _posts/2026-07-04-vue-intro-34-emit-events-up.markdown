# Vue 입문 34: emit으로 자식에서 부모에게 이벤트 전달하기

> 자식 컴포넌트가 부모 상태를 직접 바꾸지 않고 이벤트로 의도를 전달하는 흐름을 익힙니다.

props가 부모에서 자식으로 내려가는 데이터라면, emit은 자식에서 부모로 올라가는 신호입니다. 자식 컴포넌트는 버튼 클릭, 입력 완료, 삭제 요청 같은 사용자 행동을 감지할 수 있습니다. 하지만 그 행동이 실제 상태를 어떻게 바꿀지는 부모가 결정하는 편이 안전합니다.

예를 들어 `TodoItem` 자식 컴포넌트 안에서 삭제 버튼을 누를 수 있습니다. 그렇다고 자식이 전체 목록 배열을 알고 직접 삭제하는 구조는 좋지 않습니다. 자식은 "이 항목을 삭제해달라"고 이벤트를 올리고, 부모는 그 이벤트를 받아 자신의 목록 상태를 수정합니다. 이렇게 하면 상태 소유자가 분명해집니다.

Vue 3의 `<script setup>`에서는 `defineEmits`를 사용해 자식이 어떤 이벤트를 발생시킬 수 있는지 선언합니다. 이벤트 이름은 템플릿에서는 보통 kebab-case로 듣습니다. 이름을 명확하게 지으면 부모 템플릿만 봐도 자식이 어떤 행동을 알리는지 이해할 수 있습니다.

## 이번 글에서 먼저 잡을 관점

이번 구간부터는 Vue를 단순히 한 파일 안에서 쓰는 단계에서 벗어나, 여러 컴포넌트가 함께 동작하는 구조를 다룹니다. 그래서 문법 하나만 보는 것보다 역할과 책임을 같이 보는 것이 중요합니다. 부모 컴포넌트가 무엇을 알고 있어야 하는지, 자식 컴포넌트는 어디까지 책임져야 하는지, 사용자의 행동을 어느 방향으로 전달해야 하는지 계속 질문하면서 읽어보시면 좋습니다.

컴포넌트 설계는 처음부터 완벽하게 나누는 일이 아닙니다. 작은 화면을 만들고, 반복되는 부분이나 책임이 분명한 부분을 발견하고, 그때 적절히 분리하는 과정에 가깝습니다. 이 글의 예제도 정답이라기보다 기준을 잡기 위한 출발점으로 봐주세요. 직접 이름을 바꿔보고, props를 하나 추가해보고, 이벤트 흐름을 바꿔보면 훨씬 오래 기억에 남습니다.

## 작은 실습으로 확인해보기

아래 예제는 자식 컴포넌트가 완료 토글과 삭제 요청을 emit으로 부모에게 전달합니다.

{% raw %}
```vue
<!-- TodoItem.vue -->
<script setup>
defineProps({
  todo: {
    type: Object,
    required: true
  }
})

const emit = defineEmits(['toggle', 'remove'])
</script>

<template>
  <li>
    <label>
      <input
        type="checkbox"
        :checked="todo.done"
        @change="emit('toggle', todo.id)"
      />
      {{ todo.title }}
    </label>
    <button @click="emit('remove', todo.id)">삭제</button>
  </li>
</template>

<!-- TodoList.vue -->
<template>
  <TodoItem
    v-for="todo in todos"
    :key="todo.id"
    :todo="todo"
    @toggle="toggleTodo"
    @remove="removeTodo"
  />
</template>
```
{% endraw %}

## 코드가 움직이는 순서

`TodoItem`은 `todo`를 props로 받아 보여줍니다. 체크박스를 바꾸면 `toggle` 이벤트와 todo id를 부모에게 보냅니다. 삭제 버튼을 누르면 `remove` 이벤트를 보냅니다. 부모는 각각 `toggleTodo`, `removeTodo` 함수로 실제 배열 상태를 수정합니다. 자식은 목록 전체를 몰라도 됩니다.

여기서 중요한 것은 코드 줄 수보다 의도입니다. 컴포넌트를 나누면 파일은 늘어나지만, 각 파일이 맡는 역할이 선명해져야 합니다. 부모는 전체 상태와 흐름을 관리하고, 자식은 자신이 맡은 UI 조각을 표현하거나 사용자 행동을 이벤트로 알려주는 식으로 역할을 나누면 디버깅이 훨씬 쉬워집니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 자식이 부모 배열을 직접 수정하려고 하면 컴포넌트 역할이 섞입니다. 자식은 이벤트를 올리고 부모가 상태를 바꾸는 흐름을 우선하세요. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 이벤트 이름이 부모 템플릿에서 듣는 이름과 다르면 아무 일도 일어나지 않습니다. `remove-item`과 `removeItem` 같은 표기 차이에 주의해야 합니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: emit payload에 너무 많은 데이터를 담으면 이벤트 의미가 흐려집니다. 필요한 최소 정보만 전달하는 것이 좋습니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.

컴포넌트 관련 오류는 한 파일만 봐서는 바로 보이지 않을 때가 많습니다. 부모가 넘기는 prop 이름, 자식이 선언한 prop 이름, 자식이 emit하는 이벤트 이름, 부모가 듣는 이벤트 이름을 한 줄씩 맞춰보는 습관이 필요합니다. 브라우저 콘솔의 Vue warning도 그냥 넘기지 말고, 어떤 컴포넌트에서 발생했는지 확인해보시면 좋습니다.

## 실무에서 생각할 점

emit은 부모-자식 관계에서 가장 기본적인 상향 통신 방식입니다. 하지만 부모와 자식 사이 단계가 너무 깊어지면 이벤트를 여러 단계로 다시 올려야 할 수 있습니다. 그때는 컴포넌트 구조를 다시 보거나 전역 상태, provide/inject 같은 대안을 검토할 수 있습니다.

실무에서는 컴포넌트가 "동작한다"보다 "변경에 견딘다"가 더 중요해집니다. 요구사항은 계속 바뀌고, 디자인도 바뀌고, 같은 컴포넌트를 다른 화면에서 쓰고 싶어질 수 있습니다. 그래서 처음부터 모든 것을 일반화하려고 하기보다, 현재 책임을 명확히 하고 나중에 반복이 보일 때 재사용성을 높이는 방향이 안전합니다.
