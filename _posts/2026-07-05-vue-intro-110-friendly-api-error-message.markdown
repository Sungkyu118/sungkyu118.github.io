# Vue 입문 110: API 에러 메시지를 사용자에게 친절하게 보여주는 방법

> API 에러는 개발자에게 필요한 정보와 사용자에게 필요한 안내를 나누어 다뤄야 합니다.

API 요청이 실패했을 때 서버 에러를 그대로 화면에 보여주면 사용자에게 너무 어렵거나 민감한 정보가 노출될 수 있습니다. 반대로 모든 에러를 "오류가 발생했습니다"로만 보여주면 사용자는 무엇을 고쳐야 할지 알 수 없습니다.

좋은 에러 처리는 개발자용 정보와 사용자용 메시지를 나누는 것에서 시작합니다. 콘솔이나 모니터링에는 상세 에러를 남기고, 화면에는 사용자가 다음 행동을 결정할 수 있는 문장을 보여줍니다.

폼에서는 필드별 에러와 전체 에러도 구분해야 합니다. 이메일 형식이 틀렸다는 메시지는 이메일 필드 옆에, 서버가 일시적으로 실패했다는 메시지는 폼 상단에 보여주는 식입니다.

## 이번 글에서 먼저 잡을 관점

이번 API 구간에서는 화면이 서버와 대화할 때 필요한 상태와 실패 처리를 함께 봅니다. 실제 앱에서 API 호출은 성공만 있는 것이 아니라 로딩, 실패, 빈 결과, 인증 만료, 중복 제출 같은 상황을 계속 만납니다.

코드를 읽을 때는 요청을 보내는 줄보다 요청 전후 상태가 어떻게 바뀌는지를 먼저 따라가 보세요. 사용자가 기다리는 동안 무엇을 보는지, 실패했을 때 어떤 안내를 받는지까지 생각하면 예제의 의도가 더 잘 보입니다.

지금 단계에서는 완벽한 구조를 외우려고 하기보다, 왜 이 코드가 특정 위치에 있어야 하는지, 그 위치가 바뀌면 어떤 장점과 비용이 생기는지 함께 생각해보시면 좋습니다. Vue 프로젝트는 문법을 많이 아는 것보다 상태, 화면, 서버, 테스트의 책임을 구분하는 힘이 중요해지는 순간이 많습니다.

## 작은 실습으로 확인해보기

아래 예제는 서버가 fieldErrors와 message를 내려준다고 가정하고 사용자용 에러 상태를 나누어 저장합니다.

{% raw %}
~~~vue
const formErrors = reactive({})
const globalErrorMessage = ref('')

async function submitSignup() {
  Object.keys(formErrors).forEach((key) => {
    delete formErrors[key]
  })
  globalErrorMessage.value = ''

  try {
    const response = await fetch('/api/signup', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(form)
    })

    if (response.status === 400) {
      const errorBody = await response.json()
      Object.assign(formErrors, errorBody.fieldErrors ?? {})
      globalErrorMessage.value = errorBody.message ?? '입력값을 확인해주세요.'
      return
    }

    if (!response.ok) {
      globalErrorMessage.value = '지금은 가입을 처리할 수 없습니다. 잠시 후 다시 시도해주세요.'
      return
    }
  } catch (error) {
    console.error(error)
    globalErrorMessage.value = '네트워크 상태를 확인해주세요.'
  }
}
~~~
{% endraw %}

## 코드가 움직이는 순서

요청 전에 이전 에러를 비웁니다. 400은 사용자가 수정할 수 있는 입력 오류로 보고 fieldErrors를 반영합니다. 그 외 실패나 네트워크 오류는 전역 메시지로 안내합니다. 실제 에러 객체는 console이나 모니터링에 남깁니다.

예제를 따라 작성할 때는 먼저 상태가 만들어지는 위치를 찾고, 그다음 그 상태를 바꾸는 함수를 찾고, 마지막으로 템플릿이나 테스트에서 어떤 결과를 확인하는지 살펴보세요. Vue 코드는 겉으로는 여러 파일에 나뉘어 보이지만, 실제로는 "상태가 바뀌고, 계산값이 갱신되고, 화면이나 테스트 결과가 달라지는 흐름"을 반복합니다. 이 순서를 말로 설명할 수 있으면 문법을 조금 잊어도 다시 찾아가며 구현할 수 있습니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 서버 에러 원문을 그대로 보여주면 내부 정보가 노출될 수 있습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: 이전 필드 에러를 지우지 않으면 수정 후에도 낡은 메시지가 남습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: 사용자에게 해결 방법이 없는 에러라면 재시도, 문의, 나중에 다시 시도 같은 다음 행동을 안내해야 합니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.

문제가 생겼을 때는 한 번에 모든 코드를 의심하지 말고, 입력값, 상태 변경 함수, 비동기 요청 결과, 화면 렌더링 또는 테스트 검증 지점을 차례로 확인해보세요. 특히 Pinia, API, 테스트는 코드가 여러 파일에 나뉘기 쉬워서 어디서 값이 바뀌었는지 놓치기 쉽습니다. 브라우저 콘솔, Network 탭, Vue Devtools, 테스트 실패 메시지를 함께 보면 눈으로 보이지 않는 흐름을 훨씬 빠르게 확인할 수 있습니다.

## 실무에서 생각할 점

친절한 에러 처리는 코드가 길어지지만 이탈을 줄입니다. 특히 가입, 결제, 저장처럼 중요한 흐름에서는 실패 메시지 품질이 사용자 신뢰와 직결됩니다.

실무에서는 정답 패턴을 한 번에 고르는 것보다 현재 팀과 프로젝트의 복잡도에 맞는 선택을 하는 것이 중요합니다. 작은 화면에서는 단순한 코드가 가장 좋은 코드일 수 있고, 여러 화면에서 같은 문제가 반복되기 시작하면 그때 분리하는 편이 더 안전할 수 있습니다. 반대로 인증, 결제, 관리자 권한, 테스트 자동화처럼 실수의 영향이 큰 영역은 초반부터 책임 경계를 조금 더 엄격하게 잡는 것이 좋습니다.

## 디버깅하거나 검증할 때 확인할 순서

1. 현재 값이 어디에서 만들어지는지 확인합니다.
2. 그 값을 바꾸는 함수나 action이 어느 파일에 있는지 확인합니다.
3. API 요청이 있다면 loading, success, error 상태가 모두 처리되는지 확인합니다.
4. 사용자 입력이 있다면 입력 전, 입력 중, 제출 후 상태를 나누어 확인합니다.
5. 테스트가 있다면 내부 구현보다 사용자에게 보이는 결과를 검증하는지 확인합니다.

이 순서를 습관처럼 적용하면 문제를 만났을 때 훨씬 덜 흔들립니다. 특히 입문 단계에서는 코드를 많이 아는 것보다, 문제가 생겼을 때 확인할 순서를 알고 있는 것이 더 큰 힘이 됩니다.
