Vue를 검색하다 보면 Vue 2 예제와 Vue 3 예제가 섞여 나옵니다. 입문자 입장에서는 `new Vue()`로 시작하는 코드도 보이고, `createApp()`으로 시작하는 코드도 보이고, 어떤 글은 `data()`와 `methods`를 쓰고 어떤 글은 `ref`와 `<script setup>`을 씁니다. 이때 "내가 뭘 잘못 설치했나?"라고 느끼기 쉽지만, 대부분은 Vue 버전과 API 스타일 차이 때문입니다.

현재 새 프로젝트를 만든다면 보통 Vue 3 기준으로 시작하는 것이 자연스럽습니다. Vue 2는 공식적으로 지원 종료 시점이 지났고, Vue 3 문서와 생태계는 Composition API, `<script setup>`, Vite 기반 개발 흐름을 중심으로 설명하는 경우가 많습니다. 그렇다고 Vue 2 지식이 전부 쓸모없다는 뜻은 아닙니다. 컴포넌트, props, 이벤트, 템플릿 문법 같은 핵심 개념은 이어지지만, 앱 생성 방식과 코드 구성 방식에서 차이가 있습니다.

가장 눈에 띄는 차이는 앱 시작 코드입니다. Vue 2에서는 `new Vue({ ... })` 형태를 많이 봤다면, Vue 3에서는 `createApp(App).mount('#app')`처럼 애플리케이션 인스턴스를 만들어 마운트합니다. 또 Vue 3에서는 Composition API가 공식적으로 중심에 들어오면서 상태와 함수를 기능 단위로 묶기 쉬워졌습니다.

## 이번 글에서 먼저 잡을 관점

이번 주제에서 가장 중요한 것은 문법을 외우는 것보다 흐름을 이해하는 것입니다. Vue 코드는 보통 상태를 준비한다 -> 템플릿에서 상태를 읽는다 -> 사용자 행동으로 상태가 바뀐다 -> Vue가 화면을 다시 맞춘다는 순서로 움직입니다. 이 순서를 머릿속에 두고 읽으면 새로운 문법을 만나도 훨씬 덜 흔들립니다.

또 하나 중요한 점은 Vue가 HTML, CSS, JavaScript를 대체하는 것이 아니라는 사실입니다. Vue는 이 세 가지를 더 구조적으로 연결해주는 도구입니다. 그래서 예제를 따라 칠 때도 "이 문법이 Vue에서만 특별한가?", "아니면 원래 HTML/JavaScript 개념을 Vue 방식으로 연결한 것인가?"를 나누어 생각하면 좋습니다.

처음에는 한 번에 완벽하게 이해하지 못해도 괜찮습니다. 대신 예제 코드를 조금씩 바꿔보면서 어떤 값이 바뀌면 화면의 어느 부분이 바뀌는지 확인해보세요. 손으로 바꿔본 경험이 쌓이면, 단순히 읽기만 했을 때보다 훨씬 빠르게 감이 잡힙니다.

## 작은 실습으로 확인해보기

아래 코드는 같은 카운터를 Options API와 Composition API 방식으로 나란히 보여줍니다. 둘 중 하나만 무조건 맞는 것이 아니라, 같은 문제를 다른 스타일로 표현한다고 이해하시면 좋습니다.

{% raw %}
```vue
<!-- Options API 스타일 -->
<script>
export default {
  data() {
    return {
      count: 0
    }
  },
  methods: {
    increase() {
      this.count += 1
    }
  }
}
</script>

<!-- Composition API + script setup 스타일 -->
<script setup>
import { ref } from 'vue'

const count = ref(0)

function increase() {
  count.value += 1
}
</script>

<template>
  <button @click="increase">현재 숫자: {{ count }}</button>
</template>
```
{% endraw %}

## 코드가 움직이는 순서

Options API는 `data`, `methods`, `computed`처럼 역할별 옵션 안에 코드를 배치합니다. Composition API는 `setup` 범위 안에서 반응형 상태와 함수를 직접 선언합니다. `<script setup>`을 쓰면 템플릿에서 사용할 변수와 함수를 별도로 `return`하지 않아도 되므로 예제 코드가 짧아집니다. 입문자는 Vue 3 기준으로 배우되, 오래된 글을 볼 때 `new Vue`, `this.count`, `filters`, `.native` 같은 표현이 나오면 Vue 2 자료일 가능성을 의식하면 좋습니다.

여기서 꼭 기억하셔야 할 부분은 Vue가 화면을 갱신해준다고 해서 개발자가 흐름을 몰라도 되는 것은 아니라는 점입니다. 오히려 Vue를 잘 쓰려면 상태가 어디에 있고, 어떤 이벤트나 함수가 그 상태를 바꾸며, 템플릿이 그 상태를 어떻게 읽는지 계속 추적할 수 있어야 합니다. 작은 예제부터 이 흐름을 말로 설명해보면 나중에 코드가 길어져도 훨씬 덜 막힙니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 검색한 예제를 그대로 붙여 넣었는데 `new Vue is not defined` 같은 오류가 난다면 Vue 3 프로젝트에 Vue 2 예제를 섞었을 가능성이 큽니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: Options API가 오래된 방식이라서 무조건 나쁘다고 판단하면 안 됩니다. 작은 컴포넌트나 기존 프로젝트에서는 여전히 읽기 쉽고 안정적인 선택이 될 수 있습니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: Composition API는 유연하지만, 아무 기준 없이 상태와 함수를 흩뿌리면 Options API보다 더 읽기 어려워질 수 있습니다. 기능 단위로 묶는 습관이 중요합니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.

에러를 만났을 때는 먼저 터미널 로그와 브라우저 개발자 도구 Console을 함께 봐야 합니다. Vue 프로젝트는 빌드 단계에서 나는 오류와 브라우저 실행 중에 나는 오류가 다를 수 있습니다. 터미널은 정상처럼 보여도 브라우저 콘솔에는 컴포넌트 렌더링 오류가 남아 있을 수 있고, 반대로 브라우저를 열기도 전에 Vite 개발 서버가 실패하는 경우도 있습니다.

## 실무에서 생각할 점

신규 학습과 신규 프로젝트는 Vue 3, Vite, Composition API, `<script setup>` 조합을 기준으로 잡는 것이 좋습니다. 다만 회사 프로젝트나 오래된 강의에서는 Vue 2 문법을 만날 수 있으니, 버전 차이를 무시하기보다 "이 예제는 어느 버전 기준인가?"를 먼저 확인하는 습관이 안전합니다.

실무에서는 "동작한다"만으로는 부족한 경우가 많습니다. 다른 사람이 읽었을 때 의도를 이해할 수 있는지, 요구사항이 조금 바뀌어도 고치기 쉬운지, 에러 상황에서도 사용자가 무엇을 해야 하는지 알 수 있는지가 중요합니다. 입문 시리즈에서 계속 예제와 주의사항을 함께 보는 이유도 여기에 있습니다. 문법을 하나 배울 때마다 그 문법이 실패할 수 있는 지점까지 같이 봐야 실제 프로젝트에서 덜 흔들립니다.

## 오늘 내용 정리

이번 글에서는 $(System.Collections.Specialized.OrderedDictionary.Title) 주제를 중심으로 Vue의 기본 흐름을 살펴봤습니다. 핵심은 Vue 문법을 낱개로 외우는 것이 아니라, 상태와 템플릿과 이벤트가 서로 어떻게 연결되는지 보는 것입니다. 같은 예제라도 값을 바꿔보고, 함수 이름을 일부러 틀려보고, 조건을 반대로 바꿔보면 훨씬 깊게 이해할 수 있습니다.

다음 글로 넘어가기 전에 예제 코드를 그대로 한 번 작성해보시고, 최소한 한 군데는 직접 바꿔보시는 것을 추천드립니다. 버튼 문구를 바꾸거나, 상태 초기값을 바꾸거나, 조건을 하나 추가하는 정도면 충분합니다. 그렇게 작은 변화를 직접 만들어보면 "아, 이 부분이 화면과 연결되어 있구나"라는 감각이 생깁니다.
