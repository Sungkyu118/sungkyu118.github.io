> watch를 computed 대체품으로 쓰지 않고, 상태 변화에 따른 부수 효과 처리 도구로 이해합니다.

`watch`는 특정 상태가 바뀌는 순간을 감지해 코드를 실행할 때 사용합니다. 예를 들어 검색어가 바뀌면 API를 다시 호출하거나, 설정 값이 바뀌면 localStorage에 저장하거나, 특정 상태 변화 로그를 남기는 식입니다. computed가 값을 계산하는 도구라면, watch는 변화에 반응해 부수 효과를 실행하는 도구라고 이해하면 좋습니다.

입문자가 가장 많이 하는 실수는 computed로 충분한 상황에 watch를 쓰는 것입니다. 총액, 필터링 목록, 버튼 비활성 여부처럼 상태에서 계산할 수 있는 값은 computed가 더 자연스럽습니다. watch는 "값을 계산"하기보다 "값이 바뀌었으니 어떤 일을 하자"에 가깝습니다.

또 조심해야 할 점은 비동기 처리입니다. 검색어가 바뀔 때마다 API를 호출하면 이전 요청보다 나중 요청이 먼저 끝나는 순서 문제가 생길 수 있습니다. 입문 단계에서는 간단한 watch부터 시작하되, 실제 서비스에서는 디바운스, 요청 취소, 로딩 상태 관리까지 함께 생각해야 합니다.

## 이번 글에서 먼저 잡을 관점

이번 주제에서 가장 중요한 것은 문법을 외우는 것보다 흐름을 이해하는 것입니다. Vue 코드는 보통 상태를 준비한다 -> 템플릿에서 상태를 읽는다 -> 사용자 행동으로 상태가 바뀐다 -> Vue가 화면을 다시 맞춘다는 순서로 움직입니다. 이 순서를 머릿속에 두고 읽으면 새로운 문법을 만나도 훨씬 덜 흔들립니다.

또 하나 중요한 점은 Vue가 HTML, CSS, JavaScript를 대체하는 것이 아니라는 사실입니다. Vue는 이 세 가지를 더 구조적으로 연결해주는 도구입니다. 그래서 예제를 따라 칠 때도 "이 문법이 Vue에서만 특별한가?", "아니면 원래 HTML/JavaScript 개념을 Vue 방식으로 연결한 것인가?"를 나누어 생각하면 좋습니다.

처음에는 한 번에 완벽하게 이해하지 못해도 괜찮습니다. 대신 예제 코드를 조금씩 바꿔보면서 어떤 값이 바뀌면 화면의 어느 부분이 바뀌는지 확인해보세요. 손으로 바꿔본 경험이 쌓이면, 단순히 읽기만 했을 때보다 훨씬 빠르게 감이 잡힙니다.

## 작은 실습으로 확인해보기

아래 예제는 검색어가 바뀔 때마다 너무 짧은 값은 무시하고, 실제 검색어를 기록합니다. API 호출 대신 콘솔 로그로 흐름을 확인합니다.

{% raw %}
```vue
<script setup>
import { ref, watch } from 'vue'

const keyword = ref('')
const lastSearchedKeyword = ref('')

watch(keyword, (newValue, oldValue) => {
  const trimmed = newValue.trim()

  if (trimmed.length < 2) {
    lastSearchedKeyword.value = ''
    return
  }

  console.log('검색어 변경:', oldValue, '->', newValue)
  lastSearchedKeyword.value = trimmed
})
</script>

<template>
  <input v-model="keyword" placeholder="두 글자 이상 입력하세요" />
  <p>마지막 검색 대상: {{ lastSearchedKeyword || '아직 없음' }}</p>
</template>
```
{% endraw %}

## 코드가 움직이는 순서

`watch(keyword, callback)`은 `keyword`가 바뀔 때 콜백을 실행합니다. 콜백은 새 값과 이전 값을 받을 수 있습니다. 예제에서는 두 글자 미만이면 검색 대상으로 보지 않고, 조건을 통과한 값만 `lastSearchedKeyword`에 저장합니다. 실제 API 호출을 붙인다면 이 위치에 비동기 함수가 들어갈 수 있습니다.

여기서 꼭 기억하셔야 할 부분은 Vue가 화면을 갱신해준다고 해서 개발자가 흐름을 몰라도 되는 것은 아니라는 점입니다. 오히려 Vue를 잘 쓰려면 상태가 어디에 있고, 어떤 이벤트나 함수가 그 상태를 바꾸며, 템플릿이 그 상태를 어떻게 읽는지 계속 추적할 수 있어야 합니다. 작은 예제부터 이 흐름을 말로 설명해보면 나중에 코드가 길어져도 훨씬 덜 막힙니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: computed로 계산 가능한 값을 watch로 동기화하면 코드가 더 복잡해질 수 있습니다. 먼저 computed로 해결할 수 있는지 생각해보세요. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: watch 안에서 감시 중인 값을 다시 바꾸면 무한 반복에 가까운 흐름이 생길 수 있습니다. 변경 대상과 감시 대상을 분리해야 합니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: 검색 API처럼 자주 호출될 수 있는 watch는 디바운스나 요청 취소를 고민해야 합니다. 그렇지 않으면 서버와 UI가 모두 불안정해질 수 있습니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.

에러를 만났을 때는 먼저 터미널 로그와 브라우저 개발자 도구 Console을 함께 봐야 합니다. Vue 프로젝트는 빌드 단계에서 나는 오류와 브라우저 실행 중에 나는 오류가 다를 수 있습니다. 터미널은 정상처럼 보여도 브라우저 콘솔에는 컴포넌트 렌더링 오류가 남아 있을 수 있고, 반대로 브라우저를 열기도 전에 Vite 개발 서버가 실패하는 경우도 있습니다.

## 실무에서 생각할 점

watch는 강력하지만 남용하면 상태 흐름을 추적하기 어려워집니다. 값 계산은 computed, 사용자 행동은 함수, 상태 변화에 따른 외부 작업은 watch라는 기준을 잡으면 훨씬 안전합니다.

실무에서는 "동작한다"만으로는 부족한 경우가 많습니다. 다른 사람이 읽었을 때 의도를 이해할 수 있는지, 요구사항이 조금 바뀌어도 고치기 쉬운지, 에러 상황에서도 사용자가 무엇을 해야 하는지 알 수 있는지가 중요합니다. 입문 시리즈에서 계속 예제와 주의사항을 함께 보는 이유도 여기에 있습니다. 문법을 하나 배울 때마다 그 문법이 실패할 수 있는 지점까지 같이 봐야 실제 프로젝트에서 덜 흔들립니다.
