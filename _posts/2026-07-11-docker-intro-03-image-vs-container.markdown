Docker를 처음 공부하면 이미지와 컨테이너라는 말을 거의 동시에 듣게 됩니다. 그리고 많은 분들이 여기서부터 헷갈리기 시작합니다. "이미지를 실행하면 컨테이너가 된다"라고 들으면 얼핏 이해한 것 같지만, 막상 `docker images`, `docker ps`, `docker run`, `docker rm` 같은 명령어를 보게 되면 머릿속이 다시 복잡해집니다. 그래서 이번 글에서는 이 둘을 완전히 분리해서 생각하는 연습을 해보겠습니다.

이미지와 컨테이너를 구분할 수 있게 되면 Docker가 훨씬 덜 추상적으로 느껴집니다. 왜 같은 이미지로 여러 개의 컨테이너를 띄울 수 있는지, 왜 컨테이너를 지워도 이미지가 남는지, 왜 이미지를 빌드한 뒤 컨테이너를 다시 생성해서 실행하는 흐름이 자연스러운지까지 한 번에 이해할 수 있기 때문입니다. Docker 명령어를 억지로 외우는 대신 구조를 이해하고 싶으시다면, 이 단계가 정말 중요합니다.

## 먼저 이해해야 할 핵심 관점

이번 글의 핵심은 아주 단순합니다. 이미지는 "실행을 위한 재료 묶음"이고, 컨테이너는 "그 재료로 실제로 실행된 결과"입니다. 많은 설명에서 이미지를 설계도, 컨테이너를 설계도로 만든 실제 물건에 비유하곤 하는데, 이 비유는 입문 단계에서 꽤 도움이 됩니다. 다만 설계도라는 표현만으로는 파일 시스템, 라이브러리, 실행 명령 같은 요소가 함께 들어 있다는 점이 충분히 전달되지 않을 수 있으니, 이번 글에서는 조금 더 현실적인 감각으로 설명드리겠습니다.

지금 단계에서는 이미지를 "앱을 실행하는 데 필요한 파일과 설정의 패키지" 정도로 이해하시면 좋습니다. 그리고 컨테이너는 그 패키지를 실제로 띄워서 돌아가게 만든 프로세스 환경이라고 생각하시면 됩니다. 이 차이를 정확히 잡아두면, Docker에서 저장과 실행이 왜 분리되는지도 훨씬 자연스럽게 받아들이실 수 있습니다.

## 이미지는 무엇이라고 생각하면 이해가 쉬울까요?

이미지는 애플리케이션을 실행하는 데 필요한 기준 상태를 묶어둔 것입니다. 베이스 운영체제 계층, 라이브러리, 애플리케이션 파일, 기본 실행 명령 같은 정보가 여기에 들어갑니다. 즉, 이미지는 "실행 준비가 된 패키지"에 가깝습니다. 그런데 중요한 점은, 이미지 자체는 실행 중인 프로세스가 아니라는 것입니다. 그냥 디스크에 저장되어 있는 읽기 중심의 결과물이라고 생각하시면 됩니다.

예를 들어 `nginx` 이미지는 Nginx 웹 서버를 실행할 수 있도록 준비된 패키지입니다. 하지만 `nginx` 이미지를 갖고 있다고 해서 웹 서버가 자동으로 실행되는 것은 아닙니다. 실제로 실행하려면 그 이미지를 기반으로 컨테이너를 만들어야 합니다.

```bash
docker pull nginx
docker images
```

위 두 줄은 이미지를 내려받고 확인하는 흐름입니다. 여기까지는 아직 서버가 뜬 것이 아닙니다. 초보자분들이 자주 하는 실수 중 하나가 `docker pull`만 해놓고 실행이 된 것으로 착각하는 것입니다. 하지만 이미지는 실행 전 상태이고, 실제로 동작하는 것은 컨테이너라는 점을 꼭 구분해두셔야 합니다.

## 컨테이너는 무엇인가요?

컨테이너는 이미지로부터 만들어진 실제 실행 인스턴스입니다. 다시 말해, 이미지는 재료이고 컨테이너는 그 재료를 사용해 지금 돌아가고 있는 실행 결과입니다. 그래서 하나의 이미지로 여러 개의 컨테이너를 동시에 만들 수도 있습니다. 예를 들어 같은 `nginx` 이미지를 바탕으로 포트만 다르게 주면 여러 컨테이너를 각각 띄울 수 있습니다.

```bash
docker run -d --name web1 -p 8080:80 nginx
docker run -d --name web2 -p 8081:80 nginx
```

이 예제는 같은 이미지 하나로 두 개의 컨테이너를 만든 상황입니다. 여기서 핵심은 `nginx` 이미지 하나는 그대로 있고, 그 이미지를 기반으로 `web1`, `web2`라는 실행 결과가 각각 만들어졌다는 점입니다. 즉, 이미지와 컨테이너는 1대1 관계가 아니라 1대다 관계가 될 수 있습니다. 이 감각을 잡아두면 Docker의 많은 동작이 갑자기 훨씬 자연스러워집니다.

## 왜 이 차이가 중요한가요?

이미지와 컨테이너를 구분하는 것이 중요한 이유는 Docker의 작업 흐름 대부분이 이 차이를 전제로 움직이기 때문입니다. 이미지를 만드는 단계와 컨테이너를 실행하는 단계는 완전히 다릅니다. 이미지를 수정하고 싶으면 Dockerfile을 바꾸고 다시 빌드해야 합니다. 반면 컨테이너를 다시 띄우고 싶으면 기존 컨테이너를 지우고 새 컨테이너를 만들면 됩니다. 이 차이를 모르면 실습할 때 자꾸 컨테이너 안에서 수동으로 뭔가를 고쳐놓고, 그 상태가 영구적으로 유지될 것처럼 기대하게 됩니다.

특히 초보자분들이 자주 겪는 문제는 `docker exec`로 컨테이너 안에 들어가서 파일을 바꿔놓고 안심하는 경우입니다. 잠깐 디버깅하는 데는 도움이 될 수 있지만, 컨테이너를 지우고 다시 만들면 그 변경은 대부분 사라집니다. 왜냐하면 영구적으로 관리해야 할 기준 상태는 컨테이너가 아니라 이미지 또는 외부 볼륨 쪽에 있어야 하기 때문입니다.

## 잘못 이해하면 어떤 문제가 생길까요?

가장 흔한 문제는 "실행 중인 컨테이너가 곧 프로젝트 그 자체"라고 착각하는 것입니다. 이렇게 이해하면 컨테이너를 수동으로 고치는 습관이 생기고, 나중에 같은 환경을 다시 만들기 어려워집니다. Docker의 장점은 재현 가능한 실행 흐름인데, 컨테이너를 손으로 계속 수정하기 시작하면 그 장점을 스스로 무너뜨리게 됩니다.

또 다른 흔한 실수는 이미지를 너무 자주 다시 내려받거나, 반대로 컨테이너만 지우고 이미지도 같이 사라졌다고 생각하는 것입니다. 실제로는 이미지와 컨테이너가 분리되어 있기 때문에, `docker rm`은 컨테이너를 지우는 것이고, 이미지까지 지우려면 별도 명령이 필요합니다. 이 구분을 알고 있으면 디스크 정리나 재실행 흐름도 훨씬 덜 헷갈립니다.

## 아주 작은 비유로 다시 정리해보기

입문 단계에서는 아래 비유로 기억하셔도 좋습니다.

- 이미지: 냉동 밀키트
- 컨테이너: 그 밀키트를 실제로 조리해서 먹는 상태

밀키트를 여러 개 사둘 수 있지만, 밀키트 자체가 식사 중인 상태는 아닙니다. 반대로 식사를 하나 끝냈다고 해서 냉동실의 밀키트가 사라지는 것도 아닙니다. 물론 Docker는 이 비유보다 훨씬 복잡하지만, 저장된 실행 재료와 실제 실행 상태를 분리한다는 감각을 잡는 데는 도움이 됩니다.

## 오늘 내용 정리

이번 글에서는 이미지와 컨테이너는 왜 다른 개념일까요?라는 질문을 중심으로, 이미지는 실행에 필요한 패키지이고 컨테이너는 그 이미지를 실제로 실행한 결과라는 점을 정리했습니다. 이 차이를 이해하면 왜 같은 이미지로 여러 컨테이너를 띄울 수 있는지, 왜 컨테이너를 지워도 이미지가 남는지, 왜 Dockerfile과 `docker run`이 서로 다른 단계인지까지 훨씬 자연스럽게 이해할 수 있습니다.

지금 단계에서는 정의를 완벽하게 외우기보다, `pull은 이미지`, `run은 컨테이너`, `rm은 보통 컨테이너`, `build는 이미지 생성`이라는 흐름 정도를 먼저 머릿속에 정리해두시면 좋겠습니다. 그 감각을 잡은 상태로 다음 설치 점검 글과 hello-world 실습 글을 보시면 Docker의 흐름이 훨씬 더 손에 잡히게 느껴질 것입니다.
