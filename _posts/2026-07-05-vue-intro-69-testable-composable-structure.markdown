# Vue 입문 69: Composable 테스트를 쉽게 만들기 위한 구조

> Composable을 만들 때부터 테스트 가능한 구조를 고려하면 나중에 변경과 검증이 훨씬 쉬워진다는 점을 배웁니다.

처음에는 테스트를 나중 문제처럼 느끼기 쉽습니다. 하지만 Composable은 화면에서 로직을 분리하는 역할을 하므로, 구조만 잘 잡아두면 테스트하기 좋은 단위가 됩니다. 반대로 내부에서 fetch, localStorage, window, router를 직접 마구 사용하면 테스트할 때 많은 환경을 흉내 내야 합니다.

테스트하기 쉬운 Composable의 핵심은 의존성을 밖에서 받을 수 있게 만드는 것입니다. 예를 들어 API를 직접 호출하는 대신 `fetcher` 함수를 인자로 받으면 테스트에서는 가짜 fetcher를 넣을 수 있습니다. 검증 규칙도 순수 함수로 분리하면 Vue 없이도 간단히 확인할 수 있습니다.

입문 단계에서 모든 테스트 코드를 작성하지 않더라도, 이런 구조를 알고 있으면 나중에 Vitest나 Vue Test Utils를 배울 때 훨씬 편합니다. "이 코드는 왜 테스트하기 어렵지?"라는 질문은 보통 책임이 너무 섞여 있다는 신호이기도 합니다.

## 이번 글에서 먼저 잡을 관점

이번 Composable 구간에서는 "코드를 함수로 빼는 것"보다 "상태와 동작의 책임을 어디까지 묶을 것인가"를 더 중요하게 보겠습니다. Composable은 반복 코드를 줄이는 도구이기도 하지만, 화면 컴포넌트가 너무 많은 일을 떠안지 않게 도와주는 설계 단위이기도 합니다.

읽으실 때는 예제의 파일 이름보다 데이터 흐름을 먼저 따라가 보시면 좋습니다. 어떤 값이 `ref`로 만들어지는지, 어떤 함수가 상태를 바꾸는지, 컴포넌트는 무엇을 몰라도 되는지 확인해보면 Composable의 장점과 위험이 훨씬 선명하게 보입니다.

지금 단계에서는 완벽한 구조를 외우려고 하기보다, 왜 이 코드가 컴포넌트 안에 있으면 불편해지는지, 분리하면 어떤 장점이 생기는지, 반대로 너무 분리하면 어떤 비용이 생기는지를 함께 생각해보시면 좋습니다. 기술을 배우는 속도보다 판단 기준을 만드는 속도가 더 중요할 때가 많습니다.

## 작은 실습으로 확인해보기

아래 예제는 사용자 목록을 가져오는 Composable입니다. 실제 요청 함수는 기본값으로 제공하지만, 테스트에서는 다른 함수를 넣을 수 있게 설계합니다.

{% raw %}
~~~vue
// composables/useUsers.js
import { ref } from 'vue'

async function defaultFetchUsers() {
  const response = await fetch('/api/users')

  if (!response.ok) {
    throw new Error('사용자 목록 요청 실패')
  }

  return response.json()
}

export function useUsers(fetchUsers = defaultFetchUsers) {
  const users = ref([])
  const loading = ref(false)
  const error = ref(null)

  async function load() {
    loading.value = true
    error.value = null

    try {
      users.value = await fetchUsers()
    } catch (err) {
      users.value = []
      error.value = err
    } finally {
      loading.value = false
    }
  }

  return {
    users,
    loading,
    error,
    load
  }
}

// 테스트에서는 이런 식으로 가짜 함수를 넣을 수 있습니다.
const fakeFetchUsers = async () => [
  { id: 1, name: '테스트 사용자' }
]

const { users, load } = useUsers(fakeFetchUsers)
~~~
{% endraw %}

## 코드가 움직이는 순서

`useUsers`는 기본적으로 실제 API를 호출하지만, 인자로 다른 함수를 받을 수 있습니다. 이 구조 덕분에 테스트에서는 네트워크 없이도 성공 상황과 실패 상황을 만들 수 있습니다. 중요한 점은 Composable이 "사용자 목록을 불러오는 상태 흐름"을 담당하고, 실제 데이터를 어디서 가져올지는 교체 가능하게 열어둔다는 것입니다.

예제를 따라 작성할 때는 먼저 상태가 만들어지는 위치를 찾고, 그다음 그 상태를 바꾸는 함수를 찾고, 마지막으로 템플릿에서 어떤 조건으로 화면이 바뀌는지 확인해보세요. Vue 코드는 겉으로는 HTML과 JavaScript가 섞여 보이지만, 실제로는 "상태가 바뀌고, 계산값이 갱신되고, 템플릿이 다시 그려지는 흐름"을 반복합니다. 이 순서를 말로 설명할 수 있으면 문법을 조금 잊어도 다시 찾아가며 구현할 수 있습니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: Composable 안에서 전역 객체를 직접 사용하면 테스트가 어려워질 수 있습니다. window, localStorage, fetch 같은 의존성은 필요할 때 분리할 수 있는지 생각해보세요. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: 테스트를 위해 구조를 지나치게 복잡하게 만들 필요는 없습니다. 다만 API 요청처럼 외부 세계와 연결되는 부분은 교체 가능하게 만들면 장점이 큽니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: 상태 변경 함수가 여러 일을 동시에 하면 테스트가 길어집니다. 한 함수가 무엇을 보장하는지 설명할 수 있을 정도로 책임을 유지하는 것이 좋습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.

문제가 생겼을 때는 한 번에 모든 코드를 의심하지 말고, 입력값, 상태 변경 함수, 반환값 또는 라우트 이동 결과를 차례로 확인해보세요. 특히 Composable과 Router는 코드가 여러 파일에 나뉘기 쉬워서 "어디서 바뀌었는지"를 놓치기 쉽습니다. 브라우저 콘솔, Vue Devtools, Network 탭을 함께 보면 눈으로 보이지 않는 상태 변화와 요청 흐름을 훨씬 빠르게 확인할 수 있습니다.

## 실무에서 생각할 점

의존성 주입은 테스트에는 좋지만 코드가 낯설어 보일 수 있습니다. 팀원이 모두 초보라면 먼저 단순 구조로 시작하고, 테스트가 필요해지는 지점에서 인자를 열어주는 방식도 현실적인 선택입니다.

실무에서는 정답 패턴을 한 번에 고르는 것보다 현재 팀과 프로젝트의 복잡도에 맞는 선택을 하는 것이 중요합니다. 작은 화면에서는 단순한 코드가 가장 좋은 코드일 수 있고, 여러 화면에서 같은 문제가 반복되기 시작하면 그때 분리하는 편이 더 안전할 수 있습니다. 반대로 인증, 결제, 관리자 권한처럼 실수의 영향이 큰 영역은 초반부터 책임 경계를 조금 더 엄격하게 잡는 것이 좋습니다.

## 디버깅할 때 확인할 순서

1. 현재 값이 어디에서 만들어지는지 확인합니다.
2. 그 값을 바꾸는 함수가 어느 파일에 있는지 확인합니다.
3. 값이 바뀐 뒤 화면이 어떤 조건으로 다시 그려지는지 확인합니다.
4. 비동기 요청이 있다면 loading, success, error 상태가 모두 처리되는지 확인합니다.
5. 라우터 이동이 있다면 URL, route params, query, guard 결과를 차례로 확인합니다.

이 순서를 습관처럼 적용하면 문제를 만났을 때 훨씬 덜 흔들립니다. 특히 입문 단계에서는 코드를 많이 아는 것보다, 문제가 생겼을 때 확인할 순서를 알고 있는 것이 더 큰 힘이 됩니다.
