Pinia를 처음 보면 state, getters, actions가 한 파일 안에 있어서 그냥 store 문법처럼 보일 수 있습니다. 하지만 이 세 가지는 역할이 분명히 다릅니다. state는 앱이 기억해야 하는 원본 값이고, getters는 그 원본 값에서 계산되는 값이며, actions는 원본 값을 바꾸는 행동입니다.

이 구분이 중요한 이유는 디버깅 때문입니다. 총 가격이 이상하다면 getters를 확인하면 되고, 장바구니 수량이 이상하게 바뀐다면 actions를 확인하면 됩니다. 역할이 섞이면 어디서 값이 바뀌었는지 찾기 어려워집니다.

이번 예제에서는 장바구니 store를 통해 각 역할을 나누어 보겠습니다. 장바구니는 목록, 총 수량, 총 가격, 추가/삭제 같은 기능이 자연스럽게 들어 있어 Pinia의 기본 구조를 이해하기 좋습니다.

## 이번 글에서 먼저 잡을 관점

이번 Pinia 구간에서는 store 문법을 외우는 것보다 상태의 범위와 책임을 먼저 보겠습니다. 전역 상태는 여러 화면을 편하게 연결해주지만, 잘못 쓰면 어디서 값이 바뀌는지 추적하기 어려운 큰 공유 공간이 될 수 있습니다.

예제를 읽으실 때는 이 값이 왜 지역 상태가 아니라 전역 상태인지, getter로 계산할 수 있는 값을 state에 중복 저장하고 있지는 않은지, action 이름이 사용자 행동을 잘 설명하는지 함께 살펴보시면 좋습니다.

지금 단계에서는 완벽한 구조를 외우려고 하기보다, 왜 이 코드가 특정 위치에 있어야 하는지, 그 위치가 바뀌면 어떤 장점과 비용이 생기는지 함께 생각해보시면 좋습니다. Vue 프로젝트는 문법을 많이 아는 것보다 상태, 화면, 서버, 테스트의 책임을 구분하는 힘이 중요해지는 순간이 많습니다.

## 작은 실습으로 확인해보기

아래 예제는 장바구니의 원본 목록은 state, 총 수량과 총 금액은 getters, 상품 추가와 제거는 actions로 나눕니다.

{% raw %}
~~~vue
import { defineStore } from 'pinia'

export const useCartStore = defineStore('cart', {
  state: () => ({
    items: []
  }),
  getters: {
    totalQuantity: (state) => {
      return state.items.reduce((sum, item) => sum + item.quantity, 0)
    },
    totalPrice: (state) => {
      return state.items.reduce((sum, item) => sum + item.price * item.quantity, 0)
    }
  },
  actions: {
    addItem(product) {
      const item = this.items.find((current) => current.id === product.id)

      if (item) {
        item.quantity += 1
        return
      }

      this.items.push({
        id: product.id,
        name: product.name,
        price: product.price,
        quantity: 1
      })
    },
    removeItem(productId) {
      this.items = this.items.filter((item) => item.id !== productId)
    }
  }
})
~~~
{% endraw %}

## 코드가 움직이는 순서

`items`는 장바구니의 원본 상태입니다. `totalQuantity`와 `totalPrice`는 items에서 계산되므로 getters에 둡니다. `addItem`과 `removeItem`은 장바구니를 변경하는 사용자 행동이므로 actions에 둡니다.

예제를 따라 작성할 때는 먼저 상태가 만들어지는 위치를 찾고, 그다음 그 상태를 바꾸는 함수를 찾고, 마지막으로 템플릿이나 테스트에서 어떤 결과를 확인하는지 살펴보세요. Vue 코드는 겉으로는 여러 파일에 나뉘어 보이지만, 실제로는 "상태가 바뀌고, 계산값이 갱신되고, 화면이나 테스트 결과가 달라지는 흐름"을 반복합니다. 이 순서를 말로 설명할 수 있으면 문법을 조금 잊어도 다시 찾아가며 구현할 수 있습니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 총 금액처럼 계산 가능한 값을 state에 중복 저장하면 원본 목록과 어긋날 수 있습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: action 이름은 상태 변경 의도를 드러내야 합니다. `setData`보다 `addItem`이 읽기 쉽습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: getter 안에서 state를 수정하면 계산과 변경 책임이 섞이므로 피해야 합니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.

문제가 생겼을 때는 한 번에 모든 코드를 의심하지 말고, 입력값, 상태 변경 함수, 비동기 요청 결과, 화면 렌더링 또는 테스트 검증 지점을 차례로 확인해보세요. 특히 Pinia, API, 테스트는 코드가 여러 파일에 나뉘기 쉬워서 어디서 값이 바뀌었는지 놓치기 쉽습니다. 브라우저 콘솔, Network 탭, Vue Devtools, 테스트 실패 메시지를 함께 보면 눈으로 보이지 않는 흐름을 훨씬 빠르게 확인할 수 있습니다.

## 실무에서 생각할 점

state, getters, actions를 분명히 나누면 파일이 조금 길어질 수 있지만, 변경 이유를 찾기 쉬워집니다. 특히 팀 작업에서는 이 구분이 코드 리뷰와 디버깅 시간을 줄여줍니다.

실무에서는 정답 패턴을 한 번에 고르는 것보다 현재 팀과 프로젝트의 복잡도에 맞는 선택을 하는 것이 중요합니다. 작은 화면에서는 단순한 코드가 가장 좋은 코드일 수 있고, 여러 화면에서 같은 문제가 반복되기 시작하면 그때 분리하는 편이 더 안전할 수 있습니다. 반대로 인증, 결제, 관리자 권한, 테스트 자동화처럼 실수의 영향이 큰 영역은 초반부터 책임 경계를 조금 더 엄격하게 잡는 것이 좋습니다.

## 디버깅하거나 검증할 때 확인할 순서

1. 현재 값이 어디에서 만들어지는지 확인합니다.
2. 그 값을 바꾸는 함수나 action이 어느 파일에 있는지 확인합니다.
3. API 요청이 있다면 loading, success, error 상태가 모두 처리되는지 확인합니다.
4. 사용자 입력이 있다면 입력 전, 입력 중, 제출 후 상태를 나누어 확인합니다.
5. 테스트가 있다면 내부 구현보다 사용자에게 보이는 결과를 검증하는지 확인합니다.

이 순서를 습관처럼 적용하면 문제를 만났을 때 훨씬 덜 흔들립니다. 특히 입문 단계에서는 코드를 많이 아는 것보다, 문제가 생겼을 때 확인할 순서를 알고 있는 것이 더 큰 힘이 됩니다.
