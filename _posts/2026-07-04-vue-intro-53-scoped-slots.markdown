# Vue 입문 53: scoped slot으로 자식의 데이터를 부모 템플릿에서 사용하기

> 자식이 데이터와 흐름을 제공하고 부모가 표시 방식을 커스터마이징하는 scoped slot을 이해합니다.

기본 slot과 named slot은 부모가 콘텐츠를 자식 안에 넣는 방식입니다. 그런데 가끔은 자식이 가진 데이터를 부모가 받아서 화면을 직접 구성하고 싶을 때가 있습니다. 예를 들어 목록 컴포넌트가 반복과 빈 상태 처리는 맡고, 각 항목을 어떻게 보여줄지는 부모가 결정하게 하고 싶을 수 있습니다. 이때 scoped slot을 사용합니다.

scoped slot은 자식이 slot에 데이터를 넘기고, 부모가 그 데이터를 받아 템플릿에서 사용하는 구조입니다. 자식은 `<slot :item="item" />`처럼 slot props를 제공하고, 부모는 `#default="{ item }"`처럼 받아 사용합니다. 이렇게 하면 자식은 로직을 제공하고 부모는 렌더링 방식을 커스터마이징할 수 있습니다.

이 패턴은 강력하지만 처음에는 조금 어렵습니다. 데이터가 부모에서 자식으로만 흐르는 props와 달리, slot props는 자식이 부모 템플릿에 값을 제공하는 것처럼 보이기 때문입니다. 실제로는 부모가 작성한 slot 콘텐츠가 자식의 렌더링 위치에서 실행되며, 자식이 제공한 값을 사용할 수 있다고 이해하면 됩니다.

## 이번 글에서 먼저 잡을 관점

이번 구간부터는 Vue를 단순히 한 파일 안에서 쓰는 단계에서 벗어나, 여러 컴포넌트가 함께 동작하는 구조를 다룹니다. 그래서 문법 하나만 보는 것보다 역할과 책임을 같이 보는 것이 중요합니다. 부모 컴포넌트가 무엇을 알고 있어야 하는지, 자식 컴포넌트는 어디까지 책임져야 하는지, 사용자의 행동을 어느 방향으로 전달해야 하는지 계속 질문하면서 읽어보시면 좋습니다.

컴포넌트 설계는 처음부터 완벽하게 나누는 일이 아닙니다. 작은 화면을 만들고, 반복되는 부분이나 책임이 분명한 부분을 발견하고, 그때 적절히 분리하는 과정에 가깝습니다. 이 글의 예제도 정답이라기보다 기준을 잡기 위한 출발점으로 봐주세요. 직접 이름을 바꿔보고, props를 하나 추가해보고, 이벤트 흐름을 바꿔보면 훨씬 오래 기억에 남습니다.

## 작은 실습으로 확인해보기

아래 예제는 `ListRenderer`가 목록 반복을 맡고, 부모가 각 항목의 표시 방식을 scoped slot으로 정합니다.

{% raw %}
```vue
<!-- ListRenderer.vue -->
<script setup>
defineProps({
  items: {
    type: Array,
    required: true
  }
})
</script>

<template>
  <ul>
    <li v-for="item in items" :key="item.id">
      <slot :item="item" />
    </li>
  </ul>
</template>

<!-- Parent.vue -->
<template>
  <ListRenderer :items="users">
    <template #default="{ item }">
      <strong>{{ item.name }}</strong>
      <small>{{ item.email }}</small>
    </template>
  </ListRenderer>
</template>
```
{% endraw %}

## 코드가 움직이는 순서

`ListRenderer`는 배열을 반복하고 `li` 구조를 만듭니다. 각 항목을 어떻게 보여줄지는 부모가 결정합니다. 자식은 slot에 `item`을 넘기고, 부모는 `{ item }`으로 받아 이름과 이메일을 렌더링합니다. 이 구조는 테이블, 리스트, 드롭다운처럼 반복 구조는 같지만 표시 내용이 달라지는 컴포넌트에 유용합니다.

여기서 중요한 것은 코드 줄 수보다 의도입니다. 컴포넌트를 나누면 파일은 늘어나지만, 각 파일이 맡는 역할이 선명해져야 합니다. 부모는 전체 상태와 흐름을 관리하고, 자식은 자신이 맡은 UI 조각을 표현하거나 사용자 행동을 이벤트로 알려주는 식으로 역할을 나누면 디버깅이 훨씬 쉬워집니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: scoped slot은 강력하지만 처음 보는 사람에게 어렵게 느껴질 수 있습니다. 단순한 경우에는 props와 일반 slot만으로 충분할 수 있습니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: slot props 이름이 많아지면 사용법이 복잡해집니다. 꼭 필요한 데이터만 넘기세요. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 자식이 로직을 너무 많이 숨기면 부모에서 화면을 읽기 어려울 수 있습니다. 반복과 렌더링 책임의 균형을 생각해야 합니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.

컴포넌트 관련 오류는 한 파일만 봐서는 바로 보이지 않을 때가 많습니다. 부모가 넘기는 prop 이름, 자식이 선언한 prop 이름, 자식이 emit하는 이벤트 이름, 부모가 듣는 이벤트 이름을 한 줄씩 맞춰보는 습관이 필요합니다. 브라우저 콘솔의 Vue warning도 그냥 넘기지 말고, 어떤 컴포넌트에서 발생했는지 확인해보시면 좋습니다.

## 실무에서 생각할 점

scoped slot은 재사용성과 커스터마이징을 동시에 얻을 수 있는 패턴입니다. 하지만 입문 단계에서는 남용하지 않는 것이 좋습니다. 같은 반복 구조를 여러 화면에서 재사용해야 하고, 항목 표시만 달라지는 상황에서 쓰면 효과가 분명합니다.

실무에서는 컴포넌트가 "동작한다"보다 "변경에 견딘다"가 더 중요해집니다. 요구사항은 계속 바뀌고, 디자인도 바뀌고, 같은 컴포넌트를 다른 화면에서 쓰고 싶어질 수 있습니다. 그래서 처음부터 모든 것을 일반화하려고 하기보다, 현재 책임을 명확히 하고 나중에 반복이 보일 때 재사용성을 높이는 방향이 안전합니다.
