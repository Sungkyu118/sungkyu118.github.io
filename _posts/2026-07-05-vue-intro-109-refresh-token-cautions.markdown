# Vue 입문 109: refresh token 흐름을 프론트엔드에서 이해할 때의 주의점

> refresh token은 편리하지만 저장 위치와 재발급 경쟁 상태를 조심해야 합니다.

access token은 보통 짧은 수명을 가지고, refresh token은 access token을 다시 발급받기 위해 사용됩니다. 프론트엔드 입장에서는 401 응답을 받았을 때 refresh 요청을 보내고, 새 access token으로 원래 요청을 다시 시도하는 흐름을 생각하게 됩니다.

하지만 refresh token은 매우 민감한 값입니다. 어디에 저장할지, JavaScript에서 접근할 수 있게 할지, httpOnly cookie를 쓸지 같은 결정은 보안 정책과 서버 구현에 따라 달라집니다. 프론트 혼자 정할 문제가 아닙니다.

또 하나의 실무 문제는 동시 요청입니다. 여러 API가 동시에 401을 받으면 refresh 요청이 여러 번 날아갈 수 있습니다. 이런 문제는 입문 예제에서는 잘 보이지 않지만 실제 서비스에서는 자주 고민하게 됩니다.

## 이번 글에서 먼저 잡을 관점

이번 API 구간에서는 화면이 서버와 대화할 때 필요한 상태와 실패 처리를 함께 봅니다. 실제 앱에서 API 호출은 성공만 있는 것이 아니라 로딩, 실패, 빈 결과, 인증 만료, 중복 제출 같은 상황을 계속 만납니다.

코드를 읽을 때는 요청을 보내는 줄보다 요청 전후 상태가 어떻게 바뀌는지를 먼저 따라가 보세요. 사용자가 기다리는 동안 무엇을 보는지, 실패했을 때 어떤 안내를 받는지까지 생각하면 예제의 의도가 더 잘 보입니다.

지금 단계에서는 완벽한 구조를 외우려고 하기보다, 왜 이 코드가 특정 위치에 있어야 하는지, 그 위치가 바뀌면 어떤 장점과 비용이 생기는지 함께 생각해보시면 좋습니다. Vue 프로젝트는 문법을 많이 아는 것보다 상태, 화면, 서버, 테스트의 책임을 구분하는 힘이 중요해지는 순간이 많습니다.

## 작은 실습으로 확인해보기

아래 예제는 refresh가 이미 진행 중이면 같은 Promise를 재사용하는 단순한 구조입니다.

{% raw %}
~~~vue
let refreshingPromise = null

async function refreshAccessToken() {
  if (!refreshingPromise) {
    refreshingPromise = fetch('/api/auth/refresh', {
      method: 'POST',
      credentials: 'include'
    })
      .then((response) => {
        if (!response.ok) {
          throw new Error('토큰 재발급 실패')
        }

        return response.json()
      })
      .finally(() => {
        refreshingPromise = null
      })
  }

  return refreshingPromise
}

export async function requestWithRefresh(url, options = {}) {
  const auth = useAuthStore()
  let response = await authRequest(url, options)

  if (response.status !== 401) {
    return response
  }

  const result = await refreshAccessToken()
  auth.accessToken = result.accessToken

  response = await authRequest(url, options)
  return response
}
~~~
{% endraw %}

## 코드가 움직이는 순서

refreshingPromise가 있으면 새 refresh 요청을 만들지 않고 기존 Promise를 기다립니다. 401을 받은 뒤 refresh가 성공하면 새 access token을 저장하고 원래 요청을 다시 시도합니다.

예제를 따라 작성할 때는 먼저 상태가 만들어지는 위치를 찾고, 그다음 그 상태를 바꾸는 함수를 찾고, 마지막으로 템플릿이나 테스트에서 어떤 결과를 확인하는지 살펴보세요. Vue 코드는 겉으로는 여러 파일에 나뉘어 보이지만, 실제로는 "상태가 바뀌고, 계산값이 갱신되고, 화면이나 테스트 결과가 달라지는 흐름"을 반복합니다. 이 순서를 말로 설명할 수 있으면 문법을 조금 잊어도 다시 찾아가며 구현할 수 있습니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: refresh token 저장 방식은 보안 정책과 서버 구현이 함께 결정해야 합니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: refresh 실패 시 사용자를 로그아웃시키고 로그인 페이지로 보낼 흐름이 필요합니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: 동시 요청을 고려하지 않으면 refresh 요청이 여러 번 발생해 상태가 꼬일 수 있습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.

문제가 생겼을 때는 한 번에 모든 코드를 의심하지 말고, 입력값, 상태 변경 함수, 비동기 요청 결과, 화면 렌더링 또는 테스트 검증 지점을 차례로 확인해보세요. 특히 Pinia, API, 테스트는 코드가 여러 파일에 나뉘기 쉬워서 어디서 값이 바뀌었는지 놓치기 쉽습니다. 브라우저 콘솔, Network 탭, Vue Devtools, 테스트 실패 메시지를 함께 보면 눈으로 보이지 않는 흐름을 훨씬 빠르게 확인할 수 있습니다.

## 실무에서 생각할 점

자동 refresh는 사용자 경험을 좋게 만들지만 인증 흐름을 복잡하게 합니다. 처음에는 401 시 로그아웃처럼 단순한 정책으로 시작하고, 필요가 명확해졌을 때 자동 재발급을 도입하는 것도 좋은 전략입니다.

실무에서는 정답 패턴을 한 번에 고르는 것보다 현재 팀과 프로젝트의 복잡도에 맞는 선택을 하는 것이 중요합니다. 작은 화면에서는 단순한 코드가 가장 좋은 코드일 수 있고, 여러 화면에서 같은 문제가 반복되기 시작하면 그때 분리하는 편이 더 안전할 수 있습니다. 반대로 인증, 결제, 관리자 권한, 테스트 자동화처럼 실수의 영향이 큰 영역은 초반부터 책임 경계를 조금 더 엄격하게 잡는 것이 좋습니다.

## 디버깅하거나 검증할 때 확인할 순서

1. 현재 값이 어디에서 만들어지는지 확인합니다.
2. 그 값을 바꾸는 함수나 action이 어느 파일에 있는지 확인합니다.
3. API 요청이 있다면 loading, success, error 상태가 모두 처리되는지 확인합니다.
4. 사용자 입력이 있다면 입력 전, 입력 중, 제출 후 상태를 나누어 확인합니다.
5. 테스트가 있다면 내부 구현보다 사용자에게 보이는 결과를 검증하는지 확인합니다.

이 순서를 습관처럼 적용하면 문제를 만났을 때 훨씬 덜 흔들립니다. 특히 입문 단계에서는 코드를 많이 아는 것보다, 문제가 생겼을 때 확인할 순서를 알고 있는 것이 더 큰 힘이 됩니다.
