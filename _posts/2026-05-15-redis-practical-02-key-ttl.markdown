# Redis 입문 실무형 2: 키 설계와 TTL (운영에서 덜 망하는 법)

Redis를 실무에서 쓰면, 결국 2가지가 운영 품질을 결정합니다.

1. 키 설계(key design)
2. TTL/만료 전략(expiration strategy)

캐시든 세션이든 레이트리밋이든, 키와 TTL을 대충 잡으면 처음엔 "빨라졌다"가, 어느 순간부터는 "왜 이 값이 남아있지?"가 됩니다.

## 1) 키 네이밍 규칙(권장)

키는 사람이 봐도 의미가 드러나야 합니다.

- 접두사(prefix): 도메인/기능
- 식별자: id, region, version

예시:

- `user:{id}`
- `product:{id}`
- `feed:home:{region}`
- `rl:login:{ip}` (rate limit)

실무 팁:

- 콜론(`:`)으로 계층을 나누면 검색/분석이 편합니다.
- 키에 "버전"을 넣으면 대규모 무효화가 쉬워집니다. 예: `product:v2:{id}`

## 2) TTL은 설계다

TTL은 그냥 "몇 분"이 아니라, "얼마나 오래 stale을 허용할 것인가"입니다.

- 설정/카테고리: 길게(예: 30분~수시간)
- 사용자 프로필(변경 잦음): 짧게(예: 1~5분) 또는 이벤트 기반 무효화
- 레이트리밋: 윈도우 길이(예: 1분/10분)
- 세션: 로그인 정책(예: 30분 idle / 7일 remember-me)

## 3) 무효화(Invalidate) 전략 3가지

### (1) TTL에 맡긴다(가장 쉬움)

장점: 구현 쉬움
단점: stale이 남는다

### (2) 쓰기 시 삭제/갱신한다

예: 유저 프로필 수정 시 `DEL user:{id}` 또는 갱신

장점: 정합성 좋음
단점: 쓰기 경로에 의존성이 생김

### (3) 버전 키로 한 번에 갈아탄다

예: `config:v{ver}` 형태로, `ver`만 올리면 전체 무효화

장점: 대규모 변경에 유리
단점: 구현/운영 기준이 필요

## 4) 스탬피드(동시 만료) 방어

여러 키가 같은 TTL로 만료되면, 특정 시점에 DB가 동시에 맞을 수 있어요.

기본 방어:

- TTL에 지터(jitter) 추가: 예) 600초 + 랜덤(0~60초)
- 핫키는 분산락/단일 비동기 갱신 고려

## 5) 용량/비용 관점

Redis는 메모리입니다.

- 값이 큰 JSON을 캐시하면 금방 메모리가 찹니다.
- "캐시할 가치가 있는 데이터"만 골라야 합니다.

운영에서 자주 하는 실수:

- "일단 다 캐시" → 메모리 폭발 → eviction → 캐시 히트율 급락 → DB 폭주

## 정리

- 키는 사람이 읽을 수 있게, 접두사/계층/버전으로 설계
- TTL은 stale 허용 범위를 숫자로 표현한 것
- 스탬피드 방어(지터)는 기본 옵션처럼 넣는 게 좋다
