> Redis 키 네이밍, TTL 설계, 충돌 방지, 만료 정책을 운영 사고 관점에서 이해하기 쉽게 설명합니다.

Redis를 실무에서 조금만 써보면 결국 계속 부딪히는 문제가 두 가지 있습니다. 첫째는 키를 어떻게 설계할지, 둘째는 TTL을 어떻게 줄지입니다. 이 두 가지가 애매하면 초반에는 빨라 보이던 캐시가 시간이 지날수록 stale 데이터, 메모리 증가, 캐시 스탬피드 같은 문제로 돌아오기 시작합니다.

이 글에서는 "예쁘게 설계하는 법"보다 **운영에서 덜 망하는 키 설계와 TTL 전략**에 초점을 맞춰보겠습니다.

## 키 설계는 나중에 읽는 사람이 이해할 수 있어야 한다

Redis 키는 단순한 문자열이지만, 운영 시점에는 사실상 로그와 디버깅의 단서 역할을 합니다. 그래서 짧게 만드는 것보다 **의미가 읽히게 만드는 것**이 훨씬 중요합니다.

예를 들면:

- `user:123`
- `product:v2:9001`
- `feed:home:kr`
- `rl:login:192.168.0.10`

이런 키는 보기만 해도 대략 무슨 용도인지 감이 옵니다.

반대로 이런 형태는 피하는 편이 좋습니다.

- `123_user`
- `cache_1`
- `temp_data`
- `result`

이런 키는 처음에는 빨리 만들 수 있지만, 한 달 뒤에 보면 본인도 무슨 용도인지 헷갈리는 경우가 많습니다.

## 추천 규칙

실무에서는 아래 정도만 지켜도 디버깅 난이도가 크게 내려갑니다.

1. 도메인 prefix를 둔다.
2. 필요하면 기능 단위를 한 단계 더 둔다.
3. 실제 식별자(id, region, endpoint)를 뒤에 둔다.
4. 대규모 구조 변경이 예상되면 version prefix를 미리 고려한다.

예:

- `user:profile:123`
- `product:detail:v2:9001`
- `feed:home:kr`
- `rate_limit:login:ip:1.2.3.4`

## TTL은 "몇 초로 할까"가 아니라 "얼마나 오래 오래된 값을 허용할까"다

TTL을 정할 때 가장 흔한 실수는 근거 없이 숫자부터 정하는 것입니다. 예를 들어 "그냥 10분"처럼 정해버리면, 데이터 성격이 바뀌었을 때 stale 허용 범위와 서비스 기대치가 어긋나기 쉽습니다.

TTL을 정할 때는 먼저 이렇게 생각하는 편이 좋습니다.

- 이 데이터는 30초 전 값이어도 괜찮은가?
- 5분 전 값이면 사용자 경험이 망가지는가?
- 변경 즉시 반영이 꼭 필요한가?

예를 들면:

- 카테고리/설정값: 수십 분 ~ 수 시간
- 인기 목록/피드: 수십 초 ~ 수 분
- 인증 제한 카운터: 짧고 명확한 window
- 세션: 로그인 정책 기준

관련해서 캐시 자체 전략은 [Redis for 캐시](/redis/cache)와 연결해서 보는 게 좋습니다.

## TTL을 너무 길게 잡았을 때 생기는 문제

TTL이 길면 캐시 적중률은 좋아 보일 수 있습니다. 하지만 그 대신 오래된 값을 사용자에게 보여줄 가능성이 커집니다.

대표적인 문제:

- 상품 가격이 바뀌었는데 예전 가격이 계속 보인다.
- 권한/설정 변경이 늦게 반영된다.
- 장애 상황에서 이미 잘못된 값이 오래 유지된다.

이런 데이터는 TTL만 믿기보다, 변경 시점에 `DEL`이나 재저장을 함께 고려해야 합니다.

## TTL을 너무 짧게 잡았을 때 생기는 문제

TTL이 짧으면 stale 이슈는 줄지만, 캐시 미스가 늘어나서 DB나 외부 API 부하가 다시 올라갑니다. 캐시를 넣었는데도 성능 이득이 거의 없거나, 특정 시간대에 미스가 몰려 오히려 더 불안정해질 수 있습니다.

대표적인 문제:

- TTL 만료 직후 같은 키에 대한 요청이 동시에 몰린다.
- DB가 순간적으로 급격히 바빠진다.
- "캐시가 있는데 왜 느리지?"라는 상황이 생긴다.

이게 바로 캐시 스탬피드와 연결됩니다.

## 만료 전략은 TTL 하나로 끝나지 않는다

운영에서는 보통 아래 세 가지를 섞어서 씁니다.

### 1) TTL 기반 자연 만료

가장 단순합니다. 구현이 쉽고 누락 위험이 적습니다. 대신 stale 허용을 받아들여야 합니다.

### 2) 데이터 변경 시 명시적 무효화

원본 데이터가 바뀌었을 때 `DEL user:123`처럼 캐시를 지우거나 새 값을 덮어씁니다. 정합성은 좋아지지만, 쓰기 경로에서 캐시를 꼭 같이 관리해야 해서 누락 위험이 있습니다.

### 3) 버전 키 전략

예를 들면 `product:v2:9001`처럼 버전을 붙여서 큰 구조 변경이나 대규모 무효화를 쉽게 처리합니다. 캐시를 전부 순회하지 않아도 되는 장점이 있지만, 버전 관리 규칙이 느슨하면 오히려 더 헷갈릴 수 있습니다.

## 흔한 운영 사고

### 사고 1: 키 이름이 중구난방이라 원인 추적이 안 된다

운영 중 메모리가 늘어나도 어떤 키 계열이 문제인지 구분이 어렵습니다. prefix 규칙이 없는 팀에서 자주 겪습니다.

### 사고 2: 모든 키에 같은 TTL을 준다

데이터 특성이 다른데도 전부 10분, 전부 1시간으로 맞추면 어떤 데이터는 너무 자주 미스가 나고, 어떤 데이터는 너무 오래 stale 상태로 남습니다.

### 사고 3: 동시에 만료된다

많은 키를 같은 시점에 생성하고 같은 TTL을 주면, 만료 시점도 같이 몰립니다. 이럴 때는 TTL에 약간의 jitter를 섞어 만료 시점을 퍼뜨리는 것이 좋습니다.

예를 들면:

- 기본 TTL 600초
- 추가 랜덤 0~60초

이 작은 차이가 실제 운영에서는 꽤 큰 효과를 냅니다.

## 실무 체크리스트

- 키만 보고도 용도를 유추할 수 있는가?
- prefix 규칙이 팀 안에서 통일되어 있는가?
- TTL이 데이터 성격에 맞는가?
- 변경 시 무효화가 필요한 데이터인지 구분되어 있는가?
- 만료 시점이 한꺼번에 몰리는 구조는 아닌가?

## 정리

Redis 키 설계와 TTL은 단순한 취향 문제가 아니라, 운영 안정성과 직결되는 설계 문제입니다.

좋은 키는 읽히고, 좋은 TTL은 stale 허용 범위와 시스템 부하 사이에서 이유 있게 정해집니다. 여기에 만료 분산과 무효화 전략까지 더해져야 Redis가 진짜 운영 도구가 됩니다.
