# Redis for 세션: 여러 서버에서 로그인 상태를 공유하는 법

> 여러 서버 환경에서 Redis로 세션을 공유할 때 필요한 TTL, 장애 대응, 보안 관점을 정리합니다.

세션은 사용자의 로그인 상태를 서버가 기억하는 방식입니다. 서버가 한 대일 때는 메모리에 세션을 저장해도 큰 문제가 없어 보입니다. 하지만 서버가 여러 대가 되거나 배포가 잦아지면 이야기가 달라집니다.

예를 들어 사용자가 A 서버에서 로그인했는데 다음 요청이 B 서버로 가면, B 서버는 그 사용자의 세션을 모를 수 있습니다. 이 문제를 해결하려고 sticky session을 쓰기도 하지만, 서버 장애나 확장 상황에서는 관리가 번거로워집니다.

Redis를 세션 저장소로 쓰면 여러 서버가 같은 세션 저장소를 바라볼 수 있습니다.

## Redis 세션이 필요한 상황

Redis 세션은 이런 상황에서 특히 유용합니다.

- 애플리케이션 서버가 여러 대다.
- 무중단 배포 중에도 로그인 상태를 유지하고 싶다.
- 서버 재시작으로 세션이 날아가면 안 된다.
- 로드밸런서가 요청을 여러 서버로 분산한다.

이런 구조에서는 세션을 특정 서버 메모리에만 두는 것보다 Redis 같은 공용 저장소에 두는 편이 운영하기 쉽습니다.

## 기본 구조

세션 key는 보통 세션 ID를 기준으로 만듭니다.

```bash
SET session:abc123 "{\"userId\":42,\"role\":\"USER\"}" EX 1800
GET session:abc123
EXPIRE session:abc123 1800
DEL session:abc123
```

로그인하면 세션을 만들고, 요청이 들어올 때 세션을 조회하고, 로그아웃하면 세션을 삭제합니다. idle timeout 정책이면 요청이 들어올 때 TTL을 갱신할 수도 있습니다.

## 세션에는 최소한의 정보만 넣자

세션에 너무 많은 정보를 넣으면 Redis 메모리를 빠르게 사용합니다. 세션은 "사용자를 식별하고 인증 상태를 확인하는 데 필요한 최소 정보"만 담는 편이 좋습니다.

추천:

- userId
- role 또는 권한 요약
- 로그인 시각
- 필요한 경우 기기/브라우저 식별 정보

비추천:

- 사용자 전체 프로필
- 큰 권한 목록
- 자주 바뀌는 상세 데이터
- 원본 DB에 있는 거의 모든 정보

필요한 데이터는 userId로 DB나 캐시를 통해 다시 조회하는 구조가 더 명확합니다.

## TTL 정책이 중요하다

세션에서 TTL은 보안과 사용자 경험을 동시에 결정합니다.

예를 들어:

- 30분 idle timeout
- 7일 remember-me
- 관리자 계정은 더 짧은 TTL

TTL이 너무 길면 탈취된 세션이 오래 살아남을 수 있습니다. TTL이 너무 짧으면 사용자가 자주 로그아웃되어 불편합니다.

중요한 것은 정책을 명확히 정하는 것입니다. "일단 하루"처럼 정하면 나중에 보안과 UX 사이에서 계속 흔들립니다.

## 쿠키 설정도 함께 봐야 한다

Redis에 세션을 저장한다고 보안이 자동으로 좋아지는 것은 아닙니다. 브라우저가 들고 있는 세션 쿠키 설정도 중요합니다.

확인할 것:

- `HttpOnly`: JavaScript에서 쿠키 접근 방지
- `Secure`: HTTPS에서만 전송
- `SameSite`: CSRF 위험 완화
- Domain/Path 범위

Redis는 서버 쪽 저장소이고, 쿠키는 클라이언트 쪽 식별자입니다. 둘 중 하나만 잘해도 충분하지 않습니다.

## 로그아웃과 강제 만료

로그아웃 시에는 Redis에서 세션 key를 삭제해야 합니다.

```bash
DEL session:abc123
```

관리자에 의한 강제 로그아웃, 비밀번호 변경 후 전체 세션 만료 같은 요구사항도 자주 생깁니다. 이 경우 사용자별 세션 목록을 별도로 관리하거나, user session version 같은 전략을 고려할 수 있습니다.

## Redis 장애 시 어떻게 할 것인가

세션 저장소로 Redis를 쓰면 Redis 장애가 곧 로그인 장애로 이어질 수 있습니다. 이 부분을 가볍게 보면 안 됩니다.

결정해야 할 것:

- Redis 조회 실패 시 요청을 실패시킬 것인가?
- 일부 기능만 제한할 것인가?
- 로그인 상태를 다시 확인하도록 유도할 것인가?
- Redis HA 구성을 어떻게 할 것인가?

세션은 사용자 경험과 직접 연결되므로 Redis 운영 기본도 함께 봐야 합니다. [Redis 운영 기본](/redis/practical-ops-basics)을 같이 읽어두면 좋습니다.

## 실무에서 자주 하는 실수

### 1) 세션에 너무 많은 데이터를 넣는다

처음에는 편하지만, 세션 수가 늘면 메모리 문제가 됩니다. 세션은 작고 짧게 유지하는 편이 좋습니다.

### 2) TTL 갱신 정책이 애매하다

요청마다 TTL을 갱신할지, 로그인 시점 기준으로만 만료할지 정하지 않으면 사용자 경험이 들쭉날쭉해집니다.

### 3) 로그아웃 시 Redis key를 지우지 않는다

클라이언트 쿠키만 지우고 서버 세션을 남기면 보안상 찜찜한 상태가 됩니다.

## 정리

Redis 세션은 여러 서버가 로그인 상태를 공유해야 할 때 좋은 선택입니다. 하지만 세션 데이터 크기, TTL, 쿠키 보안 설정, 로그아웃 처리, Redis 장애 정책까지 같이 봐야 합니다.

세션은 단순 저장 문제가 아니라 인증 경험 전체의 일부입니다. Redis를 붙이는 순간부터 운영과 보안 기준을 함께 설계해야 안전합니다.
