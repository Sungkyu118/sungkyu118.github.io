# Vue 입문 45: defineModel을 사용할 때 편한 점과 조심할 점

입력 컴포넌트를 만들 때 전통적인 방식은 `modelValue` prop과 `update:modelValue` emit을 함께 선언하는 것입니다. 이 패턴은 명확하지만 반복이 많습니다. Vue의 `defineModel`은 이 반복을 줄여 component v-model을 더 간결하게 작성할 수 있게 해줍니다.

`defineModel()`을 사용하면 부모의 v-model 값과 연결되는 ref를 자식 안에서 얻을 수 있습니다. 자식은 이 ref를 input에 연결하고 값을 바꾸면 부모 상태도 함께 갱신됩니다. 그래서 간단한 입력 컴포넌트에서는 코드가 훨씬 짧아집니다.

하지만 편리하다고 해서 항상 더 좋은 것은 아닙니다. `defineModel`은 내부적으로 props와 emits 패턴을 감싸는 문법이므로, 동작 원리를 모르면 오히려 마법처럼 느껴질 수 있습니다. 또한 기본값을 자식에서 지정할 때 부모 값과 동기화가 헷갈릴 수 있으므로 문서의 주의사항을 함께 확인해야 합니다.

## 이번 글에서 먼저 잡을 관점

이번 구간부터는 Vue를 단순히 한 파일 안에서 쓰는 단계에서 벗어나, 여러 컴포넌트가 함께 동작하는 구조를 다룹니다. 그래서 문법 하나만 보는 것보다 역할과 책임을 같이 보는 것이 중요합니다. 부모 컴포넌트가 무엇을 알고 있어야 하는지, 자식 컴포넌트는 어디까지 책임져야 하는지, 사용자의 행동을 어느 방향으로 전달해야 하는지 계속 질문하면서 읽어보시면 좋습니다.

컴포넌트 설계는 처음부터 완벽하게 나누는 일이 아닙니다. 작은 화면을 만들고, 반복되는 부분이나 책임이 분명한 부분을 발견하고, 그때 적절히 분리하는 과정에 가깝습니다. 이 글의 예제도 정답이라기보다 기준을 잡기 위한 출발점으로 봐주세요. 직접 이름을 바꿔보고, props를 하나 추가해보고, 이벤트 흐름을 바꿔보면 훨씬 오래 기억에 남습니다.

## 작은 실습으로 확인해보기

아래 예제는 `defineModel`로 간단한 입력 컴포넌트를 만드는 방식입니다.

{% raw %}
```vue
<!-- BaseTextInput.vue -->
<script setup>
const model = defineModel({
  type: String,
  default: ''
})
</script>

<template>
  <input v-model="model" />
</template>

<!-- Parent.vue -->
<script setup>
import { ref } from 'vue'
import BaseTextInput from './BaseTextInput.vue'

const nickname = ref('')
</script>

<template>
  <BaseTextInput v-model="nickname" />
  <p>닉네임: {{ nickname }}</p>
</template>
```
{% endraw %}

## 코드가 움직이는 순서

`BaseTextInput` 안의 `model`은 부모의 `nickname`과 연결됩니다. input에 입력하면 `model`이 바뀌고, 그 변화가 부모의 `nickname`에 반영됩니다. 기존 방식이었다면 `modelValue` prop과 `update:modelValue` emit을 직접 선언해야 했지만, `defineModel`은 그 반복을 줄여줍니다.

여기서 중요한 것은 코드 줄 수보다 의도입니다. 컴포넌트를 나누면 파일은 늘어나지만, 각 파일이 맡는 역할이 선명해져야 합니다. 부모는 전체 상태와 흐름을 관리하고, 자식은 자신이 맡은 UI 조각을 표현하거나 사용자 행동을 이벤트로 알려주는 식으로 역할을 나누면 디버깅이 훨씬 쉬워집니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: defineModel은 편하지만 props와 emit의 기본 원리를 먼저 이해한 뒤 쓰는 것이 좋습니다. 그래야 디버깅할 때 흐름을 놓치지 않습니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 자식에서 default 값을 두면 부모가 값을 제공하지 않았을 때 동기화 기대와 다를 수 있습니다. 기본값 정책을 명확히 해야 합니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 복잡한 입력 컴포넌트에서는 자동 편의 문법보다 명시적인 props/emits가 더 읽기 쉬울 때도 있습니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.

컴포넌트 관련 오류는 한 파일만 봐서는 바로 보이지 않을 때가 많습니다. 부모가 넘기는 prop 이름, 자식이 선언한 prop 이름, 자식이 emit하는 이벤트 이름, 부모가 듣는 이벤트 이름을 한 줄씩 맞춰보는 습관이 필요합니다. 브라우저 콘솔의 Vue warning도 그냥 넘기지 말고, 어떤 컴포넌트에서 발생했는지 확인해보시면 좋습니다.

## 실무에서 생각할 점

defineModel은 반복을 줄여주는 좋은 도구입니다. 특히 단순 입력 컴포넌트에서는 코드가 간결해집니다. 하지만 팀의 Vue 버전, 코드 스타일, 명시성 선호에 따라 도입 시점이 달라질 수 있습니다. 처음에는 전통적인 v-model 패턴을 이해하고, 그 다음 defineModel을 쓰는 순서가 안전합니다.

실무에서는 컴포넌트가 "동작한다"보다 "변경에 견딘다"가 더 중요해집니다. 요구사항은 계속 바뀌고, 디자인도 바뀌고, 같은 컴포넌트를 다른 화면에서 쓰고 싶어질 수 있습니다. 그래서 처음부터 모든 것을 일반화하려고 하기보다, 현재 책임을 명확히 하고 나중에 반복이 보일 때 재사용성을 높이는 방향이 안전합니다.
