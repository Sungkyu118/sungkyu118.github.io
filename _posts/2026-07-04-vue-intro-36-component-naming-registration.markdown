컴포넌트를 만들기 시작하면 이름을 어떻게 지어야 하는지, 어디에 등록해야 하는지 헷갈립니다. `TodoItem.vue`처럼 PascalCase 파일명을 쓰기도 하고, 템플릿에서는 `<todo-item>`처럼 kebab-case를 쓰는 예제도 보입니다. Vue는 여러 표기를 허용하지만, 프로젝트 안에서는 일관된 규칙이 중요합니다.

Vite와 SFC를 쓰는 Vue 3 프로젝트에서는 보통 컴포넌트를 import해서 로컬로 사용합니다. `<script setup>`에서는 import한 컴포넌트를 템플릿에서 바로 사용할 수 있습니다. 그래서 `import TodoItem from './components/TodoItem.vue'`라고 가져오면 `<TodoItem />`처럼 템플릿에서 쓸 수 있습니다.

전역 등록도 가능합니다. 앱 전체에서 자주 쓰는 버튼이나 아이콘 컴포넌트를 `app.component()`로 등록할 수 있습니다. 하지만 전역 등록을 남용하면 어느 파일에서 컴포넌트가 온 것인지 찾기 어려워집니다. 입문 단계에서는 로컬 import를 기본으로 익히고, 정말 전역으로 쓰는 컴포넌트만 전역 등록하는 편이 좋습니다.

## 이번 글에서 먼저 잡을 관점

이번 구간부터는 Vue를 단순히 한 파일 안에서 쓰는 단계에서 벗어나, 여러 컴포넌트가 함께 동작하는 구조를 다룹니다. 그래서 문법 하나만 보는 것보다 역할과 책임을 같이 보는 것이 중요합니다. 부모 컴포넌트가 무엇을 알고 있어야 하는지, 자식 컴포넌트는 어디까지 책임져야 하는지, 사용자의 행동을 어느 방향으로 전달해야 하는지 계속 질문하면서 읽어보시면 좋습니다.

컴포넌트 설계는 처음부터 완벽하게 나누는 일이 아닙니다. 작은 화면을 만들고, 반복되는 부분이나 책임이 분명한 부분을 발견하고, 그때 적절히 분리하는 과정에 가깝습니다. 이 글의 예제도 정답이라기보다 기준을 잡기 위한 출발점으로 봐주세요. 직접 이름을 바꿔보고, props를 하나 추가해보고, 이벤트 흐름을 바꿔보면 훨씬 오래 기억에 남습니다.

## 작은 실습으로 확인해보기

아래 예제는 로컬 등록 방식과 전역 등록 방식을 비교합니다.

```vue
<!-- App.vue: 로컬 import -->
<script setup>
import BaseButton from './components/BaseButton.vue'
</script>

<template>
  <BaseButton>저장하기</BaseButton>
</template>

<!-- main.js: 전역 등록 예시 -->
import { createApp } from 'vue'
import App from './App.vue'
import BaseButton from './components/BaseButton.vue'

const app = createApp(App)

app.component('BaseButton', BaseButton)
app.mount('#app')
```

## 코드가 움직이는 순서

로컬 import 방식은 해당 컴포넌트를 사용하는 파일에서 import가 보입니다. 그래서 의존 관계를 추적하기 쉽습니다. 전역 등록 방식은 어디서나 `<BaseButton />`을 쓸 수 있지만, 등록 위치를 모르면 출처를 찾기 어렵습니다. 작은 프로젝트에서는 로컬 import가 더 명확한 경우가 많습니다.

여기서 중요한 것은 코드 줄 수보다 의도입니다. 컴포넌트를 나누면 파일은 늘어나지만, 각 파일이 맡는 역할이 선명해져야 합니다. 부모는 전체 상태와 흐름을 관리하고, 자식은 자신이 맡은 UI 조각을 표현하거나 사용자 행동을 이벤트로 알려주는 식으로 역할을 나누면 디버깅이 훨씬 쉬워집니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 컴포넌트 이름을 `Button`처럼 너무 일반적으로 지으면 HTML 요소나 다른 라이브러리 컴포넌트와 헷갈릴 수 있습니다. `BaseButton`, `TodoItem`처럼 역할을 드러내세요. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 전역 등록을 많이 하면 사용 파일에서 import가 보이지 않아 의존 관계를 추적하기 어려워집니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 파일명 대소문자는 배포 환경에서 문제가 될 수 있습니다. import 경로와 실제 파일명 대소문자를 정확히 맞추는 습관이 좋습니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.

컴포넌트 관련 오류는 한 파일만 봐서는 바로 보이지 않을 때가 많습니다. 부모가 넘기는 prop 이름, 자식이 선언한 prop 이름, 자식이 emit하는 이벤트 이름, 부모가 듣는 이벤트 이름을 한 줄씩 맞춰보는 습관이 필요합니다. 브라우저 콘솔의 Vue warning도 그냥 넘기지 말고, 어떤 컴포넌트에서 발생했는지 확인해보시면 좋습니다.

## 실무에서 생각할 점

로컬 등록은 명시적이고 안전하지만 파일마다 import가 필요합니다. 전역 등록은 편하지만 숨겨진 의존성이 생깁니다. 공통 UI 컴포넌트처럼 정말 자주 쓰는 것만 전역 등록하고, 기능 컴포넌트는 로컬 import로 유지하는 기준이 실무에서 무난합니다.

실무에서는 컴포넌트가 "동작한다"보다 "변경에 견딘다"가 더 중요해집니다. 요구사항은 계속 바뀌고, 디자인도 바뀌고, 같은 컴포넌트를 다른 화면에서 쓰고 싶어질 수 있습니다. 그래서 처음부터 모든 것을 일반화하려고 하기보다, 현재 책임을 명확히 하고 나중에 반복이 보일 때 재사용성을 높이는 방향이 안전합니다.
