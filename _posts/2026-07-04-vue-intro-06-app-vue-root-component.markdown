# Vue 입문 6: App.vue는 왜 특별한 파일처럼 보일까요?

> `App.vue`를 모든 코드를 넣는 파일이 아니라 전체 화면의 큰 틀을 잡는 루트 컴포넌트로 이해합니다.

Vue 프로젝트를 만들면 거의 항상 `App.vue`가 있습니다. 이름도 평범해 보이지만 실제로는 루트 컴포넌트라는 중요한 역할을 맡습니다. 루트 컴포넌트는 Vue 앱의 가장 바깥 컴포넌트입니다. 다른 컴포넌트들은 보통 이 컴포넌트 아래에서 자식처럼 배치됩니다.

입문 단계에서는 `App.vue`에 모든 예제 코드를 작성해도 괜찮습니다. 하지만 실제 프로젝트에서 `App.vue`는 버튼, 입력폼, 목록, API 호출을 전부 담는 파일이 아니라, 전체 레이아웃을 잡고 공통 영역을 배치하는 파일에 가깝습니다. 예를 들어 헤더, 푸터, 라우터가 보여줄 자리, 전역 알림 영역 같은 것이 들어갈 수 있습니다.

`App.vue`가 특별한 이유는 파일 자체에 마법이 있어서가 아니라, `main.js`에서 루트 컴포넌트로 import되어 앱 생성에 사용되기 때문입니다. 즉 이름보다 연결 관계가 중요합니다. 이 사실을 이해하면 나중에 루트 컴포넌트 이름을 바꾸거나 구조를 확장할 때도 덜 두렵습니다.

## 이번 글에서 먼저 잡을 관점

이번 주제에서 가장 중요한 것은 문법을 외우는 것보다 흐름을 이해하는 것입니다. Vue 코드는 보통 상태를 준비한다 -> 템플릿에서 상태를 읽는다 -> 사용자 행동으로 상태가 바뀐다 -> Vue가 화면을 다시 맞춘다는 순서로 움직입니다. 이 순서를 머릿속에 두고 읽으면 새로운 문법을 만나도 훨씬 덜 흔들립니다.

또 하나 중요한 점은 Vue가 HTML, CSS, JavaScript를 대체하는 것이 아니라는 사실입니다. Vue는 이 세 가지를 더 구조적으로 연결해주는 도구입니다. 그래서 예제를 따라 칠 때도 "이 문법이 Vue에서만 특별한가?", "아니면 원래 HTML/JavaScript 개념을 Vue 방식으로 연결한 것인가?"를 나누어 생각하면 좋습니다.

처음에는 한 번에 완벽하게 이해하지 못해도 괜찮습니다. 대신 예제 코드를 조금씩 바꿔보면서 어떤 값이 바뀌면 화면의 어느 부분이 바뀌는지 확인해보세요. 손으로 바꿔본 경험이 쌓이면, 단순히 읽기만 했을 때보다 훨씬 빠르게 감이 잡힙니다.

## 작은 실습으로 확인해보기

아래 예시는 `App.vue`를 레이아웃 중심으로 사용하는 간단한 구조입니다. 핵심은 실제 화면 내용은 `main` 안쪽으로 두고, 공통 헤더와 푸터는 바깥에서 감싸는 것입니다.

{% raw %}
```vue
<script setup>
const title = 'Vue 입문 프로젝트'
</script>

<template>
  <div class="app-shell">
    <header class="top-bar">
      <strong>{{ title }}</strong>
    </header>

    <main class="content">
      <p>여기에 현재 화면의 주요 내용이 들어갑니다.</p>
    </main>

    <footer class="footer">
      천천히, 하지만 흐름을 놓치지 않고 배워봅니다.
    </footer>
  </div>
</template>

<style scoped>
.app-shell {
  min-height: 100vh;
  display: grid;
  grid-template-rows: auto 1fr auto;
}

.top-bar,
.footer {
  padding: 16px;
  background: #42b883;
  color: white;
}

.content {
  padding: 24px;
}
</style>
```

## 코드가 움직이는 순서

`title`은 화면 상단에서 사용되는 간단한 상태입니다. 템플릿은 헤더, 본문, 푸터로 나뉘고, CSS는 `scoped`로 현재 컴포넌트에만 적용되도록 작성했습니다. 이 정도 구조만 잡아도 `App.vue`가 단순한 예제 파일이 아니라 앱 전체의 껍데기를 담당한다는 감각이 생깁니다.

여기서 꼭 기억하셔야 할 부분은 Vue가 화면을 갱신해준다고 해서 개발자가 흐름을 몰라도 되는 것은 아니라는 점입니다. 오히려 Vue를 잘 쓰려면 상태가 어디에 있고, 어떤 이벤트나 함수가 그 상태를 바꾸며, 템플릿이 그 상태를 어떻게 읽는지 계속 추적할 수 있어야 합니다. 작은 예제부터 이 흐름을 말로 설명해보면 나중에 코드가 길어져도 훨씬 덜 막힙니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: `App.vue`에 모든 기능을 계속 추가하면 파일이 너무 커져서 수정하기 어려워집니다. 반복되는 영역은 컴포넌트로 분리하는 것이 좋습니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: 라우터를 사용하는 프로젝트라면 `App.vue` 안에 모든 페이지 내용을 직접 넣기보다 `router-view`가 들어갈 자리를 마련하는 방식으로 바뀝니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: `App.vue`의 스타일을 전역 스타일처럼 사용하면 나중에 예상치 못한 스타일 충돌이 생길 수 있습니다. 공통 스타일과 컴포넌트 스타일의 경계를 의식해야 합니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.

에러를 만났을 때는 먼저 터미널 로그와 브라우저 개발자 도구 Console을 함께 봐야 합니다. Vue 프로젝트는 빌드 단계에서 나는 오류와 브라우저 실행 중에 나는 오류가 다를 수 있습니다. 터미널은 정상처럼 보여도 브라우저 콘솔에는 컴포넌트 렌더링 오류가 남아 있을 수 있고, 반대로 브라우저를 열기도 전에 Vite 개발 서버가 실패하는 경우도 있습니다.

## 실무에서 생각할 점

루트 컴포넌트는 얇게 유지할수록 앱 구조를 파악하기 쉽습니다. 다만 아주 작은 학습 프로젝트에서는 분리를 너무 빨리 하면 파일 이동만 많아져서 오히려 어렵습니다. 처음에는 `App.vue`에서 흐름을 확인하고, 같은 UI가 반복되거나 코드가 길어질 때 분리하는 방식이 좋습니다.

실무에서는 "동작한다"만으로는 부족한 경우가 많습니다. 다른 사람이 읽었을 때 의도를 이해할 수 있는지, 요구사항이 조금 바뀌어도 고치기 쉬운지, 에러 상황에서도 사용자가 무엇을 해야 하는지 알 수 있는지가 중요합니다. 입문 시리즈에서 계속 예제와 주의사항을 함께 보는 이유도 여기에 있습니다. 문법을 하나 배울 때마다 그 문법이 실패할 수 있는 지점까지 같이 봐야 실제 프로젝트에서 덜 흔들립니다.

## 오늘 내용 정리

이번 글에서는 $(System.Collections.Specialized.OrderedDictionary.Title) 주제를 중심으로 Vue의 기본 흐름을 살펴봤습니다. 핵심은 Vue 문법을 낱개로 외우는 것이 아니라, 상태와 템플릿과 이벤트가 서로 어떻게 연결되는지 보는 것입니다. 같은 예제라도 값을 바꿔보고, 함수 이름을 일부러 틀려보고, 조건을 반대로 바꿔보면 훨씬 깊게 이해할 수 있습니다.

다음 글로 넘어가기 전에 예제 코드를 그대로 한 번 작성해보시고, 최소한 한 군데는 직접 바꿔보시는 것을 추천드립니다. 버튼 문구를 바꾸거나, 상태 초기값을 바꾸거나, 조건을 하나 추가하는 정도면 충분합니다. 그렇게 작은 변화를 직접 만들어보면 "아, 이 부분이 화면과 연결되어 있구나"라는 감각이 생깁니다.

### [Vue 입문 1: Vue는 어떤 문제를 해결하려고 만들어졌을까요?](/vue/intro-01-what-is-vue)

이 글은 Vue 프로젝트의 출발점과 개발 환경 감각을 다시 잡고 싶을 때 함께 읽기 좋습니다. 'Vue를 문법 목록으로 외우기 전에, 왜 Vue 같은 프레임워크가 필요한지 먼저 이해합니다.'라는 설명처럼, 문법을 깊게 들어가기 전에 Vue 앱이 어떤 구조로 시작되고 어떤 파일들이 서로 연결되는지 이해하면 이후 예제들이 단순한 조각 코드처럼 보이지 않습니다. 특히 지금 글을 따라 하다가 파일 위치, 실행 흐름, 빌드 결과가 헷갈린다면 이 글이 기준점을 다시 잡아주는 역할을 해줍니다.

Vue 입문 시리즈는 한 편씩 따로 읽어도 되지만, 가능하면 순서대로 따라가시는 것을 추천드립니다. 앞에서 만든 작은 감각이 뒤의 문법을 이해하는 발판이 되기 때문입니다. 지금 단계에서 중요한 것은 빠르게 많이 아는 것보다, 상태와 화면이 연결되는 흐름을 천천히 몸에 익히는 것입니다.
