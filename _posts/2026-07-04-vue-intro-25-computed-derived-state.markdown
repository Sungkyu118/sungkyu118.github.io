프론트엔드 상태에는 원본 상태와 파생 상태가 있습니다. 원본 상태는 사용자가 직접 입력하거나 서버에서 받아온 값입니다. 파생 상태는 원본 상태를 바탕으로 계산할 수 있는 값입니다. 예를 들어 상품 목록은 원본 상태이고, 총 금액은 파생 상태입니다. 검색어와 전체 목록은 원본 상태이고, 필터링된 목록은 파생 상태입니다.

초보자는 파생 상태를 별도 ref로 저장하려는 경우가 많습니다. 예를 들어 `items`가 바뀔 때마다 `totalPrice`도 직접 갱신하는 식입니다. 처음에는 동작하지만, 항목 추가, 삭제, 수량 변경 중 하나라도 갱신을 빠뜨리면 값이 틀어집니다. computed는 이런 동기화 문제를 줄여줍니다.

computed는 의존하는 값이 바뀔 때 다시 계산됩니다. 또한 계산 결과를 읽는 쪽에서는 일반 값처럼 사용할 수 있어 템플릿이 깔끔해집니다. 이 때문에 "저장해야 하는 값인가, 계산할 수 있는 값인가?"를 구분하는 습관이 중요합니다.

## 이번 글에서 먼저 잡을 관점

이번 주제에서 가장 중요한 것은 문법을 외우는 것보다 흐름을 이해하는 것입니다. Vue 코드는 보통 상태를 준비한다 -> 템플릿에서 상태를 읽는다 -> 사용자 행동으로 상태가 바뀐다 -> Vue가 화면을 다시 맞춘다는 순서로 움직입니다. 이 순서를 머릿속에 두고 읽으면 새로운 문법을 만나도 훨씬 덜 흔들립니다.

또 하나 중요한 점은 Vue가 HTML, CSS, JavaScript를 대체하는 것이 아니라는 사실입니다. Vue는 이 세 가지를 더 구조적으로 연결해주는 도구입니다. 그래서 예제를 따라 칠 때도 "이 문법이 Vue에서만 특별한가?", "아니면 원래 HTML/JavaScript 개념을 Vue 방식으로 연결한 것인가?"를 나누어 생각하면 좋습니다.

처음에는 한 번에 완벽하게 이해하지 못해도 괜찮습니다. 대신 예제 코드를 조금씩 바꿔보면서 어떤 값이 바뀌면 화면의 어느 부분이 바뀌는지 확인해보세요. 손으로 바꿔본 경험이 쌓이면, 단순히 읽기만 했을 때보다 훨씬 빠르게 감이 잡힙니다.

## 작은 실습으로 확인해보기

아래 예제는 검색어로 필터링된 목록과 결과 개수를 computed로 만듭니다.

{% raw %}
```vue
<script setup>
import { computed, ref } from 'vue'

const keyword = ref('')
const posts = ref([
  { id: 1, title: 'Vue 시작하기' },
  { id: 2, title: '반응성 이해하기' },
  { id: 3, title: 'computed 사용하기' }
])

const filteredPosts = computed(() => {
  const text = keyword.value.trim().toLowerCase()
  if (!text) return posts.value
  return posts.value.filter(post =>
    post.title.toLowerCase().includes(text)
  )
})

const resultCount = computed(() => filteredPosts.value.length)
</script>

<template>
  <input v-model="keyword" placeholder="검색어" />
  <p>검색 결과: {{ resultCount }}개</p>

  <ul>
    <li v-for="post in filteredPosts" :key="post.id">
      {{ post.title }}
    </li>
  </ul>
</template>
```
{% endraw %}

## 코드가 움직이는 순서

`keyword`와 `posts`는 원본 상태입니다. `filteredPosts`는 이 둘을 바탕으로 계산됩니다. `resultCount`는 다시 `filteredPosts`의 길이를 읽습니다. 검색어가 바뀌면 Vue는 computed 의존성을 따라 필요한 값을 다시 계산하고 화면을 갱신합니다.

여기서 꼭 기억하셔야 할 부분은 Vue가 화면을 갱신해준다고 해서 개발자가 흐름을 몰라도 되는 것은 아니라는 점입니다. 오히려 Vue를 잘 쓰려면 상태가 어디에 있고, 어떤 이벤트나 함수가 그 상태를 바꾸며, 템플릿이 그 상태를 어떻게 읽는지 계속 추적할 수 있어야 합니다. 작은 예제부터 이 흐름을 말로 설명해보면 나중에 코드가 길어져도 훨씬 덜 막힙니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: computed 안에서 API 호출이나 상태 변경 같은 부작용을 넣지 않는 것이 좋습니다. computed는 값을 계산하는 곳으로 유지하세요. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: 파생 상태를 ref로 따로 저장하면 원본과 동기화해야 하는 부담이 생깁니다. 계산 가능한 값은 computed로 두는 편이 안전합니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: computed 결과가 배열이나 객체일 때 템플릿에서 직접 수정하려고 하면 흐름이 복잡해집니다. 수정은 원본 상태를 대상으로 해야 합니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.

에러를 만났을 때는 먼저 터미널 로그와 브라우저 개발자 도구 Console을 함께 봐야 합니다. Vue 프로젝트는 빌드 단계에서 나는 오류와 브라우저 실행 중에 나는 오류가 다를 수 있습니다. 터미널은 정상처럼 보여도 브라우저 콘솔에는 컴포넌트 렌더링 오류가 남아 있을 수 있고, 반대로 브라우저를 열기도 전에 Vite 개발 서버가 실패하는 경우도 있습니다.

## 실무에서 생각할 점

computed는 파생 상태에 강하지만, 모든 값을 computed로 만들 필요는 없습니다. 사용자가 직접 변경하는 값은 ref나 reactive로 두고, 그 값에서 자연스럽게 계산되는 값만 computed로 두면 상태 구조가 훨씬 명확해집니다.

실무에서는 "동작한다"만으로는 부족한 경우가 많습니다. 다른 사람이 읽었을 때 의도를 이해할 수 있는지, 요구사항이 조금 바뀌어도 고치기 쉬운지, 에러 상황에서도 사용자가 무엇을 해야 하는지 알 수 있는지가 중요합니다. 입문 시리즈에서 계속 예제와 주의사항을 함께 보는 이유도 여기에 있습니다. 문법을 하나 배울 때마다 그 문법이 실패할 수 있는 지점까지 같이 봐야 실제 프로젝트에서 덜 흔들립니다.

## 오늘 내용 정리

이번 글에서는 $(System.Collections.Specialized.OrderedDictionary.Title) 주제를 중심으로 Vue의 기본 흐름을 살펴봤습니다. 핵심은 Vue 문법을 낱개로 외우는 것이 아니라, 상태와 템플릿과 이벤트가 서로 어떻게 연결되는지 보는 것입니다. 같은 예제라도 값을 바꿔보고, 함수 이름을 일부러 틀려보고, 조건을 반대로 바꿔보면 훨씬 깊게 이해할 수 있습니다.

다음 글로 넘어가기 전에 예제 코드를 그대로 한 번 작성해보시고, 최소한 한 군데는 직접 바꿔보시는 것을 추천드립니다. 버튼 문구를 바꾸거나, 상태 초기값을 바꾸거나, 조건을 하나 추가하는 정도면 충분합니다. 그렇게 작은 변화를 직접 만들어보면 "아, 이 부분이 화면과 연결되어 있구나"라는 감각이 생깁니다.
