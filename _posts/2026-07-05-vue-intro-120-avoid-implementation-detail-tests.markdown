# Vue 입문 120: 테스트가 너무 구현 세부사항에 묶이지 않게 작성하기

> 좋은 테스트는 내부 구현보다 사용자가 기대하는 행동을 검증해 리팩토링에 강해야 합니다.

테스트를 많이 작성했는데 리팩토링할 때마다 테스트가 우수수 깨진다면 테스트가 너무 구현 세부사항에 묶여 있을 수 있습니다. 테스트는 변경을 안전하게 만들기 위한 도구인데, 작은 내부 구조 변경마다 깨진다면 오히려 개발 속도를 늦출 수 있습니다.

좋은 테스트는 사용자가 기대하는 결과를 중심으로 작성합니다. 버튼을 눌렀을 때 어떤 문구가 보이는지, 어떤 이벤트가 발생하는지, 어떤 API 함수가 호출되는지처럼 외부에서 관찰 가능한 행동을 검증하는 것이 좋습니다.

테스트 구간 마지막 글에서는 구현 세부사항에 덜 묶이는 테스트 기준을 정리하고, 다음 성능/운영 구간으로 넘어가기 전 테스트 전략을 마무리하겠습니다.

## 이번 글에서 먼저 잡을 관점

이번 테스트 구간에서는 테스트 도구 사용법만이 아니라 무엇을 검증해야 오래가는 테스트가 되는지 함께 보겠습니다. 테스트는 완벽함을 보장하는 장치가 아니라, 중요한 동작이 깨졌을 때 빨리 알려주는 안전망입니다.

예제를 읽을 때는 내부 변수명을 확인하는지, 사용자에게 보이는 결과를 확인하는지 구분해보세요. 좋은 테스트는 리팩토링을 방해하기보다 리팩토링을 더 안전하게 만들어야 합니다.

지금 단계에서는 완벽한 구조를 외우려고 하기보다, 왜 이 코드가 특정 위치에 있어야 하는지, 그 위치가 바뀌면 어떤 장점과 비용이 생기는지 함께 생각해보시면 좋습니다. Vue 프로젝트는 문법을 많이 아는 것보다 상태, 화면, 서버, 테스트의 책임을 구분하는 힘이 중요해지는 순간이 많습니다.

## 작은 실습으로 확인해보기

아래 예제는 내부 ref 이름을 직접 확인하는 나쁜 테스트 대신, 사용자가 보는 결과를 확인하는 테스트를 보여줍니다.

{% raw %}
~~~vue
// 피하고 싶은 방향: 내부 구현에 너무 가까운 테스트
expect(wrapper.vm.internalCount).toBe(1)

// 더 나은 방향: 사용자가 보는 결과를 검증
await wrapper.get('button').trigger('click')
expect(wrapper.text()).toContain('현재 값: 1')

// TodoFilter.vue 테스트 예
it('완료된 항목만 보이도록 필터링합니다', async () => {
  const wrapper = mount(TodoFilter, {
    props: {
      todos: [
        { id: 1, title: '테스트 작성', done: true },
        { id: 2, title: '문서 정리', done: false }
      ]
    }
  })

  await wrapper.get('button[data-filter="done"]').trigger('click')

  expect(wrapper.text()).toContain('테스트 작성')
  expect(wrapper.text()).not.toContain('문서 정리')
})
~~~
{% endraw %}

## 코드가 움직이는 순서

내부 변수명인 internalCount를 확인하면 구현을 바꾸는 순간 테스트가 깨집니다. 반대로 버튼을 누른 뒤 화면에 보이는 텍스트를 확인하면 사용자가 기대하는 행동을 검증하게 됩니다.

예제를 따라 작성할 때는 먼저 상태가 만들어지는 위치를 찾고, 그다음 그 상태를 바꾸는 함수를 찾고, 마지막으로 템플릿이나 테스트에서 어떤 결과를 확인하는지 살펴보세요. Vue 코드는 겉으로는 여러 파일에 나뉘어 보이지만, 실제로는 "상태가 바뀌고, 계산값이 갱신되고, 화면이나 테스트 결과가 달라지는 흐름"을 반복합니다. 이 순서를 말로 설명할 수 있으면 문법을 조금 잊어도 다시 찾아가며 구현할 수 있습니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: wrapper.vm에 과하게 의존하면 컴포넌트 내부 구조 변경에 약해집니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: 스냅샷 테스트만 믿으면 의도하지 않은 변경을 검토 없이 승인하기 쉽습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: 모든 세부사항을 테스트하려고 하면 테스트 유지보수 비용이 커집니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.

문제가 생겼을 때는 한 번에 모든 코드를 의심하지 말고, 입력값, 상태 변경 함수, 비동기 요청 결과, 화면 렌더링 또는 테스트 검증 지점을 차례로 확인해보세요. 특히 Pinia, API, 테스트는 코드가 여러 파일에 나뉘기 쉬워서 어디서 값이 바뀌었는지 놓치기 쉽습니다. 브라우저 콘솔, Network 탭, Vue Devtools, 테스트 실패 메시지를 함께 보면 눈으로 보이지 않는 흐름을 훨씬 빠르게 확인할 수 있습니다.

## 실무에서 생각할 점

사용자 행동 중심 테스트는 리팩토링에 강하지만, 내부 복잡한 계산을 세밀하게 검증하기에는 부족할 수 있습니다. 계산은 순수 함수 테스트로, 화면 행동은 컴포넌트 테스트로 나누면 균형이 좋습니다.

실무에서는 정답 패턴을 한 번에 고르는 것보다 현재 팀과 프로젝트의 복잡도에 맞는 선택을 하는 것이 중요합니다. 작은 화면에서는 단순한 코드가 가장 좋은 코드일 수 있고, 여러 화면에서 같은 문제가 반복되기 시작하면 그때 분리하는 편이 더 안전할 수 있습니다. 반대로 인증, 결제, 관리자 권한, 테스트 자동화처럼 실수의 영향이 큰 영역은 초반부터 책임 경계를 조금 더 엄격하게 잡는 것이 좋습니다.

## 디버깅하거나 검증할 때 확인할 순서

1. 현재 값이 어디에서 만들어지는지 확인합니다.
2. 그 값을 바꾸는 함수나 action이 어느 파일에 있는지 확인합니다.
3. API 요청이 있다면 loading, success, error 상태가 모두 처리되는지 확인합니다.
4. 사용자 입력이 있다면 입력 전, 입력 중, 제출 후 상태를 나누어 확인합니다.
5. 테스트가 있다면 내부 구현보다 사용자에게 보이는 결과를 검증하는지 확인합니다.

이 순서를 습관처럼 적용하면 문제를 만났을 때 훨씬 덜 흔들립니다. 특히 입문 단계에서는 코드를 많이 아는 것보다, 문제가 생겼을 때 확인할 순서를 알고 있는 것이 더 큰 힘이 됩니다.
