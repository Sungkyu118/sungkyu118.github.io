Vue 프로젝트를 만들고 `npm run dev`를 실행하면 브라우저에서 바로 화면을 볼 수 있습니다. 파일을 저장하면 새로고침하지 않아도 화면이 바뀌는 경우도 많습니다. 이 경험이 편하다 보니 입문자는 개발 서버가 곧 배포 결과물이라고 오해하기 쉽습니다. 하지만 개발 서버와 운영 빌드는 목적이 다릅니다.

개발 서버는 개발자가 빠르게 수정하고 확인할 수 있도록 돕는 환경입니다. Vite는 네이티브 ES 모듈을 활용해 개발 중 필요한 파일을 빠르게 제공하고, HMR을 통해 변경된 모듈만 교체하려고 합니다. 그래서 저장 후 반영이 매우 빠릅니다. 반면 `npm run build`는 운영 배포를 위해 파일을 묶고 최적화하는 작업입니다. 결과는 보통 `dist` 폴더에 만들어집니다.

이 차이를 모르면 "내 컴퓨터에서는 잘 되는데 배포하면 안 된다"는 문제를 자주 만납니다. 개발 서버는 편의를 위해 많은 것을 해주지만, 실제 배포 환경에서는 정적 파일 경로, 라우팅 fallback, 환경 변수, 캐시 정책 같은 요소가 더 중요해집니다.

## 이번 글에서 먼저 잡을 관점

이번 주제에서 가장 중요한 것은 문법을 외우는 것보다 흐름을 이해하는 것입니다. Vue 코드는 보통 상태를 준비한다 -> 템플릿에서 상태를 읽는다 -> 사용자 행동으로 상태가 바뀐다 -> Vue가 화면을 다시 맞춘다는 순서로 움직입니다. 이 순서를 머릿속에 두고 읽으면 새로운 문법을 만나도 훨씬 덜 흔들립니다.

또 하나 중요한 점은 Vue가 HTML, CSS, JavaScript를 대체하는 것이 아니라는 사실입니다. Vue는 이 세 가지를 더 구조적으로 연결해주는 도구입니다. 그래서 예제를 따라 칠 때도 "이 문법이 Vue에서만 특별한가?", "아니면 원래 HTML/JavaScript 개념을 Vue 방식으로 연결한 것인가?"를 나누어 생각하면 좋습니다.

처음에는 한 번에 완벽하게 이해하지 못해도 괜찮습니다. 대신 예제 코드를 조금씩 바꿔보면서 어떤 값이 바뀌면 화면의 어느 부분이 바뀌는지 확인해보세요. 손으로 바꿔본 경험이 쌓이면, 단순히 읽기만 했을 때보다 훨씬 빠르게 감이 잡힙니다.

## 작은 실습으로 확인해보기

아래 `package.json` scripts는 Vite 프로젝트에서 자주 보는 기본 명령입니다. 세 명령의 목적을 구분해서 기억해두시면 좋습니다.

```json
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview"
  }
}
```

## 코드가 움직이는 순서

`dev`는 개발 서버를 실행합니다. 개발 중에는 이 명령을 가장 많이 씁니다. `build`는 운영 배포용 결과물을 만듭니다. `preview`는 `build` 결과물을 로컬에서 미리 확인합니다. 만약 `dev`에서는 보이는데 `build` 후 `preview`에서 깨진다면, 단순 문법 문제가 아니라 경로, 환경 변수, 빌드 시점 처리 차이를 의심해야 합니다.

여기서 꼭 기억하셔야 할 부분은 Vue가 화면을 갱신해준다고 해서 개발자가 흐름을 몰라도 되는 것은 아니라는 점입니다. 오히려 Vue를 잘 쓰려면 상태가 어디에 있고, 어떤 이벤트나 함수가 그 상태를 바꾸며, 템플릿이 그 상태를 어떻게 읽는지 계속 추적할 수 있어야 합니다. 작은 예제부터 이 흐름을 말로 설명해보면 나중에 코드가 길어져도 훨씬 덜 막힙니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: `npm run dev`가 성공했다고 운영 빌드도 성공한다는 뜻은 아닙니다. 배포 전에는 반드시 `npm run build`를 실행해봐야 합니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: HMR은 개발 편의 기능입니다. 저장할 때 화면이 빠르게 바뀌는 경험을 운영 서버의 동작 방식과 혼동하면 안 됩니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: `dist` 폴더를 직접 수정하면 안 됩니다. 빌드를 다시 하면 사라질 결과물이므로 원본은 `src`에서 수정해야 합니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.

에러를 만났을 때는 먼저 터미널 로그와 브라우저 개발자 도구 Console을 함께 봐야 합니다. Vue 프로젝트는 빌드 단계에서 나는 오류와 브라우저 실행 중에 나는 오류가 다를 수 있습니다. 터미널은 정상처럼 보여도 브라우저 콘솔에는 컴포넌트 렌더링 오류가 남아 있을 수 있고, 반대로 브라우저를 열기도 전에 Vite 개발 서버가 실패하는 경우도 있습니다.

## 실무에서 생각할 점

개발 서버는 빠른 피드백을 위해 최적화되어 있고, 운영 빌드는 사용자에게 전달할 파일을 위해 최적화되어 있습니다. 둘은 경쟁 관계가 아니라 역할이 다릅니다. 안정적인 프로젝트일수록 개발 중에는 `dev`, 배포 전에는 `build`와 `preview`를 모두 확인하는 습관을 갖습니다.

실무에서는 "동작한다"만으로는 부족한 경우가 많습니다. 다른 사람이 읽었을 때 의도를 이해할 수 있는지, 요구사항이 조금 바뀌어도 고치기 쉬운지, 에러 상황에서도 사용자가 무엇을 해야 하는지 알 수 있는지가 중요합니다. 입문 시리즈에서 계속 예제와 주의사항을 함께 보는 이유도 여기에 있습니다. 문법을 하나 배울 때마다 그 문법이 실패할 수 있는 지점까지 같이 봐야 실제 프로젝트에서 덜 흔들립니다.

## 오늘 내용 정리

이번 글에서는 $(System.Collections.Specialized.OrderedDictionary.Title) 주제를 중심으로 Vue의 기본 흐름을 살펴봤습니다. 핵심은 Vue 문법을 낱개로 외우는 것이 아니라, 상태와 템플릿과 이벤트가 서로 어떻게 연결되는지 보는 것입니다. 같은 예제라도 값을 바꿔보고, 함수 이름을 일부러 틀려보고, 조건을 반대로 바꿔보면 훨씬 깊게 이해할 수 있습니다.

다음 글로 넘어가기 전에 예제 코드를 그대로 한 번 작성해보시고, 최소한 한 군데는 직접 바꿔보시는 것을 추천드립니다. 버튼 문구를 바꾸거나, 상태 초기값을 바꾸거나, 조건을 하나 추가하는 정도면 충분합니다. 그렇게 작은 변화를 직접 만들어보면 "아, 이 부분이 화면과 연결되어 있구나"라는 감각이 생깁니다.
