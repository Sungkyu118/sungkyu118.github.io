프로젝트를 처음 생성하면 파일이 여러 개 생깁니다. 입문자에게는 이 구조가 은근히 부담스럽습니다. `index.html`도 있고, `src/main.js`도 있고, `App.vue`도 있고, `components` 폴더도 있습니다. 어떤 파일이 진짜 시작점인지, 어느 파일을 수정해야 화면이 바뀌는지 헷갈리기 쉽습니다.

Vite 기반 Vue 프로젝트에서는 `index.html`이 브라우저가 처음 읽는 HTML 진입점입니다. 이 파일 안에서 `src/main.js` 또는 `src/main.ts`를 모듈 스크립트로 불러옵니다. 그리고 `main.js`는 Vue 앱을 만들고 `App.vue`를 루트 컴포넌트로 연결합니다. `App.vue`는 화면의 가장 바깥 컴포넌트이고, 그 아래에 여러 컴포넌트가 자식처럼 배치됩니다.

중요한 것은 폴더 이름을 외우는 것이 아니라 흐름을 이해하는 것입니다. 브라우저는 HTML을 읽고, HTML은 JavaScript 진입 파일을 불러오고, JavaScript는 Vue 앱을 만들고, Vue 앱은 컴포넌트를 화면에 마운트합니다. 이 순서를 이해하면 에러가 났을 때 어느 지점을 봐야 할지 훨씬 빨리 판단할 수 있습니다.

## 이번 글에서 먼저 잡을 관점

이번 주제에서 가장 중요한 것은 문법을 외우는 것보다 흐름을 이해하는 것입니다. Vue 코드는 보통 상태를 준비한다 -> 템플릿에서 상태를 읽는다 -> 사용자 행동으로 상태가 바뀐다 -> Vue가 화면을 다시 맞춘다는 순서로 움직입니다. 이 순서를 머릿속에 두고 읽으면 새로운 문법을 만나도 훨씬 덜 흔들립니다.

또 하나 중요한 점은 Vue가 HTML, CSS, JavaScript를 대체하는 것이 아니라는 사실입니다. Vue는 이 세 가지를 더 구조적으로 연결해주는 도구입니다. 그래서 예제를 따라 칠 때도 "이 문법이 Vue에서만 특별한가?", "아니면 원래 HTML/JavaScript 개념을 Vue 방식으로 연결한 것인가?"를 나누어 생각하면 좋습니다.

처음에는 한 번에 완벽하게 이해하지 못해도 괜찮습니다. 대신 예제 코드를 조금씩 바꿔보면서 어떤 값이 바뀌면 화면의 어느 부분이 바뀌는지 확인해보세요. 손으로 바꿔본 경험이 쌓이면, 단순히 읽기만 했을 때보다 훨씬 빠르게 감이 잡힙니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: `public`과 `src/assets`를 헷갈리기 쉽습니다. 빌드 도구가 처리해야 하는 파일은 보통 `src/assets`에서 import하고, 그대로 복사해 제공할 파일은 `public`에 둡니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: `App.vue`에 모든 코드를 계속 쌓으면 금방 읽기 어려워집니다. 처음에는 괜찮지만 반복되는 UI가 보이면 컴포넌트 분리를 고민해야 합니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: `main.js`에 화면 로직을 많이 넣으면 시작 파일이 복잡해집니다. 앱 등록, 플러그인 등록, 마운트처럼 시작에 필요한 코드만 두는 편이 좋습니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.

에러를 만났을 때는 먼저 터미널 로그와 브라우저 개발자 도구 Console을 함께 봐야 합니다. Vue 프로젝트는 빌드 단계에서 나는 오류와 브라우저 실행 중에 나는 오류가 다를 수 있습니다. 터미널은 정상처럼 보여도 브라우저 콘솔에는 컴포넌트 렌더링 오류가 남아 있을 수 있고, 반대로 브라우저를 열기도 전에 Vite 개발 서버가 실패하는 경우도 있습니다.

## 실무에서 생각할 점

처음부터 완벽한 폴더 구조를 만들려고 하면 오히려 학습이 느려집니다. 작은 프로젝트는 기본 구조를 유지하고, 기능이 늘어날 때 `components`, `pages`, `composables`, `stores`처럼 역할을 나누는 편이 자연스럽습니다. 구조는 외우는 것이 아니라 복잡도를 줄이기 위해 조금씩 도입하는 도구입니다.

실무에서는 "동작한다"만으로는 부족한 경우가 많습니다. 다른 사람이 읽었을 때 의도를 이해할 수 있는지, 요구사항이 조금 바뀌어도 고치기 쉬운지, 에러 상황에서도 사용자가 무엇을 해야 하는지 알 수 있는지가 중요합니다. 입문 시리즈에서 계속 예제와 주의사항을 함께 보는 이유도 여기에 있습니다. 문법을 하나 배울 때마다 그 문법이 실패할 수 있는 지점까지 같이 봐야 실제 프로젝트에서 덜 흔들립니다.

## 오늘 내용 정리

이번 글에서는 $(System.Collections.Specialized.OrderedDictionary.Title) 주제를 중심으로 Vue의 기본 흐름을 살펴봤습니다. 핵심은 Vue 문법을 낱개로 외우는 것이 아니라, 상태와 템플릿과 이벤트가 서로 어떻게 연결되는지 보는 것입니다. 같은 예제라도 값을 바꿔보고, 함수 이름을 일부러 틀려보고, 조건을 반대로 바꿔보면 훨씬 깊게 이해할 수 있습니다.

다음 글로 넘어가기 전에 예제 코드를 그대로 한 번 작성해보시고, 최소한 한 군데는 직접 바꿔보시는 것을 추천드립니다. 버튼 문구를 바꾸거나, 상태 초기값을 바꾸거나, 조건을 하나 추가하는 정도면 충분합니다. 그렇게 작은 변화를 직접 만들어보면 "아, 이 부분이 화면과 연결되어 있구나"라는 감각이 생깁니다.
