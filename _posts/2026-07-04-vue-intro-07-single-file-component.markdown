Vue에서 가장 자주 만나는 파일 확장자는 `.vue`입니다. 이 파일을 Single File Component, 줄여서 SFC라고 부릅니다. 이름 그대로 컴포넌트 하나에 필요한 템플릿, 로직, 스타일을 한 파일 안에 모아둔 형식입니다. 처음에는 HTML, JavaScript, CSS를 한 파일에 넣는 것이 이상해 보일 수 있습니다. 기존 웹 개발에서는 파일을 종류별로 나누는 경우가 많기 때문입니다.

하지만 컴포넌트 기준으로 생각하면 SFC는 꽤 자연스럽습니다. 버튼 컴포넌트라면 버튼의 HTML 구조, 클릭했을 때의 동작, 버튼 스타일이 서로 강하게 연결되어 있습니다. 이 셋을 완전히 다른 파일에 흩어두면 컴포넌트 하나를 이해하기 위해 여러 파일을 계속 왔다 갔다 해야 합니다. SFC는 "한 UI 조각을 이해하는 데 필요한 것들을 가까이 둔다"는 장점이 있습니다.

물론 브라우저가 `.vue` 파일을 그대로 이해하는 것은 아닙니다. Vite와 Vue 플러그인이 SFC를 읽어서 브라우저가 실행할 수 있는 JavaScript와 CSS로 변환합니다. 그래서 SFC는 빌드 도구와 함께 사용할 때 특히 자연스럽습니다.

## 이번 글에서 먼저 잡을 관점

이번 주제에서 가장 중요한 것은 문법을 외우는 것보다 흐름을 이해하는 것입니다. Vue 코드는 보통 상태를 준비한다 -> 템플릿에서 상태를 읽는다 -> 사용자 행동으로 상태가 바뀐다 -> Vue가 화면을 다시 맞춘다는 순서로 움직입니다. 이 순서를 머릿속에 두고 읽으면 새로운 문법을 만나도 훨씬 덜 흔들립니다.

또 하나 중요한 점은 Vue가 HTML, CSS, JavaScript를 대체하는 것이 아니라는 사실입니다. Vue는 이 세 가지를 더 구조적으로 연결해주는 도구입니다. 그래서 예제를 따라 칠 때도 "이 문법이 Vue에서만 특별한가?", "아니면 원래 HTML/JavaScript 개념을 Vue 방식으로 연결한 것인가?"를 나누어 생각하면 좋습니다.

처음에는 한 번에 완벽하게 이해하지 못해도 괜찮습니다. 대신 예제 코드를 조금씩 바꿔보면서 어떤 값이 바뀌면 화면의 어느 부분이 바뀌는지 확인해보세요. 손으로 바꿔본 경험이 쌓이면, 단순히 읽기만 했을 때보다 훨씬 빠르게 감이 잡힙니다.

## 작은 실습으로 확인해보기

아래 예제는 SFC의 세 영역을 모두 사용합니다. 각 영역이 어떤 책임을 갖는지 주석을 따라가며 보시면 좋습니다.

{% raw %}
```vue
<script setup>
import { ref } from 'vue'

const name = ref('Vue')

function changeName() {
  name.value = 'Vue SFC'
}
</script>

<template>
  <article class="card">
    <h1>{{ name }} 배우기</h1>
    <p>한 파일 안에서 구조, 동작, 스타일을 함께 확인합니다.</p>
    <button @click="changeName">이름 바꾸기</button>
  </article>
</template>

<style scoped>
.card {
  padding: 20px;
  border: 1px solid #42b883;
  border-radius: 12px;
}

button {
  margin-top: 12px;
}
</style>
```
{% endraw %}

## 코드가 움직이는 순서

`<script setup>`에는 상태와 함수가 들어갑니다. `<template>`은 그 상태를 어떤 HTML 구조로 보여줄지 설명합니다. `<style scoped>`는 이 컴포넌트 안에서 사용할 스타일을 작성합니다. 버튼을 누르면 `changeName`이 실행되고 `name` 값이 바뀌며, 템플릿에서 그 값을 사용하는 제목도 함께 바뀝니다.

여기서 꼭 기억하셔야 할 부분은 Vue가 화면을 갱신해준다고 해서 개발자가 흐름을 몰라도 되는 것은 아니라는 점입니다. 오히려 Vue를 잘 쓰려면 상태가 어디에 있고, 어떤 이벤트나 함수가 그 상태를 바꾸며, 템플릿이 그 상태를 어떻게 읽는지 계속 추적할 수 있어야 합니다. 작은 예제부터 이 흐름을 말로 설명해보면 나중에 코드가 길어져도 훨씬 덜 막힙니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: SFC는 브라우저가 직접 실행하는 파일이 아니라 빌드 도구가 변환하는 파일입니다. 빌드 설정이 깨지면 `.vue` 파일을 해석하지 못하는 오류가 날 수 있습니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: `scoped`를 붙였다고 모든 스타일 문제가 사라지는 것은 아닙니다. 자식 컴포넌트 내부까지 깊게 영향을 주려면 별도의 문법이 필요하고, 전역 스타일과의 관계도 생각해야 합니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: 한 SFC 안에 너무 많은 책임을 넣으면 장점이 줄어듭니다. 컴포넌트 하나가 너무 커지면 다시 작은 컴포넌트로 나누어야 합니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.

에러를 만났을 때는 먼저 터미널 로그와 브라우저 개발자 도구 Console을 함께 봐야 합니다. Vue 프로젝트는 빌드 단계에서 나는 오류와 브라우저 실행 중에 나는 오류가 다를 수 있습니다. 터미널은 정상처럼 보여도 브라우저 콘솔에는 컴포넌트 렌더링 오류가 남아 있을 수 있고, 반대로 브라우저를 열기도 전에 Vite 개발 서버가 실패하는 경우도 있습니다.

## 실무에서 생각할 점

SFC는 Vue의 큰 장점이지만, 모든 상황에서 하나의 파일이 무조건 좋다는 뜻은 아닙니다. 공통 유틸 함수, API 호출 함수, 타입 정의처럼 UI와 직접 묶이지 않는 코드는 별도 파일로 분리하는 편이 좋습니다. SFC는 UI 단위 응집도를 높이는 도구라고 이해하면 안전합니다.

실무에서는 "동작한다"만으로는 부족한 경우가 많습니다. 다른 사람이 읽었을 때 의도를 이해할 수 있는지, 요구사항이 조금 바뀌어도 고치기 쉬운지, 에러 상황에서도 사용자가 무엇을 해야 하는지 알 수 있는지가 중요합니다. 입문 시리즈에서 계속 예제와 주의사항을 함께 보는 이유도 여기에 있습니다. 문법을 하나 배울 때마다 그 문법이 실패할 수 있는 지점까지 같이 봐야 실제 프로젝트에서 덜 흔들립니다.

## 오늘 내용 정리

이번 글에서는 $(System.Collections.Specialized.OrderedDictionary.Title) 주제를 중심으로 Vue의 기본 흐름을 살펴봤습니다. 핵심은 Vue 문법을 낱개로 외우는 것이 아니라, 상태와 템플릿과 이벤트가 서로 어떻게 연결되는지 보는 것입니다. 같은 예제라도 값을 바꿔보고, 함수 이름을 일부러 틀려보고, 조건을 반대로 바꿔보면 훨씬 깊게 이해할 수 있습니다.

다음 글로 넘어가기 전에 예제 코드를 그대로 한 번 작성해보시고, 최소한 한 군데는 직접 바꿔보시는 것을 추천드립니다. 버튼 문구를 바꾸거나, 상태 초기값을 바꾸거나, 조건을 하나 추가하는 정도면 충분합니다. 그렇게 작은 변화를 직접 만들어보면 "아, 이 부분이 화면과 연결되어 있구나"라는 감각이 생깁니다.
