프론트엔드 개발을 처음 시작하면 HTML, CSS, JavaScript만으로도 화면을 만들 수 있습니다. 버튼을 누르면 숫자를 올리고, 입력창에 글을 쓰면 다른 영역에 표시하고, 목록을 추가하거나 삭제하는 정도는 순수 JavaScript로도 충분히 가능합니다. 그런데 화면이 조금만 커지면 문제가 생깁니다. 어떤 값이 바뀌었을 때 어떤 DOM을 다시 찾아야 하는지, 이벤트가 여러 곳에서 발생할 때 상태를 어디에 보관해야 하는지, 같은 UI 조각을 여러 화면에서 재사용하려면 코드를 어떻게 나눠야 하는지 계속 고민하게 됩니다.

Vue는 바로 이 지점에서 도움을 줍니다. Vue의 핵심은 "데이터가 바뀌면 화면도 그에 맞춰 바뀐다"는 흐름을 개발자가 직접 DOM 조작 코드로 매번 작성하지 않게 해주는 것입니다. 공식 문서에서도 Vue의 핵심 기능을 선언적 렌더링과 반응성으로 설명합니다. 선언적 렌더링은 "어떻게 DOM을 바꿀지"보다 "현재 상태라면 화면이 어떤 모습이어야 하는지"를 표현하는 방식이고, 반응성은 상태 변경을 추적해서 필요한 부분의 화면을 갱신하는 능력입니다.

입문 단계에서는 Vue를 마법처럼 이해하면 오히려 나중에 막히기 쉽습니다. Vue는 HTML을 없애는 도구도 아니고, JavaScript를 몰라도 되게 해주는 도구도 아닙니다. HTML, CSS, JavaScript 위에 컴포넌트와 반응성이라는 규칙을 올려서 화면 개발을 더 예측 가능하게 만드는 프레임워크라고 보는 편이 훨씬 안전합니다.

## 이번 글에서 먼저 잡을 관점

이번 주제에서 가장 중요한 것은 문법을 외우는 것보다 흐름을 이해하는 것입니다. Vue 코드는 보통 상태를 준비한다 -> 템플릿에서 상태를 읽는다 -> 사용자 행동으로 상태가 바뀐다 -> Vue가 화면을 다시 맞춘다는 순서로 움직입니다. 이 순서를 머릿속에 두고 읽으면 새로운 문법을 만나도 훨씬 덜 흔들립니다.

또 하나 중요한 점은 Vue가 HTML, CSS, JavaScript를 대체하는 것이 아니라는 사실입니다. Vue는 이 세 가지를 더 구조적으로 연결해주는 도구입니다. 그래서 예제를 따라 칠 때도 "이 문법이 Vue에서만 특별한가?", "아니면 원래 HTML/JavaScript 개념을 Vue 방식으로 연결한 것인가?"를 나누어 생각하면 좋습니다.

처음에는 한 번에 완벽하게 이해하지 못해도 괜찮습니다. 대신 예제 코드를 조금씩 바꿔보면서 어떤 값이 바뀌면 화면의 어느 부분이 바뀌는지 확인해보세요. 손으로 바꿔본 경험이 쌓이면, 단순히 읽기만 했을 때보다 훨씬 빠르게 감이 잡힙니다.

## 작은 실습으로 확인해보기

아래 예제는 버튼을 누를 때마다 숫자가 올라가는 아주 작은 Vue 컴포넌트입니다. 중요한 것은 버튼 클릭 이벤트에서 숫자만 바꾸고, DOM의 텍스트를 직접 찾아서 수정하지 않는다는 점입니다.

{% raw %}
```vue
<script setup>
import { ref } from 'vue'

const count = ref(0)

function increase() {
  count.value += 1
}
</script>

<template>
  <section>
    <h1>Vue 첫 예제</h1>
    <p>현재 숫자: {{ count }}</p>
    <button @click="increase">1 증가</button>
  </section>
</template>
```
{% endraw %}

## 코드가 움직이는 순서

처음 화면이 렌더링될 때 `count`는 0입니다. 버튼을 클릭하면 `increase` 함수가 실행되고 `count.value`가 1 증가합니다. Vue는 이 값이 화면에서 사용되고 있다는 사실을 알고 있기 때문에, 개발자가 `document.querySelector`로 `p` 태그를 찾아 다시 쓰지 않아도 화면을 갱신합니다. 이 흐름이 Vue를 배우는 첫 번째 감각입니다.

여기서 꼭 기억하셔야 할 부분은 Vue가 화면을 갱신해준다고 해서 개발자가 흐름을 몰라도 되는 것은 아니라는 점입니다. 오히려 Vue를 잘 쓰려면 상태가 어디에 있고, 어떤 이벤트나 함수가 그 상태를 바꾸며, 템플릿이 그 상태를 어떻게 읽는지 계속 추적할 수 있어야 합니다. 작은 예제부터 이 흐름을 말로 설명해보면 나중에 코드가 길어져도 훨씬 덜 막힙니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: Vue를 쓰면 JavaScript를 몰라도 된다고 생각하면 안 됩니다. Vue는 JavaScript 위에서 동작하므로 변수, 함수, 배열, 객체, 이벤트 흐름은 반드시 같이 이해해야 합니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: 처음부터 상태 관리, 라우터, 빌드 최적화까지 한 번에 보려고 하면 Vue가 너무 크게 느껴집니다. 처음에는 데이터 하나가 화면과 연결되는 흐름부터 잡는 것이 좋습니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: Vue가 DOM을 갱신해준다고 해서 DOM 구조를 전혀 생각하지 않아도 되는 것은 아닙니다. 접근성, 시맨틱 태그, CSS 구조는 여전히 개발자가 책임져야 합니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.

에러를 만났을 때는 먼저 터미널 로그와 브라우저 개발자 도구 Console을 함께 봐야 합니다. Vue 프로젝트는 빌드 단계에서 나는 오류와 브라우저 실행 중에 나는 오류가 다를 수 있습니다. 터미널은 정상처럼 보여도 브라우저 콘솔에는 컴포넌트 렌더링 오류가 남아 있을 수 있고, 반대로 브라우저를 열기도 전에 Vite 개발 서버가 실패하는 경우도 있습니다.

## 실무에서 생각할 점

Vue는 작은 화면부터 큰 SPA까지 점진적으로 확장하기 좋습니다. 하지만 단순한 정적 페이지에 버튼 한두 개만 있는 상황이라면 Vue 프로젝트 전체를 도입하는 것이 과할 수 있습니다. 반대로 상태와 화면이 자주 맞물리고, 같은 UI 조각을 여러 번 재사용하며, API 응답에 따라 화면이 계속 바뀌는 서비스라면 Vue의 장점이 빠르게 드러납니다.

실무에서는 "동작한다"만으로는 부족한 경우가 많습니다. 다른 사람이 읽었을 때 의도를 이해할 수 있는지, 요구사항이 조금 바뀌어도 고치기 쉬운지, 에러 상황에서도 사용자가 무엇을 해야 하는지 알 수 있는지가 중요합니다. 입문 시리즈에서 계속 예제와 주의사항을 함께 보는 이유도 여기에 있습니다. 문법을 하나 배울 때마다 그 문법이 실패할 수 있는 지점까지 같이 봐야 실제 프로젝트에서 덜 흔들립니다.

## 오늘 내용 정리

이번 글에서는 $(System.Collections.Specialized.OrderedDictionary.Title) 주제를 중심으로 Vue의 기본 흐름을 살펴봤습니다. 핵심은 Vue 문법을 낱개로 외우는 것이 아니라, 상태와 템플릿과 이벤트가 서로 어떻게 연결되는지 보는 것입니다. 같은 예제라도 값을 바꿔보고, 함수 이름을 일부러 틀려보고, 조건을 반대로 바꿔보면 훨씬 깊게 이해할 수 있습니다.

다음 글로 넘어가기 전에 예제 코드를 그대로 한 번 작성해보시고, 최소한 한 군데는 직접 바꿔보시는 것을 추천드립니다. 버튼 문구를 바꾸거나, 상태 초기값을 바꾸거나, 조건을 하나 추가하는 정도면 충분합니다. 그렇게 작은 변화를 직접 만들어보면 "아, 이 부분이 화면과 연결되어 있구나"라는 감각이 생깁니다.
