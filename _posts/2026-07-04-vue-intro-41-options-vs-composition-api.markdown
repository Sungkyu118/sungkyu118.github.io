Vue를 공부하다 보면 Options API와 Composition API라는 두 가지 스타일을 만납니다. Options API는 `data`, `methods`, `computed`, `mounted`처럼 역할별 옵션에 코드를 배치합니다. Composition API는 `setup` 범위 안에서 반응형 상태와 함수를 직접 선언하고 조합합니다. 둘은 서로 완전히 다른 프레임워크가 아니라 Vue 컴포넌트 로직을 표현하는 방식의 차이입니다.

Options API는 입문자가 보기 편한 장점이 있습니다. 데이터는 data에, 함수는 methods에, 계산값은 computed에 있기 때문에 위치가 명확합니다. 반면 컴포넌트가 커지면 하나의 기능과 관련된 상태, 함수, watch가 여러 옵션에 흩어질 수 있습니다.

Composition API는 기능 단위로 코드를 모으기 좋습니다. 예를 들어 검색 기능과 모달 기능이 한 컴포넌트에 있을 때, 검색 관련 상태와 함수는 가까이 두고 모달 관련 상태와 함수도 가까이 둘 수 있습니다. 대신 자유도가 높은 만큼 기준 없이 작성하면 오히려 더 난잡해질 수 있습니다.

## 이번 글에서 먼저 잡을 관점

이번 구간부터는 Vue를 단순히 한 파일 안에서 쓰는 단계에서 벗어나, 여러 컴포넌트가 함께 동작하는 구조를 다룹니다. 그래서 문법 하나만 보는 것보다 역할과 책임을 같이 보는 것이 중요합니다. 부모 컴포넌트가 무엇을 알고 있어야 하는지, 자식 컴포넌트는 어디까지 책임져야 하는지, 사용자의 행동을 어느 방향으로 전달해야 하는지 계속 질문하면서 읽어보시면 좋습니다.

컴포넌트 설계는 처음부터 완벽하게 나누는 일이 아닙니다. 작은 화면을 만들고, 반복되는 부분이나 책임이 분명한 부분을 발견하고, 그때 적절히 분리하는 과정에 가깝습니다. 이 글의 예제도 정답이라기보다 기준을 잡기 위한 출발점으로 봐주세요. 직접 이름을 바꿔보고, props를 하나 추가해보고, 이벤트 흐름을 바꿔보면 훨씬 오래 기억에 남습니다.

## 작은 실습으로 확인해보기

아래 예제는 같은 카운터를 Options API와 Composition API로 비교합니다.

{% raw %}
```vue
<!-- Options API -->
<script>
export default {
  data() {
    return {
      count: 0
    }
  },
  methods: {
    increase() {
      this.count += 1
    }
  }
}
</script>

<!-- Composition API -->
<script setup>
import { ref } from 'vue'

const count = ref(0)

function increase() {
  count.value += 1
}
</script>

<template>
  <button @click="increase">현재 값: {{ count }}</button>
</template>
```
{% endraw %}

## 코드가 움직이는 순서

Options API에서는 `this.count`로 컴포넌트 인스턴스의 상태에 접근합니다. Composition API에서는 `ref`로 만든 `count`를 함수 스코프에서 직접 사용하고, 스크립트에서는 `.value`로 수정합니다. `<script setup>`을 쓰면 템플릿에 노출하기 위해 return을 작성하지 않아도 됩니다.

여기서 중요한 것은 코드 줄 수보다 의도입니다. 컴포넌트를 나누면 파일은 늘어나지만, 각 파일이 맡는 역할이 선명해져야 합니다. 부모는 전체 상태와 흐름을 관리하고, 자식은 자신이 맡은 UI 조각을 표현하거나 사용자 행동을 이벤트로 알려주는 식으로 역할을 나누면 디버깅이 훨씬 쉬워집니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: Options API가 낡았고 Composition API만 무조건 맞다고 생각할 필요는 없습니다. 기존 프로젝트와 팀 기준을 존중해야 합니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: Composition API는 자유도가 높기 때문에 기능 단위로 묶는 습관이 없으면 오히려 읽기 어려워질 수 있습니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 두 스타일을 한 컴포넌트 안에서 무리하게 섞으면 입문자에게 특히 혼란스럽습니다. 학습 단계에서는 한 스타일을 기준으로 연습하세요. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.

컴포넌트 관련 오류는 한 파일만 봐서는 바로 보이지 않을 때가 많습니다. 부모가 넘기는 prop 이름, 자식이 선언한 prop 이름, 자식이 emit하는 이벤트 이름, 부모가 듣는 이벤트 이름을 한 줄씩 맞춰보는 습관이 필요합니다. 브라우저 콘솔의 Vue warning도 그냥 넘기지 말고, 어떤 컴포넌트에서 발생했는지 확인해보시면 좋습니다.

## 실무에서 생각할 점

새 Vue 3 프로젝트에서는 Composition API와 `<script setup>` 조합을 많이 사용합니다. 하지만 Options API를 이해하면 오래된 예제와 기존 프로젝트를 읽는 데 도움이 됩니다. 두 스타일의 차이를 알아두면 검색 자료를 볼 때 버전과 문법을 구분할 수 있어 학습이 훨씬 안정적입니다.

실무에서는 컴포넌트가 "동작한다"보다 "변경에 견딘다"가 더 중요해집니다. 요구사항은 계속 바뀌고, 디자인도 바뀌고, 같은 컴포넌트를 다른 화면에서 쓰고 싶어질 수 있습니다. 그래서 처음부터 모든 것을 일반화하려고 하기보다, 현재 책임을 명확히 하고 나중에 반복이 보일 때 재사용성을 높이는 방향이 안전합니다.
