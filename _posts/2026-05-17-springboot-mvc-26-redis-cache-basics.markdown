# SpringBoot 입문 26: Redis 캐시 기본 적용

> 이 글에서는 Redis 캐시를 처음 붙일 때 어떤 메서드에 캐시를 둘지와 무효화 포인트를 고민하는 기준을 다룹니다.

조회가 많은 API는 캐시를 적용하면 응답 속도를 크게 개선할 수 있다.

## 핵심 포인트
- `@Cacheable`로 읽기 캐시 적용
- `@CacheEvict`로 데이터 변경 시 캐시 무효화
- TTL 설정으로 오래된 데이터 자동 정리

## 정리
캐시는 성능 향상 도구이지만, 데이터 일관성 기준을 먼저 정하고 적용해야 운영 안정성이 높아진다.

<!-- codex-springboot-detail:start -->

## 여기서 한 단계 더 이해해보겠습니다

캐시는 같은 데이터를 반복해서 조회하는 상황에서 응답 속도를 크게 개선할 수 있는 좋은 도구입니다. 특히 읽기 비중이 높고, 자주 바뀌지 않는 데이터라면 DB를 매번 치는 대신 메모리 캐시를 활용하는 것이 효과적일 수 있습니다. Spring Boot에서는 캐시 추상화 덕분에 비교적 간단하게 시작해볼 수 있습니다.

다만 캐시는 단순히 붙이기만 하면 끝나는 기능이 아닙니다. "언제 저장할지", "언제 지울지", "데이터가 바뀌면 어떻게 무효화할지"까지 같이 생각하셔야 합니다. 그래서 입문 단계에서는 `@Cacheable`의 편리함과 함께 캐시 무효화의 중요성을 같이 배우시는 편이 좋습니다.

이 주제에서 특히 중요하게 보셔야 하는 부분은 읽기 메서드에 캐시를 붙이고, 쓰기 작업에서는 적절히 캐시를 비우는 기본 전략 입니다. 처음 읽으실 때는 모든 문장을 외우려고 하기보다, 코드가 어느 계층에 놓이고 어떤 순서로 실행되는지를 천천히 따라가보시면 좋습니다. Spring Boot 학습은 각각의 기술을 따로 외우는 공부라기보다, 여러 조각이 실제 요청 흐름 안에서 어떻게 맞물리는지 이해하는 과정에 가깝습니다.

## 예시 코드로 흐름을 잡아보겠습니다

```java
@Configuration
@EnableCaching
public class CacheConfig {
}
```
```java
@Service
public class ProductService {

  @Cacheable(value = "product", key = "#id")
  public ProductResponse getProduct(Long id) {
    return findProductFromDatabase(id);
  }

  @CacheEvict(value = "product", key = "#id")
  public void updateProduct(Long id, UpdateProductRequest request) {
    updateProductInDatabase(id, request);
  }
}
```

위 예시는 Redis 캐시을 가장 작게 체험할 수 있는 흐름으로 구성했습니다. 처음에는 코드 한 줄 한 줄의 문법보다, 선언 위치와 실행 시점을 중심으로 읽어보시는 편이 훨씬 이해가 잘 되실 것입니다. 예를 들어 설정 클래스인지, Controller인지, Service인지에 따라 책임이 달라지고, 그 책임이 곧 Spring Boot 구조를 읽는 기준이 됩니다.

또 하나 중요한 점은 '지금 당장 돌아가는 코드'와 '나중에도 유지보수하기 쉬운 코드'는 조금 다를 수 있다는 사실입니다. 그래서 예제를 실행해보신 뒤에는 변수명, 메서드명, 경로, 설정 값을 직접 한두 번 바꿔보시면서 어떤 부분이 고정 규칙이고 어떤 부분이 프로젝트 상황에 따라 달라지는지 구분해보시면 정말 큰 도움이 됩니다.

## 자주 하는 실수와 에러도 같이 보겠습니다

- 조회 메서드에 캐시를 붙여놓고 수정 메서드에서 캐시를 비우지 않으면 오래된 데이터가 계속 반환될 수 있습니다.
- 캐시 키를 너무 단순하게 잡으면 서로 다른 조건의 조회가 같은 키를 공유해 잘못된 결과를 돌려줄 수 있습니다.
- 모든 데이터를 캐시하려고 하면 오히려 메모리 낭비와 복잡성만 커질 수 있습니다.

이런 실수들은 대부분 개념을 몰라서라기보다, 실행 순서나 설정 위치를 한 번에 다 보지 못해서 생깁니다. 그래서 에러가 나면 조급하게 코드를 많이 바꾸기보다, 로그와 요청 흐름을 기준으로 '어디까지는 정상이고 어디서부터 어긋났는지'를 차분히 확인해보시는 편이 좋습니다.

## 실무에서는 이렇게 적용하시면 좋습니다

- 처음에는 정말 자주 읽히고 자주 바뀌지 않는 데이터 한두 개에만 캐시를 적용해보시는 것이 좋습니다.
- 캐시 적용 전후 응답 시간과 DB 조회 횟수를 비교해보면 효과를 더 분명하게 느끼실 수 있습니다.
- 캐시는 성능 도구이면서 동시에 일관성 관리 주제이기도 하다는 점을 늘 같이 생각하시면 좋습니다.

처음부터 완벽한 구조를 만들려고 하실 필요는 없습니다. 다만 작은 예제라도 책임 분리, 예외 처리, 설정 관리, 로그 확인 같은 기본 습관을 함께 가져가시면 나중에 프로젝트가 커졌을 때 훨씬 덜 흔들리게 됩니다. 특히 Spring Boot는 편의 기능이 많아서 '왜 이렇게 동작하는지'를 놓치기 쉬우므로, 동작 원리를 설명할 수 있을 정도로 천천히 정리해두시는 것이 좋습니다.
