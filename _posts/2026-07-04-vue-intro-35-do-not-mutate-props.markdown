# Vue 입문 35: props를 직접 수정하면 안 되는 이유

> props는 자식의 입력값이며, 수정 요청은 emit으로 부모에게 올리는 것이 안전하다는 기준을 배웁니다.

Vue에서 props는 부모가 자식에게 내려준 값입니다. 그래서 자식 컴포넌트 입장에서는 "읽을 수 있는 입력값"으로 보는 것이 안전합니다. props를 직접 수정하려고 하면 Vue는 경고를 줄 수 있고, 더 큰 문제는 데이터 흐름이 불명확해진다는 점입니다.

부모가 상태를 갖고 있고 자식에게 props로 내려줬는데, 자식이 그 값을 마음대로 바꾸면 부모 입장에서는 언제 상태가 바뀌었는지 추적하기 어렵습니다. 특히 같은 데이터를 여러 자식에게 내려주는 경우, 어느 자식이 값을 바꿨는지 찾기 힘들어집니다. 그래서 Vue의 기본 사고방식은 단방향 데이터 흐름입니다. 부모가 값을 내려주고, 자식은 변경이 필요하면 이벤트로 요청합니다.

물론 자식 안에서 초기값을 받아 로컬로 편집해야 하는 경우도 있습니다. 예를 들어 수정 폼에서 부모가 넘겨준 사용자 정보를 자식이 입력 폼으로 편집한 뒤 저장 버튼을 누를 때만 부모에게 알려줄 수 있습니다. 이때는 props를 직접 바꾸는 것이 아니라 로컬 상태를 따로 만들고, 저장 시 emit으로 결과를 올리는 방식이 좋습니다.

## 이번 글에서 먼저 잡을 관점

이번 구간부터는 Vue를 단순히 한 파일 안에서 쓰는 단계에서 벗어나, 여러 컴포넌트가 함께 동작하는 구조를 다룹니다. 그래서 문법 하나만 보는 것보다 역할과 책임을 같이 보는 것이 중요합니다. 부모 컴포넌트가 무엇을 알고 있어야 하는지, 자식 컴포넌트는 어디까지 책임져야 하는지, 사용자의 행동을 어느 방향으로 전달해야 하는지 계속 질문하면서 읽어보시면 좋습니다.

컴포넌트 설계는 처음부터 완벽하게 나누는 일이 아닙니다. 작은 화면을 만들고, 반복되는 부분이나 책임이 분명한 부분을 발견하고, 그때 적절히 분리하는 과정에 가깝습니다. 이 글의 예제도 정답이라기보다 기준을 잡기 위한 출발점으로 봐주세요. 직접 이름을 바꿔보고, props를 하나 추가해보고, 이벤트 흐름을 바꿔보면 훨씬 오래 기억에 남습니다.

## 작은 실습으로 확인해보기

아래 예제는 props를 직접 수정하지 않고 로컬 폼 상태를 만든 뒤 저장 이벤트를 올리는 방식입니다.

```vue
<!-- UserEditForm.vue -->
<script setup>
import { reactive } from 'vue'

const props = defineProps({
  user: {
    type: Object,
    required: true
  }
})

const emit = defineEmits(['save'])

const form = reactive({
  name: props.user.name,
  email: props.user.email
})

function submitForm() {
  emit('save', {
    id: props.user.id,
    name: form.name,
    email: form.email
  })
}
</script>

<template>
  <form @submit.prevent="submitForm">
    <input v-model="form.name" />
    <input v-model="form.email" />
    <button type="submit">저장</button>
  </form>
</template>
```

## 코드가 움직이는 순서

부모가 넘긴 `user` prop을 직접 수정하지 않습니다. 대신 `form`이라는 로컬 상태를 만들고, 입력창은 이 로컬 상태와 연결합니다. 사용자가 저장 버튼을 누르면 `save` 이벤트로 변경 결과를 부모에게 전달합니다. 부모는 이 이벤트를 받아 실제 사용자 목록이나 API 요청을 처리합니다.

여기서 중요한 것은 코드 줄 수보다 의도입니다. 컴포넌트를 나누면 파일은 늘어나지만, 각 파일이 맡는 역할이 선명해져야 합니다. 부모는 전체 상태와 흐름을 관리하고, 자식은 자신이 맡은 UI 조각을 표현하거나 사용자 행동을 이벤트로 알려주는 식으로 역할을 나누면 디버깅이 훨씬 쉬워집니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: props 객체의 내부 속성을 직접 바꾸는 것도 결국 부모 상태를 우회해서 바꾸는 문제가 될 수 있습니다. 객체 prop은 특히 조심해야 합니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 로컬 복사본을 만들면 부모 prop이 나중에 바뀌었을 때 로컬 상태와 동기화할지 고민해야 합니다. 수정 폼에서는 열릴 때마다 초기화하는 패턴을 고려하세요. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 저장과 취소가 있는 폼이라면 props 직접 수정은 취소 기능을 어렵게 만듭니다. 로컬 상태를 두는 편이 훨씬 안전합니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.

컴포넌트 관련 오류는 한 파일만 봐서는 바로 보이지 않을 때가 많습니다. 부모가 넘기는 prop 이름, 자식이 선언한 prop 이름, 자식이 emit하는 이벤트 이름, 부모가 듣는 이벤트 이름을 한 줄씩 맞춰보는 습관이 필요합니다. 브라우저 콘솔의 Vue warning도 그냥 넘기지 말고, 어떤 컴포넌트에서 발생했는지 확인해보시면 좋습니다.

## 실무에서 생각할 점

props 직접 수정은 작은 예제에서는 빨라 보이지만, 실무에서는 추적하기 어려운 버그를 만듭니다. 로컬 상태와 emit 패턴은 코드가 조금 길어지지만 저장, 취소, 검증, API 실패 처리까지 자연스럽게 확장할 수 있습니다.

실무에서는 컴포넌트가 "동작한다"보다 "변경에 견딘다"가 더 중요해집니다. 요구사항은 계속 바뀌고, 디자인도 바뀌고, 같은 컴포넌트를 다른 화면에서 쓰고 싶어질 수 있습니다. 그래서 처음부터 모든 것을 일반화하려고 하기보다, 현재 책임을 명확히 하고 나중에 반복이 보일 때 재사용성을 높이는 방향이 안전합니다.
