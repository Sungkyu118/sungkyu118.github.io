웹 화면에는 목록이 정말 많이 나옵니다. 게시글 목록, 댓글 목록, 상품 목록, 알림 목록, 장바구니 목록 모두 배열 데이터를 화면에 반복해서 그리는 구조입니다. Vue에서는 `v-for`를 사용해 배열을 순회하며 요소를 렌더링합니다.

입문자가 자주 놓치는 부분은 `key`입니다. Vue는 목록을 효율적으로 갱신하기 위해 각 항목을 구분할 단서가 필요합니다. 이때 `key`가 안정적인 식별자 역할을 합니다. `key`가 없거나 배열 인덱스를 무조건 key로 쓰면 항목 삭제, 정렬, 삽입 시 화면 상태가 엉뚱한 항목에 붙는 문제가 생길 수 있습니다.

특히 입력창이 들어 있는 목록에서 이 문제가 잘 드러납니다. 첫 번째 항목을 삭제했는데 두 번째 항목의 입력 상태가 이상하게 이동하는 식입니다. 그래서 실무에서는 가능하면 서버에서 내려준 id나 클라이언트에서 생성한 고유 id를 key로 사용합니다.

## 이번 글에서 먼저 잡을 관점

이번 주제에서 가장 중요한 것은 문법을 외우는 것보다 흐름을 이해하는 것입니다. Vue 코드는 보통 상태를 준비한다 -> 템플릿에서 상태를 읽는다 -> 사용자 행동으로 상태가 바뀐다 -> Vue가 화면을 다시 맞춘다는 순서로 움직입니다. 이 순서를 머릿속에 두고 읽으면 새로운 문법을 만나도 훨씬 덜 흔들립니다.

또 하나 중요한 점은 Vue가 HTML, CSS, JavaScript를 대체하는 것이 아니라는 사실입니다. Vue는 이 세 가지를 더 구조적으로 연결해주는 도구입니다. 그래서 예제를 따라 칠 때도 "이 문법이 Vue에서만 특별한가?", "아니면 원래 HTML/JavaScript 개념을 Vue 방식으로 연결한 것인가?"를 나누어 생각하면 좋습니다.

처음에는 한 번에 완벽하게 이해하지 못해도 괜찮습니다. 대신 예제 코드를 조금씩 바꿔보면서 어떤 값이 바뀌면 화면의 어느 부분이 바뀌는지 확인해보세요. 손으로 바꿔본 경험이 쌓이면, 단순히 읽기만 했을 때보다 훨씬 빠르게 감이 잡힙니다.

## 작은 실습으로 확인해보기

아래 예제는 할 일 목록을 렌더링하고 삭제합니다. `todo.id`를 key로 사용해 각 항목을 안정적으로 구분합니다.

{% raw %}
```vue
<script setup>
import { ref } from 'vue'

const todos = ref([
  { id: 1, title: 'Vue 프로젝트 만들기', done: true },
  { id: 2, title: 'v-for 연습하기', done: false },
  { id: 3, title: 'key 역할 이해하기', done: false }
])

function removeTodo(id) {
  todos.value = todos.value.filter(todo => todo.id !== id)
}
</script>

<template>
  <ul>
    <li v-for="todo in todos" :key="todo.id">
      <span>{{ todo.done ? '완료' : '진행' }} - {{ todo.title }}</span>
      <button @click="removeTodo(todo.id)">삭제</button>
    </li>
  </ul>
</template>
```
{% endraw %}

## 코드가 움직이는 순서

`todos`는 배열 상태입니다. `v-for="todo in todos"`는 배열의 각 항목을 하나씩 꺼내 `li`를 만듭니다. `:key="todo.id"`는 Vue에게 이 `li`가 어떤 데이터 항목과 연결되는지 알려줍니다. 삭제 버튼을 누르면 해당 id를 제외한 새 배열을 만들고, Vue는 key를 기준으로 어떤 항목이 사라졌는지 판단합니다.

여기서 꼭 기억하셔야 할 부분은 Vue가 화면을 갱신해준다고 해서 개발자가 흐름을 몰라도 되는 것은 아니라는 점입니다. 오히려 Vue를 잘 쓰려면 상태가 어디에 있고, 어떤 이벤트나 함수가 그 상태를 바꾸며, 템플릿이 그 상태를 어떻게 읽는지 계속 추적할 수 있어야 합니다. 작은 예제부터 이 흐름을 말로 설명해보면 나중에 코드가 길어져도 훨씬 덜 막힙니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 목록 순서가 바뀔 수 있는 데이터에서 배열 index를 key로 쓰면 화면 상태가 꼬일 수 있습니다. 정렬, 삭제, 삽입이 있는 목록은 고유 id를 쓰는 것이 좋습니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: `v-for`와 `v-if`를 같은 요소에 함께 쓰면 가독성과 우선순위 문제가 생깁니다. 필터링된 목록을 computed로 만든 뒤 렌더링하는 방식을 추천합니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: key는 가능하면 문자열이나 숫자처럼 안정적인 원시 값을 사용하세요. 객체 전체를 key로 쓰면 의도대로 비교하기 어렵습니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.

에러를 만났을 때는 먼저 터미널 로그와 브라우저 개발자 도구 Console을 함께 봐야 합니다. Vue 프로젝트는 빌드 단계에서 나는 오류와 브라우저 실행 중에 나는 오류가 다를 수 있습니다. 터미널은 정상처럼 보여도 브라우저 콘솔에는 컴포넌트 렌더링 오류가 남아 있을 수 있고, 반대로 브라우저를 열기도 전에 Vite 개발 서버가 실패하는 경우도 있습니다.

## 실무에서 생각할 점

작은 정적 목록에서는 key 문제가 눈에 잘 보이지 않을 수 있습니다. 하지만 실제 서비스 목록은 삭제, 추가, 정렬, 필터링이 자주 일어납니다. key를 처음부터 안정적으로 지정하면 나중에 이상한 렌더링 버그를 크게 줄일 수 있습니다.

실무에서는 "동작한다"만으로는 부족한 경우가 많습니다. 다른 사람이 읽었을 때 의도를 이해할 수 있는지, 요구사항이 조금 바뀌어도 고치기 쉬운지, 에러 상황에서도 사용자가 무엇을 해야 하는지 알 수 있는지가 중요합니다. 입문 시리즈에서 계속 예제와 주의사항을 함께 보는 이유도 여기에 있습니다. 문법을 하나 배울 때마다 그 문법이 실패할 수 있는 지점까지 같이 봐야 실제 프로젝트에서 덜 흔들립니다.
