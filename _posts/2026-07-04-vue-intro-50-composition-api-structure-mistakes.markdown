Composition API는 Vue 3의 강력한 도구이지만, 처음 사용할 때는 자주 하는 실수가 있습니다. 가장 기본적인 실수는 스크립트에서 ref 값을 수정할 때 `.value`를 빼먹는 것입니다. 템플릿에서는 자동으로 풀리지만 스크립트에서는 직접 `.value`가 필요하다는 규칙을 잊기 쉽습니다.

두 번째는 기능 흐름을 흩어놓는 것입니다. 검색 기능의 상태는 위에 있고, computed는 중간에 있고, 검색 함수는 아래에 있으며, watch는 또 다른 곳에 있으면 한 기능을 이해하기 위해 파일 전체를 돌아다녀야 합니다. Composition API의 장점은 기능별로 로직을 모을 수 있다는 점이므로, 관련 코드를 가까이 두는 습관이 중요합니다.

세 번째는 watch 남용입니다. 계산 가능한 값은 computed로 두는 것이 더 안전합니다. watch는 상태 변화에 따른 API 호출, localStorage 저장, 외부 효과 처리처럼 부수 효과가 있을 때 사용하면 좋습니다. 모든 파생 값을 watch로 동기화하려고 하면 상태 버그가 늘어납니다.

## 이번 글에서 먼저 잡을 관점

이번 구간부터는 Vue를 단순히 한 파일 안에서 쓰는 단계에서 벗어나, 여러 컴포넌트가 함께 동작하는 구조를 다룹니다. 그래서 문법 하나만 보는 것보다 역할과 책임을 같이 보는 것이 중요합니다. 부모 컴포넌트가 무엇을 알고 있어야 하는지, 자식 컴포넌트는 어디까지 책임져야 하는지, 사용자의 행동을 어느 방향으로 전달해야 하는지 계속 질문하면서 읽어보시면 좋습니다.

컴포넌트 설계는 처음부터 완벽하게 나누는 일이 아닙니다. 작은 화면을 만들고, 반복되는 부분이나 책임이 분명한 부분을 발견하고, 그때 적절히 분리하는 과정에 가깝습니다. 이 글의 예제도 정답이라기보다 기준을 잡기 위한 출발점으로 봐주세요. 직접 이름을 바꿔보고, props를 하나 추가해보고, 이벤트 흐름을 바꿔보면 훨씬 오래 기억에 남습니다.

## 작은 실습으로 확인해보기

아래 예제는 Composition API에서 기능별로 정리된 작은 구조입니다.

{% raw %}
```vue
<script setup>
import { computed, ref, watch } from 'vue'

// 필터 기능
const keyword = ref('')
const items = ref(['Vue', 'Router', 'Pinia'])

const filteredItems = computed(() =>
  items.value.filter(item =>
    item.toLowerCase().includes(keyword.value.toLowerCase())
  )
)

watch(keyword, (value) => {
  localStorage.setItem('lastKeyword', value)
})

// 선택 기능
const selectedItem = ref(null)

function selectItem(item) {
  selectedItem.value = item
}
</script>

<template>
  <input v-model="keyword" />
  <button
    v-for="item in filteredItems"
    :key="item"
    @click="selectItem(item)"
  >
    {{ item }}
  </button>
</template>
```
{% endraw %}

## 코드가 움직이는 순서

필터 기능과 선택 기능을 나누어 배치했습니다. `filteredItems`는 계산 가능한 값이므로 computed입니다. `keyword` 변경 시 localStorage에 저장하는 것은 외부 부수 효과이므로 watch에 둡니다. 선택 동작은 사용자 이벤트로 발생하므로 함수로 표현했습니다.

여기서 중요한 것은 코드 줄 수보다 의도입니다. 컴포넌트를 나누면 파일은 늘어나지만, 각 파일이 맡는 역할이 선명해져야 합니다. 부모는 전체 상태와 흐름을 관리하고, 자식은 자신이 맡은 UI 조각을 표현하거나 사용자 행동을 이벤트로 알려주는 식으로 역할을 나누면 디버깅이 훨씬 쉬워집니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 스크립트에서 ref를 수정할 때 `.value`를 빼먹지 마세요. Composition API 입문 단계에서 가장 흔한 실수입니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: computed로 해결할 수 있는 값을 watch로 동기화하지 마세요. 원본과 파생 상태가 어긋나는 버그가 생길 수 있습니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 기능별 배치 기준이 없으면 Composition API 코드는 금방 읽기 어려워집니다. 관련 상태와 함수를 가까이 두세요. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.

컴포넌트 관련 오류는 한 파일만 봐서는 바로 보이지 않을 때가 많습니다. 부모가 넘기는 prop 이름, 자식이 선언한 prop 이름, 자식이 emit하는 이벤트 이름, 부모가 듣는 이벤트 이름을 한 줄씩 맞춰보는 습관이 필요합니다. 브라우저 콘솔의 Vue warning도 그냥 넘기지 말고, 어떤 컴포넌트에서 발생했는지 확인해보시면 좋습니다.

## 실무에서 생각할 점

Composition API는 큰 컴포넌트에서 기능별 로직을 모으기 좋습니다. 하지만 아무 규칙 없이 쓰면 Options API보다 더 자유롭게 망가질 수도 있습니다. 작은 기준을 세우고 반복해서 적용하는 것이 중요합니다.

실무에서는 컴포넌트가 "동작한다"보다 "변경에 견딘다"가 더 중요해집니다. 요구사항은 계속 바뀌고, 디자인도 바뀌고, 같은 컴포넌트를 다른 화면에서 쓰고 싶어질 수 있습니다. 그래서 처음부터 모든 것을 일반화하려고 하기보다, 현재 책임을 명확히 하고 나중에 반복이 보일 때 재사용성을 높이는 방향이 안전합니다.
