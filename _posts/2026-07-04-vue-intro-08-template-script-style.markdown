`.vue` 파일을 열면 보통 `<template>`, `<script>`, `<style>` 세 영역을 봅니다. 이 셋은 각각 따로 존재하는 것처럼 보이지만 실제로는 하나의 컴포넌트를 만들기 위해 연결됩니다. `<script>`는 데이터와 함수를 준비하고, `<template>`은 그 데이터와 함수를 사용해 화면 구조를 설명하며, `<style>`은 그 화면이 어떤 모양으로 보여야 하는지 정합니다.

입문자가 자주 하는 실수는 세 영역을 파일 안의 위치 정도로만 이해하는 것입니다. 더 중요한 것은 데이터 흐름입니다. 사용자가 버튼을 클릭하면 템플릿의 이벤트가 스크립트의 함수를 호출합니다. 함수는 상태를 바꿉니다. 상태가 바뀌면 템플릿에 표시되는 값이나 클래스가 바뀌고, 그 결과 스타일도 다르게 보일 수 있습니다.

이 연결 방식을 이해하면 Vue 코드를 읽을 때 시선 이동이 쉬워집니다. 화면에 보이는 글자를 바꾸고 싶다면 템플릿과 상태를 보고, 버튼 동작을 바꾸고 싶다면 이벤트와 함수를 보고, 색상이나 여백을 바꾸고 싶다면 스타일을 보면 됩니다.

## 이번 글에서 먼저 잡을 관점

이번 주제에서 가장 중요한 것은 문법을 외우는 것보다 흐름을 이해하는 것입니다. Vue 코드는 보통 상태를 준비한다 -> 템플릿에서 상태를 읽는다 -> 사용자 행동으로 상태가 바뀐다 -> Vue가 화면을 다시 맞춘다는 순서로 움직입니다. 이 순서를 머릿속에 두고 읽으면 새로운 문법을 만나도 훨씬 덜 흔들립니다.

또 하나 중요한 점은 Vue가 HTML, CSS, JavaScript를 대체하는 것이 아니라는 사실입니다. Vue는 이 세 가지를 더 구조적으로 연결해주는 도구입니다. 그래서 예제를 따라 칠 때도 "이 문법이 Vue에서만 특별한가?", "아니면 원래 HTML/JavaScript 개념을 Vue 방식으로 연결한 것인가?"를 나누어 생각하면 좋습니다.

처음에는 한 번에 완벽하게 이해하지 못해도 괜찮습니다. 대신 예제 코드를 조금씩 바꿔보면서 어떤 값이 바뀌면 화면의 어느 부분이 바뀌는지 확인해보세요. 손으로 바꿔본 경험이 쌓이면, 단순히 읽기만 했을 때보다 훨씬 빠르게 감이 잡힙니다.

## 작은 실습으로 확인해보기

아래 예제는 세 영역이 한 번에 연결되는 작은 카드입니다. 상태에 따라 버튼 문구와 클래스가 바뀌도록 구성했습니다.

{% raw %}
```vue
<script setup>
import { ref } from 'vue'

const isActive = ref(false)

function toggleActive() {
  isActive.value = !isActive.value
}
</script>

<template>
  <section class="panel" :class="{ active: isActive }">
    <h1>Vue 연결 흐름</h1>
    <p>{{ isActive ? '활성 상태입니다.' : '아직 비활성 상태입니다.' }}</p>
    <button @click="toggleActive">
      {{ isActive ? '비활성으로 변경' : '활성으로 변경' }}
    </button>
  </section>
</template>

<style scoped>
.panel {
  padding: 20px;
  border: 1px solid #ddd;
  border-radius: 12px;
}

.panel.active {
  border-color: #42b883;
  background: #ecfdf5;
}
</style>
```
{% endraw %}

## 코드가 움직이는 순서

`isActive`는 스크립트에 선언된 상태입니다. 템플릿에서는 이 값을 읽어서 문장을 바꾸고, `:class`로 `active` 클래스를 붙일지 결정합니다. 버튼을 클릭하면 `toggleActive` 함수가 실행되어 boolean 값이 반전됩니다. 스타일 영역의 `.panel.active` 규칙은 클래스가 붙었을 때만 적용됩니다.

여기서 꼭 기억하셔야 할 부분은 Vue가 화면을 갱신해준다고 해서 개발자가 흐름을 몰라도 되는 것은 아니라는 점입니다. 오히려 Vue를 잘 쓰려면 상태가 어디에 있고, 어떤 이벤트나 함수가 그 상태를 바꾸며, 템플릿이 그 상태를 어떻게 읽는지 계속 추적할 수 있어야 합니다. 작은 예제부터 이 흐름을 말로 설명해보면 나중에 코드가 길어져도 훨씬 덜 막힙니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 템플릿에서 사용하는 변수는 스크립트에 선언되어 있어야 합니다. 오타가 나면 화면에 값이 안 나오거나 런타임 경고를 볼 수 있습니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: 이벤트에서 호출하는 함수 이름이 실제 함수 이름과 다르면 클릭해도 아무 일도 일어나지 않습니다. 대소문자와 오타를 꼼꼼히 봐야 합니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: `scoped` 스타일을 사용해도 클래스 이름을 너무 대충 지으면 컴포넌트 안에서 의미가 흐려집니다. 상태를 드러내는 이름을 쓰는 것이 좋습니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.

에러를 만났을 때는 먼저 터미널 로그와 브라우저 개발자 도구 Console을 함께 봐야 합니다. Vue 프로젝트는 빌드 단계에서 나는 오류와 브라우저 실행 중에 나는 오류가 다를 수 있습니다. 터미널은 정상처럼 보여도 브라우저 콘솔에는 컴포넌트 렌더링 오류가 남아 있을 수 있고, 반대로 브라우저를 열기도 전에 Vite 개발 서버가 실패하는 경우도 있습니다.

## 실무에서 생각할 점

세 영역을 한 파일에 두면 작은 컴포넌트를 이해하기 쉽습니다. 하지만 상태 계산이 길어지면 템플릿이 지저분해지고, 스타일이 너무 길어지면 UI 구조를 찾기 어려워집니다. 이때는 computed, 컴포넌트 분리, 별도 CSS 전략을 고민하는 것이 좋습니다.

실무에서는 "동작한다"만으로는 부족한 경우가 많습니다. 다른 사람이 읽었을 때 의도를 이해할 수 있는지, 요구사항이 조금 바뀌어도 고치기 쉬운지, 에러 상황에서도 사용자가 무엇을 해야 하는지 알 수 있는지가 중요합니다. 입문 시리즈에서 계속 예제와 주의사항을 함께 보는 이유도 여기에 있습니다. 문법을 하나 배울 때마다 그 문법이 실패할 수 있는 지점까지 같이 봐야 실제 프로젝트에서 덜 흔들립니다.

다음 글로 넘어가기 전에 예제 코드를 그대로 한 번 작성해보시고, 최소한 한 군데는 직접 바꿔보시는 것을 추천드립니다. 버튼 문구를 바꾸거나, 상태 초기값을 바꾸거나, 조건을 하나 추가하는 정도면 충분합니다. 그렇게 작은 변화를 직접 만들어보면 "아, 이 부분이 화면과 연결되어 있구나"라는 감각이 생깁니다.
