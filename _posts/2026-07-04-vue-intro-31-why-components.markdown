# Vue 입문 31: 컴포넌트는 왜 나누는 걸까요?

Vue를 처음 배울 때는 `App.vue` 한 파일에 모든 코드를 작성해도 괜찮습니다. 버튼 하나, 입력창 하나, 작은 목록 하나 정도라면 한 파일에서 보는 편이 오히려 빠릅니다. 하지만 화면이 조금만 커지면 한 파일 안에 상태, 이벤트, 템플릿, 스타일이 계속 쌓이기 시작합니다. 이때부터는 "코드가 어디에 있는지"보다 "이 코드가 어떤 책임을 맡고 있는지"가 중요해집니다.

컴포넌트는 화면을 의미 있는 조각으로 나누는 단위입니다. 단순히 파일을 작게 만드는 기술이 아니라, 사용자가 보는 UI와 개발자가 이해해야 하는 책임을 같은 경계 안에 묶는 방법입니다. 예를 들어 할 일 앱을 만든다면 입력 폼, 목록, 목록 항목, 필터 버튼은 각각 다른 책임을 가질 수 있습니다. 이 조각들을 컴포넌트로 나누면 한 컴포넌트를 읽을 때 생각해야 하는 범위가 줄어듭니다.

좋은 컴포넌트 분리는 재사용보다 먼저 이해 가능성을 높입니다. 실무에서는 재사용되지 않는 컴포넌트도 충분히 의미가 있습니다. 특정 페이지에서 한 번만 쓰이더라도, 그 컴포넌트가 복잡한 영역을 독립적으로 설명해준다면 분리할 가치가 있습니다. 반대로 너무 빨리 나누면 파일만 많아져서 흐름을 따라가기 어려워질 수 있으므로 기준이 필요합니다.

## 이번 글에서 먼저 잡을 관점

이번 구간부터는 Vue를 단순히 한 파일 안에서 쓰는 단계에서 벗어나, 여러 컴포넌트가 함께 동작하는 구조를 다룹니다. 그래서 문법 하나만 보는 것보다 역할과 책임을 같이 보는 것이 중요합니다. 부모 컴포넌트가 무엇을 알고 있어야 하는지, 자식 컴포넌트는 어디까지 책임져야 하는지, 사용자의 행동을 어느 방향으로 전달해야 하는지 계속 질문하면서 읽어보시면 좋습니다.

컴포넌트 설계는 처음부터 완벽하게 나누는 일이 아닙니다. 작은 화면을 만들고, 반복되는 부분이나 책임이 분명한 부분을 발견하고, 그때 적절히 분리하는 과정에 가깝습니다. 이 글의 예제도 정답이라기보다 기준을 잡기 위한 출발점으로 봐주세요. 직접 이름을 바꿔보고, props를 하나 추가해보고, 이벤트 흐름을 바꿔보면 훨씬 오래 기억에 남습니다.

## 작은 실습으로 확인해보기

아래 예제는 모든 것을 App.vue에 넣는 대신, 할 일 목록 항목을 `TodoItem.vue`로 나누는 흐름을 보여줍니다.

{% raw %}
```vue
<!-- App.vue -->
<script setup>
import { ref } from 'vue'
import TodoItem from './components/TodoItem.vue'

const todos = ref([
  { id: 1, title: '컴포넌트 기준 이해하기', done: false },
  { id: 2, title: '작은 UI 조각으로 나누기', done: true }
])
</script>

<template>
  <main>
    <h1>오늘의 학습</h1>
    <ul>
      <TodoItem
        v-for="todo in todos"
        :key="todo.id"
        :todo="todo"
      />
    </ul>
  </main>
</template>

<!-- components/TodoItem.vue -->
<script setup>
defineProps({
  todo: {
    type: Object,
    required: true
  }
})
</script>

<template>
  <li>
    <span>{{ todo.done ? '완료' : '진행' }}</span>
    <strong>{{ todo.title }}</strong>
  </li>
</template>
```
{% endraw %}

## 코드가 움직이는 순서

처음에는 `App.vue`에서 `li` 전체를 직접 그릴 수도 있습니다. 하지만 항목 표시 방식이 길어지고, 완료 상태 스타일이나 버튼이 추가되면 목록 항목만 따로 읽고 수정하고 싶어집니다. 이때 `TodoItem.vue`로 나누면 부모는 목록을 순회하는 책임을 맡고, 자식은 항목 하나를 어떻게 보여줄지 맡습니다.

여기서 중요한 것은 코드 줄 수보다 의도입니다. 컴포넌트를 나누면 파일은 늘어나지만, 각 파일이 맡는 역할이 선명해져야 합니다. 부모는 전체 상태와 흐름을 관리하고, 자식은 자신이 맡은 UI 조각을 표현하거나 사용자 행동을 이벤트로 알려주는 식으로 역할을 나누면 디버깅이 훨씬 쉬워집니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 컴포넌트 분리는 파일을 많이 만드는 게임이 아닙니다. 분리했을 때 읽는 범위가 줄어드는지 확인해야 합니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 재사용 가능성만 기준으로 삼으면 한 번만 쓰이는 복잡한 영역을 계속 큰 파일에 남겨두게 됩니다. 이해 가능성도 중요한 기준입니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 반대로 너무 작은 컴포넌트를 무리하게 만들면 props와 emit만 늘어나서 흐름이 더 어려워질 수 있습니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.

컴포넌트 관련 오류는 한 파일만 봐서는 바로 보이지 않을 때가 많습니다. 부모가 넘기는 prop 이름, 자식이 선언한 prop 이름, 자식이 emit하는 이벤트 이름, 부모가 듣는 이벤트 이름을 한 줄씩 맞춰보는 습관이 필요합니다. 브라우저 콘솔의 Vue warning도 그냥 넘기지 말고, 어떤 컴포넌트에서 발생했는지 확인해보시면 좋습니다.

## 실무에서 생각할 점

컴포넌트를 나누면 각 파일의 책임이 선명해지지만, 부모와 자식 사이의 데이터 흐름을 이해해야 합니다. 그래서 컴포넌트 분리의 다음 단계는 props와 emit입니다. 화면을 나누는 감각과 데이터가 이동하는 방향을 함께 익히면 Vue 프로젝트 구조가 훨씬 안정적으로 보입니다.

실무에서는 컴포넌트가 "동작한다"보다 "변경에 견딘다"가 더 중요해집니다. 요구사항은 계속 바뀌고, 디자인도 바뀌고, 같은 컴포넌트를 다른 화면에서 쓰고 싶어질 수 있습니다. 그래서 처음부터 모든 것을 일반화하려고 하기보다, 현재 책임을 명확히 하고 나중에 반복이 보일 때 재사용성을 높이는 방향이 안전합니다.

다음 글로 넘어가기 전에 예제에서 컴포넌트 이름을 바꿔보거나, prop 하나를 추가하거나, emit 이벤트 이름을 일부러 틀려본 뒤 어떤 경고나 문제가 생기는지 확인해보세요. 이런 작은 실험은 실제 프로젝트에서 문제를 만났을 때 빠르게 원인을 좁히는 힘이 됩니다.
