# Redis 분산락: SET NX PX로 시작하는 실전 가이드 (주의점 포함)

분산락은 "중복 실행을 막고", "동시성으로 인한 데이터 꼬임"을 줄이기 위한 도구입니다. 하지만 잘못 쓰면 오히려 장애를 만들기 쉬운 영역이기도 해요.

이 글은 다음을 다룹니다.

1. 언제/왜 락을 쓰는지(트레이드오프)
2. Redis에서 가장 흔한 락 패턴(SET NX PX)
3. 락을 쓸 때 꼭 알아야 하는 함정과 방어
4. 대안 비교(Redisson, DB 락, 메시지 큐)

## 1) 언제/왜 쓰나 (트레이드오프)

### 분산락이 필요한 순간

- 동일 사용자/동일 리소스에 대해 "동시에 1번만" 처리되어야 함
- 캐시 스탬피드 방어: 만료 순간에 한 요청만 캐시를 재생성
- 결제/쿠폰/재고 등 중복 처리가 치명적인 케이스(단, 이 영역은 Redis 락만으로 부족할 수 있음)

### 단점/주의점

- 락이 풀리지 않으면 서비스가 멈춘 것처럼 보일 수 있음
- 락을 과하게 걸면 성능이 떨어지고 병목이 됨
- "락=정합성 보장"이 아니다. 최종 정합성은 DB/트랜잭션이 책임져야 함

## 2) 가장 흔한 패턴: SET NX PX

개념:

- `SET lockKey token NX PX ttlMs`
- 성공하면 락 획득, 실패하면 다른 누군가가 락 보유 중

여기서 `token`은 락 소유자를 식별하는 랜덤 값입니다. 해제할 때 "내 락인지" 확인하기 위해 필요합니다.

## 3) 해제는 반드시 "내 락인지 확인 후" 해야 함

문제:

- 락 TTL이 만료되어 다른 요청이 락을 다시 획득했는데,
- 이전 요청이 늦게 끝나서 `DEL lockKey`를 해버리면,
- 남의 락을 지워버립니다.

해제는 Lua로 원자 처리하는 게 안전합니다.

```lua
-- KEYS[1] = lockKey
-- ARGV[1] = token
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
end
return 0
```

## 4) TTL은 "최악의 실행 시간"을 고려

- TTL이 너무 짧으면 작업이 끝나기 전에 만료될 수 있습니다.
- TTL이 너무 길면 락이 불필요하게 오래 잡혀 병목이 됩니다.

실무에서는 대개:

- TTL을 적절히 잡고
- 정말 긴 작업이면 "연장(renew)"을 고려합니다.

## 5) 흔한 실수

### (1) 락 없이도 되는 곳에 락을 걸기

락은 비용입니다. "정말로 중복 실행이 치명적인 지"부터 판단하세요.

### (2) 락을 걸어도 DB에서 유니크/정합성을 안 보장

락은 최종 방어가 아닙니다. 예를 들어 쿠폰 발급 같은 건 DB에서 유니크 제약/트랜잭션으로 마지막 안전장치를 두는 게 일반적입니다.

### (3) 락 키 설계가 애매함

키는 "동시성 범위" 그 자체입니다.

- 사용자 단위: `lock:user:{userId}`
- 리소스 단위: `lock:coupon:{couponId}`

## 6) 대안 비교

### Redisson

Java/Spring 생태계에서 편합니다(락 구현/연장 등). 운영/신뢰성 요구가 커지면 라이브러리 사용을 고려할 만합니다.

### DB 락

정합성이 정말 중요한 영역(재고/결제)은 DB 트랜잭션/락이 더 적절한 경우가 많습니다.

### 메시지 큐(순차 처리)

"중복/동시성"을 락이 아니라 처리 파이프라인(큐)로 해결하는 전략도 실무에서 흔합니다.

## 정리

- Redis 락은 `SET NX PX`로 시작하되, 해제는 Lua로 "내 락인지 확인"이 필수
- TTL 설정이 핵심이고, 락은 최종 정합성을 대신하지 못한다
- 케이스에 따라 Redisson/DB 락/큐가 더 적절할 수 있다
