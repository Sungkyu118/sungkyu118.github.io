# Vue 입문 33: props로 부모에서 자식에게 데이터 전달하기

> props를 통해 부모의 데이터를 자식 컴포넌트가 안전하게 읽는 방법을 배웁니다.

props는 부모 컴포넌트가 자식 컴포넌트에게 데이터를 전달하는 공식적인 통로입니다. 부모가 어떤 값을 내려주고, 자식은 그 값을 읽어서 화면을 그립니다. 이때 자식은 props를 자신의 내부 상태처럼 마음대로 바꾸는 것이 아니라, 부모가 준 입력값으로 이해하는 편이 좋습니다.

props를 잘 설계하면 컴포넌트의 사용법이 코드에 드러납니다. 예를 들어 `UserCard` 컴포넌트가 `user` prop을 필수로 받는다면, 이 컴포넌트를 쓰는 사람은 사용자 객체를 넘겨야 한다는 것을 알 수 있습니다. 타입과 required를 명시하면 개발 중 실수를 더 빨리 발견할 수 있습니다.

입문 단계에서는 props를 단순히 "자식에서 쓰고 싶은 변수" 정도로 생각하기 쉽습니다. 하지만 props는 컴포넌트의 외부 인터페이스입니다. 어떤 props를 받는지가 곧 그 컴포넌트가 어떤 데이터를 필요로 하는지 설명합니다. 그래서 이름, 타입, 기본값을 신중하게 정하는 것이 중요합니다.

## 이번 글에서 먼저 잡을 관점

이번 구간부터는 Vue를 단순히 한 파일 안에서 쓰는 단계에서 벗어나, 여러 컴포넌트가 함께 동작하는 구조를 다룹니다. 그래서 문법 하나만 보는 것보다 역할과 책임을 같이 보는 것이 중요합니다. 부모 컴포넌트가 무엇을 알고 있어야 하는지, 자식 컴포넌트는 어디까지 책임져야 하는지, 사용자의 행동을 어느 방향으로 전달해야 하는지 계속 질문하면서 읽어보시면 좋습니다.

컴포넌트 설계는 처음부터 완벽하게 나누는 일이 아닙니다. 작은 화면을 만들고, 반복되는 부분이나 책임이 분명한 부분을 발견하고, 그때 적절히 분리하는 과정에 가깝습니다. 이 글의 예제도 정답이라기보다 기준을 잡기 위한 출발점으로 봐주세요. 직접 이름을 바꿔보고, props를 하나 추가해보고, 이벤트 흐름을 바꿔보면 훨씬 오래 기억에 남습니다.

## 작은 실습으로 확인해보기

아래 예제는 사용자 카드 컴포넌트가 `user`와 `highlight` props를 받는 구조입니다.

{% raw %}
```vue
<!-- UserCard.vue -->
<script setup>
defineProps({
  user: {
    type: Object,
    required: true
  },
  highlight: {
    type: Boolean,
    default: false
  }
})
</script>

<template>
  <article :class="{ highlight }">
    <h2>{{ user.name }}</h2>
    <p>{{ user.email }}</p>
  </article>
</template>

<style scoped>
.highlight {
  border: 2px solid #42b883;
  background: #ecfdf5;
}
</style>

<!-- Parent.vue -->
<template>
  <UserCard :user="currentUser" :highlight="true" />
</template>
```
{% endraw %}

## 코드가 움직이는 순서

`user`는 필수 객체 prop입니다. 부모가 넘기지 않으면 개발 중 경고를 확인할 수 있습니다. `highlight`는 선택 prop이고 기본값이 false입니다. 부모는 `:user="currentUser"`처럼 동적 바인딩으로 객체를 넘기고, 자식은 props를 읽어서 화면을 그립니다.

여기서 중요한 것은 코드 줄 수보다 의도입니다. 컴포넌트를 나누면 파일은 늘어나지만, 각 파일이 맡는 역할이 선명해져야 합니다. 부모는 전체 상태와 흐름을 관리하고, 자식은 자신이 맡은 UI 조각을 표현하거나 사용자 행동을 이벤트로 알려주는 식으로 역할을 나누면 디버깅이 훨씬 쉬워집니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: props 타입을 생략해도 동작은 할 수 있지만, 협업과 디버깅을 생각하면 최소한 중요한 props에는 타입과 required 여부를 명시하는 것이 좋습니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 객체 prop을 받을 때 자식이 내부 속성을 직접 수정하면 부모 상태를 몰래 바꾸는 것처럼 보일 수 있습니다. 단방향 흐름을 지키는 것이 안전합니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: boolean prop은 문자열과 실제 boolean을 혼동하기 쉽습니다. 동적 값이면 `:highlight=\"true\"`처럼 바인딩을 사용하세요. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.

컴포넌트 관련 오류는 한 파일만 봐서는 바로 보이지 않을 때가 많습니다. 부모가 넘기는 prop 이름, 자식이 선언한 prop 이름, 자식이 emit하는 이벤트 이름, 부모가 듣는 이벤트 이름을 한 줄씩 맞춰보는 습관이 필요합니다. 브라우저 콘솔의 Vue warning도 그냥 넘기지 말고, 어떤 컴포넌트에서 발생했는지 확인해보시면 좋습니다.

## 실무에서 생각할 점

props는 컴포넌트를 예측 가능하게 만드는 도구입니다. 하지만 props가 너무 많아지면 컴포넌트가 여러 역할을 동시에 맡고 있다는 신호일 수 있습니다. props 수가 늘어날 때는 컴포넌트를 더 작게 나누거나, 객체 하나로 묶는 것이 더 나은지 고민해보는 것이 좋습니다.

실무에서는 컴포넌트가 "동작한다"보다 "변경에 견딘다"가 더 중요해집니다. 요구사항은 계속 바뀌고, 디자인도 바뀌고, 같은 컴포넌트를 다른 화면에서 쓰고 싶어질 수 있습니다. 그래서 처음부터 모든 것을 일반화하려고 하기보다, 현재 책임을 명확히 하고 나중에 반복이 보일 때 재사용성을 높이는 방향이 안전합니다.
