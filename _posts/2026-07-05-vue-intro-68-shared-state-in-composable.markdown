# Vue 입문 68: 여러 컴포넌트가 같은 Composable을 쓰면 상태가 공유될까요?

> Composable의 상태가 호출마다 독립인지 전역처럼 공유되는지는 ref를 어디에 선언하느냐에 따라 달라진다는 점을 배웁니다.

Composable을 처음 만들 때 가장 많이 헷갈리는 질문 중 하나가 "여러 컴포넌트에서 같은 Composable을 쓰면 상태도 같이 공유되나요?"입니다. 답은 Composable의 이름이 아니라 상태를 어디에 선언했는지에 따라 달라집니다.

함수 안에서 `ref`를 만들면 Composable을 호출할 때마다 새로운 상태가 만들어집니다. 각 컴포넌트가 자기만의 상태를 갖는 구조입니다. 반대로 함수 바깥, 즉 모듈의 최상단에 `ref`를 만들면 그 파일을 import하는 곳들이 같은 상태를 바라볼 수 있습니다. 이 구조는 작은 전역 상태처럼 동작합니다.

둘 다 사용할 수 있지만 의도가 분명해야 합니다. 독립 상태를 기대했는데 공유 상태가 되면 한 화면에서 입력한 값이 다른 화면에도 나타나는 이상한 버그가 생깁니다. 반대로 공유를 기대했는데 함수 안에 상태를 만들면 컴포넌트마다 값이 따로 놀아서 동기화가 되지 않습니다.

## 이번 글에서 먼저 잡을 관점

이번 Composable 구간에서는 "코드를 함수로 빼는 것"보다 "상태와 동작의 책임을 어디까지 묶을 것인가"를 더 중요하게 보겠습니다. Composable은 반복 코드를 줄이는 도구이기도 하지만, 화면 컴포넌트가 너무 많은 일을 떠안지 않게 도와주는 설계 단위이기도 합니다.

읽으실 때는 예제의 파일 이름보다 데이터 흐름을 먼저 따라가 보시면 좋습니다. 어떤 값이 `ref`로 만들어지는지, 어떤 함수가 상태를 바꾸는지, 컴포넌트는 무엇을 몰라도 되는지 확인해보면 Composable의 장점과 위험이 훨씬 선명하게 보입니다.

지금 단계에서는 완벽한 구조를 외우려고 하기보다, 왜 이 코드가 컴포넌트 안에 있으면 불편해지는지, 분리하면 어떤 장점이 생기는지, 반대로 너무 분리하면 어떤 비용이 생기는지를 함께 생각해보시면 좋습니다. 기술을 배우는 속도보다 판단 기준을 만드는 속도가 더 중요할 때가 많습니다.

## 작은 실습으로 확인해보기

아래 예제는 독립 상태와 공유 상태를 나란히 보여줍니다. 같은 `useCounter` 계열이어도 ref 위치에 따라 동작이 완전히 달라집니다.

{% raw %}
~~~vue
// 독립 상태: 호출할 때마다 count가 새로 만들어집니다.
import { ref } from 'vue'

export function useLocalCounter() {
  const count = ref(0)

  function increase() {
    count.value += 1
  }

  return {
    count,
    increase
  }
}

// 공유 상태: 이 모듈을 import하는 컴포넌트들이 같은 count를 봅니다.
const sharedCount = ref(0)

export function useSharedCounter() {
  function increase() {
    sharedCount.value += 1
  }

  return {
    count: sharedCount,
    increase
  }
}
~~~
{% endraw %}

## 코드가 움직이는 순서

`useLocalCounter`는 함수가 실행될 때마다 `count`를 새로 만듭니다. 그래서 A 컴포넌트와 B 컴포넌트가 각각 호출하면 서로 다른 카운터가 됩니다. 반면 `sharedCount`는 함수 밖에 있으므로 모듈이 로드될 때 한 번 만들어지고 계속 재사용됩니다. `useSharedCounter`를 여러 곳에서 호출해도 같은 ref를 반환합니다.

예제를 따라 작성할 때는 먼저 상태가 만들어지는 위치를 찾고, 그다음 그 상태를 바꾸는 함수를 찾고, 마지막으로 템플릿에서 어떤 조건으로 화면이 바뀌는지 확인해보세요. Vue 코드는 겉으로는 HTML과 JavaScript가 섞여 보이지만, 실제로는 "상태가 바뀌고, 계산값이 갱신되고, 템플릿이 다시 그려지는 흐름"을 반복합니다. 이 순서를 말로 설명할 수 있으면 문법을 조금 잊어도 다시 찾아가며 구현할 수 있습니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 공유 상태는 편리하지만 새로고침하면 사라집니다. 영구 저장이 필요하다면 localStorage, 서버 저장, Pinia persist 전략을 따로 생각해야 합니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: 공유 상태를 너무 많이 만들면 프로젝트 안에 작은 전역 상태가 흩어집니다. 어떤 값이 어디서 바뀌는지 추적하기 어려워질 수 있습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: SSR이나 테스트 환경에서는 모듈 스코프 공유 상태가 요청 간, 테스트 간에 남는 문제가 생길 수 있습니다. 지금은 입문 단계라도 이런 차이가 있다는 점을 기억해두면 좋습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.

문제가 생겼을 때는 한 번에 모든 코드를 의심하지 말고, 입력값, 상태 변경 함수, 반환값 또는 라우트 이동 결과를 차례로 확인해보세요. 특히 Composable과 Router는 코드가 여러 파일에 나뉘기 쉬워서 "어디서 바뀌었는지"를 놓치기 쉽습니다. 브라우저 콘솔, Vue Devtools, Network 탭을 함께 보면 눈으로 보이지 않는 상태 변화와 요청 흐름을 훨씬 빠르게 확인할 수 있습니다.

## 실무에서 생각할 점

작은 앱에서는 모듈 스코프 공유 상태가 가볍고 빠른 해결책이 될 수 있습니다. 하지만 로그인 사용자, 장바구니, 권한처럼 앱 전체에서 중요한 상태라면 Pinia 같은 전역 상태 관리 도구로 명확한 구조를 잡는 편이 안전합니다.

실무에서는 정답 패턴을 한 번에 고르는 것보다 현재 팀과 프로젝트의 복잡도에 맞는 선택을 하는 것이 중요합니다. 작은 화면에서는 단순한 코드가 가장 좋은 코드일 수 있고, 여러 화면에서 같은 문제가 반복되기 시작하면 그때 분리하는 편이 더 안전할 수 있습니다. 반대로 인증, 결제, 관리자 권한처럼 실수의 영향이 큰 영역은 초반부터 책임 경계를 조금 더 엄격하게 잡는 것이 좋습니다.

## 디버깅할 때 확인할 순서

1. 현재 값이 어디에서 만들어지는지 확인합니다.
2. 그 값을 바꾸는 함수가 어느 파일에 있는지 확인합니다.
3. 값이 바뀐 뒤 화면이 어떤 조건으로 다시 그려지는지 확인합니다.
4. 비동기 요청이 있다면 loading, success, error 상태가 모두 처리되는지 확인합니다.
5. 라우터 이동이 있다면 URL, route params, query, guard 결과를 차례로 확인합니다.

이 순서를 습관처럼 적용하면 문제를 만났을 때 훨씬 덜 흔들립니다. 특히 입문 단계에서는 코드를 많이 아는 것보다, 문제가 생겼을 때 확인할 순서를 알고 있는 것이 더 큰 힘이 됩니다.
