# Vue 입문 99: Pinia action에서 API 호출을 해도 괜찮을까요?

> Pinia action은 비동기 로직을 담을 수 있지만 화면 책임과 store 책임을 구분해야 합니다.

Pinia action 안에서 API를 호출해도 되는지 자주 고민하게 됩니다. 공식적으로 actions는 비동기 로직을 담을 수 있고, API 호출도 가능합니다. 예를 들어 로그인, 사용자 정보 조회, 장바구니 동기화처럼 store 상태를 직접 바꾸는 요청은 action 안에 두면 흐름이 자연스럽습니다.

다만 모든 API 호출을 store action으로 몰아넣는 것은 조심해야 합니다. 특정 페이지에서만 쓰는 목록 조회까지 모두 전역 store에 넣으면 store가 서버 API 모음처럼 커질 수 있습니다. 그러면 화면 상태와 전역 상태의 경계가 흐려집니다.

이번 글에서는 store 상태와 직접 연결된 API 호출은 action에 두고, 특정 화면의 일회성 데이터는 Composable이나 페이지 안에 둘 수 있다는 기준을 잡아보겠습니다.

## 이번 글에서 먼저 잡을 관점

이번 Pinia 구간에서는 store 문법을 외우는 것보다 상태의 범위와 책임을 먼저 보겠습니다. 전역 상태는 여러 화면을 편하게 연결해주지만, 잘못 쓰면 어디서 값이 바뀌는지 추적하기 어려운 큰 공유 공간이 될 수 있습니다.

예제를 읽으실 때는 이 값이 왜 지역 상태가 아니라 전역 상태인지, getter로 계산할 수 있는 값을 state에 중복 저장하고 있지는 않은지, action 이름이 사용자 행동을 잘 설명하는지 함께 살펴보시면 좋습니다.

지금 단계에서는 완벽한 구조를 외우려고 하기보다, 왜 이 코드가 특정 위치에 있어야 하는지, 그 위치가 바뀌면 어떤 장점과 비용이 생기는지 함께 생각해보시면 좋습니다. Vue 프로젝트는 문법을 많이 아는 것보다 상태, 화면, 서버, 테스트의 책임을 구분하는 힘이 중요해지는 순간이 많습니다.

## 작은 실습으로 확인해보기

아래 예제는 로그인 사용자 정보를 불러오는 API를 auth store action 안에서 처리합니다.

{% raw %}
~~~vue
export const useAuthStore = defineStore('auth', {
  state: () => ({
    user: null,
    loading: false,
    errorMessage: ''
  }),
  actions: {
    async fetchMe() {
      this.loading = true
      this.errorMessage = ''

      try {
        const response = await fetch('/api/me')

        if (!response.ok) {
          throw new Error('사용자 정보 조회 실패')
        }

        this.user = await response.json()
      } catch (error) {
        this.user = null
        this.errorMessage = '사용자 정보를 불러오지 못했습니다.'
      } finally {
        this.loading = false
      }
    }
  }
})
~~~
{% endraw %}

## 코드가 움직이는 순서

`fetchMe`는 auth store의 핵심 상태인 user를 갱신합니다. 그래서 action 안에 두는 것이 자연스럽습니다. loading과 errorMessage도 사용자 정보 조회 흐름에 직접 연결되므로 store에 둘 수 있습니다.

예제를 따라 작성할 때는 먼저 상태가 만들어지는 위치를 찾고, 그다음 그 상태를 바꾸는 함수를 찾고, 마지막으로 템플릿이나 테스트에서 어떤 결과를 확인하는지 살펴보세요. Vue 코드는 겉으로는 여러 파일에 나뉘어 보이지만, 실제로는 "상태가 바뀌고, 계산값이 갱신되고, 화면이나 테스트 결과가 달라지는 흐름"을 반복합니다. 이 순서를 말로 설명할 수 있으면 문법을 조금 잊어도 다시 찾아가며 구현할 수 있습니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 페이지 하나에서만 쓰는 API까지 store에 넣으면 전역 상태가 불필요하게 커질 수 있습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: action 안에서 에러를 삼켜버리면 호출한 컴포넌트가 실패를 알 수 없습니다. 필요하면 에러를 반환하거나 다시 throw해야 합니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: loading을 store에 둘지 페이지에 둘지는 그 loading이 여러 화면에서 의미가 있는지 기준으로 판단합니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.

문제가 생겼을 때는 한 번에 모든 코드를 의심하지 말고, 입력값, 상태 변경 함수, 비동기 요청 결과, 화면 렌더링 또는 테스트 검증 지점을 차례로 확인해보세요. 특히 Pinia, API, 테스트는 코드가 여러 파일에 나뉘기 쉬워서 어디서 값이 바뀌었는지 놓치기 쉽습니다. 브라우저 콘솔, Network 탭, Vue Devtools, 테스트 실패 메시지를 함께 보면 눈으로 보이지 않는 흐름을 훨씬 빠르게 확인할 수 있습니다.

## 실무에서 생각할 점

action API 호출은 상태 변경 흐름을 한곳에 모으는 장점이 있습니다. 그러나 화면별 데이터 조회까지 모두 store로 넣으면 store가 비대해지므로 전역 상태와 지역 화면 상태를 구분해야 합니다.

실무에서는 정답 패턴을 한 번에 고르는 것보다 현재 팀과 프로젝트의 복잡도에 맞는 선택을 하는 것이 중요합니다. 작은 화면에서는 단순한 코드가 가장 좋은 코드일 수 있고, 여러 화면에서 같은 문제가 반복되기 시작하면 그때 분리하는 편이 더 안전할 수 있습니다. 반대로 인증, 결제, 관리자 권한, 테스트 자동화처럼 실수의 영향이 큰 영역은 초반부터 책임 경계를 조금 더 엄격하게 잡는 것이 좋습니다.

## 디버깅하거나 검증할 때 확인할 순서

1. 현재 값이 어디에서 만들어지는지 확인합니다.
2. 그 값을 바꾸는 함수나 action이 어느 파일에 있는지 확인합니다.
3. API 요청이 있다면 loading, success, error 상태가 모두 처리되는지 확인합니다.
4. 사용자 입력이 있다면 입력 전, 입력 중, 제출 후 상태를 나누어 확인합니다.
5. 테스트가 있다면 내부 구현보다 사용자에게 보이는 결과를 검증하는지 확인합니다.

이 순서를 습관처럼 적용하면 문제를 만났을 때 훨씬 덜 흔들립니다. 특히 입문 단계에서는 코드를 많이 아는 것보다, 문제가 생겼을 때 확인할 순서를 알고 있는 것이 더 큰 힘이 됩니다.
