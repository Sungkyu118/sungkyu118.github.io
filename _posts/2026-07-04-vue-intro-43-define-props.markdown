`defineProps`는 `<script setup>`에서 props를 선언하기 위한 컴파일 매크로입니다. 부모가 자식에게 어떤 값을 넘길 수 있는지 자식 컴포넌트 안에서 명시합니다. props 선언은 컴포넌트의 사용법을 설명하는 문서 역할도 합니다.

JavaScript 기준으로는 객체 형태 선언을 많이 사용합니다. 각 prop에 type, required, default를 줄 수 있습니다. 단순히 동작만 시키려면 배열 형태로도 선언할 수 있지만, 입문자에게는 타입과 필수 여부를 함께 쓰는 객체 형태가 더 안전합니다. 나중에 TypeScript를 쓰면 제네릭 기반 타입 선언도 배울 수 있습니다.

`defineProps`로 선언한 props는 템플릿에서 바로 사용할 수 있습니다. 스크립트에서 props를 참조해야 한다면 `const props = defineProps(...)`처럼 변수에 담아 사용할 수 있습니다. 다만 props는 부모가 내려준 입력값이라는 점을 잊으면 안 됩니다.

## 이번 글에서 먼저 잡을 관점

이번 구간부터는 Vue를 단순히 한 파일 안에서 쓰는 단계에서 벗어나, 여러 컴포넌트가 함께 동작하는 구조를 다룹니다. 그래서 문법 하나만 보는 것보다 역할과 책임을 같이 보는 것이 중요합니다. 부모 컴포넌트가 무엇을 알고 있어야 하는지, 자식 컴포넌트는 어디까지 책임져야 하는지, 사용자의 행동을 어느 방향으로 전달해야 하는지 계속 질문하면서 읽어보시면 좋습니다.

컴포넌트 설계는 처음부터 완벽하게 나누는 일이 아닙니다. 작은 화면을 만들고, 반복되는 부분이나 책임이 분명한 부분을 발견하고, 그때 적절히 분리하는 과정에 가깝습니다. 이 글의 예제도 정답이라기보다 기준을 잡기 위한 출발점으로 봐주세요. 직접 이름을 바꿔보고, props를 하나 추가해보고, 이벤트 흐름을 바꿔보면 훨씬 오래 기억에 남습니다.

## 작은 실습으로 확인해보기

아래 예제는 게시글 카드 컴포넌트가 title, summary, featured props를 받는 구조입니다.

{% raw %}
```vue
<script setup>
const props = defineProps({
  title: {
    type: String,
    required: true
  },
  summary: {
    type: String,
    default: '아직 요약이 없습니다.'
  },
  featured: {
    type: Boolean,
    default: false
  }
})
</script>

<template>
  <article :class="{ featured: props.featured }">
    <h2>{{ props.title }}</h2>
    <p>{{ props.summary }}</p>
  </article>
</template>
```
{% endraw %}

## 코드가 움직이는 순서

`title`은 필수 문자열입니다. 부모가 넘기지 않으면 개발 중 경고를 볼 수 있습니다. `summary`는 기본값이 있으므로 부모가 생략해도 문구가 표시됩니다. `featured`는 boolean prop으로 추천 글 여부를 표현합니다. 스크립트에서 `props.featured`처럼 참조하고 템플릿에서도 사용할 수 있습니다.

여기서 중요한 것은 코드 줄 수보다 의도입니다. 컴포넌트를 나누면 파일은 늘어나지만, 각 파일이 맡는 역할이 선명해져야 합니다. 부모는 전체 상태와 흐름을 관리하고, 자식은 자신이 맡은 UI 조각을 표현하거나 사용자 행동을 이벤트로 알려주는 식으로 역할을 나누면 디버깅이 훨씬 쉬워집니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 기본값이 객체나 배열이면 함수로 반환해야 하는 경우를 기억해야 합니다. 공유 참조 문제를 피하기 위한 규칙입니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: props를 구조 분해해서 사용할 때 반응성 동작을 정확히 이해하지 못하면 헷갈릴 수 있습니다. 입문 단계에서는 `props.title`처럼 명시적으로 접근하는 편이 안전합니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: boolean prop을 문자열로 넘기면 의도와 다를 수 있습니다. 동적 값은 콜론 바인딩으로 넘기는 습관을 들이세요. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.

컴포넌트 관련 오류는 한 파일만 봐서는 바로 보이지 않을 때가 많습니다. 부모가 넘기는 prop 이름, 자식이 선언한 prop 이름, 자식이 emit하는 이벤트 이름, 부모가 듣는 이벤트 이름을 한 줄씩 맞춰보는 습관이 필요합니다. 브라우저 콘솔의 Vue warning도 그냥 넘기지 말고, 어떤 컴포넌트에서 발생했는지 확인해보시면 좋습니다.

## 실무에서 생각할 점

props 선언을 자세히 쓰면 코드가 길어지지만 컴포넌트 사용법이 선명해집니다. 작은 개인 프로젝트에서는 생략해도 동작할 수 있지만, 글을 읽는 사람과 협업하는 사람을 생각하면 타입, required, default를 명시하는 편이 훨씬 친절합니다.

실무에서는 컴포넌트가 "동작한다"보다 "변경에 견딘다"가 더 중요해집니다. 요구사항은 계속 바뀌고, 디자인도 바뀌고, 같은 컴포넌트를 다른 화면에서 쓰고 싶어질 수 있습니다. 그래서 처음부터 모든 것을 일반화하려고 하기보다, 현재 책임을 명확히 하고 나중에 반복이 보일 때 재사용성을 높이는 방향이 안전합니다.
