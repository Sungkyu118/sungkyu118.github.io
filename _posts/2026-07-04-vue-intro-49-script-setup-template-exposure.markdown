# Vue 입문 49: script setup에서 import, 변수, 함수가 템플릿에 노출되는 방식

`<script setup>`을 쓰면 top-level에 선언한 변수와 함수, import한 컴포넌트를 템플릿에서 바로 사용할 수 있습니다. 이것은 Vue가 컴파일 단계에서 처리해주는 편의 기능입니다. 그래서 일반 setup 함수처럼 `return { count, increase }`를 작성하지 않아도 됩니다.

이 기능은 코드량을 줄여주지만, 입문자에게는 "왜 템플릿에서 갑자기 이 이름을 쓸 수 있지?"라는 의문을 만들 수 있습니다. 원리는 간단합니다. `<script setup>`의 top-level binding이 템플릿에 노출됩니다. 단, 함수 안에서 선언한 지역 변수는 그 함수 안에서만 유효합니다.

import한 컴포넌트도 마찬가지입니다. `import UserCard from './UserCard.vue'`라고 쓰면 템플릿에서 `<UserCard />`로 사용할 수 있습니다. 이 덕분에 컴포넌트 등록 코드가 줄어듭니다. 하지만 이름 충돌과 오타에는 여전히 주의해야 합니다.

## 이번 글에서 먼저 잡을 관점

이번 구간부터는 Vue를 단순히 한 파일 안에서 쓰는 단계에서 벗어나, 여러 컴포넌트가 함께 동작하는 구조를 다룹니다. 그래서 문법 하나만 보는 것보다 역할과 책임을 같이 보는 것이 중요합니다. 부모 컴포넌트가 무엇을 알고 있어야 하는지, 자식 컴포넌트는 어디까지 책임져야 하는지, 사용자의 행동을 어느 방향으로 전달해야 하는지 계속 질문하면서 읽어보시면 좋습니다.

컴포넌트 설계는 처음부터 완벽하게 나누는 일이 아닙니다. 작은 화면을 만들고, 반복되는 부분이나 책임이 분명한 부분을 발견하고, 그때 적절히 분리하는 과정에 가깝습니다. 이 글의 예제도 정답이라기보다 기준을 잡기 위한 출발점으로 봐주세요. 직접 이름을 바꿔보고, props를 하나 추가해보고, 이벤트 흐름을 바꿔보면 훨씬 오래 기억에 남습니다.

## 작은 실습으로 확인해보기

아래 예제는 import한 컴포넌트, ref 상태, 일반 함수가 템플릿에서 바로 사용되는 모습을 보여줍니다.

```vue
<script setup>
import { ref } from 'vue'
import UserCard from './components/UserCard.vue'

const user = ref({
  name: '성규',
  email: 'vue@example.com'
})

function changeEmail() {
  user.value.email = 'changed@example.com'
}
</script>

<template>
  <UserCard :user="user" />
  <button @click="changeEmail">이메일 변경</button>
</template>
```

## 코드가 움직이는 순서

`UserCard`는 import되었기 때문에 템플릿에서 컴포넌트로 사용할 수 있습니다. `user`는 top-level에 선언된 ref이므로 템플릿에서 바로 읽을 수 있습니다. `changeEmail` 함수도 top-level에 선언되어 있어서 클릭 이벤트와 연결할 수 있습니다. 별도 return 문은 필요하지 않습니다.

여기서 중요한 것은 코드 줄 수보다 의도입니다. 컴포넌트를 나누면 파일은 늘어나지만, 각 파일이 맡는 역할이 선명해져야 합니다. 부모는 전체 상태와 흐름을 관리하고, 자식은 자신이 맡은 UI 조각을 표현하거나 사용자 행동을 이벤트로 알려주는 식으로 역할을 나누면 디버깅이 훨씬 쉬워집니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 함수 내부에서 선언한 변수는 템플릿에서 사용할 수 없습니다. 템플릿에서 써야 하는 값은 top-level에 선언해야 합니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: import한 이름과 local 변수 이름이 충돌하면 코드가 혼란스러워집니다. 컴포넌트 이름은 PascalCase로 명확히 유지하세요. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 자동 노출이 편하다고 해서 모든 값을 템플릿에서 쓰는 것은 좋지 않습니다. 템플릿에는 화면에 필요한 값과 함수만 연결하세요. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.

컴포넌트 관련 오류는 한 파일만 봐서는 바로 보이지 않을 때가 많습니다. 부모가 넘기는 prop 이름, 자식이 선언한 prop 이름, 자식이 emit하는 이벤트 이름, 부모가 듣는 이벤트 이름을 한 줄씩 맞춰보는 습관이 필요합니다. 브라우저 콘솔의 Vue warning도 그냥 넘기지 말고, 어떤 컴포넌트에서 발생했는지 확인해보시면 좋습니다.

## 실무에서 생각할 점

<script setup>은 컴포넌트 코드를 짧고 직접적으로 만들어줍니다. 하지만 자동 노출 때문에 의존 관계를 놓치기 쉬운 부분도 있습니다. import, top-level 선언, 템플릿 사용 위치를 함께 보는 습관을 들이면 이 편의 기능을 안전하게 활용할 수 있습니다.

실무에서는 컴포넌트가 "동작한다"보다 "변경에 견딘다"가 더 중요해집니다. 요구사항은 계속 바뀌고, 디자인도 바뀌고, 같은 컴포넌트를 다른 화면에서 쓰고 싶어질 수 있습니다. 그래서 처음부터 모든 것을 일반화하려고 하기보다, 현재 책임을 명확히 하고 나중에 반복이 보일 때 재사용성을 높이는 방향이 안전합니다.
