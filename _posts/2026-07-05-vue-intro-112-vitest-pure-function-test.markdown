테스트를 처음 배울 때는 컴포넌트보다 순수 함수가 좋습니다. 순수 함수는 같은 입력에 대해 같은 출력을 돌려주고, DOM이나 브라우저 환경에 의존하지 않습니다. 그래서 테스트가 빠르고 실패 원인도 명확합니다.

Vitest는 Vite 기반 프로젝트와 잘 어울리는 테스트 도구입니다. `describe`는 테스트 묶음, `it`은 개별 테스트, `expect`는 기대 결과를 표현합니다. 이 세 가지를 먼저 익히면 이후 컴포넌트 테스트도 훨씬 쉽게 접근할 수 있습니다.

이번 글에서는 폼 검증 함수를 예로 들어 성공과 실패 상황을 함께 테스트해보겠습니다.

## 이번 글에서 먼저 잡을 관점

이번 테스트 구간에서는 테스트 도구 사용법만이 아니라 무엇을 검증해야 오래가는 테스트가 되는지 함께 보겠습니다. 테스트는 완벽함을 보장하는 장치가 아니라, 중요한 동작이 깨졌을 때 빨리 알려주는 안전망입니다.

예제를 읽을 때는 내부 변수명을 확인하는지, 사용자에게 보이는 결과를 확인하는지 구분해보세요. 좋은 테스트는 리팩토링을 방해하기보다 리팩토링을 더 안전하게 만들어야 합니다.

지금 단계에서는 완벽한 구조를 외우려고 하기보다, 왜 이 코드가 특정 위치에 있어야 하는지, 그 위치가 바뀌면 어떤 장점과 비용이 생기는지 함께 생각해보시면 좋습니다. Vue 프로젝트는 문법을 많이 아는 것보다 상태, 화면, 서버, 테스트의 책임을 구분하는 힘이 중요해지는 순간이 많습니다.

## 작은 실습으로 확인해보기

아래 예제는 이메일과 비밀번호를 검증하는 순수 함수를 테스트합니다.

{% raw %}
~~~vue
// utils/validateSignup.js
export function validateSignup(form) {
  const errors = {}

  if (!form.email.includes('@')) {
    errors.email = '이메일 형식을 확인해주세요.'
  }

  if (form.password.length < 8) {
    errors.password = '비밀번호는 8자 이상이어야 합니다.'
  }

  return errors
}

// utils/validateSignup.test.js
import { describe, expect, it } from 'vitest'
import { validateSignup } from './validateSignup'

describe('validateSignup', () => {
  it('올바른 입력이면 에러가 없습니다', () => {
    expect(validateSignup({
      email: 'user@example.com',
      password: 'password123'
    })).toEqual({})
  })

  it('잘못된 이메일과 짧은 비밀번호를 검증합니다', () => {
    expect(validateSignup({
      email: 'wrong',
      password: '123'
    })).toEqual({
      email: '이메일 형식을 확인해주세요.',
      password: '비밀번호는 8자 이상이어야 합니다.'
    })
  })
})
~~~
{% endraw %}

## 코드가 움직이는 순서

첫 번째 테스트는 정상 입력, 두 번째 테스트는 실패 입력을 검증합니다. 실패 상황을 테스트해야 검증 함수가 정말 필요한 조건을 잡는지 확인할 수 있습니다.

예제를 따라 작성할 때는 먼저 상태가 만들어지는 위치를 찾고, 그다음 그 상태를 바꾸는 함수를 찾고, 마지막으로 템플릿이나 테스트에서 어떤 결과를 확인하는지 살펴보세요. Vue 코드는 겉으로는 여러 파일에 나뉘어 보이지만, 실제로는 "상태가 바뀌고, 계산값이 갱신되고, 화면이나 테스트 결과가 달라지는 흐름"을 반복합니다. 이 순서를 말로 설명할 수 있으면 문법을 조금 잊어도 다시 찾아가며 구현할 수 있습니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 성공 케이스만 테스트하면 중요한 오류 조건을 놓칠 수 있습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: 날짜나 랜덤 값처럼 매번 달라지는 값은 테스트하기 어렵기 때문에 주입하거나 고정해야 합니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: 테스트가 너무 많은 세부 메시지에 묶이면 문구 수정 때 자주 깨질 수 있습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.

문제가 생겼을 때는 한 번에 모든 코드를 의심하지 말고, 입력값, 상태 변경 함수, 비동기 요청 결과, 화면 렌더링 또는 테스트 검증 지점을 차례로 확인해보세요. 특히 Pinia, API, 테스트는 코드가 여러 파일에 나뉘기 쉬워서 어디서 값이 바뀌었는지 놓치기 쉽습니다. 브라우저 콘솔, Network 탭, Vue Devtools, 테스트 실패 메시지를 함께 보면 눈으로 보이지 않는 흐름을 훨씬 빠르게 확인할 수 있습니다.

## 실무에서 생각할 점

순수 함수 테스트는 빠르고 안정적이지만 화면이 실제로 동작하는지는 보장하지 않습니다. 계산과 검증 로직은 순수 함수 테스트로, 사용자 상호작용은 컴포넌트 테스트로 나누면 좋습니다.

실무에서는 정답 패턴을 한 번에 고르는 것보다 현재 팀과 프로젝트의 복잡도에 맞는 선택을 하는 것이 중요합니다. 작은 화면에서는 단순한 코드가 가장 좋은 코드일 수 있고, 여러 화면에서 같은 문제가 반복되기 시작하면 그때 분리하는 편이 더 안전할 수 있습니다. 반대로 인증, 결제, 관리자 권한, 테스트 자동화처럼 실수의 영향이 큰 영역은 초반부터 책임 경계를 조금 더 엄격하게 잡는 것이 좋습니다.

## 디버깅하거나 검증할 때 확인할 순서

1. 현재 값이 어디에서 만들어지는지 확인합니다.
2. 그 값을 바꾸는 함수나 action이 어느 파일에 있는지 확인합니다.
3. API 요청이 있다면 loading, success, error 상태가 모두 처리되는지 확인합니다.
4. 사용자 입력이 있다면 입력 전, 입력 중, 제출 후 상태를 나누어 확인합니다.
5. 테스트가 있다면 내부 구현보다 사용자에게 보이는 결과를 검증하는지 확인합니다.

이 순서를 습관처럼 적용하면 문제를 만났을 때 훨씬 덜 흔들립니다. 특히 입문 단계에서는 코드를 많이 아는 것보다, 문제가 생겼을 때 확인할 순서를 알고 있는 것이 더 큰 힘이 됩니다.
