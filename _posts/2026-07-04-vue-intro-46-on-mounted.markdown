# Vue 입문 46: onMounted로 화면이 준비된 뒤 실행할 코드 작성하기

> 컴포넌트가 화면에 붙은 뒤 실행해야 하는 코드를 onMounted에 배치하는 기준을 배웁니다.

Vue 컴포넌트는 생성되고, 화면에 렌더링되고, 업데이트되고, 사라지는 생명주기를 갖습니다. `onMounted`는 그중 컴포넌트가 실제 DOM에 마운트된 뒤 실행되는 hook입니다. 화면 요소가 존재해야 가능한 작업은 이 시점에 두는 것이 자연스럽습니다.

예를 들어 input에 자동으로 포커스를 주거나, DOM 크기를 측정하거나, 컴포넌트가 처음 보일 때 API를 호출하는 코드가 여기에 들어갈 수 있습니다. 물론 모든 초기화 코드를 onMounted에 넣어야 하는 것은 아닙니다. 단순히 초기 상태를 만드는 코드는 setup 단계에서 해도 됩니다. DOM이 필요하거나 브라우저 환경이 필요한 작업인지가 기준입니다.

onMounted를 사용할 때는 비동기 처리와 로딩 상태도 함께 생각해야 합니다. API 호출을 onMounted에서 시작했다면 로딩 중 UI, 실패 메시지, 컴포넌트가 사라졌을 때의 처리까지 점점 고려하게 됩니다.

## 이번 글에서 먼저 잡을 관점

이번 구간부터는 Vue를 단순히 한 파일 안에서 쓰는 단계에서 벗어나, 여러 컴포넌트가 함께 동작하는 구조를 다룹니다. 그래서 문법 하나만 보는 것보다 역할과 책임을 같이 보는 것이 중요합니다. 부모 컴포넌트가 무엇을 알고 있어야 하는지, 자식 컴포넌트는 어디까지 책임져야 하는지, 사용자의 행동을 어느 방향으로 전달해야 하는지 계속 질문하면서 읽어보시면 좋습니다.

컴포넌트 설계는 처음부터 완벽하게 나누는 일이 아닙니다. 작은 화면을 만들고, 반복되는 부분이나 책임이 분명한 부분을 발견하고, 그때 적절히 분리하는 과정에 가깝습니다. 이 글의 예제도 정답이라기보다 기준을 잡기 위한 출발점으로 봐주세요. 직접 이름을 바꿔보고, props를 하나 추가해보고, 이벤트 흐름을 바꿔보면 훨씬 오래 기억에 남습니다.

## 작은 실습으로 확인해보기

아래 예제는 컴포넌트가 마운트된 뒤 input에 포커스를 주고 초기 데이터를 불러오는 흐름입니다.

{% raw %}
```vue
<script setup>
import { onMounted, ref } from 'vue'

const searchInput = ref(null)
const message = ref('데이터를 불러오는 중입니다.')

onMounted(() => {
  searchInput.value?.focus()
  message.value = '화면이 준비되었습니다.'
})
</script>

<template>
  <section>
    <input ref="searchInput" placeholder="검색어를 입력하세요" />
    <p>{{ message }}</p>
  </section>
</template>
```
{% endraw %}

## 코드가 움직이는 순서

`searchInput`은 템플릿 ref입니다. 컴포넌트가 마운트되기 전에는 실제 DOM 요소가 연결되지 않았을 수 있습니다. `onMounted` 안에서는 input 요소가 화면에 존재하므로 `focus()`를 호출할 수 있습니다. 이처럼 DOM이 필요한 코드는 mounted 이후에 실행하는 것이 안전합니다.

여기서 중요한 것은 코드 줄 수보다 의도입니다. 컴포넌트를 나누면 파일은 늘어나지만, 각 파일이 맡는 역할이 선명해져야 합니다. 부모는 전체 상태와 흐름을 관리하고, 자식은 자신이 맡은 UI 조각을 표현하거나 사용자 행동을 이벤트로 알려주는 식으로 역할을 나누면 디버깅이 훨씬 쉬워집니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: setup 단계에서 DOM ref를 바로 사용하려고 하면 아직 null일 수 있습니다. DOM 요소가 필요한 코드는 onMounted에서 처리하세요. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: onMounted에서 API를 호출할 때 실패 상황을 무시하면 사용자는 빈 화면만 보게 됩니다. 로딩과 에러 상태를 함께 설계해야 합니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 서버 사이드 렌더링 환경에서는 브라우저 전용 API 사용 시점을 더 조심해야 합니다. window나 document 접근은 환경을 고려해야 합니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.

컴포넌트 관련 오류는 한 파일만 봐서는 바로 보이지 않을 때가 많습니다. 부모가 넘기는 prop 이름, 자식이 선언한 prop 이름, 자식이 emit하는 이벤트 이름, 부모가 듣는 이벤트 이름을 한 줄씩 맞춰보는 습관이 필요합니다. 브라우저 콘솔의 Vue warning도 그냥 넘기지 말고, 어떤 컴포넌트에서 발생했는지 확인해보시면 좋습니다.

## 실무에서 생각할 점

onMounted는 초기 실행 코드를 넣기 편하지만, 모든 것을 여기에 모으면 컴포넌트 시작 흐름이 무거워집니다. DOM이 없어도 되는 계산은 setup에서 처리하고, DOM이나 외부 효과가 필요한 코드만 onMounted에 두는 기준이 좋습니다.

실무에서는 컴포넌트가 "동작한다"보다 "변경에 견딘다"가 더 중요해집니다. 요구사항은 계속 바뀌고, 디자인도 바뀌고, 같은 컴포넌트를 다른 화면에서 쓰고 싶어질 수 있습니다. 그래서 처음부터 모든 것을 일반화하려고 하기보다, 현재 책임을 명확히 하고 나중에 반복이 보일 때 재사용성을 높이는 방향이 안전합니다.
