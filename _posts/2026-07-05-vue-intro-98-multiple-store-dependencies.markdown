# Vue 입문 98: 여러 store 사이의 의존 관계를 다루는 방법

> store를 여러 개로 나눌 때 서로 참조하는 흐름을 안전하게 설계하는 방법을 배웁니다.

프로젝트가 커지면 store도 하나로 끝나지 않습니다. auth store는 로그인 사용자를 관리하고, cart store는 장바구니를 관리하며, order store는 주문을 관리할 수 있습니다. 이때 한 store가 다른 store의 값이 필요한 순간이 생깁니다.

Pinia에서는 action 안에서 다른 store를 호출할 수 있습니다. 예를 들어 주문을 생성할 때 auth store의 사용자 정보를 읽거나, 로그아웃할 때 cart store를 비울 수 있습니다. 다만 store끼리 서로 초기화 단계에서 바로 참조하면 순환 의존이 생길 수 있습니다.

중요한 기준은 참조가 필요한 시점을 늦추는 것입니다. 파일 최상단에서 서로 상태를 바로 읽기보다, action 안에서 필요한 순간에 다른 store를 가져오면 구조가 더 안전합니다.

## 이번 글에서 먼저 잡을 관점

이번 Pinia 구간에서는 store 문법을 외우는 것보다 상태의 범위와 책임을 먼저 보겠습니다. 전역 상태는 여러 화면을 편하게 연결해주지만, 잘못 쓰면 어디서 값이 바뀌는지 추적하기 어려운 큰 공유 공간이 될 수 있습니다.

예제를 읽으실 때는 이 값이 왜 지역 상태가 아니라 전역 상태인지, getter로 계산할 수 있는 값을 state에 중복 저장하고 있지는 않은지, action 이름이 사용자 행동을 잘 설명하는지 함께 살펴보시면 좋습니다.

지금 단계에서는 완벽한 구조를 외우려고 하기보다, 왜 이 코드가 특정 위치에 있어야 하는지, 그 위치가 바뀌면 어떤 장점과 비용이 생기는지 함께 생각해보시면 좋습니다. Vue 프로젝트는 문법을 많이 아는 것보다 상태, 화면, 서버, 테스트의 책임을 구분하는 힘이 중요해지는 순간이 많습니다.

## 작은 실습으로 확인해보기

아래 예제는 로그아웃할 때 auth store가 cart store를 action 안에서 가져와 장바구니를 비우는 흐름입니다.

{% raw %}
~~~vue
// stores/cart.js
export const useCartStore = defineStore('cart', {
  state: () => ({
    items: []
  }),
  actions: {
    clearCart() {
      this.items = []
    }
  }
})

// stores/auth.js
import { defineStore } from 'pinia'
import { useCartStore } from './cart'

export const useAuthStore = defineStore('auth', {
  state: () => ({
    user: null,
    accessToken: ''
  }),
  actions: {
    logout() {
      const cart = useCartStore()

      this.user = null
      this.accessToken = ''
      cart.clearCart()
    }
  }
})
~~~
{% endraw %}

## 코드가 움직이는 순서

auth store는 logout action이 실행되는 순간 cart store를 가져옵니다. 로그아웃이라는 사용자 행동 안에서 장바구니 초기화가 필요하다는 의도가 드러납니다. 반대로 store 파일을 로드하자마자 서로의 상태를 읽는 구조는 순환 의존 문제를 만들 수 있습니다.

예제를 따라 작성할 때는 먼저 상태가 만들어지는 위치를 찾고, 그다음 그 상태를 바꾸는 함수를 찾고, 마지막으로 템플릿이나 테스트에서 어떤 결과를 확인하는지 살펴보세요. Vue 코드는 겉으로는 여러 파일에 나뉘어 보이지만, 실제로는 "상태가 바뀌고, 계산값이 갱신되고, 화면이나 테스트 결과가 달라지는 흐름"을 반복합니다. 이 순서를 말로 설명할 수 있으면 문법을 조금 잊어도 다시 찾아가며 구현할 수 있습니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: store끼리 서로를 최상단에서 즉시 읽으면 초기화 순서 문제가 생길 수 있습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: 한 action이 너무 많은 store를 바꾸면 책임이 커져 테스트하기 어려워집니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: 서로 참조가 많아지면 도메인 경계가 흐려졌다는 신호일 수 있습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.

문제가 생겼을 때는 한 번에 모든 코드를 의심하지 말고, 입력값, 상태 변경 함수, 비동기 요청 결과, 화면 렌더링 또는 테스트 검증 지점을 차례로 확인해보세요. 특히 Pinia, API, 테스트는 코드가 여러 파일에 나뉘기 쉬워서 어디서 값이 바뀌었는지 놓치기 쉽습니다. 브라우저 콘솔, Network 탭, Vue Devtools, 테스트 실패 메시지를 함께 보면 눈으로 보이지 않는 흐름을 훨씬 빠르게 확인할 수 있습니다.

## 실무에서 생각할 점

store 간 참조는 실무에서 필요하지만, 남용하면 전역 객체들이 서로 얽힌 구조가 됩니다. 사용자 행동이나 명확한 도메인 이벤트 안에서 필요한 만큼만 연결하는 것이 좋습니다.

실무에서는 정답 패턴을 한 번에 고르는 것보다 현재 팀과 프로젝트의 복잡도에 맞는 선택을 하는 것이 중요합니다. 작은 화면에서는 단순한 코드가 가장 좋은 코드일 수 있고, 여러 화면에서 같은 문제가 반복되기 시작하면 그때 분리하는 편이 더 안전할 수 있습니다. 반대로 인증, 결제, 관리자 권한, 테스트 자동화처럼 실수의 영향이 큰 영역은 초반부터 책임 경계를 조금 더 엄격하게 잡는 것이 좋습니다.

## 디버깅하거나 검증할 때 확인할 순서

1. 현재 값이 어디에서 만들어지는지 확인합니다.
2. 그 값을 바꾸는 함수나 action이 어느 파일에 있는지 확인합니다.
3. API 요청이 있다면 loading, success, error 상태가 모두 처리되는지 확인합니다.
4. 사용자 입력이 있다면 입력 전, 입력 중, 제출 후 상태를 나누어 확인합니다.
5. 테스트가 있다면 내부 구현보다 사용자에게 보이는 결과를 검증하는지 확인합니다.

이 순서를 습관처럼 적용하면 문제를 만났을 때 훨씬 덜 흔들립니다. 특히 입문 단계에서는 코드를 많이 아는 것보다, 문제가 생겼을 때 확인할 순서를 알고 있는 것이 더 큰 힘이 됩니다.
