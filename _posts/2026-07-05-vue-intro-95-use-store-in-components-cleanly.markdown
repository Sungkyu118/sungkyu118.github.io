# Vue 입문 95: store를 컴포넌트에서 사용할 때 구조를 깔끔하게 유지하기

Pinia store를 컴포넌트에서 쓰기 시작하면 `const store = useStore()` 한 줄로 많은 값을 가져올 수 있습니다. 작은 컴포넌트에서는 이 방식이 충분히 좋습니다. 하지만 화면이 커지면 store에서 읽는 값, action 호출, 지역 상태가 뒤섞여 어떤 값이 어디서 온 것인지 헷갈릴 수 있습니다.

컴포넌트 구조를 깔끔하게 유지하려면 store 상태와 지역 상태를 구분해서 배치하는 습관이 필요합니다. store의 state와 getters를 구조 분해할 때는 반응성이 끊기지 않도록 `storeToRefs`를 사용하고, actions는 store에서 바로 꺼내 쓰거나 store 객체로 호출할 수 있습니다.

중요한 것은 무조건 구조 분해하는 것이 아니라 읽는 사람이 흐름을 따라가기 쉬운 형태를 선택하는 것입니다. 템플릿에서 store 값을 몇 개만 쓰는지, action 이름이 충분히 분명한지, 지역 상태와 섞여도 혼란이 없는지 살펴보면 좋습니다.

## 이번 글에서 먼저 잡을 관점

이번 Pinia 구간에서는 store 문법을 외우는 것보다 상태의 범위와 책임을 먼저 보겠습니다. 전역 상태는 여러 화면을 편하게 연결해주지만, 잘못 쓰면 어디서 값이 바뀌는지 추적하기 어려운 큰 공유 공간이 될 수 있습니다.

예제를 읽으실 때는 이 값이 왜 지역 상태가 아니라 전역 상태인지, getter로 계산할 수 있는 값을 state에 중복 저장하고 있지는 않은지, action 이름이 사용자 행동을 잘 설명하는지 함께 살펴보시면 좋습니다.

지금 단계에서는 완벽한 구조를 외우려고 하기보다, 왜 이 코드가 특정 위치에 있어야 하는지, 그 위치가 바뀌면 어떤 장점과 비용이 생기는지 함께 생각해보시면 좋습니다. Vue 프로젝트는 문법을 많이 아는 것보다 상태, 화면, 서버, 테스트의 책임을 구분하는 힘이 중요해지는 순간이 많습니다.

## 작은 실습으로 확인해보기

아래 예제는 store 상태는 `storeToRefs`로, action은 store에서 직접 꺼내 컴포넌트 상단을 정리하는 방식입니다.

{% raw %}
~~~vue
<script setup>
import { ref } from 'vue'
import { storeToRefs } from 'pinia'
import { useCartStore } from '@/stores/cart'

const cartStore = useCartStore()
const { items, totalPrice, totalQuantity } = storeToRefs(cartStore)
const { removeItem, clearCart } = cartStore

const confirmOpen = ref(false)

function openClearConfirm() {
  confirmOpen.value = true
}

function confirmClearCart() {
  clearCart()
  confirmOpen.value = false
}
</script>

<template>
  <section>
    <p>상품 수: {{ totalQuantity }}</p>
    <p>총 금액: {{ totalPrice }}</p>

    <button type="button" @click="openClearConfirm">장바구니 비우기</button>

    <ul>
      <li v-for="item in items" :key="item.id">
        {{ item.name }}
        <button type="button" @click="removeItem(item.id)">삭제</button>
      </li>
    </ul>
  </section>
</template>
~~~
{% endraw %}

## 코드가 움직이는 순서

state와 getters는 반응형 값을 유지해야 하므로 `storeToRefs`로 꺼냈습니다. actions는 함수이므로 구조 분해해도 반응성 문제가 없습니다. `confirmOpen`은 이 컴포넌트의 확인 모달 표시 여부일 뿐이므로 store가 아니라 지역 상태로 둡니다.

예제를 따라 작성할 때는 먼저 상태가 만들어지는 위치를 찾고, 그다음 그 상태를 바꾸는 함수를 찾고, 마지막으로 템플릿이나 테스트에서 어떤 결과를 확인하는지 살펴보세요. Vue 코드는 겉으로는 여러 파일에 나뉘어 보이지만, 실제로는 "상태가 바뀌고, 계산값이 갱신되고, 화면이나 테스트 결과가 달라지는 흐름"을 반복합니다. 이 순서를 말로 설명할 수 있으면 문법을 조금 잊어도 다시 찾아가며 구현할 수 있습니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: Pinia store를 일반 구조 분해하면 state 반응성이 끊길 수 있습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: 지역 UI 상태까지 store에 넣으면 전역 상태가 불필요하게 커집니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.
- **확인 포인트**: action을 너무 많이 템플릿에서 직접 호출하면 사용자 흐름을 따라가기 어려울 수 있습니다. 입문 예제에서는 작게 보일 수 있지만, 실제 프로젝트에서는 원인을 찾기 어려운 버그나 사용자 경험 문제로 이어질 수 있습니다. 코드를 작성한 뒤에는 이 문제가 어떤 상황에서 나타날 수 있는지 직접 한 번 재현해보는 습관을 들이면 좋습니다.

문제가 생겼을 때는 한 번에 모든 코드를 의심하지 말고, 입력값, 상태 변경 함수, 비동기 요청 결과, 화면 렌더링 또는 테스트 검증 지점을 차례로 확인해보세요. 특히 Pinia, API, 테스트는 코드가 여러 파일에 나뉘기 쉬워서 어디서 값이 바뀌었는지 놓치기 쉽습니다. 브라우저 콘솔, Network 탭, Vue Devtools, 테스트 실패 메시지를 함께 보면 눈으로 보이지 않는 흐름을 훨씬 빠르게 확인할 수 있습니다.

## 실무에서 생각할 점

storeToRefs는 안전하지만 모든 값을 무조건 펼치면 컴포넌트 상단이 길어질 수 있습니다. 값이 적으면 store 객체로 접근하고, 값이 많거나 템플릿에서 자주 쓰면 refs로 정리하는 식으로 균형을 잡으면 좋습니다.

실무에서는 정답 패턴을 한 번에 고르는 것보다 현재 팀과 프로젝트의 복잡도에 맞는 선택을 하는 것이 중요합니다. 작은 화면에서는 단순한 코드가 가장 좋은 코드일 수 있고, 여러 화면에서 같은 문제가 반복되기 시작하면 그때 분리하는 편이 더 안전할 수 있습니다. 반대로 인증, 결제, 관리자 권한, 테스트 자동화처럼 실수의 영향이 큰 영역은 초반부터 책임 경계를 조금 더 엄격하게 잡는 것이 좋습니다.

## 디버깅하거나 검증할 때 확인할 순서

1. 현재 값이 어디에서 만들어지는지 확인합니다.
2. 그 값을 바꾸는 함수나 action이 어느 파일에 있는지 확인합니다.
3. API 요청이 있다면 loading, success, error 상태가 모두 처리되는지 확인합니다.
4. 사용자 입력이 있다면 입력 전, 입력 중, 제출 후 상태를 나누어 확인합니다.
5. 테스트가 있다면 내부 구현보다 사용자에게 보이는 결과를 검증하는지 확인합니다.

이 순서를 습관처럼 적용하면 문제를 만났을 때 훨씬 덜 흔들립니다. 특히 입문 단계에서는 코드를 많이 아는 것보다, 문제가 생겼을 때 확인할 순서를 알고 있는 것이 더 큰 힘이 됩니다.
