# Redis 입문 실무형 1: Redis는 언제 쓰나 (캐시, 세션, 큐, 랭킹)

Redis를 "메모리 DB"라고만 설명하면 감이 잘 안 옵니다. 실무에서 Redis는 대부분 아래 역할 중 하나로 등장해요.

- 캐시(Cache): 빠른 읽기/응답 시간 개선
- 세션(Session): 스케일아웃 환경에서 로그인 상태 공유
- 레이트리밋(Rate Limit): 폭주/공격 방어
- 큐(Queue)/스트림(Streams): 비동기 작업 분리
- 랭킹(Ranking): Sorted Set 기반 리더보드

이 글은 "각 역할을 언제 선택하는지"를 판단 기준 중심으로 정리합니다.

## 1) Redis의 강점과 한계

### 강점

- 메모리 기반이라 빠르다(짧은 지연시간)
- 단순한 자료구조 연산이 강력하다(String/Hash/List/Set/ZSet)
- TTL(만료)과 만료 기반 운영이 쉽다

### 한계/오해

- 메모리라서 비용/용량이 제한적이다
- 영속성/정합성은 DB만큼 강하게 보장하지 않는 구성도 많다(설정/운영에 따라 달라짐)
- "Redis만 있으면 DB가 필요 없다"는 대부분의 웹서비스에선 사실이 아니다

## 2) 캐시를 선택해야 하는 순간

신호:

- DB 쿼리/외부 API 호출이 병목
- 동일한 데이터를 여러 번 읽는다(읽기 비율 높음)
- 약간의 정합성 지연을 허용할 수 있다(또는 TTL로 타협 가능)

주의할 것:

- 키 설계 + TTL이 곧 설계다
- 캐시 스탬피드(동시 만료) 방어가 필요하다
- 무효화 정책(언제 삭제/갱신할지)을 명확히 해야 한다

## 3) 세션을 Redis에 두는 순간

신호:

- 서버가 여러 대가 된다(스케일아웃)
- 배포/재시작에 세션이 날아가면 안 된다(정책)

주의할 것:

- 세션에는 최소 데이터만 넣기(메모리 소비)
- 쿠키 설정(SameSite/Secure/Domain)과 TTL이 보안의 핵심
- Redis 장애가 곧 로그인 장애가 될 수 있으니 구성/모니터링이 중요

## 4) 레이트리밋이 필요한 순간

신호:

- 로그인/가입/인증번호 발송 같은 엔드포인트가 있다
- 비용이 걸리는 작업(메일/SMS/결제 전 단계)이 있다
- 악성 트래픽/버그로 인한 폭주를 막아야 한다

주의할 것:

- 분산 환경에서 전역 카운트를 유지해야 해서 Redis가 유리
- 원자성(체크+증가)이 중요해서 Lua 스크립트를 쓰는 경우가 많다

## 5) 큐/스트림이 필요한 순간

신호:

- 요청-응답을 빨리 끝내고, 나머지는 백그라운드로 보내고 싶다
- 이메일 발송/알림/집계 같은 작업이 있다

주의할 것:

- "유실되면 안 된다" 요구가 강하면 Redis만으로 충분한지부터 검토
- Streams는 소비자 그룹/재처리가 가능해서 작업 큐에 더 적합한 경우가 많다

## 6) 랭킹이 필요한 순간

신호:

- 상위 N명/상위 N개를 자주 보여준다
- 점수 업데이트가 자주 일어난다

주의할 것:

- 기간 랭킹은 키를 분리하고 TTL로 운영하는 편이 깔끔하다
- 동점 정책과 메모리/업데이트 비용을 초반에 결정해야 덜 꼬인다

## 정리

Redis는 "무조건 도입"이 아니라, 문제(지연, 스케일, 폭주, 비동기, 랭킹)를 해결하기 위한 도구입니다.

다음 글에서는 실무에서 제일 먼저 부딪히는 "키 설계 + TTL + 만료/무효화"를 캐시 중심으로 더 깊게 들어가 볼게요.
