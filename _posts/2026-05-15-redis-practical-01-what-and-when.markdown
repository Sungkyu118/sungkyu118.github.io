# Redis 입문 실무형 1: Redis는 언제 쓰고, 언제 쓰면 안 될까

> Redis를 도입해야 하는 상황과 오히려 쓰지 말아야 하는 상황을 캐시, 세션, 큐, 랭킹 사례와 함께 실무 관점으로 정리합니다.

Redis를 처음 접하면 보통 "메모리 DB", "엄청 빠른 저장소" 정도로만 이해하고 넘어가기 쉽습니다. 그런데 실무에서는 그 정도 설명만으로는 거의 도움이 되지 않습니다. 중요한 건 "Redis가 빠르다"가 아니라, **어떤 문제를 해결할 때 Redis가 특히 강하고, 반대로 어떤 문제에서는 오히려 독이 되는지**를 구분하는 감각입니다.

이 글에서는 Redis를 실무에서 자주 투입하는 대표 상황과, 괜히 넣었다가 운영이 더 복잡해지는 상황을 같이 정리해보겠습니다.

## Redis가 특히 잘하는 일

### 1) 캐시

가장 대표적인 사용처는 캐시입니다. DB 조회가 비싸거나, 외부 API 응답이 느리거나, 같은 데이터를 여러 번 읽는 경우 Redis가 큰 효과를 냅니다.

예를 들면 이런 상황입니다.

- 상품 상세를 모든 사용자가 비슷하게 많이 조회한다.
- 카테고리/설정 정보처럼 자주 읽히지만 자주 바뀌지 않는다.
- 추천 결과나 통계 결과를 계산할 때 비용이 크다.

이 영역은 뒤에서 따로 다룰 [Redis for 캐시](/redis/cache)와 자연스럽게 이어집니다.

### 2) 세션 저장소

서버가 여러 대일 때 세션을 각 서버 메모리에만 들고 있으면 요청이 다른 서버로 갔을 때 로그인이 풀리는 문제가 생길 수 있습니다. 이럴 때 Redis를 공용 세션 저장소로 두면 세션 상태를 여러 서버가 함께 사용할 수 있습니다.

다만 세션을 Redis에 둔다고 해서 보안이 자동으로 해결되는 것은 아닙니다. TTL, 쿠키 설정, 장애 시 fallback 전략까지 같이 설계해야 합니다.

### 3) 레이트 리밋

로그인 시도 제한, 문자 인증 요청 제한, 비싼 API 남용 방지처럼 "짧은 시간 안에 몇 번까지 허용할 것인가"를 제어할 때 Redis가 잘 맞습니다. 단순 카운터와 TTL 조합이 가능하고, 원자성이 중요하면 Lua 스크립트까지 붙일 수 있기 때문입니다.

관련 주제는 [Redis 레이트 리밋: Lua로 원자성 보장하기](/redis/rate-limit-lua)에서 더 깊게 볼 수 있습니다.

### 4) 큐/비동기 처리

사용자 요청 흐름에서 바로 처리하지 않아도 되는 작업이 있습니다. 예를 들면 메일 발송, 알림 발행, 후처리 집계 같은 것들입니다. 이때 Redis List나 Streams를 이용해 요청-응답 흐름과 백그라운드 작업을 분리할 수 있습니다.

다만 "큐가 필요하다"와 "무조건 Redis로 큐를 만들어야 한다"는 전혀 다른 이야기입니다. 재처리, 순서 보장, 장애 복구, consumer group 운영이 중요해지면 설계 난도가 꽤 올라갑니다. 이 부분은 [Redis Streams 실전: 작업 큐로 쓰는 법](/redis/streams-queue)과 [Redis Pub/Sub vs Streams](/redis/pubsub-vs-streams)에서 같이 연결해서 보는 게 좋습니다.

### 5) 랭킹/실시간 순위

점수 기반 정렬과 상위 N개 조회는 Sorted Set이 정말 강합니다. 게임 랭킹, 인기 글 순위, 실시간 점수판 같은 곳에서는 SQL보다 구현이 단순하고 빠른 경우가 많습니다.

이 주제는 [Redis for 랭킹](/redis/ranking)과 [Redis 자료구조 3: Sorted Set(ZSET)](/redis/ds-zset) 쪽과 연결됩니다.

## Redis를 넣으면 안 되는 경우도 있다

여기서 많이 생기는 오해가 하나 있습니다. Redis를 넣으면 무조건 빨라지고, 구조가 좋아질 거라고 생각하는 경우입니다. 실제로는 반대인 경우도 적지 않습니다.

### 1) 데이터 정합성이 절대적으로 중요한 핵심 원장 데이터

주문, 결제, 정산처럼 "틀리면 안 되는 데이터"를 Redis 하나로만 들고 가는 건 위험합니다. Redis는 매우 훌륭한 도구지만, 대부분의 서비스에서 정합성의 기준점은 여전히 RDB입니다.

Redis는 보통 이런 역할이 더 어울립니다.

- 원본 DB 앞단의 캐시
- 빠른 조회를 위한 보조 저장소
- 짧은 TTL을 가진 상태 저장

### 2) 읽기보다 쓰기가 훨씬 많은 데이터

데이터가 자주 바뀌고, 매번 무효화나 재계산이 뒤따라야 한다면 캐시 효과가 생각보다 작을 수 있습니다. 캐시 적중률은 낮은데 운영 복잡도만 커지는 패턴이 대표적인 실패 사례입니다.

예를 들어:

- 거의 모든 조회 전에 데이터가 바뀐다.
- 사용자별로 값이 너무 달라서 재사용성이 낮다.
- TTL을 짧게 잡아도 stale 이슈가 민감하다.

이런 경우에는 "캐시를 넣자"보다 "쿼리 자체를 줄이거나 구조를 바꾸자"가 더 맞을 때가 많습니다.

### 3) 운영 감당 없이 일단 붙이는 경우

Redis는 넣는 것보다 운영하는 쪽이 더 어렵습니다. 키 설계, TTL, 메모리, eviction, hot key, 장애 대응까지 생각해야 합니다. 서비스가 커지면 "Redis가 느려졌다"가 아니라 "Redis 설정을 잘못해서 전체 서비스가 연쇄적으로 흔들렸다"가 됩니다.

그래서 최소한 아래 감각은 갖고 시작하는 편이 좋습니다.

- 키를 어떻게 설계할지
- TTL을 몇 초/몇 분/몇 시간으로 둘지
- 캐시 미스가 몰릴 때 DB를 어떻게 보호할지
- 메모리가 차면 어떤 키가 버려질지

이 부분은 [키 설계와 TTL](/redis/practical-key-ttl), [운영 기본](/redis/practical-ops-basics), [메모리/eviction/hot key](/redis/memory-eviction-hotkeys)에서 이어집니다.

## 실무에서 자주 나오는 의사결정 질문

Redis 도입 여부를 판단할 때는 "Redis가 빠른가?"보다 아래 질문이 더 중요합니다.

1. 이 데이터는 여러 번 재사용되는가?
2. 원본 데이터가 바뀌었을 때 stale을 얼마까지 허용할 수 있는가?
3. 캐시 미스가 한꺼번에 몰려도 원본 시스템이 버틸 수 있는가?
4. 이 값은 꼭 Redis일 필요가 있는가, 아니면 애플리케이션 메모리/DB 튜닝으로 충분한가?
5. 장애가 났을 때 Redis 없이도 서비스가 최소 동작 가능한가?

이 질문에 답하지 못한 상태에서 Redis를 넣으면, 초반에는 빨라진 것처럼 보이지만 나중에 장애 원인만 하나 더 늘어나는 경우가 흔합니다.

## 정리

Redis는 "빠른 저장소"라서 쓰는 것이 아니라, **읽기 병목, 세션 공유, 요청 제한, 실시간 순위, 비동기 분리** 같은 문제를 풀기 위해 쓰는 도구입니다.

반대로 정합성이 절대적인 핵심 데이터, 캐시 재사용성이 낮은 데이터, 운영 전략 없이 일단 붙이는 구조에는 잘 맞지 않습니다.

다음 글에서는 Redis를 붙였을 때 실제 운영 난이도를 크게 좌우하는 [키 설계와 TTL](/redis/practical-key-ttl)을 더 구체적으로 들어가보겠습니다.
