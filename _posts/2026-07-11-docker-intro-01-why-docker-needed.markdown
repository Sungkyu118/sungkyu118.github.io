Docker를 처음 접하면 많은 분들이 제일 먼저 이런 생각을 하십니다. "그냥 프로그램 실행하면 되는데, 왜 굳이 Docker까지 써야 하지?" 처음에는 이 질문이 아주 자연스럽습니다. 실제로 작은 개인 프로젝트나 간단한 실습에서는 Docker 없이도 충분히 개발할 수 있기 때문입니다. 그런데 프로젝트가 조금만 커지거나, 내 컴퓨터 말고 다른 사람의 컴퓨터나 서버에서 같은 프로그램을 실행해야 하는 순간부터 이야기가 달라집니다. 그래서 Docker는 명령어부터 외우기보다, 왜 등장했는지를 먼저 이해하는 것이 훨씬 중요합니다.

Docker가 해결하려는 가장 큰 문제는 "실행 환경 차이"입니다. 개발자는 보통 자신의 컴퓨터에서는 프로그램이 잘 실행되도록 맞춰놓습니다. 하지만 같은 코드를 다른 사람이 실행하면 Node 버전이 다르거나, Python 패키지 버전이 다르거나, 운영체제가 다르거나, 환경 변수 설정이 빠져 있어서 갑자기 프로그램이 깨지는 일이 정말 자주 생깁니다. 이때 사람들은 흔히 "내 PC에서는 되는데요"라는 말을 하게 됩니다. Docker는 바로 이 문제를 줄이기 위해, 애플리케이션이 돌아가는 데 필요한 환경까지 하나의 실행 단위로 묶어버리자는 아이디어에서 출발합니다.

## 먼저 이해해야 할 핵심 관점

이번 글의 핵심은 Docker를 "배포용 도구" 하나로만 좁게 보지 않는 것입니다. Docker는 배포에도 많이 쓰이지만, 그 이전에 개발 환경을 일정하게 맞추는 도구이기도 합니다. 즉, Docker의 장점은 단순히 서버에 올리기 편하다는 수준이 아니라, 누가 어디서 실행하든 결과가 크게 달라지지 않도록 만드는 데 있습니다. 이 관점을 먼저 잡아두면 이후에 이미지, 컨테이너, Dockerfile, Compose 같은 개념을 볼 때도 훨씬 덜 헷갈립니다.

또 하나 중요한 점은 Docker가 모든 문제를 마법처럼 해결해주는 것은 아니라는 점입니다. Docker를 쓴다고 해서 애플리케이션 버그가 없어지는 것은 아닙니다. Docker가 도와주는 영역은 주로 "실행 환경 정리", "의존성 고정", "재현 가능한 실행 흐름" 쪽입니다. 그래서 앞으로 Docker를 공부하실 때는 "이 기능이 코드 버그를 잡는가?"보다 "이 기능이 환경 차이에서 생기는 혼란을 얼마나 줄이는가?"를 기준으로 이해해보시면 좋겠습니다.

## Docker가 필요해지는 대표적인 상황

Docker의 필요성을 가장 쉽게 느끼는 상황은 버전 충돌입니다. 예를 들어 어떤 프로젝트는 Node 18에서 잘 돌아가는데, 내 컴퓨터에는 이미 Node 20이 깔려 있어서 경고나 오류가 나는 경우가 있습니다. 반대로 팀원 컴퓨터에는 Node가 아예 없을 수도 있습니다. 이런 상태에서 README에 설치 명령어를 길게 써두고 각자 수동으로 맞추기 시작하면, 겉보기에는 같은 프로젝트를 실행하는 것 같아도 실제 환경은 조금씩 달라지게 됩니다.

아래 예시는 Docker 없이 환경 차이를 맞추려 할 때 흔히 보게 되는 흐름을 단순화한 것입니다.

```bash
node -v
npm install
npm run dev
```

겉으로 보기에는 아주 단순해 보이지만, 실제로는 여기 숨어 있는 변수가 많습니다. Node 버전은 맞는지, npm lock 파일은 최신인지, 운영체제 차이 때문에 설치되는 바이너리가 다른지, 로컬에 이미 남아 있는 캐시가 영향을 주는지 같은 요소들이 모두 결과에 영향을 줄 수 있습니다. 초보자분들이 여기서 가장 자주 하는 오해는 "명령어가 같으면 환경도 같다"라고 생각하는 부분입니다. 하지만 실무에서는 같은 명령어를 실행해도 환경이 조금만 달라지면 전혀 다른 결과가 나오는 일이 흔합니다.

## Docker가 주는 가장 큰 장점

Docker를 사용하면 애플리케이션과 실행 환경을 함께 다룰 수 있다는 점이 가장 큽니다. 예를 들어 "이 프로그램은 Python 3.11이 필요하고, 특정 패키지 버전이 필요하고, 특정 포트로 열려야 한다"는 정보를 이미지 안에 담아둘 수 있습니다. 그러면 다른 사람은 로컬에 Python을 직접 맞추지 않아도, 이미지를 받아서 컨테이너만 실행하면 비슷한 환경을 바로 재현할 수 있습니다.

이 개념을 아주 단순하게 표현하면 아래와 같습니다.

```bash
docker run my-app-image
```

물론 실제로는 포트, 환경 변수, 볼륨 같은 추가 옵션이 붙기도 합니다. 하지만 중요한 점은, 이제 실행의 기준이 "내 컴퓨터에 무엇이 설치되어 있는가"에서 "이 이미지가 어떤 환경을 담고 있는가"로 바뀐다는 것입니다. 이 차이는 생각보다 아주 큽니다. 프로젝트를 처음 받아 실행하는 사람도 훨씬 덜 막히고, 서버에 배포할 때도 같은 이미지를 재사용하기 쉬워집니다.

## 초보자가 자주 오해하는 부분

초보자분들이 Docker를 처음 배울 때 가장 많이 하는 오해 중 하나는, Docker가 단순히 명령어가 많은 배포 도구라고 생각하는 것입니다. 그래서 `docker run`, `docker build` 같은 명령어만 외우고 나면 Docker를 다 안 것처럼 느껴지기도 합니다. 그런데 실제로 더 중요한 것은 "왜 이 명령이 필요한지"와 "이 명령이 어떤 환경 문제를 줄이는지"입니다. 개념 없이 명령만 외우면 나중에 에러가 났을 때 거의 대응이 되지 않습니다.

또 다른 흔한 오해는 Docker를 쓰면 환경 문제가 완전히 사라진다고 믿는 것입니다. Docker도 결국 이미지 버전, 베이스 이미지 선택, 환경 변수 누락, 볼륨 설정 오류, 포트 충돌 같은 새로운 종류의 문제를 만들 수 있습니다. 다만 이 문제들은 적어도 "눈에 보이는 설정"으로 관리되기 때문에, 사람이 머릿속으로 설치 상태를 추측하는 것보다 훨씬 낫습니다. 즉, Docker는 문제를 없애기보다 문제를 더 예측 가능하고 관리 가능하게 만들어준다고 이해하시는 편이 정확합니다.

## 실습 전에 미리 기억해두면 좋은 점

지금 단계에서는 아직 Docker Desktop 설치나 `hello-world` 실행을 본격적으로 다루지 않았지만, 앞으로 실습을 시작하면 "왜 굳이 이렇게 감싸지?"라는 생각이 한 번 더 드실 수 있습니다. 그때 오늘 내용을 떠올려보시면 좋겠습니다. Docker는 애플리케이션 실행을 더 복잡하게 만들기 위해 등장한 것이 아니라, 사람마다 달라지는 로컬 환경과 서버 환경의 차이를 줄이기 위해 등장한 것입니다.

특히 팀 프로젝트나 배포 환경에서는 이 장점이 훨씬 크게 느껴집니다. 개인 실습에서는 한 번 수동으로 설치해도 어떻게든 돌아갈 수 있지만, 팀원이 여러 명이고 서버도 여러 대라면 수동 설치 방식은 금방 한계가 옵니다. 그래서 지금은 "지금 당장 내 PC에서 편한가?"보다 "나중에 같은 환경을 다시 재현하기 쉬운가?"라는 관점으로 Docker를 이해해두시는 것이 좋습니다.

## 오늘 내용 정리

이번 글에서는 Docker는 왜 필요할까요?라는 질문을 중심으로, 환경 차이 문제, 의존성 충돌, 배포 재현성, 팀 협업 관점에서 Docker가 왜 많이 쓰이게 되었는지를 함께 살펴봤습니다. 지금 단계에서는 명령어를 많이 아는 것보다, Docker가 해결하려는 핵심 문제가 무엇인지 분명하게 이해하는 것이 더 중요합니다. 그 기준이 잡혀 있으면 이후에 이미지와 컨테이너, Dockerfile, Compose를 배울 때도 훨씬 덜 흔들리게 됩니다.

가능하시면 지금은 스스로 예를 하나 떠올려보시면 좋겠습니다. 예를 들어 "내가 예전에 버전 차이 때문에 막혔던 경험이 있었는가?", "팀원이랑 환경이 달라서 실행이 안 된 적이 있었는가?"를 떠올려보시면 Docker의 필요성이 훨씬 현실적으로 느껴질 것입니다. 그렇게 자신의 경험과 연결해두면 이후 실습 내용도 더 오래 기억에 남습니다.
