컴포넌트 단계가 깊어지면 props를 계속 내려야 하는 상황이 생깁니다. 최상위 부모가 가진 theme 값을 손자, 증손자 컴포넌트가 필요로 하는데 중간 컴포넌트들은 그 값을 직접 사용하지 않는 경우입니다. 이때 중간 컴포넌트들이 단지 전달만 하는 props drilling이 발생합니다.

`provide`와 `inject`는 이런 상황을 줄여줍니다. 상위 컴포넌트가 값을 provide하면, 아래 어딘가의 하위 컴포넌트가 inject로 그 값을 받을 수 있습니다. 중간 컴포넌트는 그 값을 알 필요가 없습니다. 테마, 폼 컨텍스트, 탭 컨텍스트처럼 계층 안에서 공유되는 값에 유용합니다.

하지만 provide/inject는 데이터 흐름을 숨기는 면도 있습니다. props처럼 부모 템플릿에 명시적으로 보이지 않기 때문에, 어디에서 값이 제공되는지 찾기 어려울 수 있습니다. 그래서 앱 전체 상태를 무분별하게 inject하는 용도로 쓰기보다, 특정 컴포넌트 트리 안의 컨텍스트 공유에 사용하는 것이 좋습니다.

## 이번 글에서 먼저 잡을 관점

이번 구간부터는 Vue를 단순히 한 파일 안에서 쓰는 단계에서 벗어나, 여러 컴포넌트가 함께 동작하는 구조를 다룹니다. 그래서 문법 하나만 보는 것보다 역할과 책임을 같이 보는 것이 중요합니다. 부모 컴포넌트가 무엇을 알고 있어야 하는지, 자식 컴포넌트는 어디까지 책임져야 하는지, 사용자의 행동을 어느 방향으로 전달해야 하는지 계속 질문하면서 읽어보시면 좋습니다.

컴포넌트 설계는 처음부터 완벽하게 나누는 일이 아닙니다. 작은 화면을 만들고, 반복되는 부분이나 책임이 분명한 부분을 발견하고, 그때 적절히 분리하는 과정에 가깝습니다. 이 글의 예제도 정답이라기보다 기준을 잡기 위한 출발점으로 봐주세요. 직접 이름을 바꿔보고, props를 하나 추가해보고, 이벤트 흐름을 바꿔보면 훨씬 오래 기억에 남습니다.

## 작은 실습으로 확인해보기

아래 예제는 상위 컴포넌트가 theme 값을 provide하고, 깊은 자식이 inject로 사용하는 구조입니다.

```vue
<!-- AppShell.vue -->
<script setup>
import { provide, ref } from 'vue'
import ToolbarButton from './ToolbarButton.vue'

const theme = ref('green')

provide('theme', theme)
</script>

<template>
  <ToolbarButton />
</template>

<!-- ToolbarButton.vue -->
<script setup>
import { inject } from 'vue'

const theme = inject('theme', 'gray')
</script>

<template>
  <button :class="`button--${theme}`">
    테마 버튼
  </button>
</template>
```

## 코드가 움직이는 순서

`AppShell`은 `theme` 값을 provide합니다. `ToolbarButton`은 중간 컴포넌트가 몇 단계 있더라도 inject로 값을 받을 수 있습니다. 두 번째 인자인 gray 값은 제공자가 없을 때 사용할 기본값입니다. 이렇게 하면 사용하지 않는 중간 컴포넌트가 theme prop을 계속 전달하지 않아도 됩니다.

여기서 중요한 것은 코드 줄 수보다 의도입니다. 컴포넌트를 나누면 파일은 늘어나지만, 각 파일이 맡는 역할이 선명해져야 합니다. 부모는 전체 상태와 흐름을 관리하고, 자식은 자신이 맡은 UI 조각을 표현하거나 사용자 행동을 이벤트로 알려주는 식으로 역할을 나누면 디버깅이 훨씬 쉬워집니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: provide/inject는 값의 출처가 템플릿에 명시적으로 보이지 않습니다. 너무 많이 쓰면 데이터 흐름을 추적하기 어려워집니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: inject 키를 문자열로 쓰면 오타에 취약합니다. 큰 프로젝트에서는 Symbol 키를 사용하는 방식을 고려할 수 있습니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 앱 전역 상태를 모두 provide/inject로 해결하려고 하면 구조가 흐려질 수 있습니다. 전역 상태는 Pinia 같은 상태 관리 도구가 더 적합할 수 있습니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.

컴포넌트 관련 오류는 한 파일만 봐서는 바로 보이지 않을 때가 많습니다. 부모가 넘기는 prop 이름, 자식이 선언한 prop 이름, 자식이 emit하는 이벤트 이름, 부모가 듣는 이벤트 이름을 한 줄씩 맞춰보는 습관이 필요합니다. 브라우저 콘솔의 Vue warning도 그냥 넘기지 말고, 어떤 컴포넌트에서 발생했는지 확인해보시면 좋습니다.

## 실무에서 생각할 점

provide/inject는 props drilling을 줄이는 훌륭한 도구입니다. 하지만 명시성을 일부 포기합니다. 특정 컴포넌트 트리 안에서 자연스럽게 공유되는 값에는 잘 맞고, 여러 페이지와 기능을 넘나드는 전역 상태에는 신중하게 사용해야 합니다.

실무에서는 컴포넌트가 "동작한다"보다 "변경에 견딘다"가 더 중요해집니다. 요구사항은 계속 바뀌고, 디자인도 바뀌고, 같은 컴포넌트를 다른 화면에서 쓰고 싶어질 수 있습니다. 그래서 처음부터 모든 것을 일반화하려고 하기보다, 현재 책임을 명확히 하고 나중에 반복이 보일 때 재사용성을 높이는 방향이 안전합니다.
