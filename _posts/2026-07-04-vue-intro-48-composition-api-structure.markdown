# Vue 입문 48: Composition API에서 함수와 상태를 어디에 배치하면 좋을까요?

Composition API는 자유롭습니다. `ref`, `computed`, `watch`, 함수, lifecycle hook을 원하는 순서로 작성할 수 있습니다. 이 자유도는 장점이지만, 기준이 없으면 코드가 금방 뒤섞입니다. 상태는 위에 있고, 함수는 아래에 있고, watch는 중간에 흩어져 있는데 어떤 기능과 관련된 것인지 알기 어려워질 수 있습니다.

좋은 기준은 기능 단위로 묶는 것입니다. 예를 들어 검색 기능이 있다면 검색어 상태, 필터링 computed, 검색 실행 함수, 검색어 watch를 가까이 둡니다. 모달 기능이 있다면 열림 상태, 열기/닫기 함수, 선택된 항목 상태를 가까이 둡니다. 이렇게 배치하면 컴포넌트를 읽을 때 기능 단위로 흐름을 따라갈 수 있습니다.

물론 모든 컴포넌트에 복잡한 구조가 필요한 것은 아닙니다. 작은 컴포넌트는 상태, computed, 함수 순서만으로 충분할 수 있습니다. 컴포넌트가 커질수록 기능별 블록을 나누고, 더 커지면 Composable로 분리하는 흐름을 생각하면 됩니다.

## 이번 글에서 먼저 잡을 관점

이번 구간부터는 Vue를 단순히 한 파일 안에서 쓰는 단계에서 벗어나, 여러 컴포넌트가 함께 동작하는 구조를 다룹니다. 그래서 문법 하나만 보는 것보다 역할과 책임을 같이 보는 것이 중요합니다. 부모 컴포넌트가 무엇을 알고 있어야 하는지, 자식 컴포넌트는 어디까지 책임져야 하는지, 사용자의 행동을 어느 방향으로 전달해야 하는지 계속 질문하면서 읽어보시면 좋습니다.

컴포넌트 설계는 처음부터 완벽하게 나누는 일이 아닙니다. 작은 화면을 만들고, 반복되는 부분이나 책임이 분명한 부분을 발견하고, 그때 적절히 분리하는 과정에 가깝습니다. 이 글의 예제도 정답이라기보다 기준을 잡기 위한 출발점으로 봐주세요. 직접 이름을 바꿔보고, props를 하나 추가해보고, 이벤트 흐름을 바꿔보면 훨씬 오래 기억에 남습니다.

## 작은 실습으로 확인해보기

아래 예제는 검색 기능과 모달 기능을 한 컴포넌트 안에서 기능별로 가까이 배치한 구조입니다.

{% raw %}
```vue
<script setup>
import { computed, ref } from 'vue'

const users = ref([
  { id: 1, name: '지민' },
  { id: 2, name: '하린' }
])

// 검색 기능
const keyword = ref('')
const filteredUsers = computed(() =>
  users.value.filter(user => user.name.includes(keyword.value))
)

// 상세 모달 기능
const selectedUser = ref(null)
const isModalOpen = computed(() => selectedUser.value !== null)

function openUser(user) {
  selectedUser.value = user
}

function closeModal() {
  selectedUser.value = null
}
</script>

<template>
  <input v-model="keyword" placeholder="이름 검색" />
  <button
    v-for="user in filteredUsers"
    :key="user.id"
    @click="openUser(user)"
  >
    {{ user.name }}
  </button>

  <section v-if="isModalOpen">
    <p>{{ selectedUser.name }} 상세 정보</p>
    <button @click="closeModal">닫기</button>
  </section>
</template>
```
{% endraw %}

## 코드가 움직이는 순서

검색 관련 상태와 computed가 가까이 있고, 모달 관련 상태와 함수도 가까이 있습니다. 이렇게 하면 `keyword`가 어디서 쓰이는지, `selectedUser`가 어떤 함수로 바뀌는지 한눈에 따라가기 쉽습니다. 나중에 검색 로직이 더 커지면 이 블록을 `useUserSearch` 같은 Composable로 분리할 수도 있습니다.

여기서 중요한 것은 코드 줄 수보다 의도입니다. 컴포넌트를 나누면 파일은 늘어나지만, 각 파일이 맡는 역할이 선명해져야 합니다. 부모는 전체 상태와 흐름을 관리하고, 자식은 자신이 맡은 UI 조각을 표현하거나 사용자 행동을 이벤트로 알려주는 식으로 역할을 나누면 디버깅이 훨씬 쉬워집니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: Composition API라고 해서 모든 상태를 파일 맨 위에, 모든 함수를 맨 아래에 무조건 배치할 필요는 없습니다. 기능 단위로 읽기 쉬운지가 중요합니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 한 컴포넌트 안에 서로 관련 없는 기능 블록이 너무 많아지면 컴포넌트 분리나 Composable 분리를 검토해야 합니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 주석은 남용하면 지저분하지만, 기능 블록을 구분하는 짧은 주석은 입문자와 협업자에게 도움이 될 수 있습니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.

컴포넌트 관련 오류는 한 파일만 봐서는 바로 보이지 않을 때가 많습니다. 부모가 넘기는 prop 이름, 자식이 선언한 prop 이름, 자식이 emit하는 이벤트 이름, 부모가 듣는 이벤트 이름을 한 줄씩 맞춰보는 습관이 필요합니다. 브라우저 콘솔의 Vue warning도 그냥 넘기지 말고, 어떤 컴포넌트에서 발생했는지 확인해보시면 좋습니다.

## 실무에서 생각할 점

Composition API는 구조를 개발자가 설계할 수 있다는 장점이 있습니다. 그만큼 팀 규칙이 중요합니다. 작은 컴포넌트는 단순한 순서로, 큰 컴포넌트는 기능별 묶음으로, 반복되는 로직은 Composable로 옮기는 단계적 기준이 좋습니다.

실무에서는 컴포넌트가 "동작한다"보다 "변경에 견딘다"가 더 중요해집니다. 요구사항은 계속 바뀌고, 디자인도 바뀌고, 같은 컴포넌트를 다른 화면에서 쓰고 싶어질 수 있습니다. 그래서 처음부터 모든 것을 일반화하려고 하기보다, 현재 책임을 명확히 하고 나중에 반복이 보일 때 재사용성을 높이는 방향이 안전합니다.
