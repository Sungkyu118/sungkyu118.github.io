Vue 템플릿에서는 `@click="count++"`처럼 상태를 바로 바꿀 수 있습니다. 작은 예제에서는 이 방식이 간단하고 좋습니다. 하지만 실제 프로젝트에서는 상태 변경이 단순 증가로 끝나지 않는 경우가 많습니다. 검증을 하고, 로그를 남기고, API를 호출하고, 다른 상태도 함께 바꿔야 합니다.

이때 이름 있는 함수가 중요해집니다. `@click="openModal"`처럼 쓰면 템플릿만 봐도 사용자의 행동이 어떤 의도를 갖는지 알 수 있습니다. 함수 안에서는 필요한 상태 변경을 순서대로 작성할 수 있습니다. 나중에 조건이 추가되어도 템플릿을 크게 건드리지 않아도 됩니다.

입문 단계에서부터 모든 한 줄 코드를 함수로 빼야 하는 것은 아닙니다. 하지만 상태 변경에 의미가 있거나, 두 개 이상의 상태를 함께 바꾸거나, 조건이 들어간다면 함수로 분리하는 습관이 좋습니다. 코드의 목적을 이름으로 남기는 것이 유지보수에 큰 도움이 됩니다.

## 이번 글에서 먼저 잡을 관점

이번 주제에서 가장 중요한 것은 문법을 외우는 것보다 흐름을 이해하는 것입니다. Vue 코드는 보통 상태를 준비한다 -> 템플릿에서 상태를 읽는다 -> 사용자 행동으로 상태가 바뀐다 -> Vue가 화면을 다시 맞춘다는 순서로 움직입니다. 이 순서를 머릿속에 두고 읽으면 새로운 문법을 만나도 훨씬 덜 흔들립니다.

또 하나 중요한 점은 Vue가 HTML, CSS, JavaScript를 대체하는 것이 아니라는 사실입니다. Vue는 이 세 가지를 더 구조적으로 연결해주는 도구입니다. 그래서 예제를 따라 칠 때도 "이 문법이 Vue에서만 특별한가?", "아니면 원래 HTML/JavaScript 개념을 Vue 방식으로 연결한 것인가?"를 나누어 생각하면 좋습니다.

처음에는 한 번에 완벽하게 이해하지 못해도 괜찮습니다. 대신 예제 코드를 조금씩 바꿔보면서 어떤 값이 바뀌면 화면의 어느 부분이 바뀌는지 확인해보세요. 손으로 바꿔본 경험이 쌓이면, 단순히 읽기만 했을 때보다 훨씬 빠르게 감이 잡힙니다.

## 작은 실습으로 확인해보기

아래 예제는 모달 열기/닫기와 저장 흐름을 이름 있는 함수로 표현합니다.

{% raw %}
```vue
<script setup>
import { ref } from 'vue'

const isModalOpen = ref(false)
const isSaving = ref(false)
const savedMessage = ref('')

function openModal() {
  savedMessage.value = ''
  isModalOpen.value = true
}

function closeModal() {
  if (isSaving.value) return
  isModalOpen.value = false
}

function saveAndClose() {
  isSaving.value = true
  savedMessage.value = '저장되었습니다.'
  isSaving.value = false
  isModalOpen.value = false
}
</script>

<template>
  <button @click="openModal">설정 열기</button>
  <p>{{ savedMessage }}</p>

  <section v-if="isModalOpen" class="modal">
    <h2>설정</h2>
    <button @click="saveAndClose" :disabled="isSaving">저장</button>
    <button @click="closeModal" :disabled="isSaving">닫기</button>
  </section>
</template>
```
{% endraw %}

## 코드가 움직이는 순서

`openModal`은 단순히 열기만 하지 않고 이전 저장 메시지를 비웁니다. `closeModal`은 저장 중에는 닫히지 않도록 조건을 둡니다. `saveAndClose`는 저장 상태와 메시지, 모달 상태를 함께 바꿉니다. 이 로직을 템플릿 안에 모두 직접 쓰면 의도가 흐려지고 수정이 어려워집니다.

여기서 꼭 기억하셔야 할 부분은 Vue가 화면을 갱신해준다고 해서 개발자가 흐름을 몰라도 되는 것은 아니라는 점입니다. 오히려 Vue를 잘 쓰려면 상태가 어디에 있고, 어떤 이벤트나 함수가 그 상태를 바꾸며, 템플릿이 그 상태를 어떻게 읽는지 계속 추적할 수 있어야 합니다. 작은 예제부터 이 흐름을 말로 설명해보면 나중에 코드가 길어져도 훨씬 덜 막힙니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 템플릿에 상태 변경식을 많이 넣으면 UI 구조와 비즈니스 흐름이 섞입니다. 조건이 들어가면 함수로 분리하는 것이 좋습니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: 함수 이름은 구현보다 의도를 드러내야 합니다. `changeValue`보다 `openModal`, `saveAndClose`가 훨씬 읽기 쉽습니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: 상태를 여러 곳에서 제각각 바꾸면 버그를 찾기 어렵습니다. 중요한 상태 변경은 가능한 한 함수로 모아두는 것이 좋습니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.

에러를 만났을 때는 먼저 터미널 로그와 브라우저 개발자 도구 Console을 함께 봐야 합니다. Vue 프로젝트는 빌드 단계에서 나는 오류와 브라우저 실행 중에 나는 오류가 다를 수 있습니다. 터미널은 정상처럼 보여도 브라우저 콘솔에는 컴포넌트 렌더링 오류가 남아 있을 수 있고, 반대로 브라우저를 열기도 전에 Vite 개발 서버가 실패하는 경우도 있습니다.

## 실무에서 생각할 점

작은 카운터 예제에서 `@click="count++"`는 괜찮습니다. 하지만 실무 코드는 시간이 지나며 조건이 늘어납니다. 처음에는 한 줄이던 코드가 세 줄, 다섯 줄이 될 수 있습니다. 이때 의도 중심 함수로 옮기면 변경에 훨씬 강한 구조가 됩니다.

실무에서는 "동작한다"만으로는 부족한 경우가 많습니다. 다른 사람이 읽었을 때 의도를 이해할 수 있는지, 요구사항이 조금 바뀌어도 고치기 쉬운지, 에러 상황에서도 사용자가 무엇을 해야 하는지 알 수 있는지가 중요합니다. 입문 시리즈에서 계속 예제와 주의사항을 함께 보는 이유도 여기에 있습니다. 문법을 하나 배울 때마다 그 문법이 실패할 수 있는 지점까지 같이 봐야 실제 프로젝트에서 덜 흔들립니다.

## 오늘 내용 정리

다음 글로 넘어가기 전에 예제 코드를 그대로 한 번 작성해보시고, 최소한 한 군데는 직접 바꿔보시는 것을 추천드립니다. 버튼 문구를 바꾸거나, 상태 초기값을 바꾸거나, 조건을 하나 추가하는 정도면 충분합니다. 그렇게 작은 변화를 직접 만들어보면 "아, 이 부분이 화면과 연결되어 있구나"라는 감각이 생깁니다.
