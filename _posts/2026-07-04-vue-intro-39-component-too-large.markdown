컴포넌트가 커지는 것은 자연스러운 일입니다. 처음에는 작은 화면이었는데 검색, 필터, 목록, 페이지네이션, 모달, 저장 상태가 붙으면서 한 파일이 길어집니다. 문제는 길이 자체보다 한 파일 안에서 너무 많은 이유로 변경된다는 점입니다. 검색 UI를 고치는데 저장 로직이 눈에 걸리고, 목록 스타일을 바꾸는데 모달 상태까지 함께 읽어야 한다면 분리 신호입니다.

컴포넌트가 너무 커졌다는 대표 신호는 몇 가지가 있습니다. 템플릿에서 접히지 않는 영역이 너무 많고, script에 상태가 10개 이상 흩어져 있으며, 함수 이름이 서로 다른 도메인을 다루고, 스타일도 여러 UI 조각을 한꺼번에 관리한다면 컴포넌트 책임이 커진 상태일 가능성이 큽니다.

분리 기준은 "재사용"만이 아닙니다. 화면 영역 기준, 상태 소유 기준, 반복 구조 기준, 테스트 가능성 기준으로 나눌 수 있습니다. 예를 들어 검색 바는 한 번만 쓰여도 검색 조건을 다루는 책임이 뚜렷하다면 분리할 수 있습니다. 목록 항목은 반복되므로 분리하기 좋고, 모달은 열림/닫힘과 접근성 처리가 있으므로 별도 컴포넌트가 자연스럽습니다.

## 이번 글에서 먼저 잡을 관점

이번 구간부터는 Vue를 단순히 한 파일 안에서 쓰는 단계에서 벗어나, 여러 컴포넌트가 함께 동작하는 구조를 다룹니다. 그래서 문법 하나만 보는 것보다 역할과 책임을 같이 보는 것이 중요합니다. 부모 컴포넌트가 무엇을 알고 있어야 하는지, 자식 컴포넌트는 어디까지 책임져야 하는지, 사용자의 행동을 어느 방향으로 전달해야 하는지 계속 질문하면서 읽어보시면 좋습니다.

컴포넌트 설계는 처음부터 완벽하게 나누는 일이 아닙니다. 작은 화면을 만들고, 반복되는 부분이나 책임이 분명한 부분을 발견하고, 그때 적절히 분리하는 과정에 가깝습니다. 이 글의 예제도 정답이라기보다 기준을 잡기 위한 출발점으로 봐주세요. 직접 이름을 바꿔보고, props를 하나 추가해보고, 이벤트 흐름을 바꿔보면 훨씬 오래 기억에 남습니다.

## 작은 실습으로 확인해보기

아래 예제는 커진 페이지를 검색 바, 목록, 모달로 나눌 때의 구조를 간단히 보여줍니다.

```vue
<!-- UserPage.vue -->
<script setup>
import { ref } from 'vue'
import UserSearchBar from './UserSearchBar.vue'
import UserList from './UserList.vue'
import UserDetailModal from './UserDetailModal.vue'

const keyword = ref('')
const selectedUser = ref(null)

function openDetail(user) {
  selectedUser.value = user
}
</script>

<template>
  <UserSearchBar v-model="keyword" />
  <UserList :keyword="keyword" @select-user="openDetail" />
  <UserDetailModal
    v-if="selectedUser"
    :user="selectedUser"
    @close="selectedUser = null"
  />
</template>
```

## 코드가 움직이는 순서

`UserPage.vue`는 전체 페이지 흐름만 보여줍니다. 검색어 상태는 페이지가 소유하고, 검색 UI는 `UserSearchBar`가 맡습니다. 목록 표시는 `UserList`가 맡고, 사용자를 선택하면 이벤트를 올립니다. 상세 모달은 선택된 사용자가 있을 때만 열립니다. 이렇게 나누면 각 컴포넌트를 읽을 때 생각해야 하는 범위가 줄어듭니다.

여기서 중요한 것은 코드 줄 수보다 의도입니다. 컴포넌트를 나누면 파일은 늘어나지만, 각 파일이 맡는 역할이 선명해져야 합니다. 부모는 전체 상태와 흐름을 관리하고, 자식은 자신이 맡은 UI 조각을 표현하거나 사용자 행동을 이벤트로 알려주는 식으로 역할을 나누면 디버깅이 훨씬 쉬워집니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 분리 기준 없이 파일 길이만 보고 쪼개면 오히려 props와 emit이 불필요하게 늘어납니다. 책임이 분리되는지 먼저 확인하세요. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 상태를 어디에 둘지 정하지 않은 채 컴포넌트를 나누면 부모와 자식이 서로 상태를 중복해서 갖게 됩니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.
- **확인 포인트**: 분리 후에도 각 컴포넌트 이름이 역할을 설명하지 못하면 효과가 줄어듭니다. 이름만 봐도 책임이 떠오르게 지어야 합니다. 이 문제는 예제 단계에서는 작게 보일 수 있지만, 컴포넌트가 늘어나면 원인을 찾기 어려운 버그로 커질 수 있습니다. 코드를 작성할 때는 데이터가 어느 컴포넌트에서 시작되고, 어떤 prop이나 event를 통해 이동하며, 어느 컴포넌트가 최종적으로 상태를 바꾸는지 함께 확인해보세요.

컴포넌트 관련 오류는 한 파일만 봐서는 바로 보이지 않을 때가 많습니다. 부모가 넘기는 prop 이름, 자식이 선언한 prop 이름, 자식이 emit하는 이벤트 이름, 부모가 듣는 이벤트 이름을 한 줄씩 맞춰보는 습관이 필요합니다. 브라우저 콘솔의 Vue warning도 그냥 넘기지 말고, 어떤 컴포넌트에서 발생했는지 확인해보시면 좋습니다.

## 실무에서 생각할 점

큰 컴포넌트를 나누면 읽기 쉬워지지만, 파일 이동과 데이터 전달이 늘어납니다. 그래서 무조건 잘게 나누기보다 변경 이유가 다른 영역을 분리하는 것이 좋습니다. 한 컴포넌트를 수정할 때 머릿속에 담아야 하는 맥락이 줄어든다면 좋은 분리일 가능성이 큽니다.

실무에서는 컴포넌트가 "동작한다"보다 "변경에 견딘다"가 더 중요해집니다. 요구사항은 계속 바뀌고, 디자인도 바뀌고, 같은 컴포넌트를 다른 화면에서 쓰고 싶어질 수 있습니다. 그래서 처음부터 모든 것을 일반화하려고 하기보다, 현재 책임을 명확히 하고 나중에 반복이 보일 때 재사용성을 높이는 방향이 안전합니다.
