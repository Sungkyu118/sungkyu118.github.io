Vue를 어느 정도 따라 하다 보면 "값은 바뀐 것 같은데 화면이 안 바뀐다"는 문제를 만납니다. 이때 Vue가 이상하다고 느끼기 쉽지만, 대부분은 반응형 상태로 만들지 않았거나, ref의 `.value`를 빼먹었거나, reactive 객체를 구조 분해했거나, 목록 key가 불안정한 경우입니다.

디버깅은 감으로 찍는 일이 아니라 범위를 좁히는 일입니다. 먼저 값이 실제로 바뀌는지 콘솔로 확인합니다. 그 다음 그 값이 Vue가 추적하는 반응형 상태인지 확인합니다. 템플릿에서 사용하는 이름이 맞는지 보고, 목록이라면 key를 확인합니다. DOM 업데이트 직후 값을 읽어야 한다면 `nextTick`이 필요한 상황인지 생각합니다.

중요한 것은 체크리스트를 갖는 것입니다. 매번 새로운 문제처럼 보이지만, 입문 단계의 반응성 문제는 자주 반복되는 패턴이 있습니다. 패턴을 알고 있으면 해결 속도가 빨라지고, 무엇보다 Vue를 덜 무섭게 느끼게 됩니다.

## 이번 글에서 먼저 잡을 관점

이번 주제에서 가장 중요한 것은 문법을 외우는 것보다 흐름을 이해하는 것입니다. Vue 코드는 보통 상태를 준비한다 -> 템플릿에서 상태를 읽는다 -> 사용자 행동으로 상태가 바뀐다 -> Vue가 화면을 다시 맞춘다는 순서로 움직입니다. 이 순서를 머릿속에 두고 읽으면 새로운 문법을 만나도 훨씬 덜 흔들립니다.

또 하나 중요한 점은 Vue가 HTML, CSS, JavaScript를 대체하는 것이 아니라는 사실입니다. Vue는 이 세 가지를 더 구조적으로 연결해주는 도구입니다. 그래서 예제를 따라 칠 때도 "이 문법이 Vue에서만 특별한가?", "아니면 원래 HTML/JavaScript 개념을 Vue 방식으로 연결한 것인가?"를 나누어 생각하면 좋습니다.

처음에는 한 번에 완벽하게 이해하지 못해도 괜찮습니다. 대신 예제 코드를 조금씩 바꿔보면서 어떤 값이 바뀌면 화면의 어느 부분이 바뀌는지 확인해보세요. 손으로 바꿔본 경험이 쌓이면, 단순히 읽기만 했을 때보다 훨씬 빠르게 감이 잡힙니다.

## 작은 실습으로 확인해보기

아래 예제는 항목을 추가한 뒤 DOM 갱신 이후의 목록 개수를 확인하기 위해 `nextTick`을 사용하는 흐름입니다.

{% raw %}
```vue
<script setup>
import { nextTick, ref } from 'vue'

const items = ref(['Vue 시작', '반응성 이해'])
const listElement = ref(null)

async function addItem() {
  items.value.push(`새 항목 ${items.value.length + 1}`)

  await nextTick()

  console.log('DOM에 렌더링된 li 개수:', listElement.value.children.length)
}
</script>

<template>
  <button @click="addItem">항목 추가</button>

  <ul ref="listElement">
    <li v-for="item in items" :key="item">
      {{ item }}
    </li>
  </ul>
</template>
```
{% endraw %}

## 코드가 움직이는 순서

`items.value.push`를 호출하면 상태는 즉시 바뀌지만 DOM 업데이트는 Vue의 렌더링 타이밍에 맞춰 처리됩니다. 그래서 상태 변경 직후 DOM을 바로 읽으면 아직 이전 DOM일 수 있습니다. `await nextTick()`은 Vue가 DOM 업데이트를 끝낸 다음 코드를 이어가게 해줍니다. 이런 상황은 스크롤 이동, 포커스 이동, 렌더링 후 크기 측정에서 자주 나옵니다.

여기서 꼭 기억하셔야 할 부분은 Vue가 화면을 갱신해준다고 해서 개발자가 흐름을 몰라도 되는 것은 아니라는 점입니다. 오히려 Vue를 잘 쓰려면 상태가 어디에 있고, 어떤 이벤트나 함수가 그 상태를 바꾸며, 템플릿이 그 상태를 어떻게 읽는지 계속 추적할 수 있어야 합니다. 작은 예제부터 이 흐름을 말로 설명해보면 나중에 코드가 길어져도 훨씬 덜 막힙니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 값이 안 바뀌는지, 값은 바뀌지만 화면이 안 바뀌는지 먼저 나누어 보세요. 콘솔 로그 위치에 따라 판단이 달라질 수 있습니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: ref를 스크립트에서 수정할 때 `.value`를 확인하세요. 이 실수는 반응성 문제처럼 보이지만 사실 접근 방식 문제입니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: 목록 화면이 이상하면 반응성보다 key 문제일 수 있습니다. 삭제, 정렬, 필터링이 있는 목록은 안정적인 key를 사용해야 합니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.

에러를 만났을 때는 먼저 터미널 로그와 브라우저 개발자 도구 Console을 함께 봐야 합니다. Vue 프로젝트는 빌드 단계에서 나는 오류와 브라우저 실행 중에 나는 오류가 다를 수 있습니다. 터미널은 정상처럼 보여도 브라우저 콘솔에는 컴포넌트 렌더링 오류가 남아 있을 수 있고, 반대로 브라우저를 열기도 전에 Vite 개발 서버가 실패하는 경우도 있습니다.

## 실무에서 생각할 점

디버깅 도구를 많이 아는 것도 좋지만, 처음에는 작은 체크리스트가 더 강력합니다. 상태 생성 방식, 값 변경 위치, 템플릿 이름, key, DOM 업데이트 타이밍을 순서대로 보면 대부분의 입문 단계 문제를 해결할 수 있습니다. 나중에는 Vue Devtools까지 함께 사용하면 상태 흐름을 더 자세히 볼 수 있습니다.

실무에서는 "동작한다"만으로는 부족한 경우가 많습니다. 다른 사람이 읽었을 때 의도를 이해할 수 있는지, 요구사항이 조금 바뀌어도 고치기 쉬운지, 에러 상황에서도 사용자가 무엇을 해야 하는지 알 수 있는지가 중요합니다. 입문 시리즈에서 계속 예제와 주의사항을 함께 보는 이유도 여기에 있습니다. 문법을 하나 배울 때마다 그 문법이 실패할 수 있는 지점까지 같이 봐야 실제 프로젝트에서 덜 흔들립니다.
