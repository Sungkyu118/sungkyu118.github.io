Vue 템플릿은 JavaScript 표현식을 어느 정도 허용합니다. 그래서 처음에는 템플릿 안에서 모든 것을 해결하고 싶어집니다. 문자열을 붙이고, 조건을 검사하고, 배열 길이를 확인하고, 상태에 따라 문구를 바꾸는 정도는 바로 쓸 수 있습니다. 문제는 이 습관이 커지면 템플릿이 화면 구조를 보여주는 곳이 아니라 계산식 창고가 된다는 점입니다.

템플릿 로직이 길어지면 세 가지 문제가 생깁니다. 첫째, HTML 구조를 읽기 어려워집니다. 둘째, 같은 조건식이 여러 곳에 반복되어 수정할 때 빠뜨리기 쉽습니다. 셋째, 테스트하거나 디버깅하기 어렵습니다. 템플릿 안의 긴 표현식은 이름이 없기 때문에 "이 조건이 무슨 의미였지?"라고 다시 해석해야 합니다.

해결책은 무조건 복잡한 패턴을 도입하는 것이 아닙니다. 먼저 computed와 이름 있는 함수를 활용하면 됩니다. 템플릿에는 `canSubmit`, `statusText`, `filteredUsers`처럼 의미 있는 이름을 두고, 계산 과정은 스크립트에서 관리하는 방식입니다.

## 이번 글에서 먼저 잡을 관점

이번 주제에서 가장 중요한 것은 문법을 외우는 것보다 흐름을 이해하는 것입니다. Vue 코드는 보통 상태를 준비한다 -> 템플릿에서 상태를 읽는다 -> 사용자 행동으로 상태가 바뀐다 -> Vue가 화면을 다시 맞춘다는 순서로 움직입니다. 이 순서를 머릿속에 두고 읽으면 새로운 문법을 만나도 훨씬 덜 흔들립니다.

또 하나 중요한 점은 Vue가 HTML, CSS, JavaScript를 대체하는 것이 아니라는 사실입니다. Vue는 이 세 가지를 더 구조적으로 연결해주는 도구입니다. 그래서 예제를 따라 칠 때도 "이 문법이 Vue에서만 특별한가?", "아니면 원래 HTML/JavaScript 개념을 Vue 방식으로 연결한 것인가?"를 나누어 생각하면 좋습니다.

처음에는 한 번에 완벽하게 이해하지 못해도 괜찮습니다. 대신 예제 코드를 조금씩 바꿔보면서 어떤 값이 바뀌면 화면의 어느 부분이 바뀌는지 확인해보세요. 손으로 바꿔본 경험이 쌓이면, 단순히 읽기만 했을 때보다 훨씬 빠르게 감이 잡힙니다.

## 작은 실습으로 확인해보기

아래 예제는 나쁜 예와 개선 예를 함께 보여줍니다. 핵심은 긴 조건식을 템플릿에서 반복하지 않는 것입니다.

{% raw %}
```vue
<script setup>
import { computed, ref } from 'vue'

const email = ref('')
const password = ref('')
const isSaving = ref(false)

const canSubmit = computed(() =>
  email.value.includes('@') &&
  password.value.length >= 8 &&
  !isSaving.value
)

const helperMessage = computed(() => {
  if (!email.value.includes('@')) return '이메일 형식을 확인해주세요.'
  if (password.value.length < 8) return '비밀번호는 8자 이상 입력해주세요.'
  return '제출할 수 있습니다.'
})
</script>

<template>
  <form>
    <input v-model="email" placeholder="email@example.com" />
    <input v-model="password" type="password" />

    <p>{{ helperMessage }}</p>
    <button :disabled="!canSubmit">
      {{ isSaving ? '저장 중...' : '가입하기' }}
    </button>
  </form>
</template>
```
{% endraw %}

## 코드가 움직이는 순서

만약 `canSubmit` 조건을 버튼, 안내 문구, 스타일 클래스에 매번 직접 썼다면 템플릿이 매우 길어졌을 것입니다. computed로 빼면 템플릿은 의도만 보여줍니다. `helperMessage`도 마찬가지입니다. 여러 조건을 순서대로 판단해야 하므로 스크립트에서 함수처럼 작성하는 편이 훨씬 읽기 쉽습니다.

여기서 꼭 기억하셔야 할 부분은 Vue가 화면을 갱신해준다고 해서 개발자가 흐름을 몰라도 되는 것은 아니라는 점입니다. 오히려 Vue를 잘 쓰려면 상태가 어디에 있고, 어떤 이벤트나 함수가 그 상태를 바꾸며, 템플릿이 그 상태를 어떻게 읽는지 계속 추적할 수 있어야 합니다. 작은 예제부터 이 흐름을 말로 설명해보면 나중에 코드가 길어져도 훨씬 덜 막힙니다.

## 자주 만나는 에러와 유의사항

- **확인 포인트**: 템플릿에 삼항 연산자가 여러 겹 들어가면 읽는 사람이 조건을 다시 해석해야 합니다. 이런 경우 computed로 빼는 것이 좋습니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: 같은 조건식이 두 번 이상 반복되면 리팩토링 신호입니다. 한 곳만 수정하고 다른 곳을 놓치면 UI가 서로 다른 기준으로 움직입니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.
- **확인 포인트**: computed 이름을 대충 지으면 효과가 줄어듭니다. `value1`보다 `canSubmit`, `isEmpty`, `statusText`처럼 의도를 드러내는 이름이 좋습니다. 이 문제는 처음에는 작은 실수처럼 보이지만, 화면이 커질수록 원인을 찾기 어려워질 수 있습니다. 그래서 코드를 작성할 때마다 상태가 어디에서 만들어지고, 어디에서 바뀌며, 템플릿에서는 어떤 이름으로 읽히는지 함께 확인하는 습관이 좋습니다.

에러를 만났을 때는 먼저 터미널 로그와 브라우저 개발자 도구 Console을 함께 봐야 합니다. Vue 프로젝트는 빌드 단계에서 나는 오류와 브라우저 실행 중에 나는 오류가 다를 수 있습니다. 터미널은 정상처럼 보여도 브라우저 콘솔에는 컴포넌트 렌더링 오류가 남아 있을 수 있고, 반대로 브라우저를 열기도 전에 Vite 개발 서버가 실패하는 경우도 있습니다.

## 실무에서 생각할 점

템플릿에 아주 짧은 표현식을 쓰는 것은 괜찮습니다. 모든 것을 함수로 빼면 오히려 파일 이동이 많아집니다. 기준은 읽는 사람이 한눈에 의미를 알 수 있는가입니다. 한 번에 의미가 들어오지 않는다면 이름을 붙여 분리하는 편이 좋습니다.

실무에서는 "동작한다"만으로는 부족한 경우가 많습니다. 다른 사람이 읽었을 때 의도를 이해할 수 있는지, 요구사항이 조금 바뀌어도 고치기 쉬운지, 에러 상황에서도 사용자가 무엇을 해야 하는지 알 수 있는지가 중요합니다. 입문 시리즈에서 계속 예제와 주의사항을 함께 보는 이유도 여기에 있습니다. 문법을 하나 배울 때마다 그 문법이 실패할 수 있는 지점까지 같이 봐야 실제 프로젝트에서 덜 흔들립니다.

## 오늘 내용 정리

다음 글로 넘어가기 전에 예제 코드를 그대로 한 번 작성해보시고, 최소한 한 군데는 직접 바꿔보시는 것을 추천드립니다. 버튼 문구를 바꾸거나, 상태 초기값을 바꾸거나, 조건을 하나 추가하는 정도면 충분합니다. 그렇게 작은 변화를 직접 만들어보면 "아, 이 부분이 화면과 연결되어 있구나"라는 감각이 생깁니다.
