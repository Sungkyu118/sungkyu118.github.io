# Docker / Kubernetes / Cloud Native 시리즈 기획안

## 문서 목적

이 문서는 블로그에서 진행할 `Docker / Kubernetes / Cloud Native` 대주제 시리즈의 전체 방향을 먼저 정리하기 위한 기획 문서입니다. 바로 글을 쓰기 시작하면 중간에 주제 순서가 꼬이거나, 독자가 아직 이해하지 못한 개념을 너무 빨리 꺼내게 되는 경우가 많습니다. 그래서 이번 시리즈는 먼저 큰 흐름을 문서로 정리한 뒤, 그 흐름에 맞춰 순서대로 포스트를 발행하는 것을 목표로 합니다.

이번 시리즈의 가장 중요한 원칙은 단순 개념 나열이 아니라, 실제로 따라 하면서 이해할 수 있는 흐름으로 구성하는 것입니다. 즉, `Docker 명령어 모음` 같은 식으로 흩어진 정보만 전달하기보다, "왜 컨테이너가 필요한지", "Docker만으로는 어디까지 가능한지", "왜 Kubernetes가 등장하는지", "Cloud Native는 단순히 Kubernetes와 같은 말이 아닌 이유는 무엇인지"까지 단계적으로 연결해서 설명하는 구조를 목표로 합니다.

---

## 왜 이 주제를 지금 진행하는가

`Docker / Kubernetes / Cloud Native`는 서로 완전히 분리된 기술처럼 보이지만, 실제로는 하나의 학습 흐름으로 묶이는 주제입니다. Docker를 배우면 컨테이너 단위의 패키징과 실행 방식을 이해하게 됩니다. 그 다음에는 여러 컨테이너를 어떻게 안정적으로 배포하고 관리할지라는 질문이 자연스럽게 따라오고, 여기서 Kubernetes가 필요해집니다. Kubernetes를 어느 정도 이해한 뒤에는 다시 한 번 더 큰 질문이 생깁니다. "그렇다면 결국 운영을 어떤 철학으로 설계해야 하는가?" 이 지점에서 Cloud Native를 설명해야 흐름이 완성됩니다.

이 주제는 검색 유입 관점에서도 장점이 큽니다. 다만 짧은 명령어 정리 글만 많이 쓰는 방식으로는 경쟁력이 약할 수 있습니다. 그래서 이번 시리즈는 입문자 관점 설명, 실습 예제, 실수 사례, 운영 중 유의사항, 실무 트레이드오프까지 함께 포함하는 긴 호흡의 글로 작성하는 것을 전제로 합니다.

---

## 전체 시리즈 방향

전체 시리즈는 아래 3개 축으로 나눕니다.

1. `Docker 시리즈`
2. `Kubernetes 시리즈`
3. `Cloud Native 시리즈`

이 3개 축은 서로 연결되지만, 독자가 학습 순서를 놓치지 않도록 `Docker -> Kubernetes -> Cloud Native` 순서로 진행합니다.

이 순서를 권장하는 이유는 분명합니다.

- Docker를 이해하지 못한 상태에서 Kubernetes를 보면 `Pod`, `이미지`, `컨테이너`, `볼륨`, `환경 변수` 같은 기본 요소가 한꺼번에 섞여서 더 어렵게 느껴질 수 있습니다.
- Kubernetes를 이해하지 못한 상태에서 Cloud Native를 보면, 추상적인 운영 철학처럼만 느껴질 수 있습니다.
- 반대로 Docker부터 먼저 다져두면, Kubernetes는 "여러 컨테이너를 더 잘 운영하기 위한 도구"로 이해하기 쉬워지고, Cloud Native는 "이 도구들을 어떤 방식으로 운영 문화와 연결할지"라는 관점으로 자연스럽게 받아들일 수 있습니다.

## 시리즈 구성 원칙

각 포스트는 아래 기준을 지키며 작성합니다.

- 입문자가 실제로 따라 할 수 있는 예제를 반드시 포함합니다.
- 개념 설명 뒤에는 최소 하나 이상의 기본 예제를 붙입니다.
- 가능하면 잘못된 예제와 개선된 예제를 같이 보여줍니다.
- 단순 성공 사례만 적지 않고, 자주 만나는 에러와 해결 포인트를 함께 설명합니다.
- 실무에서 왜 이 설정을 쓰는지, 언제는 오히려 피해야 하는지도 같이 설명합니다.
- 이전 글, 다음 글, 함께 읽으면 좋은 글을 자연스럽게 연결합니다.

특히 이 주제는 설정 파일이 많이 등장하기 때문에, YAML, Dockerfile, Compose 파일, 명령어 예시를 짧게 던지고 끝내면 독자가 따라오지 못할 가능성이 큽니다. 그래서 코드 블록 앞뒤 문단에서 "이 파일이 왜 필요한지", "이 줄이 어떤 역할을 하는지", "이 줄을 빼먹으면 어떤 문제가 생기는지"를 자세하게 설명하는 방식을 기본 원칙으로 삼습니다.

이 문서 시점에서는 먼저 `Docker 입문 1~30`을 가장 우선순위로 둡니다. 이유는 다음과 같습니다.

- 독자가 가장 빠르게 실습 성공 경험을 얻을 수 있습니다.
- 특정 프레임워크에 묶이지 않은 범용 예제로도 충분히 깊이 있는 설명이 가능합니다.
- 이후 Kubernetes 글에서 재사용할 개념이 많습니다.
- 포스팅을 쓰는 입장에서도 예제 재활용과 내부 링크 연결이 쉬워집니다.

## 시리즈별 학습 목표

### Docker 시리즈 학습 목표

Docker 시리즈에서는 독자가 아래 질문에 답할 수 있게 만드는 것을 목표로 합니다.

- 컨테이너는 가상머신과 무엇이 다른가
- 이미지는 무엇이고 컨테이너는 무엇인가
- `docker run`, `docker build`, `docker exec`, `docker logs`는 각각 언제 쓰는가
- Dockerfile은 어떤 순서로 작성해야 하는가
- 볼륨과 바인드 마운트는 왜 필요한가
- Compose는 단일 컨테이너 실행과 무엇이 다른가
- 로컬 개발 환경에서 앱, DB, 캐시를 함께 띄울 때 무엇을 조심해야 하는가

즉, Docker를 단순 실행 도구로만 아는 수준이 아니라, 개발 환경 구성과 배포 준비 단계까지 연결해서 이해하도록 만드는 것이 목표입니다.

### Kubernetes 시리즈 학습 목표

Kubernetes 시리즈에서는 아래 내용을 자연스럽게 이해하게 만드는 것을 목표로 합니다.

- 왜 Docker만으로는 운영 규모가 커질수록 한계가 생기는가
- Pod는 왜 컨테이너와 완전히 같은 말이 아닌가
- Deployment와 ReplicaSet은 어떤 역할을 하는가
- Service는 왜 필요한가
- ConfigMap과 Secret은 어떻게 다르게 다뤄야 하는가
- 롤링 업데이트와 롤백은 어떤 구조로 이루어지는가
- Ingress, Namespace, Resource Limit은 왜 운영에서 중요한가

이 시리즈에서는 YAML 문법보다 "왜 이런 리소스 구조가 필요한가"를 먼저 이해시키는 것이 중요합니다.

### Cloud Native 시리즈 학습 목표

Cloud Native 시리즈에서는 아래 관점을 독자가 갖게 만드는 것을 목표로 합니다.

- Cloud Native는 단지 Kubernetes를 쓰는 것만 의미하지 않는다
- 애플리케이션을 운영 친화적으로 설계한다는 것은 무엇인가
- 상태를 어디에 두어야 하는가
- 헬스체크, 로그, 메트릭, 트레이싱은 왜 중요한가
- 자동화 배포와 롤백이 왜 운영 안정성과 연결되는가
- 작은 서비스 여러 개로 나누는 것이 항상 정답은 아닌 이유는 무엇인가

이 구간은 도구 사용법보다 설계와 운영 판단 기준을 설명하는 데 더 비중을 둡니다.

## 내부 링크 전략

내부 링크는 단순히 "이 글도 보세요"가 아니라, 학습 순서를 안내하는 방식으로 넣어야 합니다.

예를 들면 아래처럼 연결합니다.

- Docker에서 `컨테이너 실행`을 설명한 뒤, 다음 글로 `Dockerfile`을 연결
- `Dockerfile` 글을 마무리하면서 `이미지 레이어와 캐시` 글로 연결
- `Docker Compose` 글을 마무리하면서 "여러 컨테이너를 더 큰 규모에서 관리하려면 Kubernetes가 필요하다"는 식으로 Kubernetes 시리즈 첫 글과 연결
- Kubernetes 글에서는 중간중간 Docker 글을 다시 참조해서 독자의 기억을 보조
- Cloud Native 글에서는 Kubernetes 개념을 전제로 하되, 단순 반복이 아니라 운영 관점으로 확장

이 주제는 특히 시리즈 간 다리 역할이 중요하므로, `이전 글`, `다음 글`, `함께 보면 좋은 글` 추천 이유를 자세히 써야 합니다.

## Docker를 먼저 시작할 때의 장점

Docker를 먼저 시작하면 특정 프로젝트에 묶이지 않고도 실습 구성이 좋습니다.

- `nginx`, `alpine`, `busybox`, `redis`, `mysql` 같은 범용 이미지로도 핵심 개념을 충분히 설명할 수 있습니다.
- 정적 파일 서빙, 간단한 API 실행, 데이터 저장, 포트 매핑, 환경 변수 전달 같은 흐름을 프로젝트 독립적으로 보여주기 좋습니다.
- 이후 Kubernetes로 넘어갈 때도 이미지를 만드는 단계와 실행 환경 차이를 비교하기가 쉬워집니다.

즉, Docker는 특정 기술 스택에 종속되지 않고도 독립적인 입문 시리즈로 충분히 완성도 있게 운영할 수 있습니다.

## 작성 시 특히 주의할 점

이 주제를 쓸 때는 아래 실수를 피해야 합니다.

- 명령어만 나열하고 왜 쓰는지 설명하지 않는 방식
- Kubernetes YAML을 붙여넣고 리소스 구조를 설명하지 않는 방식
- Cloud Native를 지나치게 추상적으로만 설명하는 방식
- 로컬 실습과 운영 환경 차이를 구분하지 않는 방식
- Docker Compose와 Kubernetes를 단순히 대체 관계처럼만 설명하는 방식

독자는 대체로 "지금 당장 따라 할 수 있는 실습"과 "나중에 실무에서 왜 중요한지"를 동시에 알고 싶어합니다. 그래서 이번 시리즈는 항상 `실습 관점 + 운영 관점`을 같이 담는 방향으로 가야 합니다.
